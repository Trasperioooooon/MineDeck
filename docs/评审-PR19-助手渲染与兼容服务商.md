## 二、总的印象

方向是对的，几处设计取舍我都赞同：服务商的差异写成预设里的数据（多套地址、Key 前缀提示、静态建议模型、鉴权方式、回传策略），而不是在逻辑里写死某一家；思考内容一律存进历史、到组请求时再决定带不带，这样降级重发不用改历史；Key 和地址对不上只提醒、不自动换地址；`/models` 只对 404/405/501 兜底，401/403 照样报出来。手写渲染器的安全边界也守住了，第六节单独说。

但是有两处后端回归和两处渲染回归，合并前必须改：官方 Claude 预设现在不发 `x-api-key` 了；测试连接新加的第二轮失败时会被误报成「连接正常、只是不支持工具」，恰好把这个功能想抓的问题吞掉；引用块里的文字被转义了两遍；斜体里套加粗会露出控制字符。另外思考节流有一个尾巴推不出去、中途打开面板会重复一段的问题，自动降级每一轮都要重新撞一次 400，这些建议在这个 PR 里一起改掉，改动都不大。

## 三、必须改

**1. 官方 Claude 预设和自定义的 Claude 中转都不再发 `x-api-key`。**
位置：`internal/ai/service.go:307-325`（`config()`）、`internal/ai/anthropic.go:62-80`（`claudeHeader()`）、`internal/ai/presets.go:145`（自定义预设的 `Auth: AuthBearer`）、`internal/ai/service.go:548-571`（`setProvider()` 给自定义补默认 `bearer` 并校验）、`internal/ops/catalog/aiops.go:43` 和 `aiops.go:66`（`auth` 参数的取值范围），以及 `internal/web/ui/app.js:3854` 的「鉴权」下拉框。

`config()` 在预设没写鉴权方式时把它补成 `AuthBearer`，而 `claudeHeader()` 遇到 `AuthBearer` 只写 `Authorization: Bearer`。结果官方 Claude 预设（`Auth` 为空）发出去的请求只有 Bearer、没有 `x-api-key`；自定义预设本身写的就是 `AuthBearer`，保存时还会把空值补成 `bearer`，所以自定义的 Claude 中转也一样。升级上来的老用户不用动任何设置就会中招：他们存的设置里没有 `auth` 字段，读出来以后照样落到 `bearer`。我用临时测试走了一遍 `Service.config()` 和 `Models()`，两种情况下请求头都是 `x-api-key` 为空、`Authorization: Bearer …`。PR 描述里说的是「Claude 协议仍以 x-api-key 为主」，`client.go` 里 `Official` 的注释也写着「官方地址只发 x-api-key」，代码两样都没做到。

这一条的后果要说准确：Anthropic 现在的 API 概览页（https://platform.claude.com/docs/en/api/overview ，我自己打开核对过）在请求头说明里写着，`Authorization` 可以是 `Bearer <API Key>`，`x-api-key` 是「仍然支持的旧方式」，所以官方地址很可能照样能用，要用真实 Key 测一次才确定。真正会坏的是只认 `x-api-key` 的第三方 Claude 中转，哪些中转只认哪个头没查到。不管官方认不认，这都是一次没打算做、也没有测试覆盖的鉴权行为变更，波及所有 Claude 协议的用户，改起来又只有几行，所以放在必须改。

现有测试没抓到，是因为 `client_test.go` 的 `presetConfig()` 直接拿 `p.Auth`（空值）拼 `Config`，绕开了 `Service.config()`，走的是 `claudeHeader()` 的 `default` 分支。

建议的改法：让空值一路代表「这个协议的默认做法」。`config()` 不要把空值补成 `bearer`；自定义预设的 `Auth` 改成空；`setProvider()` 不给自定义强塞 `bearer`，校验也要放行空值；`aiops.go` 两处 `auth` 的 `OneOf` 加上空串（否则「默认」这个选项会被操作层拒掉）；界面上的「鉴权」下拉框加一个「默认」选项（OpenAI 兼容是 Bearer，Claude 协议是 `x-api-key`，中转另带 Bearer，也就是 PR 之前的行为），或者在 Claude 协议下干脆隐藏这一行。再补一条走 `Service` 的测试：每个预设、两种协议各发一次，断言实际请求头。

**2. 测试连接的第二轮失败，会被当成「不支持工具」吞掉，界面显示连接正常。**
位置：`internal/ai/service.go:970`（`Test()` 里判断要不要去掉工具重试）和 `internal/ai/service.go:1040-1075`（`probe()` 新加的第二轮）。

`Test()` 原来的逻辑是：第一次探测报 400、原文里带 `tool` 字样，就认为模型不支持工具，去掉工具再探一次。新加的第二轮失败时，错误用 `%w` 包着返回，`errors.As` 照样能取到里面的 400；而工具结果交回之后被拒，原文里几乎总会出现 `tool`（`tool_calls`、`tool_call_id`、「multi-turn tool calls」之类）。于是 `Test()` 去掉工具重探，第三个请求成功，最后返回 `OK=true, Tools="no", Rounds=1`，没有任何错误。我用临时测试复现了：第一轮正常调用工具，第二轮回 400「reasoning_content … must be passed back … in multi-turn tool calls」，界面上会显示「连接正常 · 这个模型不支持工具调用，助手用不了」。这正是第二轮想抓住的情况（思考内容没带回），结论却被说反了。

建议的改法：`probe()` 区分是哪一轮失败的（比如返回一个带轮次的错误类型，或者在 `probeResult` 里记下阶段），`Test()` 只在第一轮失败时才去掉工具重试。第二轮失败时照实返回错误，`Tools` 记成 `yes`（第一轮已经证明能调用），提示语单独写一句，比如「工具结果交回后被拒：多半是思考内容没有原样传回」，自定义服务商再加一句「可以把思考回传改成总是回传」。补一条测试覆盖这个路径。

**3. 引用块里的文字被转义两遍。**
位置：`internal/web/ui/md.js:33`。

`parts()` 一开头已经把整段源文转义过，引用块又把已经转义过的行拼起来交给 `render()`，`render()` 再调一次 `parts()`，再转义一遍。`> a & b < c` 显示出来是 `a &amp; b &lt; c`；引用里的代码块，复制按钮复制到的也是 `&lt;` 这样的字面文字。旧渲染器（`assistant.js` 里的 `mdLines`）是直接递归处理已转义的行，没有这个问题，所以这是回归。助手排错时常把日志原文放进引用里，日志里 `<`、`>`、`&` 很常见。

建议的改法：把 `parts()` 拆成两层，外层负责转义和切行，内层 `partsOfLines(lines)` 只处理已转义的行；引用块调内层。补一条测试：`> a & b < c` 的输出里有 `a &amp; b &lt; c`，没有 `&amp;amp;`。

**4. 斜体或删除线里套加粗时，加粗丢失并露出控制字符。**
位置：`internal/web/ui/md.js:279-287`（`style()`）。

`style()` 用 `\u0001序号\u0001` 占位，最后一次性换回。外层的斜体把内层加粗留下的占位符原样包进了自己的片段，最后那次替换不会再扫描换进去的内容，所以 `*x **y** z*` 渲染成 `<em>x \u00010\u0001 z</em>`，`~~a **b** c~~` 也一样。旧渲染器不认斜体，这两种写法至少能看到加粗，所以也算回归。顺带一个小问题：模型输出里如果本来就含 `\u0001数字\u0001`，会被替换成别处的片段（不能注入标签，只是内容错乱）。

建议的改法：最后的替换改成循环，直到没有占位符为止（或者在 `put()` 时就把片段里的占位符先换回）；进入 `parts()` 时先把源文里的 `\u0001` 去掉。补两条测试。

## 四、建议改（建议在这个 PR 里一起做，改动都不大）

**5. 思考节流：最后一小段要等整轮结束才推；中途订阅会看到重复的一段。**
位置：`internal/assistant/turn.go:22-46`（`thinkBuf`）和 `turn.go:365-392`。

`flush()` 只会在收到下一段思考、或者整个 `Chat()` 返回之后被调用，没有定时器。模型从思考转到正文的那一刻，缓冲里不满 240 字节、距上次推送不到 100ms 的那段思考就一直留着，要等这一轮的正文（或工具调用）全部结束才推出去。另一个问题是 `it.Think` 在收到片段时就立刻追加了（`turn.go:386`），推送却是延后的：这期间有人订阅这个会话（打开面板、切回会话、局域网设备打开、`hub` 把慢订阅者踢掉后重连），拿到的快照里已经有缓冲那段，随后 `flush` 又把它当增量推一次，界面上就重复了一段，直到这一轮结束、整条记录被替换才恢复。文字增量原本也有同样的窗口，但只隔一次解锁，思考这里放大到了 100ms 的量级，思考期间几乎每次订阅都会碰上。

建议的改法：收到 `EvText` 和 `EvToolStart` 时先 `flushThink(true)`；`it.Think` 的追加挪到 `flush` 里，和推送放在同一次加锁里做，让快照和增量对得上。补一条测试：假服务商先推思考再推正文，断言思考事件拼起来等于最终的 `Think`，并且在第一个正文增量之前推完。

**6. 自动降级每一轮都要重新撞一次 400；「总是回传」的预设不该参与降级；判断条件太宽。**
位置：`internal/ai/client.go:262-268`、`client.go:286-297`（`reasoningRejected`），以及 `internal/assistant/turn.go:354`。

助手每一轮都用 `s.ai.Client(true)` 新建一个客户端，`dropReasoning` 记在客户端上，所以「对方不认 reasoning_content」这个结论只活一轮。对一家不认这个字段的自定义服务商，之后每一次工具调用后的请求都要先吃一个 400 再去掉重发；在按次数限流的服务商那里，这些 400 也算请求次数。其次，`downgrade()` 对 `on` 也生效，而 DeepSeek、MiMo 设成 `on` 正是因为文档写明必须回传，这两家去掉思考字段重发只会得到第二个 400，原来那条更有用的报错反而被盖掉。第三，`reasoningRejected()` 只要求原文里同时有 `reasoning` 和「not support」之类的词，`reasoning_effort is not supported with this model` 这样跟回传无关的报错也会触发（临时测试里确认会命中）。

建议的改法：降级只对 `auto` 生效；判断要求原文里出现 `reasoning_content` 这个字段名（或者带引号的 `"reasoning"`），不认 `reasoning_effort`；学到的结论记在 `Service` 上，按「预设 + 地址 + 模型」存在内存里，或者像 Claude 中转的 `Eager`、`Fallback` 那样在测试连接后存进设置。拿第十一节实测拿到的真实报错原文补正反两类测试。

**7. 400 的提示会把「上下文超长」说成「模型名不对」。**
位置：`internal/ai/ai.go:205-212`、`ai.go:214`。

400 里只要出现 `model` 就提示「多半是模型名不对」，可是 OpenAI 兼容服务商最常见的上下文超长报错就是「This model's maximum context length is …」，会被说成模型名不对（临时测试确认）。助手会话越聊越长（代码里已经有 `sess.Long` 这个状态），这会是长会话里最常见的一类 400。`reasoning` 那一支也会被 `reasoning_effort` 之类的报错误触发。401 那一支靠 `mix`、`mismatch` 猜 MiMo 的报错措辞，没有出处。

429 那一支也漏了几家的真实写法。子代理查到（核实）：智谱余额不足是 429、错误码 1113，原文是「您的账户已欠费，请充值后重试」，现在的关键词里没有「欠费」，会被说成「请求太频繁」；Kimi 余额不足也是 429，类型是 `exceeded_current_quota_error`（含 `quota`，能认出来）；OpenAI 现在的原文是「Credit balance exhausted」（含 `credit`，能认出来）。上下文超长的写法，Kimi 是 400「Input token length too long」，智谱是 400、错误码 1261「Prompt 超长」。

建议的改法：400 先判断上下文超长（`context length`、`context_length`、`maximum context`、`too long`、`prompt is too long`、`超长` 等），提示「对话太长，超过了模型能看的长度，可以开一个新会话」；`reasoning` 改成 `reasoning_content`；429 的额度关键词加上「欠费」；401 不要猜措辞，改由服务层用 `KeyWarning()` 判断，前缀和地址对不上时直接把那句提醒当提示。DeepSeek 要求回传时的 400 原文是「The reasoning_content in the thinking mode must be passed back to the API」（摘自 Cherry Studio 的 PR），现在的 `reasoning` 分支能认出来、`reasoningRejected()` 也不会误判，可以直接拿它做测试用例。

**8. `scrub` 会误伤正常单词。**
位置：`internal/ai/ai.go:282`。

正则前面没有单词边界，`http-proxy-connection refused` 会变成 `h*** refused`，`task-manager-timeout` 变成 `ta***`，`risk-control-blocked` 变成 `ri***`（临时测试确认）。报错原文本来是给人排查用的，被抹掉一截就看不懂了。建议在前面加 `\b`（Go 的 RE2 支持 ASCII 单词边界），补一条正反例测试。

**9. 模型列表加载时关掉弹层，箭头按钮会一直灰着。**
位置：`internal/web/ui/app.js:4125` 和 `app.js:4139`。

`openModelPop()` 在 `await` 之后发现弹层已经被关掉（点了别处或按了 Esc）就直接 `return`，跳过了最后的 `btn.disabled = ro`，箭头按钮从此按不了，要等设置页重画或者点「刷新」才恢复。改成 `try … finally` 恢复按钮状态。

**10. 一轮「只有思考加工具调用」结束后，那条消息的摘要会一直停在「思考中…」。**
位置：`internal/web/ui/assistant.js:557`、`assistant.js:626`、`assistant.js:402`。

摘要用「会话在忙、是最后一条、还没有正文」来判断是不是「思考中…」。一轮只有思考和工具调用、没有正文时，工具执行期间它一直是最后一条，摘要显示「思考中…」（其实在跑工具）；下一轮新建了一条之后旧的不会重画，会话结束时 `state` 事件也只重画最后一条，于是旧消息的摘要一直是「思考中…」，直到重新打开面板。建议「思考中…」再加一个条件：这一条还没有工具调用、也没有 `_tool`；收到新的助手条目时顺手重画上一条助手消息。

**11. 前端认协议时没看所选的可选地址。**
位置：`internal/web/ui/app.js:3894`（`protoNow`）。

非自定义预设一律取预设的默认协议，后端却会按 `matchURL()` 把 MiMo 的 `/anthropic` 地址认成 Claude 协议。结果选了 MiMo 的「Claude 协议」地址以后，界面上「思考深度」那一行被藏起来，保存时 `effort` 被清空，模型缓存的键里协议也不对。建议前端照后端的规则在 `altUrls` 里找匹配的地址，用它声明的协议。

**12. `*.jar 和 *.zip` 会被当成斜体；中文里的 `_` 也会。**
位置：`internal/web/ui/md.js:283-284`。

斜体的结束符没有要求前面不是空白，`删除 *.jar 和 *.zip 文件` 渲染成 `删除 <em>.jar 和 </em>.zip 文件`（Node 实测）。开服排错的回答里 `*.jar`、`*.zip`、`*.log` 很常见，模型不一定每次都放进反引号。下划线那条只把 ASCII 字母数字当单词字符，`配置_文件_名` 会把「文件」变成斜体。建议结束符加 `(?<=\S)`，下划线的前后判断改成 `\p{L}\p{N}`（正则加 `u` 标志）。

**13. 拖宽面板时如果拖动被打断，监听留在手柄上。**
位置：`internal/web/ui/assistant.js:147-176`（`wireResize`）。

只在 `pointerup` 时移除 `pointermove` 和 `pointerup` 的监听、去掉 `drag` 样式。拖动中被打断（切走窗口、触控被系统取消）时收不到 `pointerup`，监听和高亮都留着，下次再拖又叠一组。用了 `setPointerCapture`，就改成监听 `lostpointercapture` 做收尾，它在正常松手和被打断时都会触发。

**14. Key 前缀提醒按完整地址比对，路径稍有不同就误报。**
位置：`internal/ai/presets.go:197-217`（`KeyWarning`），前端 `app.js:3798` 是同一条规则。

Key 绑定的是域名，不是路径。现在一把 `tp-` Key 填在 `https://token-plan-cn.xiaomimimo.com/v1/chat/completions` 这种多带一截路径的地址上，会被提醒「只能用在 token-plan 的地址上」，其实域名是对的。建议 `KeyHint` 改成按主机名比对（`URLs` 换成 `Hosts`，或者只比 `Host`）。

**15. 测试里有两条恒真的断言。**
位置：`internal/web/ui/md.test.js:80` 和 `md.test.js:82`。

两条断言末尾都带着 `|| html.includes("尾")`，而前面已经断言过有「尾」，所以它们永远成立，「列表里的代码块不把列表拆开」这件事其实没被检查。建议改成结构断言，比如断言 `<pre` 和「尾」都落在同一个 `<li>…</li>` 里，并且整段只有一个 `<ul>`。

**16. DeepSeek 预设「总是回传」补空串的范围不够。**
位置：`internal/ai/openai.go:88-118`（`adjustReasoning()` 里 `echo == EchoOn` 那一段）。

现在只给带 `tool_calls` 的助手消息补空的 `reasoning_content`。DeepSeek 官方的思考模式文档（https://api-docs.deepseek.com/guides/thinking_mode.md ，子代理先查到，我又打开核对过）写的判断条件是这次请求带不带 `tools`，不是那条消息有没有调用工具：带了 `tools`，之后所有请求都要完整传回 `reasoning_content`，包括模型那一轮没有调用工具的情况，没传对会返回 400；不带 `tools` 时不用传，传了也会被忽略。MineDeck 助手的每次请求都带工具，所以 DeepSeek 这里应该给所有助手消息补齐。平时 DeepSeek 自己的回复都带思考、PR 也都存下了，碰不到这个问题；会出事的是历史里没有思考的那几条，比如会话中途从别家服务商换到 DeepSeek，之前那些助手消息就没有这个字段。Vercel 的 `@ai-sdk/deepseek` 和 Cherry Studio 都是每条助手消息都补（摘要）。MiMo 的文档只强制「含工具调用的助手消息」，可以保持现状。

建议的改法：补空的范围做成预设上的一个属性（比如 `EchoPad: "tool-calls" | "all"`），DeepSeek 用 `all`，MiMo 先用 `tool-calls`，自定义的 `auto` 一律不补。空串能不能被接受，几家官方都没写，要实测（见第十一节）。

**17. 接口文档和说明没跟上。**
位置：`docs/API.md:146-149`，`README.md:63`、`README.md:86`，`docs/功能清单.md:215`。

`/api/ai/models` 的返回从数组改成了 `{models, source, warning}`，请求体多了 `auth`、`echo`；`/api/ai/test` 多了 `warn`、`rounds`；`/api/ai/settings` 的 `provider` 多了 `auth`、`echo`；`PUT /api/ai/provider` 多了 `auth`、`echo` 两个参数。`docs/API.md` 这几行都还是旧的，尤其 `/api/ai/models` 还写着返回数组，照文档写的调用方会直接出错。README 和功能清单还写着「七个预设」，按文档原来不算自定义的数法，加上小米 MiMo 以后是八个。PR 描述自己也列了这一项。建议在这个 PR 里一起改掉，都是文字。

## 六、专项结论

### XSS 和 HTML 注入

没有发现能注入标签或脚本的路径。查过的地方：`parts()` 一开头就把整段源文的 `& < > " '` 全部转义，之后所有标签都是在转义过的文字外面拼出来的；链接只认 `http`、`https` 开头，地址取自转义后的文字，引号已经是 `&quot;`，拼不出新属性（试过 `"onmouseover=` 和 `javascript&#58;` 两种写法，都没成）；不渲染图片；代码块的语言名用白名单正则过滤，试过在语言位置塞 `"><img onerror>`，被整个丢掉；表格对齐只会写入 `left`、`center`、`right` 三个固定值；任务列表的勾选框是 `disabled`；思考内容用 `esc()` 拼进 HTML，流式时用 `textContent` 更新；模型下拉框里的模型名和说明、Key 前缀提醒、测试连接的 `warn` 都经过 `esc()`；复制按钮读的是 `textContent`；「正在调用某某工具…」这句这次也补上了转义。占位符 `\u0001` 的问题（第 4 条）只会让内容错乱，换回来的片段都是渲染器自己生成的 HTML，注入不了东西。

性能上也试了几种病态输入：三千个星号、两万个反引号、五千个方括号、四百层缩进的列表、三千行的表格，单次渲染都在 10 毫秒以内；九万多字的正文整段解析约 13 毫秒。流式时每一帧都会把全文重新解析一遍，正常长度的回答没有问题，超长回答会接近一帧的预算，暂时不用处理。

### 服务商兼容逻辑

**边界覆盖得怎么样。** 已经接住的：一个预设可以有多条地址，每条可以声明自己的协议，比对地址时看协议、主机（不分大小写）和路径，末尾斜杠不算差别；文档写明没有模型列表的地址不发请求；模型列表 404、405、501 或返回空列表时退回建议模型，401、403 照样报错；Key 和地址对不上只提醒；回传分 `off`、`on`、`auto` 三档，`auto` 被拒后去掉重发。没接住的，前面都列了：Claude 协议的鉴权头（第 1 条）、DeepSeek 补空的范围（第 16 条）、自动降级只记一轮（第 6 条）、Key 提醒按完整路径比对（第 14 条）。还有一处小的：非自定义预设靠地址认协议，用户贴的地址多带一截路径（比如 `https://api.xiaomimimo.com/anthropic/v1`）就认不出来，`setProvider()` 会悄悄按 OpenAI 兼容协议保存（`service.go:548-571`），结果是请求发到错的路径上。可以在认不出时给一句提醒，或者先把常见的多余尾巴（`/v1`、`/chat/completions`、`/v1/messages`）去掉再比。

**有没有写死。** 各家的差异基本都写成了预设里的数据（地址、协议、Key 前缀、鉴权方式、回传策略、建议模型），逻辑本身没有按服务商名字分支，这一点做得好。真正写死在逻辑里的是几张关键词表：`scrub()` 认的 Key 前缀（`sk`、`tp`、`ttp`、`ak`，`ai.go:282`），`Hint()` 按状态码分的关键词（`ai.go:205-235`），`reasoningRejected()` 的拒绝词（`client.go:286-297`），以及模型列表兜底的状态码（404、405、501）。这几张表最容易随服务商改措辞而失灵，第 7 条和第十一节已经补了几家的真实原文。建议把实测拿到的报错原文存成测试数据，让测试成为这几张表的依据。

**Key 类型会不会判错。** 前缀提示只在声明了 `KeyHints` 的预设里生效，目前只有 MiMo，DeepSeek 的 `sk-` 不会被当成 MiMo 的按量 Key。匹配取最长的前缀，认不出的前缀不提醒；提醒从不拦截保存和测试，也不会自动换地址，所以判错的最坏结果是多一句不该有的提醒，不会让请求失败。会误报的情况有两种：多带路径的地址（第 14 条）；MiMo 以后如果给 Token Plan 也发 `sk-` 开头的 Key，现在的规则就会说反。前端 `keyWarn()` 和后端 `KeyWarning()` 是同一条规则写了两份，以后要一起改。`scrub()` 只认四个前缀，智谱那种「编号.密钥」格式或别家其他格式的 Key 认不出来；不过用户自己那把 Key 是按原文整串抹掉的，漏网的只可能是报错里回显的别人的 Key，影响很小。

## 七、Go 并发和超时、前端监听

这个 PR 没有新开 goroutine，也没有新的定时器，所以没有 goroutine 泄漏的问题（思考节流不用定时器，代价就是第 5 条说的尾巴）。测试连接的两轮共用 `Test()` 里那个 90 秒的 `context`，第二轮会被同一个超时管住，本机慢模型两轮加起来要注意别超时，可以放进实测清单。`dropReasoning` 的读写都在 `c.mu` 里，`openaiBody()` 读它时也加了锁。`-race` 没跑成，需要补跑。

前端：设置页的 `pointerdown` 全局监听挂在 `window.__aiModelAway` 上，每次重画会先摘掉旧的，离开设置页后会留一个空转的闭包，无害；设置页里的输入框每次重画都是新元素，监听跟着元素一起丢掉；面板上的复制按钮用一个委托监听，每次挂载只挂一次。唯一的问题是拖宽手柄被打断时的清理（第 13 条）。

## 八、测试覆盖：缺的关键路径

最该补的是两条能直接抓住必须改问题的：走 `Service` 的请求头测试（每个预设、两种协议，断言实际请求头，能抓住第 1 条），和测试连接第二轮失败的测试（能抓住第 2 条）。

其余按价值排：`md.js` 的引用块转义、斜体套加粗、`*.jar` 和中文下划线、链接外面的加粗，并把两条恒真断言改成结构断言；`adjustReasoning()` 的表格测试（`off`、`on`、`auto` 乘以「有没有思考」「有没有工具调用」「降级了没有」）；`reasoningRejected()` 用真实报错原文做正反例（Groq 拒字段的原文、DeepSeek 和 MiMo 要求回传的原文，第十一节实测拿到）；思考节流的事件顺序和最终一致性；`Models()` 的 405、501、空列表兜底、401 不兜底、MiMo `/anthropic` 地址认成 Claude 协议、Token Plan 的 Claude 地址不发请求；`sanitize()` 和 `setProvider()` 对 MiMo Claude 协议的保存、离开自定义时清掉 `auth` 和 `echo`、非法值被拒；`scrub()` 的边界；`KeyWarning()` 的前后端一致。流式增量渲染（`paintMd()`、`updateStream()`）没有 DOM 测试环境，至少可以给 `parts()` 补「文字一点点变长时，已完成块的签名不变、表格成形和代码块闭合时签名会变」的测试。

## 九、探索：还值得补的东西

这一节不扩大 PR 的范围，只说值不值得做、大概多少工作量、放在哪里。服务商的事实来自子代理读官方文档的结果，标了「核实」的才当事实用，只读到搜索摘要的都放进了第十一节的实测清单。

### 服务商兼容

**Kimi 和智谱的预设改成 `auto` 回传。** 这是我觉得最值得顺手做的一条。Kimi 现在的文档（核实）要求多轮对话和工具调用时把返回的助手消息原样传回，包括 `reasoning_content`，而 Kimi 预设现在没设回传策略，等于 `off`，每次都把思考删掉。智谱开了「保留思考」时要求完整、不改动地传回，Coding Plan 的地址默认就开着（核实）。`auto` 只传回收到过的内容，对方不认还能自动去掉，风险很低；通义（缺了不报错，核实）和 OpenRouter（把 `reasoning_content` 当 `reasoning` 的别名，核实）也可以一起改。工作量是几行预设数据加一条测试。建议并进这个 PR，和第 6 条一起改，再各用真实 Key 测一次。

**DeepSeek 预设的建议模型名可能写错了。** 子代理读到的思考模式页、接口参考和模型列表示例里都是 `deepseek-flash` 和 `deepseek-v4-pro`，没有预设里写的 `deepseek-v4-flash`。这一行不是这个 PR 改的，建议另开 issue，用真实 Key 拉一次模型列表核对。

**MiMo 的模型列表接口有没有，两边说法对不上。** PR 描述引了一个「列出模型」的文档页，子代理在 OpenAI 接口参考和 FAQ 里都没找到 `/models`。PR 对按量地址照常请求、失败了再兜底，这个处理两种情况都能接住，只需要实测确认。另外 MiMo 的 FAQ（核实）建议调用工具时关掉思考，否则工具调用可能被写进 `reasoning_content` 里，这直接关系到第十节的第 1 个问题。

**本机模型。** Ollama 的 OpenAI 兼容接口里思考内容放在 `reasoning` 字段（核实），PR 两个字段都读，没问题；`/v1/models` 也有。LM Studio 的地址是 `http://localhost:1234/v1`，有 `/v1/models`（核实），可以照 Ollama 的样子加一个本机预设，工作量很小，但这次 PR 有意没加没核实过的预设，建议另开 issue。

**Groq、Azure、Cloudflare 这类。** Groq 会拒绝 `reasoning_content`（Cherry Studio 记录的原文是「property 'reasoning_content' is unsupported」，摘要），以后要是加 Groq 预设，回传必须设成 `off`；走自定义的 `auto` 也能用，第 6 条改完以后每个会话只多一次 400。Azure OpenAI 的 `api-key` 头 PR 已经能发，但 deployments 路径还要带 `api-version` 查询参数（核实），现在没有地方填，等有人要用再说。Cloudflare AI Gateway 开了鉴权（新网关默认开）时要带 `cf-aig-authorization` 头（核实），这要靠附加请求头，见第十节第 2 个问题。

**按模型的上下文上限提醒。** 现在「会话太长」是按固定的 10 万 token 判断的（`turn.go:401`）。程序已经在下载 LiteLLM 的价格表，那份数据里有每个模型的输入上限，可以拿来显示「上下文已用多少」，到七成左右提醒，比固定阈值准，也正好对上第 7 条说的上下文超长报错。工作量半天左右，另开 issue。

### 助手的交互

已经有的：停止回复、「继续回复」、服务商出错时的重试提示、每条回复的用量、会话太长的提醒、代码块复制。还缺、值得做的有这几样。一是复制整条回复的 Markdown 原文，很小，另开 issue。二是重新生成上一条：对话层已经有撤回用户消息的能力，难点在上一轮可能已经执行过工具，重新生成不能把有副作用的工具再跑一遍，要先想清楚，另开 issue。三是思考摘要显示用时和字数（比如「思考了 12 秒」），很小，正好落在这次的思考界面上，可以并进这个 PR，不做也不影响。四是流式时用户往上翻了，给一个「回到底部」的按钮，很小，另开 issue。

### 结合开服场景的 AI 能力

先说现状：助手已经能读日志、列崩溃报告和 JVM 崩溃日志、跑内置规则诊断（缺前置、客户端模组、装错加载器、重复模组等）、看模组依赖和开关模组、查端口占用、改 Java 和服务器属性、做备份。所以「读日志诊断崩溃」「改端口」这些基础已经在了，下一步是让它更准、更省。

**崩溃诊断补规则。** 把最常见的几种签名做成内置规则：`UnsupportedClassVersionError`（Java 版本不对）、`OutOfMemoryError`（内存给少了）、`FAILED TO BIND TO PORT`（端口被占，直接接 `port.check`）、没同意 EULA、Mixin 报错里点名的模组。规则结果先交给模型，便宜的模型也能答对。价值高，工作量中等，另开 issue。

**模组冲突二分排查向导。** 先备份，再用开关模组的工具每次关掉一半、启动、看结果，一步步缩小范围，每一步都走确认卡片。整合包用户最需要这个，工作量中到大，另开 issue。

**JVM 参数推荐。** 读本机内存、服务端类型、模组数量和人数，给出 `-Xmx`、`-Xms` 和一套 G1 参数，经确认后用现有的 Java 设置工具写进去。工作量小到中，另开 issue。

**防火墙。** 现在代码里完全没有防火墙相关的东西，`port.check` 只看本机端口有没有被占。可以先做只读的检查：Windows 防火墙里有没有放行 java.exe 或这个端口的入站规则。真要加规则就要管理员权限加确认卡片；从外网测能不能连进来要借助第三方服务，涉及隐私，要单独设计。另开 issue。

### 可靠性

**额度用完的 429 不要重试。** 现在所有 429 都会重试两次（`ai.go:198`），可是额度用完（OpenAI 的 `insufficient_quota`、Kimi 的 `exceeded_current_quota_error`、智谱的 1113「欠费」）重试多少次都没用，只会让用户多等几秒。可以复用第 7 条的关键词表，额度类的 429 直接报错。改动很小，建议跟第 7 条一起并进这个 PR。

**断线重连和密钥存储。** 事件流断了浏览器会自己重连、重连后先拿一份完整会话；回复中途断开会标成「没说完」并给「继续回复」，这些都已经有了，这次相关的问题只有第 5 条的重复片段。Key 已经用 DPAPI 加密存放，以后加附加请求头，值也要走同一个存放处。

**测试连接的超时。** 两轮共用 90 秒，本机慢模型加载加两轮生成可能不够。可以在本机预设上放宽到两分钟，几行改动，可以并进这个 PR，也可以等实测确实超时了再改。

## 十、三个还没拍板的问题

**1. 要不要加关闭思考的开关？倾向：加，但另开一个 PR，做成按预设声明的「思考：默认 / 关闭」两档。**

赞同加的理由有三条。MiMo 的 FAQ 明确建议调用工具时关掉思考，否则工具调用可能落进思考内容里，而助手的每次请求都带工具。开服的操作大多很直接（重启、改端口、看日志），每一轮都思考既慢又费 token。关掉思考以后，回传 `reasoning_content` 的那一整套麻烦对这些服务商也就不存在了。

不做成一个通用的布尔开关，是因为各家参数不一样，有的根本关不掉（子代理核实）：DeepSeek、MiMo、智谱都是 `thinking: {type: "disabled"}`，但智谱的 GLM-5.3 是强制思考；通义是 `enable_thinking: false`，纯思考的模型关不掉；OpenRouter 是 `reasoning: {effort: "none"}`，标了必须推理的模型会拒绝；Ollama 是 `reasoning_effort: "none"`；Kimi 的 K3 系列始终推理，没有这个参数；Claude 已经有「思考深度」。各家遇到不认识的参数是报 400 还是忽略，没查到。所以只对声明了参数的预设显示这一行；自定义给一个下拉框，选「不发」或上面几种格式之一。默认一律「默认」（什么都不发），保持现在的行为；MiMo 要不要默认关，等实测完工具调用的表现再定。工作量一天左右：预设加字段、请求体按声明拼参数、界面一行、测试。不放进这个 PR，是因为它要改的正是这次已经改了一千五百行的那几个文件，等这次的必须改合并了再做，审起来清楚。

**2. 要不要支持自定义附加请求头？倾向：支持，只给自定义服务商，值和 Key 一样当密钥处理。另开 PR。**

确实有需要：Cloudflare AI Gateway 开了鉴权就必须带 `cf-aig-authorization`，OpenRouter 的署名头 `HTTP-Referer`、`X-OpenRouter-Title`（可选），Anthropic 的 Key 没绑定工作区时要 `anthropic-workspace-id`（都是核实）。Cline 和 Continue 都提供了这个功能。

要守住几条：头的名字只允许合法字符，不能有换行；`Host`、`Content-Length`、`Content-Type`、`Accept`、`Transfer-Encoding` 不让填；`Authorization`、`x-api-key`、`api-key` 也不让填，引导用户用「鉴权」那一行，这样 Key 只有一个来源，报错里的抹除也只管一处。值要像 Key 一样用 DPAPI 加密存放，界面上只显示「已设置」，不回传给页面，不进日志和操作记录，报错原文里出现了也要抹掉（`cf-aig-authorization` 本身就是令牌）。换了网站就跟 Key 一样清掉。数量和长度设个上限（比如 8 个、每个 1 KB）。Azure 要的 `api-version` 是查询参数，不是请求头，这个功能解决不了，别在说明里承诺。工作量一天左右，另开 PR。

**3. 是不是每一轮都补一个空的 `reasoning_content`？推荐：不要全局每一轮都补，按预设声明补的范围。**

- **DeepSeek 补所有助手消息。** 官方文档写的是请求带 `tools` 时所有历史助手消息都要回传，助手每次都带工具，所以 DeepSeek 应该给每条助手消息都补齐，就是第 16 条。
- **MiMo 维持现在只补工具调用轮。** 官方强制的范围就是「含工具调用的助手消息」，FAQ 只建议保留全部历史思考。PR 已经把收到的思考都存下来了，差别只在没有思考的那几条上。
- **自定义的 `auto` 一律不补。** Groq 会直接拒绝这个字段，Cherry Studio 自己就为此把 Groq 拆成了专用实现，全局补空会伤到这类服务商。
- **Kimi、智谱用 `auto` 原样传回，不补。**

还有一个前提没落实：空串到底被不被接受，几家官方都没写，只有第三方客户端的做法可以参考，要先用 DeepSeek 和 MiMo 的真实 Key 各测一次再依赖它。

### 跨提供商复审（Codex）

第一轮（对 `197e42b`）：作者指定用 Codex 的 GPT-6-Astra、max 档，只读沙箱，在 PR 工作树里审最终源码，另给了完整 diff 和修复部分的 diff。它自报「GPT-6 系列」，具体型号未确认。结论是「改完以下几条能合并」，找出了前两轮都漏掉的问题。主会话逐条核实，全部成立，都改了，提交 `91cc8ae`：

- **Markdown 能被短输入拖死、深度嵌套会撑爆调用栈**（必须改）。标题的正则在「# a」后面跟几千个空格时严重回溯（实测两千个空格就要 0.8 秒），一长串星号让强调一层套一层地递归。这个标题正则旧渲染器里就有。助手的回复会引用日志和玩家的话，所以这条要当成可以被利用的问题对待。改法：标题和分隔线改成逐步检查；引用和强调最多嵌套 12 层；一长串方括号不再每个都从头往后找；一行超过 4000 字就不再认加粗和斜体（成串没收尾的星号会让查找变成平方级）；万一还是出了异常，整段按转义过的纯文字显示。加了一条测试，七种构造输入每种都要在 500 毫秒内渲染完，实际都在几毫秒。
