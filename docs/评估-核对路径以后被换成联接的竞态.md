# 评估：核对路径以后、真正动文件之前被换成联接的竞态（2026-11-16，Claude 写）

这是 beta.3 之后整改的第 7 条。作者 11-16 定的是「先评估」：只实测、写清改法和改动面，报回去再决定动不动。这份文件就是评估的结果，没有改产品代码。实验程序的源码在 `docs/research/os-root-实验/` 里，存成 `.go.txt`，免得被 `go build ./...` 编进去；要重跑就复制到仓库外面的空文件夹，改回 `.go`，配一个 `go.mod`（第二个要 `golang.org/x/sys`）。

## 问题是什么

Codex 复审 beta.3 最后一遍记下的一条，它自己也标明是 beta.2 就有的，不是这一版带进来的。MineDeck 读写服务器里的配置（`instance.config.write`，`internal/ops/catalog/files.go`）、补整合包里没装上的文件（`internal/inst/import.go` 的 `pendingDestination`）、写没装上文件的清单（`internal/inst/pendingstore.go`）时，先把要动的路径和它的上一级解开目录联接、符号链接，确认真实落点在服务器文件夹里，然后才按字符串路径去建临时文件、用 `MoveFileEx` 换上去，或者 `os.Remove` 删掉。核对和动手之间隔着几毫秒。要是正好在这几毫秒里，另一个程序把路径上的某个文件夹改名挪走、换成一个指到外面的目录联接，后面按路径做的创建、替换、删除就会落到外面去。程序里的锁只管 MineDeck 自己的并发，挡不住别的程序。

已经挡住的是「事先埋好的陷阱」：交接包、整合包、手放进去的联接和符号链接，核对那一步都会认出来，上一级也核对（beta.3 第四轮）。剩下的只有「有人正好在中间动手」这一种。

## 真实风险有多大

要碰上它，得有一个和 MineDeck 同时在跑的程序，能改服务器文件夹，还要卡准那几毫秒。这样的程序如果是以同一个 Windows 用户身份跑的，它自己就能直接读写、删除外面那些文件，借 MineDeck 的手并不能多做什么；Minecraft 服务端和它加载的插件、模组也是同一个用户跑的，同理。真正会让 MineDeck「被人借刀」的情形要满足一个前提：能改服务器文件夹的人，权限比跑 MineDeck 的人小。比如服务器文件夹放在别的用户也能写的共享盘、多人共用电脑的公共文件夹里，而 MineDeck 用权限更大的账户在跑；或者局域网另一台机器能往这个共享文件夹里放联接（联接指向的是这台电脑上的路径，要在这台电脑上解开才有用）。这些在 MineDeck 的用户里很少见。所以这一条的实际风险低，属于纵深防御，不是一碰就出事的洞。

## 实测：Go 的 os.Root 在 Windows 上怎么对待目录联接

在这台电脑上（Windows 11，Go 工具链 1.27.1，`go.mod` 写的是 1.25）用临时文件夹实测，联接用 `mklink /J` 建（这台机器没有建符号链接的权限，所以没测符号链接）。

实验一（`实验一-os.Root碰到联接.go.txt`）：

- 服务器文件夹里有一个指到外面的联接，经 `os.OpenRoot(服务器文件夹)` 去读、写、删它下面的文件，三样都被拒（`path escapes from parent`），外面的文件没被动到。这正是想要的。
- 联接指回服务器文件夹**里面**（绝对路径），也一样被拒。现在的代码是放行的（真实落点在里面就行），换成 `os.Root` 会更严：服务器里有这种联接的，配置读写会改成报错。
- `Root.Rename` 能覆盖已有文件；但目标正被别人打开着时报「拒绝访问」，目标是只读文件时也报「拒绝访问」。这两种情况 `atomicfile` 现在都有专门的处理：PR #24 加的替换重试（目标被一眨眼的占用挡住时隔一会儿再试），和只读目标用 `FileRenameInfoEx` 带 `IGNORE_READONLY` 替换。换成 `Root.Rename` 这两样都没了。
- 先用 `Root.OpenRoot("config")` 打开子文件夹，再把 `config` 改名挪走、换成指到外面的联接：经这个子 Root 写的文件落在挪走的原文件夹里，外面没被写到。也就是说，按已打开的目录句柄操作确实绑住了。经服务器根的 Root 走新的 `config/` 路径，被拒。
- 子文件夹的 Root 开着时，那个子文件夹照样能改名、能删（空的时候）。但**服务器文件夹本身的 Root 开着时，整个服务器文件夹改不了名**（「另一个程序正在使用此文件」）。所以用 `os.Root` 时，每次操作要开完就关，不能长期拿着，不然会挡住移出列表、手动挪文件夹这类操作。
- 服务器文件夹本身放在联接后面（`D:\链接` 指向真文件夹）时，`OpenRoot` 那个联接路径没问题，能正常读写里面的文件。

实验二（`实验二-按目录句柄改名.go.txt`）：想保住 `atomicfile` 现有的重试和只读处理，又要绑住目录，办法是自己用 `FileRenameInfoEx` 改名，把已核对的目录句柄填进 `RootDirectory`、目标只给文件名。实测：经 `os.Root` 打开的临时文件句柄没有删除权限，拿它改名被拒；按路径另开一个带删除权限的句柄，再填目录句柄改名，Win32 这一层报「参数错误」（多半要直接用 `NtSetInformationFile`，Win32 的 `SetFileInformationByHandle` 对带 `RootDirectory` 的改名不认）。顺带看到一件事：目录里有文件开着的时候，这个目录改不了名（拒绝访问），所以「把正在写的那个文件夹整个挪走」这条路本来就会被 Windows 挡住；但如果那一级本来就是一个指回里面的联接，改它指向哪里不需要挪文件夹，按道理挡不住（这一点没有实测）。

## 改法和改动面

**甲：只把读、删、建临时文件换成 `os.Root`，最后的替换照旧按路径。** 改动小（三处入口各几行），能挡住删除那一路（`reset` 模式删配置）和临时文件建到外面。但写配置最后那一下 `MoveFileEx` 还是按路径，窗口没有关上，只是挪了位置；Codex 的原话是「再检查一次路径只能缩小窗口」，这个也一样。

**乙：整条写入都绑在目录句柄上。** 自己写一小层 Windows 的「相对打开」：用 `NtCreateFile` 按已核对的目录句柄建临时文件（带删除权限）、用 `NtSetInformationFile` 带 `RootDirectory` 改名、删除也按句柄（`FileDispositionInfoEx`），每一级路径都不跟随联接、自己核对。再把 PR #24 的替换重试、只读目标的处理、锁键（`atomicfile.PathKey` 按规范路径算）搬到这条新路上。实际上就是照着 Go 标准库 `os.Root` 在 Windows 上的做法再写一份我们自己能控制细节的。只有那三处入口要用新路，`server.properties`、`instance.json` 这些 MineDeck 自己的文件照旧。估计新代码三四百行加测试，而且是安全相关的底层代码，按 beta.3 的经验要请 Codex 看好几遍。还要接受两处行为变化：服务器文件夹里指回里面的联接会被拒；操作期间拿着服务器文件夹的句柄（开完就关，影响很小）。

**丙：不改，留作已知情况。** beta.3 的发布说明里已经写了这一条。

## 建议

这一版不做乙。理由是风险低（见上面「真实风险」），而改动落在 `atomicfile` 这种所有写盘都要经过的地方，PR #24、PR #26 都在这附近反复修过，改错的代价比这个竞态本身大得多。甲只是挪了窗口，不推荐单独做。

如果以后要做（比如有人要把 MineDeck 放在多人共用的电脑上、用不同账户跑），建议单开一个分支和 PR 专门做乙，配一组在 CI 的 Windows 机器上真建联接、在核对和动手之间插钩子换联接的用例，做之前先确认 `NtSetInformationFile` 带 `RootDirectory` 的改名在 NTFS 和 exFAT（移动硬盘）上都能用。

这一条要作者拍板：是照建议留着（丙），还是排进后面哪一版做乙。
