【结果】部分通过（换代理后通过）
【步骤】
1. 在未开代理的环境里开始部署。
2. 观察 `servers\S1` 的体积和安装器日志。
【实际】部署停在第 4 步「安装服务端」，`servers\S1` 五分钟停在 62.8 MB 不再增长，Java 进程 CPU 几乎为 0。安装器日志 `neoforge-21.1.265-installer.jar.log` 里 36 次 `java.net.SocketTimeoutException: Connect timed out`，每次约 30 秒，错误栈都指向 `DownloadUtils.downloadLibrary`。开启代理后同一个安装器自己接着跑完，20 秒下载了 41.75 MB，最后一行是 `The server installed successfully`。
【原因】`maven.neoforged.net` 在这台机器上不可达：系统 DNS 把它解析成 `157.240.12.35`（Facebook 的 157.240.0.0/16 段，典型的 DNS 污染），用公共 DNS 拿到的真实 IP 直连也是超时。同一时刻 `maven.minecraftforge.net`（Cloudflare）返回 200、`cdn.modrinth.com` 通、`api.modrinth.com` 通、`bmclapi2.bangbang93.com` 通，只有 `github.com` 和 `maven.neoforged.net` 这类站点被卡。
【影响】MineDeck 自己的镜像下载是有效的——Java 运行时 144.5 MB、NeoForge 安装器 7 MB 都已进 `cache\`——但 NeoForge 安装器运行时自己去 `maven.neoforged.net` 拉剩余库，这一段不受「设置 → 下载与网络」的下载源影响，也没有超时上限或失败提示，用户只会看到「部署中，请勿关闭程序…」一直不动。
【建议】可考虑在调用安装器前，用 bmclapi 之类的镜像把 NeoForge 库预热进 `libraries\`，安装器会跳过已存在的文件；实测 `https://bmclapi2.bangbang93.com/maven/net/neoforged/coremods/7.0.3/coremods-7.0.3.jar` 是 302 命中、0.2 秒返回，技术上可行。另外安装器连不上时最好能给一句「下载 NeoForge 库超时」的提示，而不是静默卡住。

**H-02 连接（P0）— 大部分通过，附带一条「断线被记成警告」的问题**

- 开服后 `Done` 之后几秒内，「和伙伴模组的连接」变成**已连上**，副标题是「伙伴模组 0.2.1 · PlayerEngine 1.21.1-1.4.0」，「最近的事件」里记着「连上了伙伴模组 0.2.1（PlayerEngine 1.21.1-1.4.0），现有 0 个伙伴」。控制台同时有 `[minedeck_companion/]: 伙伴控制端口已打开: 127.0.0.1:24480`、`MineDeck 伙伴模组已就绪：存档里记着 0 个伙伴，已接管 0 个（PlayerEngine 1.21.1-1.4.0）`、`控制连接已建立：「MineDeck 2.9.0-beta.2」(#1, 来自 127.0.0.1:…, 协议版本 1)`。
- 关服后连接状态回到「等服务器开好」，没有反复重连；再开一次服自动连上（两次开服各记了一条「连上了伙伴模组」）。这条符合预期。
- 【发现 8】用**控制台 `stop`** 停服时，这条断开被记成**警告**：「和伙伴模组的连接断开了：伙伴模组结束了连接：服务器正在关闭（伙伴和任务还在游戏里，会自动重连）」，事件行左边是黄色三角。计划里的预期是「服务器正在关闭……（普通提示，不是警告）」。
  - 【原因】`internal/companion/service.go:458-474` 判断「这次断开是不是正常关服」靠的是那一刻实例的状态是不是 `stopping`/`stopped`。控制台 `stop` 之后，Java 还在打印 `Stopping server`、世界还在存盘，实例状态仍是 `running`，于是走了「异常断开」那个分支（warn + 「会自动重连」）。点界面的「停止」按钮时 MineDeck 自己先置成 stopping，就不会有这个问题。
  - 【影响】用控制台 `stop`（日志里那行 `> stop` 回显）是很常见的停服方式，尤其排查问题时。这时用户看到「会自动重连」，会以为 MineDeck 要去重连一台已经停掉的服，而实际上它并没有重连（连接状态确实停在「等服务器开好」）。
  - 【建议】把判定从「那一刻的状态」换成「控制台里是不是刚发过 stop / 日志里有没有`Stopping server`」，或者干脆在发 `stop` 之前先把状态置成 stopping。
  - 附带：这次没有能按计划验「托盘『全部停止并退出』时伙伴断开」这条，因为托盘退出已经在 I-01 里做过（当时没有伙伴连接）。「服务器开着时关掉 AI 伙伴开关」这一条也还没做，留给下一批。

**F-04 长回复和特殊字符（P1）— 不通过：在当前配置下不可能触发**

试了三次，模型每次都自己压到 100–133 字，最后一次直接说「这样长文发不出来，我一次只能回答一两句」。原因不在模型：

- `internal/chatai/prompt.go:19` 的系统提示写着「简短直接：一般一两句话，**最多 150 个字**」；
- 拆分线是 `internal/chatai/tellraw.go:22` 的 `MaxMsgRunes = 180`。

150 < 180，模型被提示约束在 150 字以内，永远够不到拆分阈值；「完整回答请在 MineDeck 面板查看」还要超过 3 条（540 字）才出现，更不可能。所以这一项不是「没测到」，是**预期和实现互相矛盾**。

emoji 那半是好的：问「结尾加个 🐉」时回复末尾确实带了 🐉，游戏里和控制台回显里都正常。

建议二选一：把提示的字数上限提到 400 字左右（这样「详细攻略」这类问题能真拿到长回答，超 180 字自动拆条，超 540 字才截断并提示去看面板）；或者承认现状，把这条从计划里去掉，把 `Pack()` 当纯防御性代码。另外 `MaxMsgRunes` 定 180 也值得复核——既然提示只允许 150 字，180 这个阈值在当前提示下永远不会被触到。

### 重启与局域网（C-02 那一批）

为了测手机管理，需要把「允许局域网访问」打开并重启程序。这一段记录重启过程和重启后才暴露的两个问题。

**局域网访问的开启方式本身有个坑。** 「设置 → 远程访问」里那个「允许局域网访问」开关**没有绑定任何保存动作**——它只在点旁边「访问密码」那个「保存」按钮时一起提交（`app.js:2515-2520`）。所以单独点开关，界面看起来是开了，实际上什么都没写入，也没有任何提示。我第一次点开关、截图确认它变成了绿色，`config.json` 里却查不到 `listenLan`，就是这个原因。后端其实还做了一道保护（`appops.go:219`：没设密码就拒绝`listenLan:true`），但前端这个「点了不生效也不说」的交互会让人以为已经开了。

**重启之后 S1 从列表里消失了。** 这是这一轮最值得记的一条。

- 现象：程序重启后服务器列表只有 2 台（S2、S2b），「共 2 台」，S1 完全不在界面上；`servers\S1` 目录、`instance.json`、`world`、存档全都在。
- 原因：S1 的 `instance.json` 前三个字节是 `EF BB BF`（UTF-8 BOM），而 S2、S2b 没有。`internal/inst/inst.go:104-111` 读文件后直接 `json.Unmarshal`，带 BOM 会解析失败，然后 `continue` 跳过这个目录——**不记日志、界面不提示、也不告诉用户「有个目录读不出来」**。
- 为什么上一轮没发现：上一轮测试用 PowerShell 还原过这个文件（PowerShell 5.1 的 `Set-Content` / `Out-File` 默认写 BOM），而当时运行中的进程在启动时就已经把实例读进内存了，之后再改文件不影响列表——只有**下一次启动程序**才会发作。也就是说，任何用 PowerShell、记事本「UTF-8 带 BOM」、某些编辑器改过 `instance.json` 的房主，都会在下次开程序时发现自己的服务器「没了」。
- 处置：我把带 BOM 的原文件备份成 `instance.json.bom-bak`，剥掉 BOM 后重启，S1 回到列表（共 3 台）。
- 建议：读之前先剥 BOM（`bytes.TrimPrefix(b, []byte("\xef\xbb\xbf"))`）；解析失败时至少 `log.Printf` 一行；更好的做法是在列表页显示「有 N 个目录读不出来」，别让服务器静默消失。这条对「存档看起来丢了」这种最吓人的场景是直接的止损。

**过程中的一次失误（记下来备查）**：第二次重启时我点错了确认框的按钮，多启动了一个 MineDeck 实例。它因为 27333 被占而自动换了 51756，并在 `data\mcp\runtime.json` 里把自己写成了当前实例。那个实例上没有任何服务器（S1 当时是停的），我直接结束了它，然后把原实例走界面正常退出、只留一个。现在 `runtime.json` 由唯一实例重写，没有残留。顺带说明：J-09 那条「端口被占自动换端口」在这一轮又复现了一次。

**局域网起来之后的状态**：唯一实例监听 `::27333`（全网卡，IPv6 + IPv4），端口回到了 27333（27333 此时已空出）。从本机用内网地址验证：

```
http://192.168.0.8:27333/          → 200（登录页）
http://192.168.0.8:27333/api/instances → 401 {"error":"需要登录"}
```

二维码和 URL 都在「设置 → 远程访问」页上（`http://192.168.0.8:27333`），多网卡时页面会列出四个地址让用户切换。防火墙不需要动——已经有两组针对 `D:\minedeck\minedeck.exe` 的入站放行规则（TCP/UDP 任意端口），是 Windows 之前弹窗时生成的，不是这一轮加的。

顺带一条代码层面的观察：局域网打开后，`secure()` 里的 Host 头校验会被整体跳过（`server.go:135-145`：只有在「没开局域网」时才校验 Host）。也就是说这时候防跨站只剩 API Token 和会话 Cookie 两道。Token 每次启动随机、只通过启动 URL 交给前端、不落盘，所以风险不高，但这是设计上的取舍，记一笔。

**手机端：没法用，这一批（C-02 / E-08 / J-07 后半 / F-13 后半 / G-08 后半）就此中止。**

房主在手机上实际打开后给的反馈是：界面「超级差，近乎不可用」，**顶部和底部的内容都无法显现、点不到**，底部标签栏切换时那个「平滑」的选中动画有卡顿。然后就让我别再测手机了。这条记成【发现 11】，具体的代码线索和桌面窄窗对照见「交互与可用性观察」第 15 条。

## 交互与可用性观察

这一节不按测试计划的编号走，专门记我在操作界面时遇到的、和交互设计有关的问题。有的已经在逐条结果里作为功能缺陷记过，这里只写「为什么别扭」。

**1. 定时任务的时间控件几乎没法用。** 「小时」和「分钟」是两个各自约 20×21 像素的小数字格，嵌在一个 `input[type=time]` 里。想填 21:42，得先点中「小时」那一小格、全选、退格、敲 2 和 1，再点中「分钟」那一小格重复一遍。我用系统粘贴和自动化接口都写不进去，最后一次是老老实实敲的数字键。更要紧的是测试场景本身：我需要的是「几分钟后执行一次」，而界面只接受「每天某个固定时刻」，我只能先去算 21:42 再回来填。建议把时间输入做成一整块可点击的区域，或者干脆给几个快捷项（5 分钟后、10 分钟后、明天这个时间）。

**2. 双击标题栏不能最大化或还原。** 这条在 A-02 里已经作为缺陷记过，交互上它违背 Windows 的习惯——窗口是无边框的，标题栏只能用来看和拖，双击不管用会让人以为程序卡住了。

**3. 关窗直接退出程序，和界面上的说明对不上。** 「设置 → 启动与托盘」里写着「托盘图标在程序运行时始终显示」，但同一个页面上的「最小化到系统托盘」默认是关的，关窗就直接退出。第一次用的人很可能会以为「点了×只是收起来」，结果把正在跑的服务器一起关了。

**4. 部署时没有超时提示。** 这条在 B-01 里记过。界面上只有一句「部署中，请勿关闭程序…」，安装器在后台反复连接超时（每次 30 秒）时，用户看到的是进度条长时间不动，既不知道在重试也不知道还要等多久。

**5. 开关控件的可点区域很小。** 用无障碍接口读到的勾选框矩形只有 1×2 像素，真正能点的是视觉上那个约 44×24 的胶囊。鼠标点当然没问题，但如果实现是「隐藏的小 input + 兄弟元素」，键盘的 Tab 焦点环和自动化都会很难对准。建议确认一下可点击区域是否覆盖整个胶囊（或者整个 label）。

**6. 「管理」用的是超链接语义。** 页面上「启动」是按钮、「管理」是超链接，两者视觉上并排、行为都是页内跳转。对读屏和自动化来说，把它们统一成按钮更清晰。

**7. 命令输入框把用法说明放在 placeholder 里。** 「输入服务器命令（回车发送，Tab 补全，↑↓ 翻历史），如 op 玩家名 / say 大家好」——一敲字这条说明就消失，之后再想确认 Tab 能不能补全就得先清空输入。建议把快捷键提示常驻在输入框下方或右侧。

**8. 「全部配置」页一次性渲染 60 多个输入框。** 滚动条很长，也没有搜索（「常用设置」里有搜索，这一页没有）。找某个键只能一个个滚。

第二轮（配伙伴、音乐共享、游戏内 AI）又攒了一批，编号接着往下排：

**9. 同名的「保存」和「安装」按钮太多，靠无障碍接口根本分不清。** 「游戏内 AI」一页里有 7 个名字都叫「保存」的按钮（触发前缀、别名、四项限流、自定义正则各一个），我只能靠「离我填的那个输入框最近的保存按钮」去筛坐标。资源页搜 `Simple Voice Chat` 回来 20 条结果，20 个按钮全叫「安装」，第一个是 Simple Voice Chat、第二个是 Talking Heads、第四个是 Simple Voice Chat Discord Bridge——名字都差不多，点错就装上别的模组了。建议每个按钮的 `aria-label` 带上字段名或模组名（「保存触发前缀」「安装 Simple Voice Chat」），读屏用户同样受益。

**10. 「刷出伙伴」弹窗里的「主人」输入框在无障碍树里不是输入框。** 弹窗里能读到的 Edit 只有「名字」一个，「主人」那一栏用 UIA 按控件类型枚举时完全看不到（键盘 Tab 能进去）。第一次自动化时我按名字点不到它，只能靠坐标猜，猜偏了点到页面上，Ctrl+A 把整页文字全选中了。建议补一个 `aria-label`。

**11. 可折叠那一行的无障碍名字是一整段。** 「高级识别」那行是 `role=button`，读到的名字是「高级识别 认不出聊天时再来改：放宽名字规则、不看线程名、自定义正则。」——按名字精确匹配会失败，得按「包含」去找。同样的问题在伙伴页的「和伙伴模组的连接」那行也有（名字里带版本号）。建议把折叠行的名字固定成标题本身，副标题放在 `aria-describedby` 里。

**12. 右上角两个「关闭」太像了。** 窗口的关闭按钮叫「关闭」，AI 助手面板的关闭按钮叫「关闭 AI 助手」，两者都在右上角、只差三个字。我用无障碍接口点名时选错了一次，把整个窗口关进了托盘（当时 `minimizeToTray` 是开着的，服务器没受影响，但把测试打断了几分钟）。建议面板那个改成「收起 AI 助手」或「返回」。

**13. 音乐共享的检查清单只肯「指路」，不肯「动手」。** Simple Voice Chat 那一行写的是「mods 里没有」，右边一个「去「资源」页搜索」；点过去以后还得自己从 20 条结果里认出哪条是对的（见第 9 条）。MineDeck 其实完全知道该装哪个模组、哪个版本（清单里桥接模组那一行就是自己装的），建议这一行也给一个「装 Simple Voice Chat」的直接按钮，装的时候顺手核对一下版本。

**14. 游戏里的提示文案换行断得很难看。** `/tp 怎么用` 的提示在游戏里显示成第一行「[AI] 不认」、第二行「识 /tp。可用：/私（只回你）……」，一个 59 字的句子被断成「前面两三个字 + 后面一大串」。我用手写同样内容的 tellraw 复现了同样的断法，而 8 字、19 字的同类提示都完整显示，所以是这句话开头只有一个空格、后面一长串没有断点导致的换行计算问题。建议这类提示在文案里多用逗号顿号（每个短句都能成为断点），或者干脆一句一条 tellraw。

**15. 手机端（局域网界面）基本不可用。** 房主在手机上打开后反馈：顶部和底部的内容显现不出来、点不到，底部标签栏切换时的「平滑」动画卡顿。这一条卡住了 C-02 / E-08 / J-07 后半 / F-13 后半 / G-08 后半五个测试项。

代码里能对上的线索（桌面窄窗口复现不出来，原因也在这里）：

- `#app { height: 100vh }`（`app.css:142`）。手机浏览器的地址栏和工具栏会让 `100vh` 大于**可视**高度，而底部标签栏是 `position: fixed; bottom: 0`（`app.css:1088`），于是它被压到浏览器工具栏下面——「底部的点不到」就是这么来的；内容顶部同样会被顶出去。
- `index.html:5` 的 viewport 只写了 `width=device-width, initial-scale=1`，没有 `viewport-fit=cover`；CSS 里全篇没有一处 `env(safe-area-inset-*)`。iPhone 的刘海和底部横条会继续吃掉底栏的点击区域，而 `#main` 只有写死的 `padding-bottom: 84px`（`app.css:1098`），跟实机高度无关。
- `.console { height: calc(100vh - 500px) }`（`app.css:1105`）在手机上同样基于错误的 `100vh`，控制台高度会算偏。
- 断点是 `@media (max-width: 640px)`，按 CSS 像素宽度切：竖屏手机命中，横屏手机（常见 844×390）会掉回桌面那套两栏布局。
- 动画卡顿的嫌疑：`.nav-item` 和一批控件过渡的是 `background`（不是 `background-color`），移动端会整块重绘；`.sw` 那条用了 `var(--ease-spring)` 的 `transform` 长过渡（`app.css:369`）；页面切换还有 `view-in` 入场动画。这些在桌面上看不出来，在手机上就是掉帧。

对照实验：我把桌面窗口缩到 420×860（iPhone 14 的 CSS 尺寸附近），移动端布局能正常出现——底部标签栏在、页面能滚到底、二维码正常。因为桌面 WebView2 里 `100vh` 恰好等于可视高度，所以这个 bug 在桌面上永远复现不出来，只在真机上暴露。

建议（按性价比排）：把 `#app` 的高度换成 `100dvh`（Safari 15.4+ / Chrome 108+ 支持，旧浏览器保留 `100vh` 作为回退）；viewport 加 `viewport-fit=cover`，底栏 padding 用 `max(6px, env(safe-area-inset-bottom))`、`#main` 的底部内边距同样加上 safe-area；底栏从 `position: fixed` 改成参与 flex 布局（`#shell` 已经是 column 方向，直接让侧栏 `flex: none` 排在最后即可），这样就不需要 84px 这个魔法数字；移动端把过渡改成 `background-color`、并关掉 `--ease-spring` 那类长过渡。

**16. 「允许局域网访问」开关点了不生效，也不提示。** 这个开关没有绑定保存动作，必须和「访问密码」一起点右边的「保存」才提交（`app.js:2515-2520`）。但它的样子和页面里其他开关一模一样（别的开关都是即时生效的），所以点完看到变绿就会以为开好了。我是靠 `config.json` 里查不到 `listenLan` 才发现的。建议要么让它即时保存（并在没设密码时就地提示「请先设置访问密码」），要么把「保存」按钮放到开关这一行、把两个字段框在一起。

**三条做得好的，也记一下：**

- **还原备份的确认框。** 写清了「需要服务器处于停止状态；当前世界会先自动备份一份」，而且真的先存了一份「还原前自动」再回滚。把后果和兜底措施都说在前面，比只说「确定要还原吗」好得多。
- **一键开启白名单的确认框。** 同样把话说全了：「先把勾选的人加进白名单，再开启白名单，免得把好友关在外面。服务器正在运行：会发送 whitelist add 和 whitelist on。」下面还列出了已经在白名单里的人（「已经在白名单里：TesterA」），让人一眼看出这次到底会改动谁。我点确认后服里的人确实没被踢。
- **伙伴安装那一屏的状态文案。** 三个模组各自一行，写着「装的是 0.2.1 · MineDeck 内置的是 0.2.1」「装的是 12H-1.4.0 · 实测过的是 1.21.1-1.4.0，要求 [1.21.1-1.4.0,1.21.1-1.5)」，底部一句「三个都装好了 · 以后 MineDeck 更新了伙伴模组，这里会提示「要换」」。版本、来源、下一步都说清楚了，不用去猜。而且 S2 那台本来就有 Architectury 9.2.14，页面直接标成「已装好」并把下载量从 4.8 MB 降到 4.3 MB，没有硬装一份新的。

## 发现的问题（按严重程度排）

**问题 1（严重，数据丢失）：改了接口地址再保存，AI 的 Key 会被静默清空。**

【编号】D-01 / D-06 相关
【步骤】
1. AI 已经配好（Key 已存，输入框显示「已设置（留空不修改）」）。
2. 只把「接口地址」从 `https://api.deepseek.com` 改成 `https://api.deepseek.com/nonexistent-path`，Key 输入框保持留空，点「保存」。
3. 再改回原地址保存。
【预期】按占位文字的说法，「留空不修改」，Key 应该保留。
【实际】`secrets.json` 从 `{"ai.key":"dpapi:..."}` 变成 `{}`，界面顶部从「已启用 DeepSeek · deepseek-flash」变成「未启用 · 还差：填写 Key」，「测试连接」按钮变成不可用。整个过程没有任何确认框或提示。
【原因】`internal/ai/service.go:510-521`：
```go
// 换了服务商、协议或地址：旧 Key 作废，Claude 中转的功能探测也要重来
moved := changedPreset || st.Protocol != old.Protocol || st.BaseURL != old.BaseURL
if moved {
    ...
    if newKey == nil {
        empty := ""
        newKey = &empty
    }
}
```
前端 `internal/web/ui/app.js:2748` 只在 Key 输入框非空时才带上 `key` 字段，所以只改地址时 `newKey == nil`，走到上面那段被写成空串。而输入框的占位文字是 `keepKey ? "已设置（留空不修改）" : "粘贴 API Key"`（`app.js:2648`），两处说法直接冲突。
【影响】用户只是改了地址（比如从官方站换到中转站），或者不小心点了一下服务商下拉，Key 就没了，而且不会有人告诉他。我这次就是这么把它弄丢的，房主需要重新填一次。
【建议】三种改法任选：一是改地址时如果没给新 Key，就保留旧 Key，只在真正测试失败后再提示重填；二是确实要清空时给一个确认框，写明「地址变了，旧 Key 会作废」；三是把占位文字改成「已设置（改地址会清空）」并即时提示。顺带一提，`ai.provider.set` 的操作记录里 Key 缺失时 args 里完全没有 `key` 字段，事后从日志也看不出这次保存把 Key 删了，建议补成 `"key":"***"` 或 `"key":""`。
【附件】`d01-fail.png`（Key 被清空后的界面）、当时的 `logs\ops` 记录

S2（BMC4）启动时崩溃，崩溃报告 `crash-reports\crash-2026-11-01_22.09.41-fml.txt` 写得很清楚：

控制台顶部的横幅出现了，橙红色，标题「服务器异常退出」，正文是「服务器自己退出了，本地规则没认出来具体原因。」，展开「看详情和怎么修」后给的建议是「1. 查看控制台里退出前最后几行 ERROR 和异常 2. 配了 AI 的话，可以让 AI 结合崩溃报告分析」。

【问题 2】这正是计划里 E-06 的第 1 种样本（少装前置模组），但本地规则没认出来。日志里 `Mod X requires Y` 是极其常见的模组加载失败格式，识别它应该不难。
【问题 3】横幅标题说「异常退出」，展开后的证据却引用 MineDeck 自己写的那句 `[MineDeck] 服务器已正常关闭`，前后矛盾。用户看到「异常退出」又看到「已正常关闭」，会不知道该信哪个。

**S2 崩溃本身不是 MineDeck 的问题，但值得记一笔**

`continuity` 是纯客户端的光影/字体类模组，BMC4 v59 的 `modrinth.index.json` 把全部 340 个文件都标成了 `(client=required, server=required)`，所以服务端也装了它。整合包自带的 Missing Mods Checker 在首次启动时又补装了 34 个模组（Connector、fabric_api 0.92.6、FTB 系列等），其中 fabric_api 的版本低于 continuity 要求的版本，导致第二次启动崩溃。也就是说：这个包在服务端跑不起来，跟 MineDeck 的导入行为无关——导入那一侧（B-02）的识别和完整性都是对的。

**E-06 第二轮样本：客户端模组放进服务端（认出来了）**

把 continuity 移出后，S2 换了个错：`Attempted to load class net/minecraft/client/gui/screens/Screen for invalid dist DEDICATED_SERVER`，堆栈指向 `entity_texture_features$etf$illegalPathOverride`。移出 entity_texture_features 和 entity_model_features 之后，又变成 Mixin 的 `ClassInfo.isMixin() ... fieldOwner is null`。

这一轮横幅表现明显更好，标题「客户端模组放进了服务端」，说明写的是「某个模组只能装在客户端（小地图、界面美化、光影一类），服务端加载它时用到了客户端才有的类 net.minecraft.client.main.Main」，一共认出 2 个问题：一个是客户端模组误装，一个是 Mixin 冲突（直接点名 `colorwheel` 的 `IrisMixin`）。修复建议也给了：「把这个模组从服务端禁用（mods 目录里改名成 .jar.disabled）」，认不出 jar 时还教了怎么从堆栈反查。

还有一处可以改进：客户端模组这一类只说了「某个模组」，没有像 Mixin 冲突那样直接点名 jar 名。计划里 H-09 的要求是「照样认出来，而且只点名那个小地图」，点名这块还没完全做到。

**S2 的结论：BMC4 不适合当服务端，继续删模组是无底洞**

BMC4 v59 把 340 个文件全标成双端必需，服务端因此装进了 continuity、entity_texture_features、entity_model_features 这类纯客户端模组，删掉一个立刻有另一个模组的 Mixin 找不到目标（colorwheel 的 IrisMixin）。这与 MineDeck 的导入行为无关——B-02 的识别和完整性都是对的——所以在 S2 上继续做 F-05 的 1.20.1 那半、H-08、G 组相关项之前，得先换一个服务端友好的整合包。

本轮为验证做的改动（可逆）：`D:\MineDeck\servers\S2\_mods-removed\` 里放着移出来的 `continuity-3.0.0+1.20.1.forge.jar`、`entity_model_features-3.2.4-1.20.1-forge.jar`、`entity_texture_features_1.20.1-forge-7.1.jar`，放回 `mods\` 即还原。

**S2 的替代方案：S2b（the horrors in the fog，Forge 1.20.1）**

BMC4 在服务端跑不起来之后，换了一个轻量包：Modrinth 上的 the horrors in the fog 1.0.5，Forge 47.2.17，59 个文件、53 个模组。导入流程和 B-02 一样顺利，八步全绿，`整合包文件下载完成（59 个）`。Forge 安装器的日志里能看到 MineDeck 注入的镜像：`--mirror https://bmclapi2.bangbang93.com/maven/`。

这个包同样把所有文件标成双端必需，所以导入后我先人工挑出 19 个纯客户端模组（embeddium、oculus、entityculling、Xaeros 小地图和世界地图、BetterF3、ImmediatelyFast、appleskin、firstperson、notenoughanimations、modelfix、spawnanimations、rubidium-extra、AmbientSounds、EnhancedVisuals、Nyctophobia、CrosshairBobbing、WI-Zoom、Essential），移进 `servers\S2b\_client-only-mods\`，服务端只留 34 个。这些 jar 放回 `mods\` 即还原。

之后 S2b 正常启动：`Done (24.504s)!`，监听 25566，Simple Voice Chat 在 UDP 24454 启动（`Voice chat server started at port 24454`），Open Parties and Claims 的权限系统回退提示也是正常 WARN。

启动日志里有一条无害的 ERROR 可以忽略：`Failed to load function watching:check`，是包里某个模组自带的数据包函数引用了不存在的命令，不影响服务器起来。

也就是说：**同样标注「服务端必需」的两个整合包，BMC4 跑不起来、fog 清掉客户端模组后能跑**。区别在于 BMC4 的客户端模组 hook 得太深（entity_texture_features 改写了 `ResourceLocation`），一删就有别的模组 Mixin 崩。这条对「导入整合包」这个功能本身是个有价值的边界样本。

**E-09 端口占用（P2）— 不通过：端口明明被占，工具报「空闲」**

我先把一个监听绑在 `0.0.0.0:25566` 上（这次是真的占住：自己再绑 `Any:25566` 会失败），然后问助手「25566 这个端口现在被谁占了？」。它调了「检查端口占用」，回答「25566 现在没人占用，TCP、UDP 都空闲」，还推测「S2 和 S2b 都是停止状态，所以端口没有程序占用」。

直接调工具核对，原始返回是：

```json
{"instances":[{"instance":"S2b","status":"stopped"},{"instance":"S2","status":"stopped"}],"port":25566,"tcp":{"free":true},"udp":{"free":true}}
```

同一时刻我自己去绑 `0.0.0.0:25566` 是失败的，说明端口确实被占。

原因在 `internal/ops/catalog/port.go:56-70`：判断方式是「试着 `net.Listen("tcp", ":端口")`，成功就算空闲」。在 Windows 上，当双方都允许地址复用（SO_REUSEADDR）时，第二次 bind 仍会成功，于是把「被占」误判成「空闲」。同样的检测在 MCP 服务换端口那次（J-09）是对的，因为那里绑的是 `127.0.0.1` 且失败被正确捕获。

影响：这一项按预期应该「查到占用端口的程序名」，实际连「被占用」都没识别出来；连带 E-06 里「端口被占」这个样本如果靠这条规则判断，也可能漏报。建议改成枚举真实监听者（`GetExtendedTcpTable` / IP Helper API，或 `netstat -ano` 的等价调用），或者在 bind 时加上 `SO_EXCLUSIVEADDRUSE`。

另外记一个我自己的方法错误：一开始我用只绑 `127.0.0.1:25566` 的监听去模拟占用，助手答「没人占用」其实站得住——因为 Windows 上 loopback 的监听不阻止别人绑通配地址。换成 `0.0.0.0` 才是真正的占用。

## 提案：游戏内 AI 的限流默认值偏保守

这一节不是缺陷，是测试过程中撞出来的体验问题和几条建议。F-12 那一项原本要「1 分钟连发 6 次」才验得到，实际是我在正常问答里自然撞上的——这说明默认值对一个真人玩家来说太紧。

**现在的出厂默认值**（每台服务器都能在「游戏内 AI」页改，下面说的是没人改过时的行为）：

| 项 | 默认值 | 代码 |
|---|---|---|
| 每人冷却 | 15 秒 | `chatai/settings.go:25` |
| 每人每天 | 30 次 | `:26` |
| 全服每天 | 300 次 | `:27` |
| 全服每天 token | 50 万 | `:28` |
| 防刷屏 | 同一个人 1 分钟内触发超过 5 次 → 静默 10 分钟（完全不出声） | `chatai.go:117-119` |
| 同时处理 | 1 个，最多排队 3 个 | `chatai.go:116` |

**实测撞上的那一次**（2026-11-02 01:45:51–01:46:46，55 秒内 6 次）：

```
01:45:51 @AI 把天气改晴      → 回答 + 执行 weather clear
01:46:06 @AI 把天气改晴      → 冷却中，1 秒后再问
01:46:11 @AI /问 把天气改晴  → 只回答不动手
01:46:24 @AI 给我 op         → 冷却中，3 秒后再问
01:46:29 @AI 给我 op         → 拒绝并说明原因
01:46:46 @AI 把所有人传送过来 → 静默 10 分钟，一个字都不回
```

玩家侧的感受是「AI 坏了」，而不是「我被限流了」。三条具体原因：

1. **冷却期间的再问也计入刷屏计数。** `handle()` 里 `spam()` 在 `limit()` 之前，所以「被冷却挡回的那句」照样记一次触发。等于是「越急着问，越快被静默」，而且玩家完全推不出这个因果。
2. **静默完全无声。** 静默期间 `handle()` 直接 return，什么都不发；只在 `gameai-state.json` 的 history 里留一条 `kind=silenced` 的 note，`logs\ops` 里连记录都没有（这次的 ops 最后一条停在 01:46:31 的 `gameai.ask`）。事后想解释「为什么没反应」，只能靠翻实例目录里的状态文件。
3. **每人每天 30 次是「@AI」和「@小方」共用的。** `accept()` 对所有受理的提问都 `Players[k]++`，伙伴指令也一样。而伙伴是高频短指令的交互（H-04 那种「砍 10 个原木」加报告，来回几次就吃掉好多次），30 次很容易用完。

**钱不是瓶颈。** 用这次的真实账算：`data\ai\usage.json` 今天 `gamechat` 记了 8 次请求、11,920 token、$0.00246，折成每次提问约 1,500 token、**$0.0003**。也就是说每人 30 次/天大约 $0.01，全服 50 万 token 的预算大约 **$0.1**。限流卡的是刷屏和滥用，不是成本。

**建议（按改动量和收益排序）**

1. **冷却中的再问不计入刷屏计数**，只把真正受理的提问算进去。改动最小，正好掐掉「问得急 → 冷却提示 → 计数 +1 → 更快静默」这条连锁。
2. **第一次静默要私下说一句**，比如「你问得太快了，X 分钟后再问」，带上剩余时间；同时把静默和冷却写进 `logs\ops`（现在这两个动作在操作记录里完全看不到，和「有日志才能解释」的原则不符）。
3. **静默从 10 分钟降到 2–3 分钟**，或者改成「静默期间每 N 分钟允许再试一次」。10 分钟对一个正在打游戏的人来说很长，足够让他去群里说「这服的 AI 坏了」。
4. **每人冷却 15 秒 → 6–8 秒。** 读完一句答案大概 5–10 秒；这次两次被挡分别只差 1 秒和 3 秒，说明 15 秒比正常节奏慢一截。
5. **每人每天 30 次 → 60–100 次，并且把「@伙伴」的指令单独计。** 伙伴任务和「问 AI 一个问题」不是一类操作，混在一起计会让人觉得不敢用伙伴。
6. **全服 50 万 token 保留**，但建议在页面上写清「50 万 token 约合多少钱」（按 DeepSeek 的价格约 $0.1），房主才知道这个数字跟钱是什么关系。
7. 顺带一个界面上的缺口：**房主在界面上看不到「谁今天用了几次」**，只有玩家自己在游戏里发 `/额度` 才看得到。建议额度那一行列出用量最高的人，或者干脆在「最近的问答」里按人合计。

**不建议改的**：同一时间只答 1 个、最多排队 3 个。这次日志里从没出现过「AI 正忙，请稍后再问」，说明这个上限没挡到正常使用。

以上都是出厂默认值的问题，房主自己在页面上就能改；但如果大多数人不会去改，默认值就等于产品的实际体验。

- **「自己不会听到两遍」这条验得很干净。** 把「我在游戏里的名字」填成 TesterA 时（写进 `voicebridge.properties` 的 `exclude=TesterA`），桥接日志是「玩家连上语音：TesterA（在排除名单里，不推送），当前听众 0 位」「发出 0 帧」，房主确认只听到原声一遍；把那一栏改成别的（「无」）后变成「当前听众 1 位」「发出 1501 帧」，房主确认**听到两遍**（原声 + 语音通道一份）。
- 客户端侧：SVC 的「调整音量」界面里出现独立分类「MineDeck 音乐共享」（房主截图，当时是 +38%），可以单独调小或静音，不影响「其他」。
- 没验到的三条，都要第二台电脑：好友在另一台电脑上听到；额外延迟是否在 0.5 秒以内（只能确认两份能明显分辨，量不出毫秒）；游戏声音和语音聊天没被录进去（按程序采集在机制上排除了，但同一台机器上没法彻底区分）。

**G-05 听众状态（P1）— 部分通过**

「会听到音乐：1 人 · TesterA」——连上语音的人确实进了这一栏；被填进「我在游戏里的名字」时，桥接里把他标成「在排除名单里」，不算听众。「在线但没连上语音」「版本不兼容」两栏没有样本：一台电脑上要造出来得删客户端 SVC 或换版本再重启客户端，本轮没做。

**G-04 停下来（P1）— 通过（四种停法都验了）**

- **停止广播（界面按钮）**：桥接日志「音频暂停（广播，100 毫秒没有新数据），已通知客户端收尾」→「广播连接已断开：…原因：对方结束了广播（用户停止）；本次共收到 27771 帧」；操作记录 `music.stop src=ui`。
- **关掉音乐软件**：房主退出网易云之后，日志「原因：对方结束了广播（**音乐软件退出了**）」，操作记录 `music.stop src=schedule actor=自动停止 args.reason="音乐软件退出了"`——和计划要求的「自动停下的来源是 schedule」一致。
- **停服**：广播在跑（连接 #3、听众 1 位）时从控制台发 `stop`，2 秒后操作记录是 `music.stop src=schedule actor=自动停止 args.reason="服务器已停止"`，桥接日志「音乐共享已停止（语音服务器已停止）」。符合预期。
- **托盘「全部停止并退出」**：广播在跑、房主在服里（12:39:15 时还是「当前听众 1 位」）的情况下，房主自己点托盘菜单的这一项（按规则危险操作留给他点）。结果：`music.stop src=schedule actor=自动停止 args.reason="MineDeck 已退出"`，桥接日志「广播连接已断开：…原因：对方结束了广播（MineDeck 已退出）；本次共收到 13643 帧」→「音乐共享已停止（语音服务器已停止）」，随后 MineDeck 进程和服务器 java 都没了，`data\mcp\runtime.json` 被删。
- 没验到的只有一句「好友那边音乐几乎马上停下」——听的人是房主本人（同一台机器），没有第二台电脑。

**【新发现】用控制台 `stop` 停服，如果开着「崩溃自动重启」，服务器会被重新拉起来**

这条是测 G-04 第三种停法时顺带撞上的：

```
12:34:03 instance.command src=ui   {"cmd":"stop"}
12:34:05 music.stop      src=schedule {"reason":"服务器已停止"}
12:34:15 instance.start  src=schedule actor=崩溃自动重启 {"attempt":1}
12:34:31 Done (1.245s)!
```

也就是说：用户明确要求停服，10 秒后服务器自己又起来了。根因和 H-02 发现 8 是同一处——`internal/companion/service.go:458` 那套「按那一刻的实例状态判断这次退出是不是正常关服」的思路，在控制台 `stop` 这条路上同样失效：发 `stop` 时实例状态还是 `running`，Java 退出被当成异常退出，于是走了崩溃重启。

比 H-02 那条更值得修：H-02 只是把正常关服记成了「警告」加一句「会自动重连」，而这条是行为错误——想停服却停不掉，还白跑一次重启。建议在发 `stop`（或任何用户主动停服）之前先把实例状态置成 `stopping`，或者用「控制台发过 stop / 日志里有 `Stopping server`」来判断这次退出是正常的。

测完之后 S1 的「崩溃自动重启」我没有动（它本来就是 B-07 留下的 `true`），只是记下这个组合。

**I-02 开机自启（P1）— 部分通过：进了托盘、不播启动画面，但开机时白闪一下**

「设置 → 启动与托盘 → 开机自动启动」原本是关的，打开后：

- 注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 里新增 `MineDeck`，值是 `"D:\MineDeck\MineDeck.exe" -minimized`；
- 操作记录 `app.config.set args.autoStart=true`；
- 页面上那行说明写着「登录 Windows 后自动在后台（托盘）启动 MineDeck…程序换目录后重新开关一次即修正路径」，下面还补了一句「开机自启以「静默进托盘」方式启动（附加 `-minimized` 参数），配合上面的托盘开关体验最佳」。

这也是本轮唯一一处写注册表的地方（改之前 Run 键下有九项别的程序，没有 MineDeck）。**还原方法**：把「开机自动启动」关掉，或直接删掉 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 下的 `MineDeck` 值。

房主重启后的实测（重启时刻 12:48:05，MineDeck 进程 12:48:57 起来，也就是登录后约 52 秒）：

| 预期 | 结果 |
|---|---|
| 开机后静默进托盘，不弹窗口 | **不完全符合**：窗口没有停在桌面上，托盘图标和气泡「MineDeck · MC 一键开服」都在，但**有一个白色窗口一闪而过** |
| 第一次从托盘打开时，不播启动画面 | 符合：房主确认「没播，直接就出现界面」 |

进程侧能核对的都对上了：唯一的 MineDeck 进程（pid 13188）监听回 27333，`data\mcp\runtime.json` 里 `started` 是 12:48:58；三台服务器都还是停止状态，没有被自动拉起；开完机之后 `logs\ops` 里没有任何多余记录。

【发现】开机自启的白闪是另一处机制，和 A-03 那条不是一回事。

- 现象：登录后有一个白色窗口一闪而过（房主原话「一闪而过的一个白色窗口」）。
- 原因（`main.go:146-178`）：`webview2.NewWithOptions` 建窗时窗口就是可见的，`hideTrayWindow`（`tray_windows.go:227`，就是 `ShowWindow(SW_HIDE)`）排在这一串初始化的最后——`applyDarkTitleBar`、`applyWindowIcon`、`setupTray`、`applyFrameless` 和六个 `w.Bind` 全在它前面。这中间 WebView2 还没把页面画出来，用户看到的就是一块还没上色的白窗口。
- 和 A-03 的区别：A-03 管的是「窗口可见之后、页面画出来之前不能白」，做法是 `setWebViewBackground` 把底色设成标题栏色；这条是「`-minimized` 时窗口根本不该被显示出来」，压根没走到上色那一步。
- 建议：`-minimized` 时不要先建可见窗再隐——要么在创建前就把窗口藏起来（建窗后立刻 `SW_HIDE`，不要在中间插六次 `Bind`），要么改用 `WS_EX_TOOLWINDOW` + 不带 `WS_VISIBLE` 的方式创建。开销最小的是把 `hideTrayWindow(hwnd)` 提前到 `hwnd := uintptr(w.Window())` 之后的第一行（`applyDarkTitleBar` 之前）。

## 第五轮：内网穿透（樱花穿透，C-03 / G-07）

房主在樱花后台建了两条隧道，都在同一个节点上：TCP（本地 25565）和 UDP（本地 24454），远程端口由樱花分配。（入库前把隧道的公网地址和远程端口换成了 `<节点IP>`、`<节点域名>`、`<游戏端口>`、`<语音端口>` 这样的占位，隧道 ID 删掉了。）MineDeck 这一侧用「+ 添加隧道」各加一条：服务商「樱花frp SakuraFrp」、用途分别选「游戏」和「语音」、填隧道 ID、访问密钥由房主本人粘贴、绑定 S1、打开「跟随实例启动」。`tunnels.json` 里两条隧道的 `credential` 都是 `dpapi:` 开头，`logs\ops` 里 `tunnel.add` 的 `credential` 是 `***`。

**首次使用的门槛：樱花 frpc 要手动放一次**

第一次点「启动」，卡片没起来，操作记录是 `tunnel.start ok:false`，错误原文：

> 首次使用需手动放置樱花 frpc：登录 SakuraFrp 管理面板 → 软件下载 → 下载「frpc」Windows amd64 版，把 exe 放入 D:\MineDeck\runtimes\frpc\natfrp 目录后重试（仅需一次）

源码里的理由是樱花没有稳定的直链下载 API（`internal/tunnel/providers.go` 的 `EnsureFrpc`），所以不自带；OpenFrp 和自定义 frps 都是自动下载的（自定义 frps 还带 SHA256 校验）。房主下载后把 `frpc_windows_amd64.exe`（14.2 MB）放进那个目录，再点一次就起来了：`tunnel.start ok:true ms=2867`。

第一次启动时 frpc 会问服务条款，MineDeck 自动回了 `y`（`tunnel.go` 的 `handleLine` 里处理），不用人工介入。

**C-03 樱花穿透：游戏隧道（P0）— 部分通过，发现「停服不停隧道」**

做通的：

- 启动后卡片变「运行中」，抓到公网地址 `<节点IP>:<游戏端口>`，点「复制」后剪贴板里就是这串（实测读剪贴板核对过）。
- **公网地址真的打到 S1**：用 Minecraft 服务器列表协议（协议号 769）从公网地址 ping，返回 `version 1.21.1`、`protocol 767`、`players 0/15`，和 S1 的配置一致（脚本在 `D:\MineDeck-tools\mpping.ps1`）。
- **跟随实例启动有效**：把两条隧道都停掉（frpc 归零）之后点 S1 的「启动」，两条隧道自己起来了（frpc 变 2 个）。
- 隧道日志里同时给了两种地址：`使用 >><节点域名>:<游戏端口><< 连接你的隧道` 和 `或使用节点 TP 连接（不推荐）>><节点IP>:<游戏端口><<`。

没做通的：

- **停服时隧道不跟着停。** S1 在跑、两条隧道都「运行中」的时候用控制台 `stop` 停服，`frpc` 进程数一直是 2，`logs\ops` 里没有任何 `tunnel.stop`。代码里只有 `StartBound`（实例启动时调用），**没有对应的停服停止逻辑**——`internal/ops/catalog/instances.go:219` 只把 `StartBound` 挂在 `instance.start` 和 `instance.restart` 上，`instance.stop` / `instance.kill` 一概没管。
- 影响：停服之后公网端口还开着，好友能连到樱花节点（节点会接受连接，但后端已经没有服务），语音端口也继续挂着；用户以为「停服就下线了」，实际上隧道和端口都还在。
- 建议：`instance.stop` / `instance.kill` 之后把该实例上开了跟随启动的隧道一并停掉（和启动对称）；或者在「跟随实例启动」这个开关旁边写清「停服时也会跟着停」并真的实现。
- 没验到的：远程好友真的进服。这需要第二台电脑，和 C-01 同一个条件。

**G-07 樱花穿透：语音隧道（P0）— 部分通过，发现「停隧道不清 voice_host」**

做通的：

- 语音隧道（UDP，远程端口 <语音端口>）启动后，MineDeck 把地址写进了 S1 的 `config/voicechat/voicechat-server.properties`：`voice_host=<节点IP>:<语音端口>`，同时生成 `voicechat-server.properties.bak`（3214 字节，就是原文件）。
- 控制台里有一句提示：「[MineDeck] 音乐共享：语音隧道的公网地址变了：已写进 voice_host=<节点IP>:<语音端口>，**重启服务器后远程好友才连得上语音**」——把「要重启才生效」说清楚了，这句是对的。
- 「音乐共享」页的「远端好友的语音」变成「<节点IP>:<语音端口> · voice_host 已经是语音隧道的公网地址，远程好友连服后就能听到」，「发给好友的说明」第 3 条也自动带上这个地址。

没做通的：

- **把语音隧道停掉之后，`voice_host` 没有被清回去**，仍然是 `<节点IP>:<语音端口>`。更麻烦的是「音乐共享」页还在说「voice_host 已经是语音隧道的公网地址，远程好友连服后就能听到」，发给好友的说明也照样给这个地址。SVC 只在开服时读这个值，所以下一次开服会让所有人的语音都去连一个已经不存在的地址——本机玩家也一样走这个地址。
- 建议：隧道停止时把「由它写进去的」 `voice_host` 清回空（`internal/musicshare` 里已经有 `voiceHostWritten` 记录上次写进去的值，可以据此只清自己写的），并在页面上把语音隧道的运行状态一起显示。
- 没验到的：远程好友听到音乐、能用语音。需要第二台电脑。

**这一批里顺带看到的现象**

- **隧道卡片状态更新有延迟。** 点「启动」后约 10 秒，卡片还写着「尚未启动」、顶部「运行中 0」，退出这一页再进来才变成「运行中 / 运行中 1」。用户这时候容易以为没启动成功又点一次。
- **跟随启动不写操作记录。** 手动启动有 `tunnel.start`，跟随启动（`StartBound`）没有，事后在 `logs\ops` 里查不到「隧道是谁拉起来的」。
- **跟随启动失败时界面上看不出来。** 第一次没有 frpc 时，卡片一直停在「尚未启动」，只有点开那张卡片的「日志」才看到「跟随启动失败: 首次使用需手动放置樱花 frpc…」。代码里已经有 `LastError`（取 frpc 输出里的 error / fail 行），建议直接显示在卡片上。
- **`tunnels.json` 里两条隧道的端口字段是误导性的。** `localPort` 都是 25565、`remotePort` 都是 25566；语音那条本该是 24454，游戏那条樱花给的远程端口是 <游戏端口>。对樱花这两项不参与启动（`Launch` 只传 `-f 密钥:隧道ID`），所以不影响功能，但存着这两个数会让人误判。
- **公网地址优先取了 IP 而不是域名。** 樱花同时给了 `<节点域名>:<游戏端口>`（域名）和 `<节点IP>:<游戏端口>`（IP），MineDeck 的正则抓到的是最后出现的那个，于是卡片和「复制」给好友的都是 IP。IP 会随节点变，域名更稳，建议优先取域名形式。
- **崩溃自动重启后隧道不会自动跟起。** 这一批里服务器的崩溃自动重启触发了两次（10 秒、30 秒退避各一次，`instance.start src=schedule actor=崩溃自动重启`），两次都没把隧道带起来——和 C-03 那条同源，`StartBound` 只挂在页面上的「启动」和「重启」两个操作里。
- **frpc 第一次启动后自行退过一次。** 15:31:27 启动成功，到 15:35 前后 frpc 进程消失，隧道日志只留一行「[MineDeck] 隧道已停止」，没有错误信息；重启之后连着跑了 5 分钟以上没有再掉。原因没查清（可能和 Sakura 那边的会话策略有关），建议 MineDeck 在 frpc 非正常退出时把退出码和最后几行输出一起打到隧道日志里，否则用户只能看到「已停止」。

下面按「发布前值得先处理」排一遍，都是这次实测出来的，按影响排不按编号排。

**建议先修的（会造成数据丢失、停不下来，或者用户明显被误导）**

1. **改「接口地址 / 服务商 / 协议」再保存会静默清空 Key**（问题 1，`internal/ai/service.go:511`）。房主已经因此丢过一次 Key。输入框还写着「留空不修改」。
2. **用控制台 `stop` 停服会被当成崩溃，触发「崩溃自动重启」把服务器又拉起来**（第四轮【新发现】）。这一条实测复现两次（10 秒、30 秒各一次，`instance.start src=schedule actor=崩溃自动重启`）。用户明确要停服却停不掉，还白跑一次重启。
3. **停服不会停掉跟着启动的隧道**（C-03）。公网端口在服务器停下后继续开着，好友能连到樱花节点、后端却没有服务；语音端口也一直挂着。
4. **停掉语音隧道后 `voice_host` 不清，页面还宣称有效**（G-07）。下一次开服会让所有玩家的语音去连一个已经不存在的地址，连本机玩家也走它。
5. **`instance.json` 带 UTF-8 BOM 时那台服务器会从列表里静默消失**（发现 10）。对「存档是不是丢了」这种最吓人的场景，这是直接止损项；至少该记一行日志并在列表页提示「有 N 个目录读不出来」。
6. **手机端（局域网界面）基本不可用**（发现 11）。`100vh` 加 `fixed; bottom: 0` 让底部标签栏被浏览器工具栏压住，缺 `viewport-fit=cover` 和 safe-area。这一条卡着 C-02 / E-08 / J-07 后半 / F-13 后半 / G-08 后半五项。
7. **F-04 的「长回复拆分」在当前配置下不可能触发**：系统提示限 150 字，拆分线是 180 字。要么把提示放到 400 字左右，要么把这条从计划里去掉。
8. **E-09 的端口占用检测在端口真被占时仍报「空闲」**（`internal/ops/catalog/port.go:56-70`），因为它是「试 bind」而不是枚举监听者。
9. **伙伴在改了掉落逻辑的整合包里捡不到东西**（H-08）：`Pickup Dropped Items` 走到掉落物跟前就卡住，150 秒 `have: 0`。至少要能在界面上说清「拿不到掉落物」而不是只说「卡住了」。

**值得顺手改的（不影响功能，但让人困惑）**

- 双击标题栏不能最大化 / 还原（A-02，`app.js:375` 的 mousedown 抢走 dblclick）。
- 开机自启时有一块白窗口一闪而过（I-02）：`-minimized` 的窗口是先建可见窗再 `SW_HIDE`，中间那段 WebView2 还没上色。
- 「连过的 AI 工具」不自动刷新（要 F5）；隧道卡片启动后状态要等约 10 秒或者重进页面才更新。
- 隧道跟随启动失败时，卡片上没有提示，只有点开「日志」才看得到；跟随启动也不写 `logs\ops`。
- 「复制配置…」菜单里「其他（HTTP）（HTTP）」文案重复；弹窗里的「复制」和页面上的「复制」同名。
- 「允许局域网访问」开关单独点不生效也不提示，必须和密码一起点「保存」（`app.js:2515-2520`）。
- 游戏内 AI：命令输出只等 1 秒，`locate` 一类慢命令拿不到结果，AI 只能让玩家自己敲；「问某个命令怎么用」这种自然写法（`/tp 怎么用`）会被当成选项吃掉；防刷屏的默认值偏紧，房主这一轮又被静默了 8 分钟。
- 伙伴任务完成通知里的「背包里共 N 个」和面板数字对不上（H-04 发现 9，这一轮没有复现）。
- 「好友进不来（模组对不上）」的横幅把 `com.mojang.authlib.GameProfile@…` 整个打印出来了，应该只写玩家名。
- 「好友的客户端」只讲伙伴模组，不讲整合包——整合包服务端的好友光装伙伴模组进不来（这一轮实测差 8 个模组）。
- 樱花隧道的公网地址优先取了 IP（`<节点IP>`）而不是域名（`<节点域名>`），IP 会随节点变。
- `tunnels.json` 里樱花隧道的 `localPort` / `remotePort` 是两个不参与启动的数（都写成 25565 / 25566），容易误导。

**四条操作经验**：

- 无障碍接口拿到的矩形是**真实屏幕坐标**，可以直接点；但 `PrintWindow` 截图比真实窗口压了约 5%（越靠下差得越多），不要拿截图量的坐标去点。
- 用 `powershell -File 脚本 -Value <带引号的字符串>` 传参会被重新拆词，长命令一律走「写文件 + `sendcmd.ps1` 读文件」这条路。
- 点元素时优先用 `InvokePattern`：它对**离屏**元素也有效，而退化成鼠标点击时坐标会落在屏幕外（比如列表页的「启动」被滚出视口时）。`clickname.ps1` 会先试 InvokePattern。
- 数字输入框（每日额度、内存那类）在无障碍树里是 `Spinner` 而不是 `Edit`，`setfield.ps1 -Kind Spinner` 能填，但**清空**要用 `ValuePattern.SetValue('')`（粘贴空字符串不会生效）。
