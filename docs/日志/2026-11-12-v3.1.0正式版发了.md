第一次试 v3.0.0 没成功。查下来是测试方法的问题，可也带出了一个一直藏着的毛病。更新脚本 `update.bat` 靠 `tasklist ... | find "进程号"` 等旧进程退出（`internal/update/update.go` 的 `Apply`，148 行）。那次旧版是从 Git Bash 里起的，PATH 里 Git 自带的 GNU find 排在 System32 前面，cmd 找到的是它，报一句找不到文件，等待那一行一下就过去了。旧进程还没退，`move` 换不了文件，脚本接着又把旧版启动了一遍，`MineDeck.new.exe` 留在旁边。双击启动时用的是注册表里的 PATH，这台电脑上 System32 排第一；第二次改从 PowerShell 起旧版，一次就成了。

普通用户碰上的机会不大，但有的电脑会把 Unix 那套 find 放在 System32 前面，比如装了 MSYS2、Cygwin 一类工具，又把它们的目录排到了 PATH 前头。具体哪些软件的哪种安装方式会这样，没有实测过，这台电脑上只证实了 Git Bash 里是这样。这样的电脑点更新，程序重开以后还是旧版，`MineDeck.new.exe` 留在 exe 旁边，数据不受影响，手动把它改名换上就行。修法是把脚本里的 `tasklist` 和 `find` 写成 `%SystemRoot%\System32\` 下的全路径，`move` 失败时等一会儿再试，不要马上把旧版拉起来。要注意，更新脚本是旧版本写出来的，修好以后只有从修好的那一版往后升级才用得上；从 3.1.0 升级的人跑的还是 3.1.0 的脚本。以后再测应用内更新，旧版要从 PowerShell 或资源管理器里起，别从 Git Bash 里起。
