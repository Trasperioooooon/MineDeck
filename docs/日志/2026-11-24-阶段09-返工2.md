## 做了什么

都在分支 `claude/clear-backlog-1122` 上，基准是 `c297dd4`（阶段 12 第 1 轮返工的日志提交；第 1 轮返工之后分支上合入的 v3.2.6 和阶段 11、12 的返工不碰这次的代码）。代码七个提交，这份日志另一个提交。

**启动脚本整份展开的上限（`a5bffef`，A43）。** 原来 `scriptJavaOptions` 把每一行启动 Java 的命令拆出来的参数全留着，变量的值也一直留着，单个、单行都有上限，合起来没有。现在展开交给一个小的 `scriptExpander`：它记着赋值过的变量，也记着整份已经展开了多少，各个变量的值加上各行展开以后的长度合计超过 1 MB（`maxScriptExpand`），就和单个超长一样回 `errScriptTooLong`，整份按认不出办，什么都不带，任务日志那句改成「一个变量或一行超过 32 KB，或者整份加起来超过 1 MB」。所有行都记账，不只是启动 Java 的那几行。挑哪一行的规矩没变（第一行点名启动文件的，没有就第一行启动 Java 的），只是不再把每一行都留着：只留第一行，碰到点名启动文件的那一行就直接返回，后面的不再展开。这有一个小变化：点名那一行后面再写的东西不管多长都不会让整份认不出了，以前会。一千行那份脚本现在展开三十来行就停下，一路申请四十几 MB（以前一个多 GB）；两千个变量那份两三 MB（以前一百多 MB）。展开循环里「边写边量」那一步原来没有用例钉住，补了一条一行里把将近 32 KB 的变量引用两万次的，bat 和 sh 各一份，断言申请的内存在 16 MB 以内。三条新用例断言的都是 `runtime.MemStats.TotalAlloc` 前后的差，不只看返回得快不快。

**JVM 参数名单补几样（`1ba22cc`，A43）。** `-D` 按名字不带的补了 `user.dir`、`user.home`、`jna.`、`org.apache.logging.log4j.`（log4j 2.10 起 `log4j2.` 的另一种写法，能盖掉 MineDeck 给老版本加的 `formatMsgNoLookups`）、`fabric.addMods`、`bundler`（Paper 启动器的 `bundlerRepoDir`、`bundlerMainClass`）；`user.timezone`、`user.language`、`user.country` 照旧带。名字过了的再按值看一遍（新的 `propOutside`）：值是绝对路径的（盘符开头、`\` 或 `/` 开头）、`file:` 网址、路径里带 `..` 段的，原因写「指到服务器文件夹外面」；用 `;` 或 `,` 隔开的一串路径逐个看。Aikar 参数里的网址、`config/foo` 这种相对路径、`Asia/Shanghai` 不受影响。`-XX:` 单列拒了 `+ShowMessageBoxOnError`（崩溃时弹窗等人点，后台的服务器会卡着）、`+PauseAtStartup`、`-BytecodeVerificationRemote`、`-BytecodeVerificationLocal`（等于 `-Xverify:none`）；`+UnlockDiagnosticVMOptions`、`+UnlockExperimentalVMOptions` 照旧带。`-D` 那一支从 `judgeScriptJVM` 里拆成 `judgeProp`，先按名字、再按值，所以原来那条值是盘符路径的 `-Djava.library.path` 原因还是「Java 自己的设置」。每样在 `TestFilterScriptJVM` 的表里有能带的和不带的。

**建服务器文件夹用 `os.Mkdir`（`78ceeb2`，A48）。** 四条路（普通新建、整合包、现成服务端、交接包）原来各自写「`MkdirAll` 加放记号」，现在都调 `creating_leftover.go` 里新的 `MkdirCreating`：上一层照旧 `MkdirAll`，本层用 `os.Mkdir`，已经有了就回「这个位置已经有一个同名文件夹（可能是刚放进来的），没有动它」加上路径。失败以后清半成品的入口统一成 `discardFailed`，遇到这个错误直接跳过、不进清理，所以不会再补一句「文件夹里有不是这次建的东西」，别人放的空文件夹也不会被 `os.Remove` 顺手删掉；交接包的 `DiscardCreate` 多了一个失败原因的参数，走同一处。交接包失败出口那句 `m.Delete(req.Name, false)` 去掉了：登记是 `FinalizeCreate` 的最后一步，`FinalizeCreate` 又是 `runImport` 的最后一步，走到失败出口时这台一定还没登记；万一真走到，`Delete` 会先把记号去掉，后面的清理就只删空文件夹，整个文件夹会留下。注释照实写了，提醒以后在后面加步骤要先处理清理。用例：新建、整合包、现成服务端在 `MkdirCreating` 建文件夹之前（包内变量 `beforeCreateDir`，同 `afterRootRemembered` 的做法）往那个位置放一个空文件夹或一个带东西的文件夹，任务都按那句失败，文件夹原样、没有记号、重开以后不列为没建完的、不登记；交接包建文件夹之前没有能停下来的地方，用例照 `ImportAsync` 的先后直接走（预留、放文件夹、`runImport`、`DiscardCreate`）。

**清理没成时失败框照实说（`e022472`，A48）。** 任务快照照 `cancelled` 的样子加了 `cleanupFailed`（只在单个任务的快照里，列表摘要不带），`tasks.Task.MarkCleanupFailed` 设它。「；清理半成品失败：…」那句原来在 `install.go` 的 `failCreate` 和交接包各写一遍，合成 `inst.FailLeftover`：先记标记再 `Fail`，四条路都经它。任务页 `drawMsgs` 认到 `cleanupFailed` 就不接各类任务的 `failHint`（交接包、现成服务端那两项写的是「半成品的文件夹已经清理干净，可以重试」），换一句「文件夹没删干净：这次建了一半的会列在服务器页上方「没建完的文件夹」里，到那里处理。」只认这个字段，不按 error 里的字认。这句比返工单给的原句多了「这次建了一半的会」几个字：清理失败不全是带着记号留下的那种，比如建文件夹之前就失败、那个位置上又冒出了别人的文件夹（`TestImportFailedBeforeMarkerKeepsOthersFolder` 那种），文件夹不是这次建的，不会出现在「没建完的文件夹」里，原句会让人去找一个找不到的东西；失败原因里会说是哪一种。仿真后端的状态说明写上这个字段，`docs/设计与参考/API.md` 取消那一段补了一句。Go 这边几条清理失败的用例都加了断言标记，`tasks` 加了一条；界面加了一条：带标记的三种（现成服务端、交接包、整合包）说去没建完的文件夹、不说已经清理干净，error 里写着「清理半成品失败」却没带标记的照旧接 `failHint`。

**往里看一层只在最外层旁证很弱时（`73ce122`，A40）。** `parseFiles` 往里看的那一步拆成 `parseInside`：最外层带着 `mods/` 或 `plugins/`（不分大小写）时只找文件夹里的整合包清单，找到照收（服务端包最外层常带着 `mods/`，清单套在一层文件夹里），找不到就照旧报最外层认不出核心，不拿里面的服务端顶替——这种最外层多半就是那台服务端本身，只是加载器、核心没放进来，里面的是 `backup/` 之类，认成它会把外面的模组和配置丢下。旁证只有 `eula.txt`、`libraries/` 的照旧清单和服务端都找。`parseLayout` 里按清单种类解析的那几行抽成 `parseIndex`，两处共用。用例跟着改的：`TestUnknownJarAloneIsNotServer` 里 `mods/a.jar`、`plugins/a.jar` 两条改回报认不出核心，另加大写的 `Mods/a.jar`；`TestPackShapes` 里上一轮加的「最外层 `mods/` 里有 fabric-api、里面套着 Paper」「最外层 `plugins/` 里有 PaperLib、里面套着 Paper」两行也改成报认不出核心（和阶段 09 之前一样）。另加两行：没装加载器的服务端包旁边 `backup/` 里放着一台老 Paper，报认不出核心；最外层 `eula.txt` 加 `libraries/` 里有名字像服务端的 jar、里面套着 Paper，认出里面那台——这一行钉住 `serverRoot` 里不把 `libraries` 当成一台的那段，原来钉住它的两行现在走不到那里了。

**`MANIFEST.MF` 超长不连累整个 jar（`4882550`，A50）。** 带签名的 jar 清单后面逐个文件列着摘要，原版 1.21.11 的有 1.9 MB、forge 1.7.10 universal 的有 112 KB，以前都会让整个 jar 判断不了。`MANIFEST.MF` 这里只用来看 `Main-Class`，改由新的 `readJarManifest` 读：申报超过 64 KB 的只读前 64 KB，主段（到第一个空行）在里面完整的就只用主段；主段在这 64 KB 里没结束的照旧算靠不住，因为后面还能再写一个 `Main-Class`。申报没超过的照旧走 `readJarMeta`，申报写小、实际超长的仍算靠不住；同名两份仍算靠不住。用例：1 MB 的签名清单、`Main-Class` 在开头，认得出 CraftBukkit、自带的 2.17.1 照常判成修过；主段八万多字节的、申报写小实际 1 MB 的，都算靠不住。同一个提交里补了 `patch.json` 同名两份的用例（原来只有 `patch.properties` 的）。

**Mac 包里和真文件夹并排的 `._` 文件（`9092f79`，A41）。** 原来表里的 `._` 都在 `__MACOSX/` 里，被那条规矩整个跳过，`._` 那条规矩本身没被测到。形状表补了两行：中间一层 `A/._Srv` 和 `A/Srv/` 并排、最外层 `._A` 和 `A/` 并排，都不带 `__MACOSX`。临时关掉 `._` 那条判断，两行都认不出，确认钉住了。
