# 2026-11-24 阶段 13 frpc 下载的 TLS 退路

## 要做什么

没有作者的原话。这是 11-22 清账的阶段 13，对应待修清单 A55：OpenFrp 的 frpc 下载只走 TLS 1.3，握手失败没有退路。来历见 `2026-11-13-v3.1.2-OpenFrp的frpc下载.md`：3.1.2 为了过下载站前面腾讯 EdgeOne 的机器人防护，给这一处下载单配了一个只报 TLS 1.3 的客户端，当时就留下「握手失败时退回默认客户端再试一次」没做，v3.2.0 发布说明的「已知情况」里也写了。

主会话交代的要求：握手失败时退回一次不限 TLS 版本的客户端，整次下载只退一次；退回的客户端和原来的一样只跟 https 的跳转，超时、代理也一样，最好是同一个构造函数只换最低版本；下回来的文件照旧检查；控制台说一句「TLS 1.3 连不上，改用兼容的连接方式重试」；退回也失败时照现在的指引叫人手动放 frpc，并说清两种方式都试过了、各自为什么没成；404、连接超时、DNS 失败不退回。不为过 567 伪造 TLS 指纹，不加依赖，`internal/dl` 不改。基准是 `d3fc591`。

做到一半主会话追加了一条：新用例单跑一遍要 36 秒左右，把 `internal/tunnel` 整包的测试时间翻了一倍，要查清时间花在哪，在只改 `internal/tunnel` 的测试和这次新加的产品代码、不改 `internal/dl` 的前提下压到每遍几秒；断言不许放松，压不下来就写清原因和每条各花多少秒。

## 做了什么

代码三个提交：`3f1b24f` 是改动和大部分用例，`5142a33` 补了一条用例，`8127d5e` 让几条慢的下载用例并行跑。这份日志另一个提交，都在分支 `claude/clear-backlog-1122` 上。

**两个客户端，一个构造函数。** `internal/tunnel/providers.go` 里原来的 `openfrpHTTPClient` 改由 `newOpenfrpHTTPClient(minTLS)` 生成，另加一个 `openfrpCompatHTTPClient = newOpenfrpHTTPClient(0)`，0 就是 Go 默认的最低版本（现在是 TLS 1.2）。代理、两个超时、h2、只跟 https 的跳转都写在构造函数里，退回的那个不会漏掉哪一条。两个仍是包变量、仍是 `*http.Client`，现有测试「复制一份结构体、换掉传输层」的替换办法照用。注释里补了退回的作用和局限：它报的就是 Go 默认那种 ClientHello，直连 EdgeOne 那个源多半还是会被回 567，能不能下成要看别的下载源，下不成就照报错手动放 frpc，不为过 567 去伪造指纹。

**怎么认「握手失败」。** 任务单建议用 `errors.As` 认 `tls.AlertError`、`tls.RecordHeaderError`，再加上握手时连接被重置，并提醒先看标准库实际返回什么。我在仓库外写了个小探针，把几种对端都试了一遍（go1.27.1，Windows），结论是光看 `dl` 交回来的错误认不全：

- `tls.AlertError` 在 TCP 上收不到，标准库只在 QUIC 那条路上用它。对方回告警时拿到的是 `*net.OpError`，`Op` 是 "remote error"，里面是不导出的告警类型，说法是「remote error: tls: protocol version not supported」。
- 最像真实情况的一种是不认 supported_versions 扩展的老式服务器或中间设备，照 ClientHello 开头写的 1.2 直接回 TLS 1.2 的 ServerHello。这时 Go 给的是一句没有类型的「tls: server selected unsupported protocol version 303」，只能比字符串。Go 自己的 TLS 服务器认得那个扩展，只会回告警，所以拿 httptest 起的「只会 1.2」的服务器测过了，并不说明这一种认得出来。
- 握手时被重置（Windows 上是 wsarecv 报远程主机强迫关闭了连接）、对方直接断开（EOF），和传数据时出同样的事是同一种错误，分不出是哪一步；Windows 上的错误码也不等于 `syscall.ECONNRESET`。
- 对方回明文时（比如一张拦截页），握手那一步的错误是 `tls.RecordHeaderError`，可 net/http 交出来的已经换成「server gave HTTP response to HTTPS client」，类型丢了。

所以改成直接看握手这一步。`watchTLSHandshake` 在传给 `dl.Fetch` 的 ctx 上挂一个 `httptrace.ClientTrace`，`TLSHandshakeDone` 带回错误时记下第一个。ctx 里的值会一路带到 `dl` 建的请求和传输层的拨号（net/http 拨号用的是去掉取消、保留值的 ctx），`dl` 一行没改。上面几种都会走到这个回调、带着各自的错误；连不上（端口没人听、DNS 失败）根本走不到握手。`tlsVersionMayHelp` 再排掉换版本也没用的：超时（含 ctx 到期）、被取消、证书对不上（`*tls.CertificateVerificationError`）。回调在拨号的协程里跑，请求结束以后还可能在跑，所以加了锁。没有用 `dl.AnyFailure` 去认，原因就是上面这几条。

**退回。** 新的 `openfrpDownloadZip` 先用只报 1.3 的客户端调一次 `dl.Fetch`。没下成、途中又记下了握手失败、总时限也还没到的，往控制台写「[MineDeck] TLS 1.3 连不上，改用兼容的连接方式重试 ...（握手时：……）」，换兼容的客户端，用同一个 `dl.Request` 把整次下载再来一遍，只这一次。两次是同一个请求，1 MiB 的下限一样；下回来以后的解压、结构检查在 `openfrpFetchExtract` 里照旧，没有动。没退回的路径交回的错误和原来一个字不差。

退回也没下成时，错误是「两种连接方式都试过了。只用 TLS 1.3 时：……；改用兼容的连接方式后：……」，外面照旧套着手动放 frpc 的那句：指引在前，两段原因在后，隧道卡片截断时丢的是后面。往外传（`%w`）的是退回那次的错误，前一次只留说法。原因是 `frpcBlockedHint` 用 `dl.AnyFailure` 认「写盘时被杀毒软件拦下」，而 `AnyFailure` 只逐个看它找到的第一个多源汇总错误；两个都用 `%w` 的话，找到的是前一次（多半连握手都没过、没写过盘），退回那次被拦下就认不出了。`openfrpFetchExtract` 里原来调 `dl.Fetch` 的那一行换成调它，别的没动。

`con` 没有判空：`EnsureFrpc` 一开头就直接 `con.Append`，`openfrpInstall` 里也是，照现有写法。

**用例。** 新文件 `internal/tunnel/openfrp_tlsfallback_test.go`。测试用的两个客户端都从产品里的克隆，传输层 `Clone()` 以后只加测试证书，TLS 最低版本、跳转规矩、超时都是原样，不然反向验证测不出东西；下载源直接用 httptest 的 127.0.0.1 地址，证书对得上，也不走本机的代理环境变量。下载走的是 `openfrpInstall`（查完版本以后那一段），下载、解压、结构检查都过一遍。下面前五条是 `TestOpenfrpZipTLSFallback` 底下的并行子用例（为什么并行见后面「用例的耗时」一段），最后一条是单独的 `TestOpenfrpHandshakeFailuresWorthFallback`。

- 只会 TLS 1.2 的下载源：只报 1.3 的三轮都握不上手、进不了处理函数，退回以后下一次就下成，解压出来的 frpc 能用，控制台有那句话。
- 握不上手的不是最后一个源：第一个源只会 1.2、放着好的 zip，第二个会 1.3、回 404。`dl` 交回的错误只认得出最后那个 404，这里照样退回，从第一个源下成；第二个源只进来只报 1.3 的那三次。
- 同样的下载源把 zip 跳到一个 http 地址，那边真放着一个好的 zip：退回以后照样被拒，那边一次都没被请求，不留 frpc。
- 退回以后回 567：报错先有手动放 frpc 的办法，再有「两种连接方式都试过了」和两段各自的原因（protocol version not supported、HTTP 567 那句）；只有退回那三次进得来；`dl.AnyFailure` 看得到退回那次的每一次尝试。
- 会 TLS 1.3 的下载源回 404：照原样报错，不出现「两种连接方式」，控制台没有那句话，只有三次请求；接着下成，也没有退回的事。
- 哪些握手失败算数，一张表直接对着 `watchTLSHandshake` 跑：只会 1.2 回告警、老式服务器回 1.2 的 ServerHello、读完 ClientHello 就掐断（发 RST）、回明文，这四种记下；握手超时（握手时限改成 200 毫秒）、证书对不上不记；连不上、握手成功的什么都不记。为了「不记」那几行不白过，另挂一个 trace 确认握手确实走到了（连不上那行确认没走到）。后三种对端是自己按字节回的，Go 的 TLS 服务器造不出来。

原来钉住「只报 TLS 1.3」的 `TestOpenfrpHTTPClientOffersOnlyTLS13` 加了一句：退回用的客户端 1.2、1.3 都报。

**用例的耗时（主会话追加的那条）。** 一开始五条下载用例是各自独立的顶层用例，按顺序跑要 42 秒左右，各条是 6、6、12、12、6 秒，正好是 6 秒的整数倍。时间全在 `dl.Fetch` 整次失败时的轮间等待上：它一共试三轮，第二、三轮开始前各等 2 秒、4 秒（`internal/dl/dl.go` 的 `retryWait`），整次失败一次就固定等 6 秒。握手失败本身是毫秒级的，握手那张表里除了故意等到超时的那行（0.20 秒），每行都是 0.00 秒，不是握手或响应头的超时在空等。`dl.Request` 没有重试次数、等待时间这类参数，`retryWait` 不导出，只有 `dl` 自己的测试能改，`internal/tunnel` 里调不了。

能做的是让它们一起等：五条挂到一个父用例 `TestOpenfrpZipTLSFallback` 底下当并行子用例，一遍从 42 秒降到 12 秒左右。父用例里只换一次「两个客户端都认得测试证书」（httptest 起的服务器都用同一张自带的测试证书，哪天不是了，这几条会因为证书对不上失败，不会悄悄通过），子用例里不写任何包变量：放 frpc 的文件夹和缓存的 zip 直接用各自的临时文件夹传给 `openfrpInstall`，不经 `frpcDir`、`app.CacheDir`。断言一条没动。

12 秒是这个范围里的下限：「退回后跳到 http 照样被拒」和「两次都失败的说法」两条都要先后等两次整次失败（只报 1.3 的那次、退回的那次），同一条用例里没法并行。试过的念头里没采用的有两种：握手失败以后提前取消第一次下载，报错会变成「context canceled」、请求次数也跟着变，等于改产品行为或者放松断言；把 `dl.Fetch` 换成假的，测的就不是真东西了。真要再快，得给 `dl` 开一个测试里调短轮间等待的口子（比如放在 `dltest` 里），那要改 `dl`，不在这一阶段的范围里。

## 验证了什么

本机 Windows，go1.27.1，在最后的代码提交 `8127d5e` 上：`gofmt -l internal/tunnel` 无输出；`go vet ./...`、`GOOS=darwin go vet ./...` 都过；`go test ./internal/tunnel/ ./internal/dl/ -count=1` 两个包都过，阶段 11 改过的那几组 frpc 用例都在里面，`internal/tunnel` 整包单独跑 32 秒，跳过这两组新用例是 19 秒（并行之前整包是 55 到 61 秒）；新用例和改过的那条 `-v` 单跑过，五条下载子用例各 6、6、6、12、12 秒，父用例一共 12 秒左右；`-count=20` 也过了，245 秒。并行之前在 `3f1b24f`、`5142a33` 上也各跑过一次 `-count=20`，都过。

反向验证（主会话要的三条）在 `8127d5e` 上又做了一遍，每次跑整个父用例；`3f1b24f` 上先做过一次，那次每条只跑了对应的一两条用例，该失败的也都失败了。每次把 `providers.go` 拷到仓库外、改坏、跑、拷回，拷回后 `git diff --exit-code` 都干净：

- 退回用的客户端去掉 `CheckRedirect`：只有「退回后跳到 http 照样被拒」失败，退回以后跟着跳到 http、下成了。
- 让所有错误都退回（去掉「途中有握手失败」那个条件）：只有「会 TLS 1.3 的 404 不退回」失败，报错里出现了「两种连接方式都试过了」。
- 退回用的客户端也只报 TLS 1.3：「只会 TLS 1.2 的下载源退回后下成」「握不上手的不是最后一个源」都失败，两次都是 protocol version not supported；另外两条退回以后的用例和只报 1.3 那条用例里新加的一句也失败；「404 不退回」照常通过。

## 没做完或没验证的

- 没有真的去 OpenFrp 的下载源试，也没有在真的只支持 TLS 1.2 的网络、代理、杀毒软件 HTTPS 扫描后面试过（规矩不连真实下载站）。退回的那次在 EdgeOne 那个源上会不会 567、别的两个源能不能下成，没有证据。
- 杀毒软件的 HTTPS 扫描是中间人，它替我们跟下载站重新握手，下载站看到的是它的 ClientHello，不是 Go 的。这种情况下退回以后会不会碰上 567，说不准。
- 途中只要有一次握手失败、整次又没下成就退回，哪怕最后失败的原因是别的（比如另一个源 404）。那时控制台那句「TLS 1.3 连不上」只说对了一半。
- 能在半路掐断连接的人可以逼出这次退回。退回以后最低还是 Go 默认的 TLS 1.2，证书照验，跳转照样只跟 https，下回来的照样检查；我认为可以接受，请审核方确认。
- 握手超时不退回，是照任务单「超时不退回」定的。要是哪种中间设备对只报 1.3 的 ClientHello 一声不吭、等到超时，这里认不出，还是只能手动放。
- `openfrpInstall` 的第二轮（解压出来的 frpc 坏了、重新下载一次）会再从只报 1.3 的客户端开始、再退一次，控制台那句话会出现两次。这一阶段的范围只到下载那一步，没改。
- 新用例只在 Windows 上跑过，darwin 只过了 `go vet`。「读完 ClientHello 就掐断」在 macOS 上拿到的错误说法会不同，用例只看记没记下、不看说法。
- 并行的子用例共用两个下载客户端，本机没有 C 编译器、带不了 `-race`，没有用竞态检测跑过。子用例只读这两个包变量，写只在父用例开头和收尾。
- 用例一遍还要 12 秒，没压到主会话要的「几秒」，原因见上面「用例的耗时」。

## 留给下一位的

- 「握手失败」是靠 `httptrace` 的 `TLSHandshakeDone` 认的，靠的是 net/http 在握手失败时带着错误调它（文档写明了），以及 `dl.Fetch` 把调用方的 ctx 一路传到请求上。以后 `dl` 要是改成不用调用方的 ctx 建请求，退回就不会再触发，`TestOpenfrpZipTLSFallback` 底下几条退回的子用例会失败。
- EdgeOne 哪天连「只报 TLS 1.3 的 Go」也拦了，主客户端拿到的是 567，那不是握手失败，不会退回。到时要重新判断的是主客户端那段注释说的事。
- 这几条下载用例慢在 `dl.Fetch` 整次失败时固定的 6 秒轮间等待，包外改不了，所以并行跑，一遍 12 秒左右。往 `TestOpenfrpZipTLSFallback` 底下加子用例时，子用例里别调 `frpcTempDirs`、别换客户端（都会写包变量），也别用 `frpcDir`、`app.CacheDir`（并行时没换成临时文件夹，指的是真的位置）。整个 `internal/tunnel` 里还有两条老用例（`TestOpenfrpEnsureFrpcDownloadFailure`、`TestOpenfrpRefusesRedirectToHTTP`）也各等 6 秒，同一个原因。要整体变快，得给 `dl` 开一个测试里调短轮间等待的口子，请主会话定。
- 测试里的下载源用的都是 httptest 自带的同一张测试证书，父用例里只换一次客户端，靠的就是这一点。
- v3.2.0 发布说明「已知情况 → 内网穿透」第一条说 TLS 1.3 握手失败没有退路，这一阶段的范围不含发布说明，没改；下次发版写说明时要跟着改。
