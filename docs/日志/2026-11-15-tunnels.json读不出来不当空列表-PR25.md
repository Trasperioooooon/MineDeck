## 2026-11-15 tunnels.json 读不出来时不再当成空列表（Claude 写，PR #25）

这是 PR #22 交接里记下的那个老问题。以前 `Manager.load()` 读 `tunnels.json` 失败、或者读出来了解析不了，都悄悄当成空列表，什么记号也不留；之后随便哪一次保存成功（新增一条隧道、平台导入、记公网地址），都会把磁盘上的原文件整份换掉。开机时文件刚好被杀毒或同步盘占着，或者文件坏了一半，用户看到列表是空的，再加一条，原来的隧道和凭据就全没了。

现在 `load()` 分三种情况。文件不在是新装，空列表是对的，照常能加能存，和以前一样；不过要三样都对上才算新装：读的时候报的是「文件夹在、文件不在」（Windows 上的 `ERROR_FILE_NOT_FOUND`），程序文件夹本身看得到，再看一眼文件还是「文件夹在、文件不在」。因为 Windows 上路径里某一级不在（网络盘断了、程序文件夹暂时访问不了）读文件也报「不存在」（`ERROR_PATH_NOT_FOUND`、`ERROR_BAD_NETPATH` 在 Go 里都算 `fs.ErrNotExist`），当成新装的话路径一恢复，下一次新增就把原文件盖掉了。这一条是 Codex 两轮复审找出来的：第一轮发现程序文件夹访问不了被当成新装，加了查文件夹；第二轮发现查完文件夹、再看文件之前路径又失联，仍会放行，于是改成只认 `ERROR_FILE_NOT_FOUND`（这一判断放在 `notfound_windows.go`，别的系统上照旧用 `fs.ErrNotExist`）。文件在但读不出来（被别的程序独占着、没有读取权限），或者读出来了解析不了（坏文件，包括解析得了却没有 `tunnels` 这一项、多半是手改时键名改错了的），都记成新的 `tunnel.LoadError`，用 `Corrupt` 分开这两种。只要它还在，隧道列表就是空的，新增、修改、删除、启动、平台导入和平台创建一律报这个错，内存和磁盘都不动。拦的位置在改内存之前，`Add`、`UpdateOpt`、`Delete`、`start` 拿到锁以后第一件事就是查它；`save()` 里另有一道闸，兜住迁移凭据、记公网地址和以后新加的保存点。平台创建在去平台上建之前就拦下，免得平台上多出一条、本机又存不进去。`LoadError` 没有包成 `SaveError`：「这次的改动没有保存、检查磁盘」说的不是这回事，而且账户层见到 `SaveError` 会改口说「平台上的隧道已经建好」。

处理办法选的是「记下状态、拒绝保存、原文件不动、读成了自动恢复」，没选「先把原文件改名备份，再从空列表开始」。被占用多半是一时的，改名备份反倒让用户的隧道从列表里消失，还得自己去找备份改回来；坏文件常见的来源是手改出了错，比如多了一个逗号，挡着不让存、告诉他大概坏在第几行，用记事本改好就回来了，比替他挪走省事。真想从头来，把文件改名挪走就行：下一次读到的是「文件不在」，从空列表开始，挪走的那份原样留着。另外加了一点短暂重试：开机时读不出来（坏文件不算，再读也是坏的）隔 200 毫秒再读，最多三次。之后有人要列表（隧道页开着时 4 秒刷新一次）、要保存、要启动，以及服务器启动触发跟随时，都会在锁里再读一次，读成了直接换上，不用重启。没读成期间内存里一直是空列表、什么都存不进去，所以换上去不会冲掉谁的改动。读成的那一次照常把老版本的明文凭据加密写回。

`load()` 里顺手处理了几件小事。只有空白的文件、`{}`、`null` 和只有 `seq` 的文件按空列表算，里面没有能丢的东西（MineDeck 从 v2.0.0 起写的文件一直带着 `tunnels` 这一项，没有 `omitempty`，翻过历史确认的，所以缺这一项又有别的内容才算坏文件）；空白文件是老版本覆盖写时断电留下的，挡着只会让人多跑一趟，记一行日志。记事本存的 UTF-8 可能带 BOM，先去掉再解析，不然按提示用记事本修完反而读不出来。列表里写着 `null` 的项跳过，以前读到它会空指针崩溃。坏文件的报错原文里带着大概坏在第几行。

隧道列表空了不只隧道页在用。音乐共享开服前同步 `voice_host` 时也看隧道列表，没读出来时会以为没有语音隧道，把 MineDeck 上次写的地址清回空；这也是 Codex 指出来的，现在隧道配置没读出来时它不动 `voice_host`（`musicshare` 对隧道管理器做一次 `LoadErr` 的接口断言，测试用的假隧道也加了这个方法）。音乐共享页面上这时显示的语音隧道是空的，只是显示，没处理。

界面上，操作层的 `tunnel.list` 遇到 `LoadError` 回 503 加一句 hint，不再拿空列表冒充「没有隧道」，AI 助手和 MCP 问到的也是这句；`tunnel.start`、`tunnel.stop` 预览时查隧道也先查它。隧道页认出 503，就在列表的位置画一个报错框：正文是「无法显示隧道：」接后端那句，两种情况分开说，被占着的说「关掉占用它的程序后会自动重读」，坏了的说「用记事本修好它，或者改名挪走后从空列表开始」，两句分别是 57 和 54 个字，用真的 `errSummary` 跑过，都会被整句接上；下面一行说原来的隧道和凭据都还在文件里，读出来之前不能添加、修改或删除；带「重试」和「复制报错信息」。表单和页头的「添加隧道」收起来，不让人填半天才被拒。4 秒一次的刷新在原因没变时不重画报错框，免得按钮在手底下被换掉；读成了就照常画列表、放出表单。平台账户区的导入、创建被拒时，提示也是后端那句。仿真后端加了 `tunnelsLoadFail` 开关（`locked` 和 `corrupt` 两种），界面原型加了两个对应的场景。

验证：最后一个代码提交 `ac7ee99` 上，本机 `GOOS=windows go build ./...`、`go vet ./...`、`go test ./... -count=1` 全过（48 个包，其中 41 个有测试），PR 的 CI：前三个提交上的两次都过了；`ac7ee99` 上两次各挂了一条和这次无关的时序用例，pull_request 那次是 `internal/inst` 的 `TestUpdatePropsKeepsEveryonesChange`（替换 `server.properties` 时 `Access is denied`，PR #22 交接里记过的那条），push 那次是 `internal/chatai` 的 `TestCommandOutputWait`（等待时间多了约 0.16 秒）。这两个包这次都没碰，本机全量也过了，没有为它们改代码；推交接说明这个提交时会重新跑一遍 CI，结果以 PR 上的为准。新的 Go 用例在 `internal/tunnel/load_test.go`（坏 JSON、缺 `tunnels` 键、同名文件夹顶着读不出来、文件不在、程序文件夹访问不了、空白文件、只有 `seq` 的文件、`null` 项、读成后照常迁移、账户层先拦、跟随启动自己再读、修好以后修改删除启动各自恢复）、`internal/tunnel/load_windows_test.go`（用共享模式为 0 的句柄独占文件，模拟被别的程序占着；开机重试读回来；两次检查之间路径失联；「文件不在」只认 `ERROR_FILE_NOT_FOUND`）、`internal/web/tunnelload_test.go`（接口回 503 和 hint、修好以后不重启就回来）和 `internal/musicshare/checks_test.go`。被占用那条没有只断言「原文件没变」：独占的句柄同样挡住保存时的改名，旧代码也会落得原文件没变，所以它断言的是报错类型，以及放开以后再加一条，旧的新的都在。`tools/ui-dev` 的 `npm test` 在最终的界面代码上全量跑过，183 条全过，`npm run proto:check` 119 个场景都走通。更早一遍全量（界面还没改最后一处重试键的时候，机器上同时跑着 Codex 和 Go 测试）有一条「状态切换：卡片胶囊换成新状态并播换场」没过，和这次改动无关（没碰服务器卡片），单独连跑三遍都过，最后这遍全量也过了，看着是机器忙时的动效时序。故意改坏一共做了九次，每次都有用例失败，改完都还原并和备份逐字节核对过：把 `load()` 改回读失败当空列表（九条失败）、去掉 `save()` 里的闸（两条）、去掉改内存前的检查（四条）、不确认程序文件夹就当新装、不查 `tunnels` 键、音乐共享不查读没读出来、第二次看文件时不分路径失联、界面去掉 503 分支、界面每次刷新都重画报错框。工作树里没有装 Playwright，界面测试借的是主检出 `tools/ui-dev/node_modules`（只设了 `NODE_PATH`，没有安装任何东西）。

没做、留给以后的：真机上杀毒或同步盘占着 `tunnels.json` 没有制造过，测试用的是不共享的句柄（和真的占用报同一个系统错误）和同名文件夹顶在那里；「没有读取权限」（ACL）没有专门测，它和被占用走同一条路。开机时读不出来、用户又一直不打开隧道页，只有服务器启动触发跟随时才会再读一次；那时还读不出来，跟随的隧道这次就不拉起，只记一行程序日志，没有操作记录，因为不知道是哪几条隧道。`tunnels.json` 里的 `seq` 比现有编号小（手改出来的）时新增会撞号，这是原来就有的，没动。音乐共享页在隧道配置没读出来时显示的是「没有语音隧道」，还会引导去添加；只开着音乐共享页时也不会触发隧道重读（要打开隧道页、或者有保存、启动的操作）。这不会再改配置，只是说法不准，可以另做：给音乐共享的状态加一个「隧道配置没读出来」的说法和重试入口。
