第二个提交 `8672839` 处理 `internal/atomicfile` 与 `internal/dl` 里的 A19、A20、A24：

对于 A19，`internal/atomicfile/replace_windows.go` 原先只在普通可写文件的 `MoveFileEx` 循环里按 `retryDelays`（总计约半秒）重试短暂占用；原文件一开始是只读时走 `FileRenameInfoEx` 扩展改名退路，不仅退路本身不重试，而且当只读文件同时被独占句柄占着时，前面的 `MoveFileEx` 会先报 `ERROR_SHARING_VIOLATION` 而非 `ERROR_ACCESS_DENIED`，连扩展改名退路都进不去就当场返回。现在把 `ERROR_SHARING_VIOLATION` 一并放进只读退路的入口条件，抽出 `replaceReadOnly` 按同一张 `retryDelays` 间隔表重试拒绝访问与共享冲突，每次重试前都重新调用 `os.Lstat` 与 `os.SameFile` 确认目标没有在等待期间被调包成别的文件，找不到临时文件或文件系统不支持等非占用错误则一次不试直接返回。同时新增 `atomicfile.ReplaceContext`，把刷盘前重开临时文件（`openForSyncCtx`）和改名替换（`replaceCtx`）两处的等待都换成监听 `ctx.Done()` 的定时器，`internal/dl/dl.go` 的 `fetchOne` 落盘改调 `atomicfile.ReplaceContext(ctx, part, r.Dest)`，下载任务取消时落盘重试等待立即中断退出，不再白等半秒甚至多轮累加。

对于 A20，`internal/atomicfile/lock.go` 的 `canonicalEntryPath` 在目标文件尚不存在时会逐级退回父目录查询真实路径。当上一级目录是末尾带空格或点的名字（如 `a..`、`a `，或经 `\\?\` 访问的 `a.`），而同级旁边又有一个正常目录 `a` 时，原先退回父目录后调用 `longPath` 经 `filepath.Abs`（`GetFullPathNameW`）和普通 Win32 `CreateFile` 打开父目录，会把末尾的空格和点剥掉、误打开旁边的 `a`，等文件真建出来以后按完整路径打开又落回特殊目录本身，建文件前后锁键分裂成两把。现在两头一起收紧：`canonicalEntryPath` 与 `longPath` 对调用方已带 `\\?\` 或 `\\.\` 前缀的路径不再调 `filepath.Abs` 剥尾字符；`handlePath` 在 `follow == true`（逐级退回解析上层目录）时直接用 `verbatimPath` 加上 `\\?\` 字面前缀打开父目录，既保留 NTFS 联接和短名展开，又按原样比对末尾的空格和点。

对于 A24，核实 `internal/atomicfile/replace_windows.go` 的 `verifyRenamed` 确实用 `strings.EqualFold` 比对改名后句柄的规范路径与目标路径的规范路径。两边其实都是 `GetFinalPathNameByHandle` 从文件系统取回来的真实大小写路径：在普通不区分大小写的目录里，同一个目录项两边取到的大小写本来就逐字一致；在开启了区分大小写的目录里，`EqualFold` 反而会漏掉只差大小写的另一个文件。现抽出纯函数 `checkRenamedPath` 改为原样逐字相等比对（`got == want`），任一边取不到规范路径时照旧跳过核对。

第三个提交 `e4ea981` 处理 `internal/inst` 里的 A22 与 A23 第 2 点。核实 `internal/inst/install.go` 的 `writeRunBat` 原先直接调用 `os.WriteFile` 覆盖写 `run.bat`（及 `user_jvm_args.txt`），断电可能留下半截脚本，多台服通过硬链接或符号链接共用脚本时还会把另一台指向的那份一起改掉；现改为调用 `atomicfile.WriteProtected`，既经同目录临时文件刷盘后原子替换（断链而不改共用目标、不留半截），又保留原有的只读保护（接管流程里 `run.bat` 只读回滚的语义不变）。备份取名方面，`internal/inst/backup.go` 原先在压缩开始前用 `os.Lstat` 看一眼目标名在不在，压缩完直接调 `atomicfile.Replace` 覆盖上去，两份进程同时备份同一台服或在压缩窗口内撞名时后完成的一方会把前一份盖掉；现抽出 `zipDirsExclusive`，先把世界压缩进临时文件并通过进程代际核对，发布时用 `os.OpenFile(..., os.O_WRONLY|os.O_CREATE|os.O_EXCL, 0o644)` 原子占住最终 `.zip` 名字后再替换，撞上 `fs.ErrExist` 就睡眠 1 毫秒换时间重取，压缩失败时也不会在备份目录留下空 `.zip`。

第四个提交 `2026011` 单独处理 A23 第 1 点（单实例检查）。核实全仓此前确实没有按程序目录的互斥检查。动手前逐一核对了四条启动路径：一是 `-mcp` 标准输入输出桥需要与同一文件夹里运行着的主程序并存，因此单实例检查放在 `*mcpBridge` 分支之后、`app.Init()` 读写任何配置之前；二是程序内更新（`internal/update/run_windows.go` 的 `swapScript` 与 `internal/ops/catalog/appops.go`）先写 `update.bat`、500 毫秒后触发主程序关闭，`update.bat` 等旧 PID 退出且 `move /y` 替换完 exe 后才拉起新进程，万一旧进程退出收尾稍慢，新进程最多等 10 秒（同时认 `WAIT_OBJECT_0` 与旧进程未显式释放就退出的 `WAIT_ABANDONED`）即可接手；三是开机自启（`internal/autostart`）只写一条带 `-minimized` 的注册表 `Run` 项（旧名 `AutoMCHUB` 已清理），开机首次拉起无竞争；四是隐藏启动（`cmd/minedeck/hiddenstart_windows.go`）的 `WH_CBT` 钩子只在后续 `openWebView` 线程上针对类名 `"webview"` 短暂挂载，不会把启动早期的系统提示框藏起来。实现上按与 `app.Init()` 一致的程序目录经 `EvalSymlinks` 归一并大写后算 SHA-256 前缀生成 `Local\MineDeck-<哈希>` 互斥量名，不在内核对象名里暴露路径或用户名；获取与持有放在独立 `runtime.LockOSThread()` 的协程上（规避 Windows 互斥量同线程递归放行与跨线程释放限制），等满 10 秒仍超时则调用 `MessageBoxW` 弹出「这个文件夹里的 MineDeck 已经开着了」后直接退出，非 Windows 平台留空实现保证交叉编译通过。
