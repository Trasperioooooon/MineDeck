# 工作日志怎么写

从 2026-11-16 起，交接不再靠一份越写越长的文档。眼下的状况只看 `docs/现状.md`，这个文件夹里是一次次工作的记录。接手的人（不管是哪家的 AI，还是作者自己）先读现状，要追究来龙去脉再按日期和主题翻这里。

## 规矩

每次工作新写一份日志，文件名是「YYYY-MM-DD-主题.md」，日期按东京时间，主题用几个关键词，不带空格和括号。同一天做了几件不相干的事就写几份。

日志写完就不再改。后来情况变了（修好了、改主意了、发现当时写错了），另写一份新的，在新的里面说清楚变了什么、指向旧的那份。这样每份日志都是当时的真实记录，不会被后来的人悄悄改掉。

每份日志固定分这几段，没有内容的段写「无」，不要省掉：

- **要做什么**：作者的原话，照抄；作者的话很长时抄关键的几句，其余概括并注明。
- **做了什么**：改了什么、为什么这样改；提交号、分支、PR、标签都写上。
- **谁做的**：哪个工具、请求的模型和思考档、观察到的实际模型；确认不了就写「未确认」。主会话和每个委派出去的执行者分开写。
- **验证了什么**：跑了哪些测试、在哪台机器上、结果如何；反向验证做了没有。
- **没做完或没验证的**：照实写，不要藏。
- **留给下一位的**：接手的人要知道的坑、等作者拍板的事、下一步建议。

收工时改写 `docs/现状.md`：只写眼下的状况，一两屏以内，每条后面指向对应的日志。不挡发版的实测欠账和以后再做的改进放在 `docs/待办.md`，现状里只留一句指过去，两份一起改。已经了结的事从这两份里拿掉，不往里堆历史。还在等处理的事必须进现状或待办，不能只留在日志里。

这个仓库在 GitHub 上是公开的（2026-11-16 作者定的规矩）。只跟作者电脑有关的事——文件夹挪位置、本机工具的安装和配置、清理本机文件——不写日志，也不进现状和待办，各家 AI 记在自己的记忆或笔记里。项目工作照常写日志，但仓库里的文档不写本机的绝对路径（盘符开头的路径、带用户名的用户目录）和用户名：仓库里的文件用相对路径，仓库外的测试目录只写文件夹名；引用作者原话时把里面的本机路径换掉并注明。提交前搜一遍盘符路径。CI 机器上的路径（GitHub 的 runner）不算本机路径。
