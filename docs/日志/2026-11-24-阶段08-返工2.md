# 2026-11-24 阶段 08 返工 2

## 要做什么

清账阶段 08 第一轮返工审过以后的第二轮返工，没有作者的原话，是主会话按审核结论写的返工单。挡过关的只有一条：没建完的文件夹的编号是「存放位置在列表里的序号/文件夹名」，位置的先后一变，界面上停着的旧编号就指到另一个位置里的同名文件夹去了。复审方走真实的导入现成服务端流水线实测过：两个新位置里各有一个同名的半成品，界面列出来以后其中一个位置里建成了一台、升成了扫描根，人点另一个位置的那一行，删掉的是这边带世界文件的那个，接口还返回成功。改默认存放位置也会让序号挪，这种从这批功能一开始就有。删文件的路径，改法又小，所以挡下。

一起要改的几件小的：登记处是「写 `instance.json` → 去记号 → 记扫描根」，写完 `instance.json` 还没记扫描根时程序没了，重开以后这台既不在列表里也不算没建完的，相对上一轮是退了一步；交接包登记那里的记扫描根没有用例钉住；「哪些子文件夹算数」写了两份，路径比较在 `inst` 和 `app` 里也各有一份；两处注释（`checkChosenJava` 认便携 Java 靠的前提、`adoptiumDown` 的注释里混着调查过程）；`API.md` 和两个操作的说明跟上新行为。编号那一条、登记的先后和交接包那条要求反向验证。

## 做了什么

都在分支 `claude/clear-backlog-1122` 上，基准是 `9e0016c`，代码三个提交，这份日志另一个提交。第三个提交 `1af7929` 是收尾前问过 advisor 以后补的，下面分开说。

**编号改按存放位置的短哈希（`be0c240`，A38）。**

编号现在是「位置的短哈希/文件夹名」。短哈希是把位置路径化简、转小写以后算 FNV-32a，写成十进制数字，所以仿真后端校验「斜杠前是数字」的那一处和界面用例的种子都不用动。删除时在要扫的位置里找哈希对得上的，正好一个才往下走，一个都对不上（这个位置已经不扫了）或者对上不止一个（哈希撞了）都回「没有这一项」，不去猜。位置先后怎么变，同一个位置算出来的编号都一样，旧编号只会删到原来那一个，或者对不上。

这样一改，有一个原来没人在意的情形会变坏：扫描根里有两条只差大小写的路径时（比如默认存放位置手填时大小写和程序目录不一样），两条算出来的哈希相同，那里的半成品会列两遍、编号一模一样，删的时候对上两个，永远删不掉；原来序号不同，两行都删得掉。所以找半成品要扫的位置按同一个写法（化简、转小写）去重，同一个文件夹只列一次。这一条写了用例，改之前在旧代码上跑是列两遍。

「哪些子文件夹算数」（真文件夹、不是链接和目录联接、名字在 Windows 上能用、里面有我们的记号）原来在列半成品和启动时整理小清单两处各写一遍，现在并成一个 `creatingChildren`，下面说的启动补记也用它，三处一份。`app` 里原来不导出的 `samePath` 改成导出的 `SamePath`，`inst` 里那份 `hasPathFold` 去掉，整理小清单时直接用它。

用例里原来写死 `0/…` 的几处：在列表里的从列表取编号，不在列表里的（正在创建的、目录联接、移出列表留下 `.bak` 的这些）用包里算编号的同一个函数拼。有两处换了编号以后会悄悄变成空测，一并改了：一处是那串非法编号（`0/..`、末尾带空格的 `0/.. ` 之类），前缀对不上任何位置的话，名字校验拿掉了也照样回「没有这一项」，而父目录里故意放着记号，现在前缀用这个位置真实的编号；另一处是几个不该删的文件夹只断言「出错了」，现在还要求错误不是「没有这一项」，确认是因为它本身不能删。操作层那条用例（`pr31_review_test.go`）在包外，算不了编号，就在同一个位置里另放一个普通半成品，从列表里取它斜杠前那段，再接上要删的文件夹名，没有为测试导出东西。

界面上删半成品失败以后也重新取一次列表，不让人接着拿旧的那一行再点；确认框里写上它在哪个存放位置，两个位置里有同名的时候看得出删的是哪个。

**登记的先后和启动补记（同一个提交）。**

新建、导入整合包、导入现成服务端走的 `completeCreate` 和交接包走的 `FinalizeCreate` 都改成调同一个小函数 `markCreated`：`instance.json` 写好以后先把位置记成扫描根，再去掉创建记号。先后的理由写在它的注释里：两步之间程序没了，文件夹里带着记号又有 `instance.json`，下次启动认得出来；反过来先去记号，就什么线索都不留了。

启动时，在扫服务器之前（`NewManager` 里加一行 `promoteCreatedRoots`），看「正在建的位置」里有没有带记号、又有 `instance.json` 本身的文件夹，有就把这个位置补记成扫描根，下面照常扫，这台就进了列表；之后照旧去掉残留的记号、整理小清单，这个位置已经是扫描根，随之从小清单里去掉。只认 `instance.json` 本身，移出列表留下的 `.bak` 不算。几条放记号的路都不会让外来的 `instance.json` 落到盘上：整合包的覆盖目录和清单里的下载、现成服务端的解压都过 `overrideAllowed`，它拒掉所有控制文件；交接包解包时跳过控制文件，收尾前还按盘上的实际情况再清一遍；新建时盘上只有 MineDeck 自己写的文件、下载的核心和放进世界文件夹的地图。这几处我都读过代码，地图放置那一处只看到它按世界文件夹的名字落盘，没有逐个文件核对。

`app.go` 里 `RememberRoot` 的注释原来写「只在服务器登记成功以后调」，现在启动补记也调它，改成「只在服务器的 `instance.json` 写好以后调」。

**用例。** 编号的两种挪法各一条（升格那条走真实的导入现成服务端流水线，改默认存放位置那条用 `UpdateConfig`），只差大小写的扫描根一条，登记崩在中间一条（直接造盘上的状态：有记号、有 `instance.json`、位置不是扫描根，旁边再放一个只有 `.bak` 的位置确认它不升格），交接包导入到一个新位置、重开以后还在列表里一条（在 `internal/transfer` 的测试里）。两个改默认存放位置的用例结束时把配置改回来：测试环境复位时把默认存放位置置空，`UpdateConfig` 会把改过的位置并进 `roots`，不改回去就留给后面的用例了。交接包测试的环境复位也加上了 `creatingRoots`。

**说明跟上（`59e0bd8`，A34、A35、A38）。**

## 验证了什么

都在作者这台 Windows 电脑上跑。最终代码上：`gofmt -l` 改过的目录没有输出；`go vet ./...` 没有输出；`GOOS=darwin GOARCH=arm64` 下 `go vet ./...` 和 `go build ./...` 都过。`go test ./internal/app/ ./internal/inst/ ./internal/java/ ./internal/ops/catalog/ ./internal/transfer/ -count=1` 五个包都 ok；`internal/web` 的路由和不泄密两条也跑了，过。新用例和半成品相关的老用例单跑都过，再各跑二十遍也都过。符号链接那条在这台电脑上照旧跳过（没有建符号链接的权限），它前半段「正在创建的拒绝删除」在跳过之前跑到了。

界面用例筛「没建完|半成品|删除：|Java|接管」，22 条全过（`1af7929` 没动界面）。原来 PR #31 那条用例里有一句「409 以后按钮恢复可点、横幅还在」：现在失败以后会重新取列表，而正在创建的文件夹本来就不该列出来，所以横幅收起才是对的，这一句改成断言横幅收起，下一步正常删除之前重新进一次页面。另加一条用例：两个位置里有同名的、确认框写明位置，别处已经删掉了这边还停着旧列表时，点了删不掉、重新取到的列表里只剩另一个。把界面代码换回原来的样子跑，这两条都失败；只去掉「失败以后重新取列表」那一行跑，新用例失败在「旧的那一行不该还留着」。

反向验证都在 `1af7929` 上重做了一遍，每次改回以后 `git diff --exit-code` 退出码是 0：

- 编号改回按序号：升格和改默认存放位置两条都失败，失败在「原来那个位置里的半成品应删掉」，也就是删除接口返回成功、删掉的是另一个位置里的。
- 启动时不补记（注释掉 `promoteCreatedRoots` 那一行）：登记崩在中间那条失败，「重开以后这台应在列表里」。
- 登记改回先去记号、后记扫描根：钉先后那条失败，两条路都报「记扫描根之前不该先去掉创建记号」。
- 交接包登记不记扫描根（`FinalizeCreate` 里只去记号）：交接包导入到新位置那条失败，重开以后这台不存在。
- 找半成品的位置不去重：只差大小写那条失败，同一个半成品列了两遍、编号一样。
- 补记不跳过接管进来的：接管半成品那条失败，那个位置里别的服务器进了列表。

## 没做完或没验证的

接管还留着一个很窄的窗口：人接管一个没建完的文件夹，接管写完 `instance.json`、还没单独登记这个文件夹时程序没了，下次启动补记看到的就是「带记号又有 `instance.json`、不是接管登记的」，会把它的上一层升成扫描根。要碰上得先有一个崩剩的半成品、人去接管它、又正好崩在两步之间，这一轮没处理。接管本身不碰创建记号，根子在那里，但改接管不在这一轮的范围里。

地图放置不会在服务器根目录落下 `instance.json`，是按它的写法读出来的，没有逐个文件核对。
