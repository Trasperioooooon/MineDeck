# 2026-11-17 v3.2.0 之后的七个中等问题

## 要做什么

作者让主控把 v3.2.0 之后的中等问题整理成任务交给 Gemini 做，在 `fix/mid-after-320` 分支（基于 `200f9dd`）按顺序解决以下七件事，每件单独验证并提交，最后写本工作日志：

1. `tunnels.json` 里的 `seq` 比现有编号小时，新加的隧道会撞号。
2. 导入无包装文件夹的现成服务端压缩包时，任务标题和 `pack.name` 变成缓存临时文件的随机数字。
3. AI 回复超过上限且已经开始输出时，界面报错说成「回复中途断开了」。
4. 不超内存额度（64 MiB）的小文件上传也按系统临时盘的余量拒收，报错不说是哪个盘。
5. （先核实再改）整合包导入在设完待决清单后若收尾失败或被取消，任务快照里还挂着待决清单和告警。
6. （先核实再改）装伙伴模组及其依赖写进 `mods` 失败时，缺少「可能正被服务器占用，停服后再试」提示。
7. （先核实再改）更正两处文档：`docs/设计与参考/API.md` 漏列 `stagedBytes`；`docs/使用指南/地图导入-使用说明.md` 对取消入口的说法与实际不符。

## 做了什么

1. **修复手改 `tunnels.json` 调小 `seq` 导致新增隧道撞号**（提交 `cc0df30`）
   - 根因：`internal/tunnel/tunnel.go` 的 `load()` 直接把内存 `m.seq` 设为文件里的 `data.Seq`，而 `Add()` 用 `m.seq++` 生成 `"tun" + strconv.Itoa(m.seq)`，`get(id)` 只返回第一条匹配项。手改调小 `seq` 后新增隧道会拿到既有编号。
   - 改法：仅修改 `load()`，在赋值 `m.tunnels`、`m.seq` 后扫描 `m.tunnels` 中形如 `tun` + 一位或多位 ASCII 十进制数字且 `strconv.Atoi` 不溢出的编号，将 `m.seq` 抬到 `data.Seq` 与最大现有编号中的较大者；不为此单独回写文件，下次保存时自然写回。新建 `internal/tunnel/seq_test.go` 覆盖各种 `seq` 组合、前导零、非法/溢出编号及只读不改文件。
2. **修复无包装层的现成服务端压缩包显示名为随机数字**（提交 `9ed5cb4`）
   - 根因：网页上传存成 `os.CreateTemp(dir, "*.zip")` 的随机数字文件名，`internal/modpack/format.go` 的 `serverPack` 在 `root == ""` 时直接取该临时文件名作为 `pack.Name`，导致 `instance.import` 返回的 `pack.name` 与任务标题均为一串数字。
   - 改法：在 `internal/modpack/format.go` 新增 `DisplayNameFromUpload(fileName string) string`，按规则提取最后一个斜杠或反斜杠后的文件名、去掉最后扩展名、剔除控制字符、裁剪首尾空白和点并按 rune 截断到 80 字，结果为空返回空串。`internal/web/instances.go` 的 `handleImportModpack` 传入只用于显示的 `fileName` 参数（保持 `importFormArgs` 原签名不动）；`internal/ops/catalog/instances.go` 的 `instance.import` 在 `importParams` 登记 `fileName`（确认 `ops.Object` 校验只查登记属性，登记后可作类型校验和文档说明）并在 `bind` 接收，当 `pack.Format == modpack.FormatServer && pack.Root == ""` 且整理结果非空时替换 `pack.Name`，不参与任何路径拼接，不传 `fileName` 时行为不变。新增 `internal/modpack/displayname_test.go` 与 `internal/web/import_name_test.go`。
3. **修复 AI 回复超限且已开始输出时误报「回复中途断开了」**（提交 `1ce395e`）
   - 根因：流式输出已开始后触发 `ErrResponseTooLarge` 时，错误同时满足 `ai.ErrDisconnected` 与 `ai.ErrResponseTooLarge`，而 `internal/assistant/turn.go` 的 `failText` 先匹配 `ai.ErrDisconnected` 返回了「回复中途断开了」。
   - 改法：在 `failText` 判断 `ai.ErrDisconnected` 之前增加 `errors.Is(err, ai.ErrDisconnected) && errors.Is(err, ai.ErrResponseTooLarge)` 分支，正文直接返回 `ai.ErrResponseTooLarge.Error()`，保留原文 `detail`；先于修改在 `internal/assistant/think_test.go` 的 `TestFailText` 验证了单独 `ai.ErrResponseTooLarge` 的现行输出为「请求 AI 失败：AI 回复内容过多，已停止接收，请缩小问题范围后重试」且 `detail` 为空，并补全两行测试用例。
4. **修复小文件上传受系统临时盘余量拦截及临时盘报错不明**（提交 `601e3b7`）
   - 根因：`internal/web/transfer.go` 的 `parseUpload` 无条件对 `os.TempDir()` 所在磁盘申请带 `diskguard.Reserve` 的余量租约，而 Go `ParseMultipartForm(multipartMemory)` 在请求体不超过 `64 MiB` 时完全留在内存、不写临时文件；且 `*diskguard.NoSpace` 被 `uploadError` 统一转为「接收上传文件的磁盘空间不足」，未指明是系统临时盘及盘符。
   - 改法：仅在 `r.ContentLength < 0 || r.ContentLength > multipartMemory` 时对 `os.TempDir()` 申请租约并包装 `lease.Reader`；在 `parseUpload` 内捕获 `*diskguard.NoSpace` 后当场通过 `tempNoSpaceError` 转为 `ops.Errorf(http.StatusInsufficientStorage, ...)`（使用 `%v` 而非 `%w` 避免被后续 `uploadError` 覆盖），写明「系统临时文件夹所在的磁盘」并带上 `filepath.VolumeName(os.TempDir())`（取不到时省略盘符、不暴露完整路径）。原有 `TestMultipartUploadsRejectUnknownAndFullVolumes` 无需修改即可通过；新建 `internal/web/upload_tempdisk_test.go` 覆盖小文件放行、超 `multipartMemory` 与未知长度均返回 507 且提示含「临时」和盘符。
5. **修复整合包导入在设完待决清单后失败或取消时任务残留待决清单与告警**（提交 `440240f`）
   - 核实结果：问题属实（仅 `forgetPending` 和目录清理已做，任务上的待决清单和告警未清）。`ImportModpackAsync` 里 `finishImportPack` 在 `applyModpack` 末尾就调用 `t.SetPending(items)`、`m.rememberPendingInstance`、`t.AddWarning(pendingWarning(...))` 并写盘 `.minedeck/import-pending.json`；之后 `writeCreateWhitelist`、`ctx.Err()`、`BeginCommit()`、`writeRunBat`、`saveInstance` 仍可失败或被取消。失败/取消时 `ImportModpackAsync` 已调用 `m.forgetPending(t.ID())`（故再调 `instance.import.pending` 会报「这个任务没有要处理的文件」，不会重建半个目录）且 `discardCreating` 会删除整个半成品目录（清单文件随目录一起删掉），但未调用 `t.SetPending(nil)`，也未用 `tasks.Task.RemoveWarning` 撤掉告警，导致任务列表仍显示「已完成，N 个文件待处理」且无法隐藏。用 `atomicfile.Hook` + `CoreWaterfall` + `dl.Client.Transport` 桩先写用例稳定复现了该缺陷。
   - 改法：在 `internal/inst/import.go` 的 `ImportModpackAsync` 失败/取消收尾分支调用 `t.SetPending(nil)`，并用 `t.RemoveWarning` 撤掉 `"import-pending"`、`"cf-unresolved"`、`"import-kept"`、`"java-req"` 告警；新建 `internal/inst/import_fail_pending_test.go` 覆盖收尾失败、设完待决后取消以及成功导入仍保留清单且可处置三种情况。
6. **修复安装伙伴模组及其依赖写进 `mods` 失败时缺少占用提示**（提交 `b40b2c3`）
   - 核实结果：问题属实。`internal/companion/install.go` 三处调用 `placeJar` / `placeJarCtx`（第 417、464、482 行）在外层均只包了 HTTP 状态码 `&Error{Code: 500/502, Err: err}`，没有加「可能正被服务器占用，停服后再试」提示；`atomicfile.WriteCheckedWith` 会把 `check` 回调错误以及磁盘写入、改名失败（含内部 `retry` 包装的共享冲突/拒绝访问系统错误）和 `lease.Writer` 的 `NoSpace` / `ctx.Err()` 一并返回。
   - 改法：在 `placeJarCtx` 内用文件局部类型 `jarCheckError`（实现 `Unwrap`）标记内容比对与 `check` 回调返回的错误，原样返回不加占用提示；`*diskguard.NoSpace` 与 `ctx` 取消/超时错误同样原样返回；`jarNameRe` 校验不动；其余写入与改名失败用 `fmt.Errorf("把 %s 放进 mods 失败（可能正被服务器占用，停服后再试）：%w", name, err)` 包装，保留 `%w` 供 `errors.Is` / `errors.As` 识别底层系统错误。新建 `internal/companion/place_windows_test.go`，参照 `internal/tunnel/load_windows_test.go` 用共享模式 0 句柄独占目标 jar 验证。
7. **更正两处文档错误**（提交 `2cb35b9`）
   - 核实结果：两处均属实。`internal/worldimport/service.go` 的 `RestorePoint`（`points` 元素类型）包含 `StagedBytes int64`（`json:"stagedBytes"`），`docs/设计与参考/API.md` 第 347 行字段列表漏写；`internal/worldimport` 全包未调用 `EnableCancel`，通用任务页只在 `t.canCancel` 为真时显示取消按钮，换地图的取消入口位于前端「换地图」页面走 `POST /api/world/cancel`，`docs/使用指南/地图导入-使用说明.md` 第 86 行表述不准。
   - 改法：按要求只改 `docs/设计与参考/API.md` 第 347 行（在 `keptBytes` 后补 `stagedBytes` 并在行末补一句中文解释）和 `docs/使用指南/地图导入-使用说明.md` 第 86 行（写明新建服务器、导入整合包和导入现成服务端在可取消阶段可从任务页取消，换地图要在「换地图」那一页取消，取消后都要等清理完成才结束），其余段落不动。
