# 2026-11-16 CI 失败排查（Claude 写）

## 要做什么

作者原话：「过去好几次发版、合并，一直有CI失败的情况，这些到底是偶发还是真问题？你能不能写个任务卡片，让我开个新会话完整的研究一下？Codex上次那次改动好像引入了很多问题。如果真的有问题，你来复审而不是调用codex」。

发 beta.4 的那个会话据此写了任务卡片，这个会话照卡片做：把 GitHub Actions 上历次失败的运行查一遍，每一种失败下结论（测试的毛病、CI 机器的问题，还是产品代码的真问题）；测试的毛病和产品的真问题都在分支上改；顺带把 Codex 写的 `c1007f1` 逐行读一遍。不合进 main、不打标签、不发版，复审由 Claude 做、不调 Codex。

开头问了作者「Codex 上次那次改动」指哪一次，作者答：「c1007f1 那次」。

中途 Fable 的额度用完，作者说：「fable额度用完了，主会话我已切换至opus，请你将子代理也设定为opus以继续工作」。

## 做了什么

### 结论先说

从 10-31 第一次 CI 到 11-16，`test.yml` 跑了 359 次，`release.yml` 21 次。真的挂在测试上的有 25 次（含重跑之前的那几次），归拢起来是 17 种不同的失败。另有两次是外部 PR 等批准、一个 job 都没起，三次是故意让它失败的探针和反向验证，`pages.yml` 11-02 挂过一次是 Pages 当时还没打开，这些不算。

17 种里没有一种是说不清原因的「运气不好」。6 种是产品代码的真问题，11 种是测试自己的毛病。超时的那几种背后还有一个 CI 机器的共同因素，下面单说。

**产品代码的真问题，6 种：**

- 接管服务器时路径写成 8.3 短名就认不出来（`TestCheckAdoptDir`，11-09 连挂 6 次）。GitHub 机器的临时目录正好是短名。当时 `a1ea48f` 就修了。
- MCP「连过的客户端」按时间排先后，Windows 的时钟一格一格跳，同一格里顺序不定（`TestClientIdentity`，10-31）。当时 `cc704fb` 改成按序号排。
- 保存设置偶发报「替换文件失败：Access is denied」（`TestUpdatePropsKeepsEveryonesChange`，11-14 到 11-15 挂了 4 次）。**`c1007f1` 引入的**：它把保存时排队用的锁键换了一种算法，算锁键时会把要保存的那个文件打开一下，正好把前面那位的保存挡掉。PR #24、#26 修了，beta.2、beta.3 发出。四次失败都在修之前，修之后 49 次运行没再出现。
- 只读文件保存报成功却没存上（`TestPropsSaveNeverLeavesFileMissing`，11-15）。**`c1007f1` 引入的**：它新写的替换文件代码里改名参数少了结尾的空字符。PR #27 修了，beta.4 发出。
- 伙伴刚连上的一瞬间，状态已经是「连着」，模组版本和支持的指令却还是空的（`TestServiceAutoConnect`，11-09）。这次修了，见下。
- 导入交接包失败后，任务已经显示失败，名字却还占着一瞬间，马上重试会被回「正在创建中」（`TestImportDropsRuntimeSettings`，11-10）。当时只把导出那一侧改了，导入这一侧是把测试绕开；这次修了，见下。

后两种的空档都极短，人手点不出来，但确实是产品代码里先后顺序排错了。

**测试自己的毛病，11 种：**

- 对 Windows 的假设不对，10-31 第一次上真 Windows 就暴露、当时就改了的两种：以为本机往返一定量得出时间（`TestHeartbeat`），以为 DPAPI 密文随便改一个字节都解不开（`TestUnsealFailures`，其实头部几个字段不在校验范围里，这是 Windows 的行为，密文内容本身仍受保护）。
- 查得太早的两种：回复发出去以后操作记录才写，测试紧接着就查（`TestGameChatEndToEnd`，两次，`7a4c0c4` 改成先等）；广播收尾时假模组还没来得及记下 END（`TestBroadcastStopsWithServer`，`9e07f9c` 改成先等）。
- 清理临时文件夹时东西还被占着的两种：WebView2 的浏览器进程还没放开 lockfile（`TestWebViewStatusBarDisabled`，`a1ea48f` 改成多试几次）；`internal/ai` 的测试在后台真的连外网拉价格表，拉到以后往正在清理的临时文件夹里写（`TestServiceTestConnection`，beta.4 时 CI 和发版各挂一次）。后一种这次修了。
- 时限卡得太紧的五种：Markdown 渲染器的计时用例（11-14 两次，`c6b55cf` 改成跟着机器的快慢算上限，之后两百多次没再挂）；上传那条把空闲期限设成 150 毫秒（`TestMultipartUploadsDoNotQueueBehindVolumeLease`，`79d5bfb` 放宽）；`TestClientConnectRules`、`TestCommandOutputWait`、`TestClientBusyAndVersion` 三条这次改了。

**CI 机器的因素。** 超时的那几次有个共同点：只有按字母序排在前面的包（ai、assistant、atomicfile、bridge、chatai、cmd）慢了 2 到 5 倍，modcart 往后的包和平常一样。`go test ./...` 是边编译边跑的，开头那一段还在编译、链接别的包，4 个核被抢光，时限卡得紧的测试正好排在这一段。每次运行用的都是同一份构建缓存（缓存的键只跟 `go.sum` 走，存下以后不再更新），所以每次都要现编改过的包，这是常态，只是偶尔更严重。这解释了为什么本机连跑几十遍都过、CI 上偶尔挂。机器本身没法改，能改的是测试别把落盘、建文件这些时间算进一个几百毫秒的时限里。

**和 Codex 那次改动的关系。** `c1007f1` 是一个 100 个文件、近六千行的提交。CI 上的 17 种失败里，它直接带来了两种产品真问题（Access is denied、只读文件没存上），都已经修掉。另外两种和它沾边：`ai` 那条测试连外网的毛病早就有，是它把价格缓存改成原子写入（临时文件、落盘、替换）以后写的时间变长，才开始撞上；上传那条 150 毫秒的测试是给它的「按盘排队」补的。照 Codex 意见由 Claude 改的 beta.3 那几轮和 PR #27，没有对应到任何一次 CI 失败。

所以作者的感觉有根据：这个提交确实带进了问题，而且 CI 上看到的只是一部分。逐行复审又读出几处 CI 上不会出现的，见下面「逐行读 c1007f1」。

### 分支上的改动

分支 `claude/ci-flaky-investigation`，从 main 的 `03ca31f` 起，已推到 GitHub，没有开 PR。工作树在 `.claude/worktrees/ci-flaky`。

产品代码，五处：

- `015c231` 伙伴连接：握手成功后先把欢迎信息交给服务层，再把状态标成「连着」（`internal/companion/client.go`）。原来反过来，中间那一小段里伙伴页显示连上了却没有模组版本，游戏内 AI 这时让伙伴做事会被回「这个伙伴模组不支持…」。
- `5874198` 导入交接包：先清半成品、放掉名字的占位，再报任务失败；成功时也是先放再报（`internal/transfer/import.go`）。
- `d773714` 便携 Java 装到一半留下的半截不再被当成装好了（`internal/java/java.go`）。这是复审 `c1007f1` 读出来的，CI 上没出现过。原来「装好了没有」只看 `bin\java.exe` 在不在。`c1007f1` 给解压加了磁盘余量检查，开头只要求剩 256 MiB，解到一半不够就中途返回，解出来的原地留着，而 `java.exe` 在压缩包里排得很靠前。盘上剩两三百兆时就会留下「java.exe 在、别的不全」的半截，腾出空间再试，它直接被拿去开服，报的是 JVM 自己的错，也不再重新下载，只能手动删文件夹。现在装之前在旁边放一个「还没装完」的记号（`runtimes\java-N.incomplete`），整套装完才拿掉，记号还在的不算装好；解压失败时把半截删掉；一开头就按解开后的总大小查余量。以前装好的 Java 没有记号，照旧算装好。
- `15f0a8e` 定时备份撞上服务器启动、停止或重启时，等它稳定下来再试（`internal/inst/backup.go`、`policy.go`）。也是复审读出来的。`c1007f1` 给备份加了两道闸：服务器正在启动或停止时直接拒绝；压完发现中途停止或重启过就作废。手动备份报一句让人重试没问题，定时备份却是失败了只在控制台留一行字。把定时备份和定时重启定在同一分钟（世界大到一分钟压不完），或者把备份排在重启后一两分钟（带模组的服启动要几分钟），这一天就没有备份，而且天天如此。现在定时备份因为这类原因没做成时，等服务器回到运行中或已停止（最多 15 分钟）再备份，最多再试两次，控制台里写明在等。手动备份的行为和报错不变。顺带把作废规则补了另一头：热备压到一半有人点了停止、进程还没退出压缩就结束了的，原来照样发布，现在也作废。
- `0eefbb1` 地图导入：压缩包清单刚读完就被取消时把打开的包关上（`internal/worldimport/source.go`）。不关的话随后删上传文件会失败。窗口只有几微秒，没有用例。

## 验证了什么

都在本机（Windows 11，Go 1.27.1）和 GitHub 的 Windows 机器（Go 1.27.4）上。

**怎么确认「是什么原因」的。** 不靠多跑几遍碰运气，靠把空档人为拉大、让它必现：

- 伙伴连接：把交欢迎信息那一步拖慢 150 毫秒，原来的代码必挂，报的和 CI 上那次一字不差（状态 live、模组版本空、指令列表空）。
- 导入占位：原来的代码放占位之前睡 0.2 秒，同名重试第 2 次就报「正在创建中」；不睡的话本机 100 次都碰不上。复审后用例改成在就要报结果的那一刻当场检查，反向验证不用再睡：只靠 defer 放占位，三次都报「名字还占着」；放了占位才删包，三次都报「包还在」。
- 伙伴页的读法（复审后补的）：在放锁之后插 30 毫秒，旧读法 `TestLiveMeansWelcomeIsApplied` 三次全挂，新读法照过；在交欢迎信息和标「连着」之间插 30 毫秒，整个 companion 包照过（改之前 `TestServiceActAndFinish` 会 panic）。
- 定时备份的重试（复审后补的）：「稳定满 30 秒」那条用假时钟一步一步走，不看机器快慢；读文件出错用不许共享的方式占住 `level.dat` 造出来。去掉出错时的核对、不等满一段时间、不看是否在退出、不核对是不是同一台，四种改法各自让对应的用例挂。
- 操作记录写得晚：在写记录之前睡 0.8 秒，原来的 `TestCompanionEndToEnd` 必挂，报的就是少了 `gameai.ask`。
- `TestClientBusyAndVersion`：加了个临时探针量各段耗时，300 次里写配置文件（要落盘）最慢 0.56 秒，「连上到放弃」最慢 0.17 秒且每次都只连一次；压上 CPU 和磁盘负载再量，写配置文件最慢到 6 秒。超时出在写文件，不在协议逻辑。
- 150 毫秒空闲期限：在处理函数里睡 0.3 秒，原来的写法收到 408，现在的写法照常 413。
- 60 毫秒拿锁：把期限换成已经过期的跑 40 遍，对照组挂了 24 遍。
