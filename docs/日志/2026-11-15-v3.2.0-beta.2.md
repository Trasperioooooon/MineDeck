11 月 15 日这一天，几个会话各自做完了手上的事：PR #23（公网地址显示成 `ext.go:37`）、PR #24（替换文件偶发拒绝访问，上上节）、PR #25（tunnels.json 读不出来，上一节）都开着没合，另外还有一份只在本机分支上的「锁键改法」。作者交代：「过去所有会话的工作都应该已经结束了，你来进行整理、发版v3.2.0beta.2以及清理工作。」这一节记整合、复审和发版前的验证；发出去以后的核对和清理记在本节末尾。#24、#25 各自的改法和验证在上面两节里，这里不重复。上面两节里写的「还没合并，也没发版」说的是这之前。

### PR #23 是什么

这个 PR 没有在本文件里记过，补一段。OpenFrp、樱花的隧道启动以后，卡片上的公网地址有时显示成 `ext.go:37`。原因在 `internal/tunnel/tunnel.go`：从 frpc 输出里找「主机:端口」的那条正则不认下划线，又只取一行里的第一处，于是日志前缀里的源码位置 `client/control_ext.go:37` 被切出一截当成了地址，同一行后面真正的地址反而没看。v3.1.2 和 v3.2.0-beta.1 都有这个问题，是用户在 3.1.2 上碰到的。现在一行里的候选全部找出来，去掉源码位置和粘在更长记号上的半截，再按原来的规矩挑（域名优先，同类取后面的），顺带认了方括号里的 IPv6。

第一个提交出自 Cursor Agent，实际模型没有确认。Claude 审查时发现同一行里 IP 在前、域名在后会连着存两次盘、发两次 `tunnel.up`，补了第二个提交，改成一行只写一次。细节在 PR 说明里。要紧的一点：手头没有真实的 OpenFrp、樱花隧道日志，测试用的都是照着 frpc 的写法造出来的行，「使用 [主机:端口] 来连接」这种格式是推测的。要等有人用真实账户启一次隧道，这处修复才算落实。

在单独的工作树里开了分支 `integrate/beta2`，按 #23、#24、#25 的顺序用普通合并合进来，合的是三个 PR 当时的最新提交（`7f0719f`、`ca243d3`、`c10542c`），这样推上 main 以后 GitHub 会把三个 PR 记成已合并。代码全是 git 自动合上的，冲突只有本文件一处：#24 和 #25 各在末尾加了一节，两节都留。`internal/tunnel/tunnel.go` 被 #23 和 #25 同时改过，改的是不同的函数；合在一起以后我读过一遍，Codex 也专门看了这一处，结论在下面。官网的 PR #10 照旧开着，没动。

### 锁键改法为什么没有进这一版

先说它是什么。CI 上 `TestUpdatePropsKeepsEveryonesChange` 偶发拒绝访问这件事，当天被两个主会话各派了一个会话去查，两边互相不知道。一个做成了 PR #24，办法是替换失败时有限重试。另一个走得更深：它在 CI 上加计数核实，被拒的那些改名每一次都是本程序自己算锁键时开着的句柄造成的，于是改了算锁键的办法，最后一项不再用句柄打开，改到上一级的目录列表里查（`FindFirstFile`）。这份改动当时只是它本机分支上的一个提交 `7daa609`，没有推送，没人审过。它就是 #24 那一节「还没做的」里说的头一项。

整合时我先把它也合了进来，加了一处调整：目录列表里查不准的情况先退回老查法，这样凡是老查法查得出的路径，锁键和以前一字不差。然后连同三个 PR 一起请 Codex 复审。Codex 的结论是三个 PR 都能发，锁键改法这一版不该带。它指出一处疑点：新查法把上一级文件夹拆出来单独问系统，系统会把它当成路径的最后一项重新规范一遍，名字末尾的空格和点会被去掉。要是有个文件夹叫「world 」（末尾带空格），旁边又有个「world」，问到的就是旁边那个，算出来的是另一个文件的锁键，而同一个文件换一种写法算出来的又是对的那一把。一个文件两把锁，读改写不再排队，会悄悄丢更新。它的沙箱里没法实测，标的是「存疑」。我在本机试了，属实：用 `\\?\` 开头的路径建出名字是「dir 」「dir..」的文件夹，单独规范它们的路径确实落到旁边的「dir」上，按完整路径读到的却是它们自己里面的文件。

这种文件夹很少见，改起来也只有几行。但复审的人明说了这一版不该带，它担心的那一类问题（两次保存都成功，却丢了一次）又比这份改法要解决的问题重：有 #24 的重试垫底，用户已经看不到那个报错了。所以 beta.2 没有带它，`internal/atomicfile` 这一版只有 #24 的重试。

那份改法没有丢。修掉上面这一处、补了测试以后的版本在分支 `claude/lockkey-listed-path`，开成了草稿 [PR #26](https://github.com/Trasperioooooon/MineDeck/pull/26)，没有合并。发版以后我把 main 合进了这个分支（分支头 `8428082`），这样 PR 里只剩锁键改法自己的两个文件。它的 CI 前后跑了四次，三次通过，一次失败后重跑通过，失败的那条和原因见本节末尾「CI 上见过一次的失败」。它还欠一轮复审，因为 Codex 审的是修之前的版本。Codex 提了、没人核实过的几种环境（允许打开文件却不许列上一级文件夹的权限、subst 盘、网络共享、卷挂载点、区分大小写的文件夹）也写在 PR 说明里。合不合、什么时候合，等作者定；有 #24 垫底，这件事不急。

### 复审

按作者之前的指定，请的是 Codex。命令行里请求的是 gpt-6-astra、max 档，它的会话记录里客户端设置也是这两样，服务端实际是哪个型号确认不了。只读，审的是合并以后相对 main 的全部差异（当时还带着锁键改法），用了约 12 分钟。任务单里点了四处重点：#23 整份，因为没有别家模型审过；#24 和 #25 在上一轮复审以后各自补的那个提交，Codex 当时没看过；锁键改法；另加 `tunnel.go` 和 `replace_windows.go` 两处自动合并的地方。

结论：#23、#24、#25 都是「能发」，没有挡发版的问题。它逐项核过的有这些。#23 的源码位置过滤、域名优先、同一行只存一次盘只发一次事件，都成立。#24 补的目录属性判断对目录联接和目录符号链接都对，只读目标的规矩没变。#25 两次检查都严格只认 `ERROR_FILE_NOT_FOUND`，只有 `seq` 的文件不会被误挡。`tunnel.go` 合并处，记公网地址仍然要经过 `save()`，绕不过「没读出来就不许存」那道闸；隧道配置没读出来时没有隧道启动得了，所以它没找到「配置没读出来、却不断收到 frpc 地址」的入口。

它提了一条不挡发版的：公网地址的正则会把过长的端口截成合法的，比如 `[2001:db8::1]:123456` 会取出 `:12345`，`host.example:12345abc` 会取出 `host.example:12345`。正常的日志不会这样写；域名和 IPv4 的这个毛病原来就有，这次新加的 IPv6 也跟着有。这一条没有改，留给以后：取到候选以后看一眼右边紧挨着的字符，还是数字或字母就不要。

它没有跑 `go test`，只读沙箱里建不了编译用的临时目录。它的结论来自读源码，加上把地址筛选的逻辑转写成 JavaScript 在内存里跑。Go 的测试以本机和 CI 为准。任务单、报告和会话事件存在主检出的 `.claude/archive/2026-11-15-beta2-materials/beta2-Codex复审/`（`.claude/` 不入库）。

Codex 审的那棵树带着锁键改法，最终发版的不带。两者的差别只在 `internal/atomicfile` 里锁键那几个函数和它的测试文件，三个 PR 的代码一个字没变，所以它对三个 PR 的结论对最终的代码仍然成立。

### CI 上见过一次的失败

把 main 合进 PR #26 的分支以后，那个提交（`8428082`）的两次 CI 里有一次失败。失败的是 `internal/web` 的 `TestMultipartUploadsDoNotQueueBehindVolumeLease`：这条测试把上传的空闲期限调成 150 毫秒，然后占住磁盘的写入名额，看上传会不会被误判成「没有进展」。那一次 `/api/modcart/local` 回了 408。重跑通过，同一个提交的另一次 CI 也通过。

它和 v3.2.0-beta.2 没有关系：发出去的代码里没有锁键改法，main 上这一天的几次 CI 和发版工作流里的测试都过了。它和锁键改法有没有关系，没有查清。`/api/modcart/local` 后面会用到 `atomicfile.LockPath`，又只在带着锁键改法的分支上出现过，所以不能说无关；另一方面这条测试的期限只有 150 毫秒，CI 的机器慢的时候也可能单纯是超时。我在本机把这一条在 main 和那个分支上各连跑了两百多遍，其中 150 遍带着整套测试作背景负载，两边都没有再出现。这件事记在了 PR #26 说明的「还欠的」里，合并 PR #26 之前值得再盯一下；在 main 上再碰到的话，就说明它只是一条计时偏紧的用例。
