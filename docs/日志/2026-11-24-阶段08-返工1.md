# 2026-11-24 阶段 08 返工 1

## 要做什么

清账阶段 08 审过以后的第一轮返工，这一轮没有作者的原话，是主会话按审核结论写的返工单。最要紧的一件是 A38 第 1 点换做法：上一轮放创建记号时就把存放位置记成扫描服务器的根，建不成、取消了，这个位置也永远成了扫描根。复审方走真实的导入现成服务端流水线实测过，人挑的新位置里本来就有一个带 `instance.json` 的文件夹，导入失败以后重启，那台就进了列表，之后启动时的日志配置迁移会去改它的文件。返工单要求改成另记一份「正在建的位置」小清单，只在找没建完的文件夹时多扫，建成了才记成扫描根。

另外几件小的：A34 卸载和换 Java 互斥靠的「先登记自己、再看对方」没有用例钉住；卸到一半失败的那套便携 Java 还能被换上；接管时人指定一个便携 Java 的路径不经过互斥，`java.remove` 的占用检查先拿列表后看「正在创建」也有一个空当；A35 那段注释把「连不上」写得不准；还有两处可维护性的小毛病。A38 第 1 点两处、A34 的先后两处、接管那一处要求反向验证。

## 做了什么

都在分支 `claude/clear-backlog-1122` 上，基准是 `9cbbedf`，代码分四个提交（第四个 `a01f2c7` 是收尾前的小修正：上面说的注释，和接管那两条新用例造 Java 时改用 `java.Exe` 的文件名、不写死 `java.exe`，Mac 上它叫 `java`），这份日志另一个提交。

**A38：「正在建的位置」小清单（`e699a6e`）。**

配置里加了一项 `creatingRoots`（`omitempty`），和 `roots` 分开。读、记、去三个函数照 `RememberInstanceDir` 的写法：拿着 `cfgMu` 改，改的时候另起一个切片，不在 `GetConfig` 给出去的副本共用的底层数组上动。「已经是扫描根的不记」这一条要在锁里算扫描根，而 `InstanceRoots` 自己会去拿读锁，锁不能重入，所以把它的计算挪进了 `instanceRootsOf(Config)`，`InstanceRoots` 只是调它，行为不变。

`WriteCreatingMarker` 放记号之前改记这份小清单，不再记扫描根。找没建完的文件夹用一个新函数 `leftoverRoots` 取要扫的位置：扫描根在前，后面接小清单里还不在前面的，按不分大小写的字面去重。列半成品和删半成品都经它取，编号里的序号才对得上。启动时找服务器照旧只扫扫描根，小清单里的位置不扫。新建、整合包、现成服务端走的 `completeCreate` 和交接包走的 `FinalizeCreate` 在登记成功以后把 `RememberRoot` 加了回来，位置还是上一轮删掉之前的那一处。

启动时整理小清单（`pruneCreatingRoots`），放在去掉残留记号之后：已经进了扫描根的去掉，底下已经没有带记号文件夹的去掉。位置本身读不到的留着，比如建在移动硬盘上、崩了以后没插盘就重开，插回来以后照样找得到那个半成品；接管登记的文件夹不在时也是留着登记，做法一致。代价是用户自己把那个位置整个删掉以后，配置里会一直留着这一条，下次启动多看一眼不存在的文件夹而已。只在启动时整理，那时没有正在建的任务，不会把刚记上、记号还没放下的位置去掉。

和老版本的关系：老版本读配置用的是普通的 JSON 解码，不认识的 `creatingRoots` 直接忽略；老版本下一次存配置时按它自己的结构写，这一项会丢掉，丢了的后果只是那次崩掉的半成品回到新版本以后找不到，不影响服务器。

`creating_leftover.go` 放记号那段注释、`RememberRoot` 的注释、`API.md` 没建完的文件夹那一行都按现在的做法写了。测试环境的 `adoptEnv`、`importEnv` 顺带把这一项复位，免得用例之间互相带过去。

**A34：先后的用例、卸到一半的那套、接管和占用检查的空当（`5365cdc`）。**

`remove.go` 在两边「登记了自己、还没看对方」的地方各放了一个包内的停顿点，默认什么都不做，测试里换成会停住的函数。两条用例：换 Java 停在那里时卸载，卸载要报忙、什么都不删，放开以后换 Java 照常换上；卸载停在那里时换 Java，换 Java 要被拒、真正去换的那一步不调，放开以后卸载照常卸掉。写法参考了复审方仓库外的探针，按功能起名放进了 `remove_test.go`。

`UsePortable` 登记、看过「正在卸载」以后再查一次 `IsInstalled`，不在就返回新加的 `ErrNotInstalled`，不调真正去换的那一步。卸载删到一半失败时 `java.exe` 还在、带着「没装完」记号，`removing` 已经回到 0，原来这时直接就换上了；已经卸干净的也一样拦下。这一条让原有的「卸载途中换不上」用例里两步不再成立：「别的大版本照常换」那一步换的 Java 21 根本没装，「卸完以后不再挡」那一步换的就是刚卸掉的 17。用例的本意是「卸载只挡它自己那一个大版本」和「卸载结束后不再挡」，所以前一步先把 21 装上，后一步先把 17 重新装上，断言没动。换 Java 的操作遇到这个错误按普通业务错误回 400，和「不是已知的 Java」一样，`setJava` 没改。

接管第一步，人指定的 `java.exe` 在 MineDeck 的便携 Java 文件夹里面时（按真实路径比，用的是 inst 包里接管本来就在用的 `realPath`、`within`），经 `java.UsePortable` 查，正在卸载、已经卸了、没装完整都不接管，报一句接管自己的话（新函数 `checkChosenJava`）。为什么这样就严密了：接管在 `validateAdopt` 里就占上了「正在创建」，一直占到登记进列表以后；第一步是在占上以后才去看「正在卸载」。卸载那边先记上「正在卸载」，再在占用检查里看「正在创建」和列表。两边在 `m.mu` 上的先后总有一个：卸载的检查在接管占位之前，那么卸载记「正在卸载」也在接管看它之前，接管看得到；看到的要是已经放掉的标记，说明卸载已经删完（或者删到一半失败、留着「没装完」记号），紧接着那次 `IsInstalled` 拦下。卸载的检查在接管占位之后，那么卸载看得到「正在创建」，或者接管已经做完、在列表里。后面这半句要求占用检查先看「正在创建」再拿列表，这正是另一处改动：`mc.go` 里 `java.remove` 的占用检查原来先拿列表、后看「正在创建」，新建、导入、接管都是先登记进列表再放掉「正在创建」，任务正好在两步之间做完时两样都漏；现在先把「正在创建」读进一个变量，再拿列表，报错的先后和说法照旧。

`IncompletePortable` 里写死的两处 64 改用 `maxPortableMajor`。

**A35 的注释和界面上的变量名（`61d22b2`）。**

`adoptiumDown` 的注释照实写了：错误底下是 `net.Error` 才算连不上。复审方在本机回环上逐个试过的：连接被拒、代理连不上、等到了这一问的时限算（时限到了返回的 `context.DeadlineExceeded` 也是 `net.Error`）；证书不受信、代理回 502、对面一连上就关掉、https 跳到 http 被拒、上层取消，以及回了话的 404、5xx、回的不是 JSON 都不算。没试过、按 Go 标准库的类型看也算的两种另外写明：DNS 解析失败（`net.DNSError` 实现了 `net.Error`），读到一半连接被重置（底下是 `*net.OpError`）。所以不能笼统说「连上以后出的错都不算」。只改注释，行为不变。这一段注释改了两次：`61d22b2` 先写过一版，里面有一句「连上以后才出的错都不算」，概括得过头了，收尾前在 `a01f2c7` 里改成上面只列试过的写法；`61d22b2` 的提交说明里那句注释原来「比实际窄也比实际宽」，后半句也不准，原来的注释只是写窄了，以这里为准。

一个代码不改、只在这里写明的情形：Adoptium 的接口回了话却很慢的时候，最坏要等四问。清华镜像那条路问两次校验值清单，官方源那条路问 jre 再问 jdk，每一问时限是十秒；每一问都在快到十秒时回了话（比如回 503，不算连不上），就会一问接一问地等下去，加起来接近四十秒才改用 Mojang 运行时。到了时限的那一问算连不上，会直接跳过后面的。

`app.js` 删服务器那段 `try` 里新声明的 `const r` 遮住了外层对话框结果的 `r`，改名 `res`。

## 验证了什么

都在作者的 Windows 机器上、这条分支的工作树里跑。

- `gofmt -l internal/app internal/inst internal/java internal/ops/catalog` 无输出；`go vet ./...` 在 Windows 和 `GOOS=darwin GOARCH=arm64` 下都无输出，darwin 下 `go build ./...` 也过。
- `go test ./internal/app/ ./internal/inst/ ./internal/java/ ./internal/ops/catalog/ ./internal/transfer/ -count=1` 都过；交接包也调 `FinalizeCreate`，所以带上了 `transfer`。`internal/web` 只跑了接口路由和不泄密那两条，过。
- 新加和改过的用例：`app` 一条，`inst` 六条（新位置崩了能列能删、删后清单去掉；导入失败旁边那台不进列表；建成以后成为扫描根；读不到的位置留着；接管正在卸载的便携 Java 被拒；接管卸到一半的被拒），`java` 四条（两条先后、卸到一半和卸干净的不让换、原有那条照本意改过的），各 `-v` 单跑过，`-count=20` 也都过。`-race` 跑不了：本机没有 gcc，cgo 关着。
- 界面用例按「Java|没建完|接管|半成品|删除：」筛着跑，21 条全过（含末尾的「全程无页面报错」）。
- 反向验证在 `61d22b2` 上做，临时改动没有提交，每次改回以后 `git diff --exit-code` 确认和提交一致；`a01f2c7` 没动产品代码，只在它上面把接管那一条重做了一次，结果一样：
  - 放记号时改回记扫描根：「导入失败旁边那台不进列表」失败，重开以后那台进了列表。
  - 找半成品时不扫小清单：「新位置里崩了重开能列出来」失败，列出来是空的。
  - 换 Java 那边改成先看「正在卸载」再登记：「换 Java 停在登记之后时卸载报忙」失败，卸载没报忙、往下查了占用。
  - 卸载那边改成先看「有人在换」再登记：「卸载停在登记之后时换 Java 被拒」失败，换 Java 没被拒、真的换了。
  - 接管第一步去掉那道互斥：「接管正在卸载的便携 Java 被拒」失败，接管走完了、登记了那套马上被删的 Java。

## 没做完或没验证的

- 没跑 `go test ./...` 全量和界面全量，按规矩留给审核方。
- 占用检查「先看正在创建、再拿列表」这一处没有专门的用例：要卡在两步之间得在操作层加停顿点，这次没加，只靠注释说明先后的理由。
- 半成品的编号是「在扫描列表里的序号/文件夹名」。小清单接在扫描根后面，一个新位置里建成了服务器、这个位置进了扫描根以后，排在它前面的那些小清单位置的序号会往后挪一位。界面上停着一份旧列表、正好有另一个新位置里的同名半成品时，按旧编号点删可能删到那一个；删之前照旧会复查记号和 `instance.json`，删到的也只会是一个没登记的半成品。原来改默认存放位置时也会这样挪，这次多了一种挪法，没改编号的做法，请审核方定。
- 登记处是先写 `instance.json`、去记号、再记扫描根。程序正好崩在写完 `instance.json` 和记扫描根之间时，这台在一个不扫的位置里，重开以后不在列表里（要用接管加回来），启动时它的记号会被当成残留去掉，这个位置也会从小清单里整理掉。A38 之前也是这样，这次没改。
- `GET /api/config` 现在会带出 `creatingRoots`，`API.md` 讲配置的那一段（列了 `instanceDirs`）没跟着写；`instance.creating.list` 的说明写的是「服务器根目录下」，没提小清单里的位置。这两处都不在这一轮允许改的范围里。
- 没在真程序里走一遍新建中途结束、重开看半成品，只用 `WriteCreatingMarker` 加重开管理器和真实的导入现成服务端流水线测了。

## 留给下一位的

- 「这个路径在不在某套便携 Java 里面」现在有两份：操作层的 `javaPathInside`（`mc.go`）和接管用的 `within(realPath(...))`（`adopt.go`）。操作层依赖 inst 包，inst 用不了那边的函数；要合成一份，得把操作层那个挪进 inst 再让操作层调过去，这一轮动不了 `mc.go` 里那一段，没做。
- `app.addRoot` 原地 `append` 到 `c.Roots` 的老问题（上一轮日志记过）还在，这一轮的新函数没有这样写。
- Adoptium 回了话却很慢时最坏要等近四十秒（见上），要再压就得给这四问合起来定一个总时限。
