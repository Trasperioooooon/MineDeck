## 2026-11-13 v3.1.2：OpenFrp 的 frpc 下载，go vet 的两条提醒（Claude 写）

11 月 13 日晚上作者交来的话是：「刚刚修复了一点小问题，请你复核两个既有的 cmd/minedeck unsafe.Pointer 警告并实施修复，随后进行 V3.1.2 的发版」。当时 main 的工作树里有一份没提交的改动，四个文件，修的是 OpenFrp 的 frpc 下不下来。这份改动不是这个会话写的，是谁写的、在哪台电脑上试的，这个会话不知道，只知道代码注释里写着「实测可以过闸」。

### 这一版里有什么

一共四个提交，都直接提交在 main 上，没有开 PR。

`13acb64` 是作者交来的那份改动，原样提交。OpenFrp 的下载源（`staticassets.naids.com`，前面是腾讯 EdgeOne）把 Go 默认的 TLS 握手当成机器人，回 HTTP 567，第一次启动 OpenFrp 隧道的电脑因此下不了 frpc。改法是给这一处下载单独配一个只宣告 TLS 1.3 的客户端（`internal/tunnel/providers.go` 里的 `openfrpHTTPClient`），握手的样子变了就能过。代码注释里写得很直白：这是在绕开 CDN 的机器人防护，对方随时可能把这种握手也拦掉，不能当成永久有效。同一份改动还让下载失败的汇总在状态码后面带一句原因（`internal/dl/dl.go` 的 `httpStatusHint`），并在 OpenFrp 下载失败时把手动放 frpc 的办法写进报错。

`50714f3` 是那两条 `go vet` 提醒。复核的结论是代码本身没有错：`frameless_windows.go` 和 `minsize_windows.go` 里解引用的 lparam 指向系统的内存，垃圾回收不管它。提醒一直在，是因为行尾写的 `//nolint:govet` 只有 golangci-lint 认，`go vet` 不认。两处都换成 `hiddenstart_windows.go` 里早就在用的写法 `*(**T)(unsafe.Pointer(&lparam))`，读写的还是同一个地址，vet 不再报。`go vet ./...` 现在没有任何输出。新加的 `cmd/minedeck/frameless_windows_test.go` 有两条测试，真建一个窗口把结构体递进去看读写对不对。

`04090d4` 是评审以后补的，见下面「评审」。再后面一个提交是版本号、发布说明和这一节。

### 评审

前两个提交交给 Claude 的 reviewer 子代理（Fable，只读）审了一遍。OpenFrp 那份不是 Claude 写的，按规矩正该由它审；unsafe 那两行是 Claude 写的，按规矩该换一家模型审，这次没有换，理由是改动只有两行、用的是仓库里现成的写法，并且在真窗口里量过。评审没有查出必须改的代码，它用汇编对比确认了两种写法取指针、读写的指令相同。

它提的建议里改了四条。403 原来也说成「被源站 CDN 的机器人防护拦截」，而这句话所有下载源共用，改成了「源站拒绝访问：可能是机器人防护、链接失效或没有权限」。这一处动的是作者那份改动里的措辞，是 Claude 拿的主意，作者可以改回去。OpenFrp 下载失败时提示叫人把 exe 放进 `runtimes\frpc\openfrp`，这个文件夹当时不存在，现在先建好。原来的测试守不住核心修复，去掉 `Client: openfrpHTTPClient` 或者把握手改回 TLS 1.2 测试都照过，现在补了两条能抓住这两种改坏的测试。`test.yml` 在测试前加了一步 `go vet ./...`。

没做的一条：TLS 1.3 握手失败时退回默认客户端再试一次。只支持到 TLS 1.2 的代理或者杀毒软件的 HTTPS 扫描后面，这一处下载会握手失败，发布说明的「已知情况」里写了。

### 验证了什么，没验证什么

`go test ./...` 34 个包全过，`go vet ./...` 没有输出，gofmt 干净。新测试逐条反着试过：把指针取错、去掉专用客户端、握手改回 TLS 1.2、去掉建文件夹，对应的测试都会失败。有一点要分清：把 unsafe 那两处改回旧写法，测试照样通过，因为新旧写法行为相同，守着写法的是 vet。

真窗口里量了一遍，脚本在 `D:\MineDeck-v310-test\window-auto-312`（`win312.ps1` 加 `page312.js`）。它用发版那条命令编出来的程序开真窗口，从外面用 Win32 接口量三件事：窗口的样式还带着标题栏，而客户区从窗口顶边开始；最大化以后客户区正好等于显示器的工作区；把窗口设成 400×300，它停在 1024×576。先拿发布页下载的正式版 3.1.1 跑了一遍作对照，再跑 3.1.2，两边每一个数字都相同，评审后的最终代码又跑了一遍，也相同。只在一块 100% 缩放的屏幕上试过（工作区 2560×1392），高缩放和多屏没有试；窗口是脚本摆弄的，不是人手拖的。

**没验证的是最要紧的一条：真的去 OpenFrp 的下载源下一次 frpc。** Claude 准备了一条联网的检查（先用默认客户端请求看是不是 567，再原样调 `EnsureFrpc`），运行时被 Claude Code 自动模式的安全分类器拦下了，理由是「绕过机器人检测」。这是有意设的限制，Claude 没有换别的办法绕开它，也没有用编出来的程序去起一条 OpenFrp 隧道，那是同一件事换个做法。所以这处修复管不管用，这个会话手里的证据只有代码注释里的「实测可以过闸」。还要留意，握手的样子跟编译用的 Go 版本有关：本机是 go1.27.1，`release.yml` 取的是 1.27 最新的补丁版，两边可能不同。要验的话，作者自己在一个没有 `runtimes\frpc\openfrp` 的文件夹里打开 3.1.2，启动一条 OpenFrp 隧道，看 frpc 有没有下回来就行。
