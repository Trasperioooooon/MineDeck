### 第一条：`03c970f`，1.7–1.11.2 换成 `log4j2_17-111.xml`

推断证实了。在仓库外的测试文件夹 `MineDeck-l4j` 里用 Java 8（Temurin 8u512 便携版）和官方 1.8.9 原版服务端，按 v3.2.0 给这台服写的参数（`-Dlog4j2.formatMsgNoLookups=true -Dlog4j.configurationFile=log4j2_112-116.xml`，文件夹里放着官方那份 112-116）起服，控制台发 `say ${jndi:ldap://127.0.0.1:38389/x}`，本机只监听 127.0.0.1 的那个端口收到 2 次连接；Forge 1.7.10 一样是 2 次。112-116 那份靠 `%msg{nolookups}`，这段版本的 log4j 不认；112-116 在 1.8.9 上还多报两行 `ERROR Error processing element Queue: CLASS_NOT_FOUND`（它没写 `packages="com.mojang.util"`），不影响控制台输出。

两份配置的地址和 SHA-1 照 minecraft.net 公告（2021-12-10「Important Message: Security vulnerability in Java Edition」）里的链接取，下载下来算出的 SHA-1 和地址里那串一致：17-111 是 `4bb89a97a66f350bc9f73b3ca8509632682aea2e`（主控记的是对的），112-116 是 `02937d122c86ce73319ef9975b58896fc1b491d1`（和代码里原来的一致）。17-111 那份用 `RegexFilter` 直接丢掉带 `${` 的消息，所以那句 `say` 本身不进控制台，这是 Mojang 的做法。

改法（`internal/inst/install.go`）：版本分段写成一张表 `log4jEras`，新建、接管、导入现成服务端、交接包、保存 JVM 参数时强制保留的那几条（`log4jFlags`）都按它：1.18.1 起不加；1.17 到 1.18.1 以前只加 noLookups；1.12–1.16.5 照旧（noLookups 加 112-116）；1.7–1.11.2 加 noLookups 和 17-111；1.7 以前什么都不加。分界用官方清单里真有的版本号：清单里有「1.7」这一条（排在 1.7.2 前面），也有「1.12」。noLookups 对 1.7–1.16.5 不起作用，照旧带着：已经建好的服务器里都有它，迁移时只换配置那一条。`fetchLog4jXML` 多一个文件名参数，两份按各自的 SHA-1 校验；下载地址前缀做成变量 `log4jObjects`，测试里换成本机假服务器。版本判断沿用 `mcsrc.NewerOrEqual` / `NewerOrEqualCached`：保存参数时判不出版本，照旧沿用已有的防护参数（现在也认 17-111 那条）；`applyLog4jMitigation` 遇到官方清单里没有的版本和以前一样按 1.12–1.16.5 加（调用它的几处都先确认了清单里有，实际走不到）。导入现成服务端的 `applyImportLog4j` 原来自己抄了一遍判断，改成用同一张表。下载失败那句日志改了：以前说「仅安全性降低」，其实 1.7–1.16.5 没有这份配置就等于没防，现在照实说，并提醒先别让不认识的人进服。

已经建好的（`internal/inst/log4j_migrate.go`，新文件）：程序启动后在后台过一遍（`cmd/minedeck/main.go` 里 `go mgr.MigrateLog4j(...)`），找出版本在 1.7–1.11.2、启动参数里引用着 112-116 的服务器，先把 17-111 下载好、核对过 SHA-1，再拿着 `procMu` 把那一条参数原地换掉（别的参数一条不碰，位置不变），存 `instance.json`、重写 `run.bat`。下载期间占着「更新 log4shell 防护」的使用登记，删除、换地图会等它。下载不成什么都不改，照旧用旧配置开：引用一个不存在的配置文件会让控制台只剩 ERROR，「启动完成」也认不出来。没换成时在那台服务器的控制台和程序日志里说清原因；之后每次启动这台服务器，控制台再说一声「这次照旧用它启动、后台正在下载」，并在后台再试一次，换成了下次启动生效，启动本身不等下载。版本只看本地清单，判断不了的不动。112-116 那个旧文件，要启动参数、`run.bat`、接管前的启动脚本和 `user_jvm_args` 里都不再引用它，服务器停着，内容还是官方那份（自己改过的不删），才删；服务器开着时换上了也先不删，下一次程序启动那一遍再删。

新文件名 `log4j2_17-111.xml` 加进了控制文件清单（`control.go`，别人给的包不能带）、交接包不带的清单（`transfer/export.go`）、接管失败时恢复的文件（`adopt.go`）和移出列表时列的 MineDeck 文件（`listinfo.go`）；`IsLog4jFlag` 也认它。界面 `app.js` 里「套用预设 / 清空」保留的 `LOG4J_FIX` 加了这一条，只改了这一行（不改的话后端保存时也会补回，只是界面上先消失一下）。

已有用例的改动，逐条：`internal/inst/install_test.go` 的测试版本清单补了 1.12、1.11.2、1.8.9、1.7.10、1.7、1.6.4（分界要用到 1.12 和 1.7，真清单里都有），没改任何期望；`internal/inst/import_server_test.go` 里换掉 `fetchLog4jXML` 的那个函数改成新签名（多一个文件名参数，用 `_` 接，函数体没动）。别的期望都没改，原来期望 1.16.5、1.12.2 用 112-116 的用例照旧通过；现有用例里没有期望 1.7–1.11.2 用 112-116 的。

### 第二条：`0acc543`，`cart.json` 读不出来时不当空清单

根因和主控读的一样。`internal/modcart/modcart.go` 照 `tunnel.LoadError` 改：读不出来（被占着、没权限、同名文件夹顶着、程序文件夹访问不了）、解析不了（坏 JSON、空文件、没有 `carts` 这一项）都记成 `modcart.LoadError`，用 `Corrupt` 分开两种。这期间清单是空的，加入、移除、清空（两种）、添加和移除本地文件一律在改内存和动暂存目录之前拒绝，`write` 里再挡一道；`cart.json` 和暂存的文件一个不动。每次有人要清单、要改清单时在锁里再读一次，读成了直接换上（没读成期间什么也存不进去，不会冲掉谁的改动）。启动时读不出来（坏文件不算）隔 200 毫秒再读，最多三次。`sweepStaged` 只在清单真读成了、或者确实是新装时才跑。记事本存的 BOM 去掉再解析；坏文件的报错带着大概在第几行。

解析不了时选的是第二种（照隧道的做法挡下保存，提示人去修文件），没选「另存 `.bad`、从空清单开始但不删暂存」。理由：`.bad` 里记着本地文件的登记，从空清单开始以后这些文件就成了没登记的，用户要么永远看不到它们，要么下次启动被当成没登记的清掉，等于换个方式丢；而且第一种做法下 `cart.json` 会被改名，和「`cart.json` 没被改」的验收要求也对不上。挡着不让存、告诉他坏在第几行，用记事本修好就回来了；真想从头来，把文件改名挪走，下一次读到的是「文件不在」，从空清单开始（这时暂存的本地文件因为没登记，下次启动会被清掉，报错原文里写了位置，hint 里写了两种办法）。

「确实是新装」怎么认：`data`、`data\modcart` 第一次存清单时才建，新装时都可能还不在，读 `cart.json` 报的是「路径不在」而不是「文件不在」。所以从程序文件夹（`cart.json` 往上第三级）往下逐级看：程序文件夹要看得到；在的那几级必须是文件夹；第一个不在的那一级必须是「上一级在、它不在」（Windows 上只认 `ERROR_FILE_NOT_FOUND`，照抄隧道的 `notfound_windows.go`）。程序文件夹看不到、或者中途路径失联，都不算新装。没有用 `MkdirAll` 把文件夹先建出来：程序文件夹暂时看不到时，`MkdirAll` 会把它整个建回来。

操作层（`ops/catalog/modcart.go`）：`LoadError` 一律转成 503；查看清单、检查前置、安装（预览和执行）先问一次 `LoadErr`，不拿空清单冒充「清单是空的」、也不报「待装清单是空的」。hint 两句（被占着：「清单的存档 cart.json 读不出来，可能被别的程序占着。关掉占用它的程序后点「重试」」，坏了：「清单的存档 cart.json 内容坏了。用记事本修好它，或者改名挪走后从空清单开始」），用 node 数过，45 和 42 个字，拼在「无法显示待装清单：」后面整句接得上。界面（`modcart.js`）：清单的位置一直画「无法显示待装清单」的报错框，第二行说清单和本地文件都还在、读出来之前不能加、移除或安装，带「重试」；以前「加入清单」失败会把列表重画成「清单是空的」，现在加入、移除、清空、从电脑添加、检查前置遇到 503 都记下这个状态。仿真后端加了 `modCart.loadFail`（`locked` / `corrupt`），新界面用例放在「待装清单在打开之后被别处改过」那条后面。

### 第三条：`8dd858c`，frpc 的解压、缓存和 https

`internal/tunnel/providers.go`：`extractZipFlat` 先把每个文件写成不以 `.exe` 结尾的临时文件（`.minedeck-unzip-*.part`），全部写完、CRC（`archive/zip` 读到结尾时核对）和字节数都对上，再逐个改成正式名字；任何一步失败，删掉这次写出来的临时文件和已经改了名的文件。解压前就在的同名文件不动、不覆盖（只有 `findExe` 找不到 frpc 时才会解压，所以不会有旧的 frpc exe 挡着新的；以前会覆盖 LICENSE、示例配置这类文件，现在留着旧的）。上次解压到一半被关掉留下的临时文件，开始前清掉。OpenFrp 和自定义 frps 两条都走这段。

OpenFrp：缓存的 zip 名字带上 `latest_full`（`openfrp-frpc-<latest_full>.zip`），换了版本不再复用旧 zip；解压失败、或者包里没有 frpc 时删掉缓存的 zip，下次重新下载；frpc 解压出来又被杀毒软件删了的（`errFrpcGone`）不算 zip 坏了，留着。`latest_full` 只认字母、数字和 `._-`，不全是点、不超过 80 个字，不合规的不下载。接口给的下载源只认 https 的：别的跳过，一个 https 的都不剩时报错（没有整份拒绝：一条 http 的源不影响别的 https 源）。`openfrpHTTPClient` 加上只跟 https 跳转，只宣告 TLS 1.3 的设置不动。只跟 https 跳转的规矩原来写在 `dl.GuardedClient` 里，抽成 `dl.HTTPSRedirect`（`internal/dl/guarded.go`），两边共用，报错原文没变。自定义 frps 的 zip 按官方 SHA-256 核过，解压失败（多半是盘满）不删。`frpSHA256` 从常量改成变量，只为测试能换成假 zip 的哈希。
