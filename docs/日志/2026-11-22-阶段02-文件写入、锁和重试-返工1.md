## 做了什么

工作在分支 `claude/clear-backlog-1122` 上（基准提交 `e7cf86d`），分成两个代码提交加本日志提交：

第一个提交 `8bcc6b4` 处理 R1–R4（`internal/atomicfile` 与 `internal/inst`）：

- **R1（备份一步发布，不在 Windows 上留 0 字节占位，文件名时间改回压缩前取）**：上一轮 `e4ea981` 的 `zipDirsExclusive` 先用 `O_EXCL` 在备份目录建一个 0 字节的最终 `.zip` 占住名字，关句柄后再调 `atomicfile.Replace` 换上去。Windows 上 `MoveFileEx` 只要目标被任何句柄打开就会报拒绝访问；占位文件一落地，杀毒、索引或正开着备份目录的资源管理器一旦打开它超过半秒，整次备份就会在最后一步报拒绝访问失败，若对方还不许删除，连回滚清理都删不掉，会在备份目录里留下一份占名额的 0 字节 `.zip`。现于 `internal/atomicfile` 新增 `PublishNew(tmp, path)`（与 `Replace` 的唯一区别是不覆盖已有目标）：Windows 端在刷盘和调过 `Hook` 之后直接调不带 `MOVEFILE_REPLACE_EXISTING` 的 `MoveFileEx(tmp, path, MOVEFILE_WRITE_THROUGH)` 一步到位，目标已存在时系统当场返回 `ERROR_ALREADY_EXISTS` / `ERROR_FILE_EXISTS`（满足 `errors.Is(err, fs.ErrExist)`），不重试、不动目标，临时文件被占着时仍按 `retryDelays` 重试；非 Windows 端在 `replace_other.go` 里保留 `O_EXCL` 占位加 `os.Rename`（POSIX 改名不怕目标被打开，不用 `os.Link` 是为了兼容 Mac 用户外置的 exFAT 等不支持硬链接的移动盘）。`internal/inst/backup.go` 的 `createBackupWith` 改回在压缩开始前先调一次 `backupNow()` 定下首个候选文件名，传入 `zipDirsExclusive` 调 `atomicfile.PublishNew` 发布，只有撞上 `fs.ErrExist` 时才在重试轮次里用当时的 `backupNow()` 重取。
- **R2、R3、R4（只读退路的入口注释、用例覆盖与文档说明）**：把 `internal/atomicfile/replace_windows.go` 第 194 行附近的注释按实测改正——`MoveFileEx` 面对只读目标时一律报 `ERROR_ACCESS_DENIED`，只有在临时文件被占着时才报 `ERROR_SHARING_VIOLATION`，入口放行共享冲突兜住的是「目标只读、而临时文件此刻被短暂占着」的情形；在 `replace_retry_windows_test.go` 新增 `TestReadOnlyTargetWithHeldTempRetriesUntilReleased` 守住这一支。同时改写「间隔表计数与非占用错误直返」子用例：先用独占句柄占住只读目标让代码真正走进 `replaceReadOnly`，再由 `beforeReadOnlyRetry` 在第 1 次重试前删掉临时文件并放开目标，确认退路内部遇到 `ERROR_FILE_NOT_FOUND` 这类非占用错误时只试 1 次就当场返回。顺带更新 `TestOriginallyReadOnlyTargetIsNotRetried` 的注释（写明 `setRetry` 只统计 `MoveFileEx` 那条路的重试）以及 `atomicfile.go` 里 `Write` / `WriteProtected` 关于只读退路重试的说明。

第二个提交 `ed2b09b` 单独处理 R5 与 R6（只改 `cmd/minedeck/` 下单实例相关的四个文件，方便需要时与上一轮的 `2026011` 一并撤回）：

- **R5（审核方调整后的单实例检查规格）**：复审确认应用内更新脚本 `swapScript` 只有在 `move /y` 换 exe 成功（旧进程必已退出）或换不了但旧进程号已消失时才会启动新进程，不必为更新留 10 秒等待，反倒是程序收在托盘里被用户再次双击时干等 10 秒体验不好。照审核方改定的规格，把默认等待从 10 秒改为 3 秒（兜住刚从托盘退出、马上又双击的收尾窗口）；提示文案改为「这个文件夹里的 MineDeck 已经开着了。如果刚关掉它，等几秒再打开。」；被拦下时先向标准错误写出这句话，带 `-nogui` 或 `-minimized` 启动时（脚本、无桌面计划任务、开机自启）不弹系统提示框以免无人点击挂死或打扰用户，随后统一以退出码 `1`（`os.Exit(1)`）退出，且仍在 `app.Init()` 之前返回，绝不触碰数据文件。
- **R6（消除单实例测试的数据竞争）**：`cmd/minedeck/singleinstance_windows_test.go` 里模拟旧实例延迟释放的后台协程不再改写外层 `defer` 读取的局部变量 `relA1`，改为通过 `relDone` 通道等待后台协程彻底退出（`relA1` 内部已有 `sync.Once` 保证重复调用安全）。

### 对上一份日志 `2026-11-22-阶段02-文件写入、锁和重试.md` 的两处更正

上一份日志按规矩保持原样不改，这里更正其中两处：

1. **A19 的 Win32 错误码来源说反了**：上一份日志第 17 行写「当只读文件同时被独占句柄占着时，前面的 `MoveFileEx` 会先报 `ERROR_SHARING_VIOLATION` 而非 `ERROR_ACCESS_DENIED`，连扩展改名退路都进不去」。经复审方实测核对，这句话不对：目标文件只要是只读的，不管有没有被占、哪怕被独占句柄占着，`MoveFileEx` 报的都是 `ERROR_ACCESS_DENIED`，本来就能进只读退路；当时复现用例看到的 `ERROR_SHARING_VIOLATION` 其实是进退路以后 `SetFileInformationByHandle(FileRenameInfoEx)` 报出来的。`MoveFileEx` 报 `ERROR_SHARING_VIOLATION` 只发生在**临时文件**被占着的时候，因此在退路入口一并放行 `ERROR_SHARING_VIOLATION` 实际保护的是「只读目标 + 临时文件被短暂占用」，这一轮已把代码注释和对应单测补齐。
2. **漏记了备份文件名取时间时机的变动**：上一轮 `e4ea981` 把生成备份文件名时调用 `backupNow()` 的时机从「压缩开始前」挪到了「压缩完成后发布时」，上一份日志没有写明这一行为变化；大世界压缩耗时几分钟时，备份文件名里的时间会比实际发起备份晚几分钟。这一轮已在 `8bcc6b4` 里改回压缩开始前先取一次时间作为首个候选名，只有发布撞名时才按发布当刻的时间重取。
