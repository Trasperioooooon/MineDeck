# v3.3.0-beta.1 下载与更新整改

2026-11-27 作者提了四个问题：软件更新现在还走 GitHub，其实可以走官网；加了 Forge、NeoForge 的国内镜像，大陆用户还是反馈下载老断、要重试好多次；下载到一半彻底失败的，不能重新下载部署，好像也没有清理的按钮；Java 出错时，能下载 Java，但不能修复或重新下载。主会话查了代码，给了改法和推荐的取舍，作者说「需要定的几个点都按照你的推荐来」，又说「不开工，这些都只做记录，等我们UI彻底好了，在v3.3.0beta.1版中一次性去修复这些问题」。

所以这份只是记录。下面写的是现在的程序怎么做、问题在哪、打算怎么改、作者已经认了的取舍。动手是在界面重构做完以后，和界面一起随 v3.3.0-beta.1 发。调查的经过在日志 `docs/日志/2026-11-27-下载和更新问题调查.md`。

## 一、软件更新改走官网

现在的更新分三步，都在 `internal/update/update.go`。检查有没有新版本只问 GitHub 的接口（`api.github.com`），没有镜像。拿官方 SHA-256 的那一步，代码里规定必须直连 GitHub，理由是第三方加速站可以把 exe 和校验值一起换掉。只有下载 exe 本身经过 ghfast.top、gh-proxy.com 两个加速站，最后才直连。这样一来，大陆用户多半在前两步就卡住了：要么报「检查更新失败（连不上 GitHub）」，要么报「拿不到这个版本的 SHA256SUMS」、取消更新，后面那两个加速站根本用不上。GitHub 接口不登录时每个 IP 每小时只给 60 次，校园网、运营商大内网共用一个出口的用户还可能被限流。

官网这边的东西是现成的。`https://minedeck.cn/data/latest.json` 里有稳定版和测试版各自的版本号、大小、SHA-256、dl.minedeck.cn 的下载地址和 GitHub 地址，由 `website/build.mjs` 生成。SHA-256 是官网构建时从 GitHub 接口给附件算的摘要里取的。部署时服务器还会经自己的 Nginx 把镜像文件逐个对一遍 SHA-256。11-27 取过一次，v3.2.9 和 v3.2.0-beta.5 的校验值都在。

改法：检查更新时官网和 GitHub 都问，取版本号新的那个；哪边问不到就用另一边的。下载顺序是 dl.minedeck.cn 在前，后面接原来的 ghfast.top、gh-proxy.com、GitHub 直连。

作者认了的取舍：

- **校验值以 GitHub 为准，连不上才信官网。** GitHub 能连上时，仍按它的 SHA256SUMS 核对，官网给的和它对不上就拒绝更新；GitHub 连不上时才用官网 latest.json 里的 sha256。这样大陆用户能更新，海外用户的安全性和现在一样。没选的两种：一种是全信官网，那台服务器一旦被人拿下就能给所有用户推假 exe；另一种是给每个版本签名、程序里内置公钥，要作者保管私钥、改发布流程。
- **时效。** latest.json 只在部署官网时更新。发了版、官网没部署，连不上 GitHub 的用户就看不到新版本。作者现在每次发版都更新官网，照这个习惯就行。发版说明的流程里加一句「发完记得部署官网」。
- **更新说明。** latest.json 里没有更新说明，程序的更新页要显示说明，官网构建脚本得补一个字段（或者程序去 releases.json 取 summary）。
- **测试版渠道要对齐。** 官网的 beta 取的是最新发布的那个预发布版，程序的测试版渠道取的是版本号最大的那个，平时一样，改的时候按程序的规矩比。
- **从哪一版起生效。** 已经装在用户电脑上的旧版本只认 GitHub，这个改动从 v3.3.0-beta.1 起才有用。在那之前，大陆用户要去官网手动下一次，发布说明里写上。Mac 版不能在程序里更新，不受影响。

## 二、下载老断

代码里能确认的原因有四条。

第一条最要紧。创建失败以后，整个服务器文件夹会被删掉（`internal/inst/creating_leftover.go` 的 `discardCreatingDir`）。Forge、NeoForge 的依赖库是官方安装器自己下的，就下在这个文件夹里，于是跟着一起删了。失败页上那句「已下载的文件有缓存，再试一次很快」，对 Java、安装器和原版服务端是真的，它们放在共享缓存里；对依赖库不是。以 NeoForge 21.1.77 为例，安装器要下 135 个依赖库，约 41MB，96 个在 maven.neoforged.net，39 个在 libraries.minecraft.net。用户每重试一次，都要从零开始，在安装器最多跑 3 次之内把这些全拉下来，网络一抖就白费。「要重试好多次」很可能就是这么来的。

第二条，依赖库不归 MineDeck 自己的下载逻辑管。安装器只是带了 `--mirror` 指向 BMCLAPI，它下哪个文件断了就整个退出，MineDeck 只会把整个安装器重跑 3 次（`internal/inst/install.go` 的 `runInstaller`）。我们的换源、重试、进度提示都管不到这一段。

第三条，下载不能断点续传（`internal/dl/dl.go` 的 `fetchOne`）。断一次就从零开始，每个文件最多 3 轮、每轮把几个源试一遍。文件越大越难一次下完，比如原版服务端约 50MB，Java 有几十到上百 MB。

第四条，Forge 1.17 以后的版本没有提前放好原版服务端。NeoForge 和 1.16.5 以前的 Forge 都放了，这几个版本却由安装器自己去 Mojang 下那 50MB。这段从 v2.0.0 起就是这样，看着像当初漏了。NeoForge 安装器里写着它找原版服务端的路径是 `libraries/net/minecraft/server/<版本>/server-<版本>.jar`，Forge 1.17 以后应该是同一条，改之前拿一个 Forge 1.20.1 的安装器实测确认。

还有一条是推测，从日本验证不了。BMCLAPI 收到下载请求后会跳到别的节点。11-27 从日本测，它把请求分到志愿者节点（bmclapi*.sakura.sld.tw）、高校镜像（mirrors.qlu.edu.cn、mirrors.cernet.edu.cn），原版服务端有时直接跳回 Mojang 官方。小文件从 BMCLAPI 拿，首字节要 1.3 到 5.4 秒；从官方拿，只要 0.3 到 0.5 秒。测到的节点都支持断点续传。大陆用户会被分到哪里、哪些节点会断，要靠下面的测试脚本拿结果。

**第一批要改的：**

- 依赖库放进共享缓存。安装器跑之前，把缓存里有的依赖库放进服务器文件夹；跑完以后，不管成没成，都把已经下好的收回缓存，按 install_profile 里的 SHA-1 核对。这样重试只补缺的。
- 下载支持断点续传。只在有校验值（或者服务器给了 ETag，用 If-Range 续）的时候续；换了节点可能拼出坏文件，所以最后整体校验，对不上就删掉从头下。没有校验值的文件不续。
- Forge 1.17 以后也提前放好原版服务端。
- 安装失败时，把安装器的日志 installer.jar.log 留一份到程序的日志目录。现在这份日志在服务器文件夹里，跟着文件夹一起删了，用户反馈时拿不出来。

**第二批：** 依赖库改由 MineDeck 自己先下好，安装器只做本地处理那一步。做法是读安装器里的 install_profile.json 和 version.json，按官方 SHA-1 逐个下到 libraries 里，安装器看到文件在、校验对得上就不再下。HMCL、PCL 就是这么做的。这样全部下载都归我们的换源、重试、续传和进度提示管。安装器的处理器还会去 Mojang 下映射表（install_profile 里的 MOJMAPS），这一项也要一起预下。

**拿大陆的实测结果：** 测试脚本是 `tools/cn-net-test/MineDeck下载测试.bat`，用法和它记什么、不记什么，写在同目录的 README 里。作者把它发给大陆用户，收回来的结果用来定 BMCLAPI 和官方谁排前面、哪些节点要避开、续传值不值得先做。

## 三、失败以后的重试和清理

现在已经有的：创建、导入失败以后，半成品文件夹会自动删掉；删不干净的会出现在服务器页上方「没建完的文件夹」里，有删除按钮。失败页有「返回修改」，回到向导最后一步，填过的都在，再点创建就是重来。所以清理大多是自动的，界面上没有单独的清理按钮。

真缺的有下面几样：

- **失败页没有一键重试。** 「返回修改」依赖的表单只存在网页的内存里（`app.js` 的 `formDrafts`），程序重启、页面刷新、离开这一页，表单就没了，只能从头走一遍向导。要改成后端任务记住这次的请求，存到硬盘上，失败页给「重试」，原样再提交一次。新草图的任务页（`design-system/redesign/task.html`）已经画了「重试」，但画的是有表单草稿才出现；后端记住了请求以后，没有草稿也能出，审 task.html 时一起定。
- **失败页那句「再试一次很快」。** 依赖库进缓存以前，这句话对 Forge、NeoForge 不成立。第二节第一条做了以后才算对。
- **装了一半却登记了的服务器（放进第二批）。** 安装器以 0 退出、但没说装成功时，这台服务器照样进了列表，开不起来时只能删了重建。要加「重新安装核心」：只重下核心、重跑安装器，不碰世界和配置。
- **下载缓存没有清理入口（不急）。** 缓存按校验值复用，坏不了，只是占空间。可以在设置的「存储」里加一个，看占了多少、一键清掉。

## 四、Java 修不了、重下不了

作者的原话：「有时候会遇到java错误的问题，我们可以下载java但是不能修复或者重新下载」。

现在的程序，判断一套便携 Java 装没装好，只看 `bin\java.exe` 在不在，再加一个「还没装完」的记号（`internal/java/java.go` 的 `IsInstalled`）。装到一半中断的会重装；装完以后才坏的，比如杀毒软件删了里面的文件、磁盘出错，照样算装好，开服时报的是 JVM 自己的错，MineDeck 也不会重新下载。设置里的 Java 那一页有「卸载」，但有服务器在用或配着它时会拦下，所以这种情况下，用户连「先卸了、让它重下」都做不到，只能手动删文件夹。另外，新建服务器时优先用电脑上自己装的 Java（`internal/java/scan.go` 的 `Resolve`），那一份坏了也照用。

要改的：

- 便携 Java 加「检查」：跑一次 `java -version`，看能不能起来、报出来的大版本对不对。开服前和设置页都可以用。
- 加「重新下载」：先下到旁边的临时文件夹，装好、检查过了再换上去。有服务器配着它也能换，换的是同一个路径，服务器设置不用动。
- 开服失败时，报错规则认出 JVM 起不来的那几种报错（找不到 java.dll、虚拟机初始化失败、类文件版本不对等），给一个「重新下载这个 Java」或「换一个 Java」的入口。
- 电脑上自己装的 Java 检查不过时，改用便携版，并在任务日志里说一句。

## 动手时的顺序和验证

界面重构做完以后再开工。先做第一节、第二节第一批、第三节的一键重试和第四节，第二批（MineDeck 自己预下依赖库、重新安装核心）看大陆测试结果和工作量再定是不是也放进 v3.3.0-beta.1。动手之前在仓库外编一份测试程序，实装 Forge 1.20.1 和 NeoForge 1.21.1，确认安装器认得提前放好的原版服务端和缓存里的依赖库；断点续传、重试和 Java 重新下载要有单元测试，下载中途断开用本地的假服务器模拟。更新这一块，改完用真程序从 v3.2.9 点一次更新，GitHub 连得上和连不上（拦掉 GitHub 的地址）各试一次。
