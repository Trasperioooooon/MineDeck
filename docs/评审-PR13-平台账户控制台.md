### 三、复审重点逐项回答

#### 1. 凭据安全

算法和密钥：OpenFrp 的 Authorization 和樱花的访问密钥用现有的 `secret.Store` 存进程序目录下的 `secrets.json`，键名 `tunnel.openfrp.authorization`、`tunnel.sakura.token`（`internal/tunnel/accounts.go:24-25`）。加密是 Windows DPAPI（`CryptProtectData`，当前 Windows 用户的密钥，带固定附加熵，`internal/secret/dpapi_windows.go:11,36-43`），程序自己不保存密钥。从平台取回的 frpc 密钥经 `Manager.Add` 再用 DPAPI 封一遍存进 `tunnels.json`（`internal/tunnel/tunnel.go:270-274`），列表和返回值都清空凭据（`tunnel.go:211,283`）。OpenFrp 远程授权用 NaCl box（X25519 + XSalsa20-Poly1305）解密服务端返回的 Authorization，临时私钥只在内存，5 分钟过期。

明文：没有明文落盘。操作记录按键名脱敏，`token` 会写成 `***`（`internal/ops/oplog.go:187-195`），轮询和读操作不写记录。错误信息只带对方的 msg（截到 240 字节）和 Go 的网络错误，凭据都在请求头里，不在 URL 里。返回前端的 `AccountInfo`、`AccountOverview`、`AccountTunnel` 没有 token 字段（`accounts.go:94-135`）。

换机器或重装：DPAPI 绑定 Windows 用户，换电脑、换用户、重装系统后解不开，`Status()` 会报"未连接"，重新连接即可覆盖，不会卡死。但它丢掉了"读不出来"这个标志（`accounts.go:214-218`），用户看不到原因；已导入的隧道走现有的"凭据解不开"提示。MineDeck 是便携软件，这个行为和项目里其他密钥一致。

两个凭据写入的漏洞见"必须改 M5"。

#### 2. 「账户写操作仅限本机」

实现：本机判定只看 TCP 连接的 `RemoteAddr` 是不是回环（`internal/web/hostonly.go:9-18`），写操作由操作层的 `LocalOnly` 统一拦（`internal/ops/ops.go:277-282`）。外层的 `secure()`（`internal/web/server.go:141-170`）还要求：没开局域网访问时，Host 必须是 127.0.0.1、localhost 或 ::1 且连接来自回环；所有 `/api/`（登录除外）要带本次启动随机生成的 Token，或者局域网会话 Cookie（HttpOnly、SameSite=Lax）。服务默认只监听 127.0.0.1，开了局域网访问并设了密码才监听 0.0.0.0（`cmd/minedeck/main.go:74-79`）。

能不能绕过：DNS rebinding 在非局域网模式被 Host 校验挡住；局域网模式下 Host 不校验，但攻击页拿不到 Token，Cookie 按主机名隔离也带不上。跨站 CSRF 需要自定义请求头或 Token，Cookie 是 Lax，带不上。伪造 Host 或 Origin 没用，本机判定看的是连接来源，不看请求头。局域网设备登录后算 `SrcLAN`，七个写操作都被拒（`internal/ops/catalog/accounts_test.go` 有覆盖）。

开服后的暴露：给 Minecraft 端口开隧道不会把管理界面带出去。但读接口没有限本机：`status`、`weblogin`、`overview`、`captcha`、`purchase`（`internal/ops/catalog/accounts.go:22,67,97,111,143`），而 `Human()` 把局域网会话也算作人（`ops.go:60`）。所以知道局域网访问密码的设备能看到平台用户名、流量、平台隧道列表和公网地址，每次看概览还会用本机保存的凭据向平台发四个请求，OpenFrp 轮换 Authorization 时这次"读"还会改写 `secrets.json`。不会泄露 token，但"账户接口只给本机"的印象不成立，见"建议改 S1"。

原有设计里的一点（不是本 PR 引入）：既然本机判定只看连接来源，如果有人建一条隧道把 MineDeck 自己的管理端口（默认 27333）映射出去，外来请求经 frpc 进来就是回环地址。仍然需要 Token 或局域网密码才能进，但 `LocalOnly` 会失效。本 PR 的创建接口对本地端口没有限制（`accounts.go:713`），原有的自定义隧道同样能这样配，所以只列为可选加固。

#### 3. 验证码 iframe

隔离方式：主界面在 `http://127.0.0.1:端口` 时，iframe 指向 `http://localhost:端口/captcha.html`，反之亦然（`internal/web/ui/app.js:3293`），靠主机名不同形成跨 origin；sandbox 是 `allow-scripts allow-same-origin allow-forms`（`app.js:3304`），不允许弹窗和顶层跳转。API Token 存在主界面那个主机名的 localStorage 里（`app.js:9,13`），iframe 读不到。

postMessage：这部分写得对。父页面校验 `event.source` 是这个 iframe、`event.origin` 精确等于预期、频道名和 16 字节随机 nonce 都对得上，token 有长度上限（`app.js:3327-3329`）；iframe 发消息时指定了目标 origin（不是 `*`），并校验 parent 参数是回环主机、协议端口一致、且等于 `document.referrer` 的 origin（`captcha.html:20-32`）。

CSP 和远程脚本：整个项目没有任何 Content-Security-Policy，`captcha.html` 也没有。远程只加载一个脚本 `https://cv.naids.com/sdk/load.min.js`，前后端都校验了协议和主机名，没有 SRI（这种会再拉子资源的加载器也很难用 SRI 管住）。

问题在于：这个第三方脚本跑在 `http://localhost:端口`，这是 MineDeck 自己 HTTP 服务的 origin。它对 `/api/` 发的请求是同源、来自回环的，服务端会当成本机界面。现在挡住它的只有"它拿不到 Token"：同一个浏览器配置、同一次启动里，如果两个主机名都带 Token 打开过界面，这层隔离就没了；另外 `/api/login` 不需要 Token，脚本可以同源去试局域网访问密码（有每来源 0.7 秒的限速）。宿主绑定（`hostOpenURL`、`hostWinQuit` 等）能不能从 iframe 里调到，未确认：go-webview2 只在顶层 `CoreWebView2` 上注册了 `WebMessageReceived`（模块 `pkg/edge/chromium.go:201`），也没有订阅子框架事件，按 WebView2 的文档子框架的消息不会送到这里；但注入绑定桩的 `AddScriptToExecuteOnDocumentCreated` 会不会在子框架里也执行、运行时实际怎么投递，我只看了注册的地方，没在真机上验证。M2 按"可能调得到"来定级，并列进实测清单。

调研笔记自己前后矛盾：`docs/frp-account-api-notes.md:156` 说 iframe 不带 `allow-same-origin`、是 opaque origin，`:486` 和代码说的是带 `allow-same-origin` 加主机名别名。

#### 4. 第三方 API

官方还是逆向，逐个分：

- OpenFrp 远程授权 `access.openfrp.net/argoAccess/requestLogin`、`pollLogin`：官方 OPENAPI 第 1 节写明，是官方推荐给第三方客户端的登录方式。
- OpenFrp `getUserInfo`、`getUserProxies`、`getNodeList`、`newProxy`：官方 OPENAPI 有。
- OpenFrp `userSign`：官方 OPENAPI 第 9 节有，但写明"近期加入人机验证，内容暂不可供参考"。
- OpenFrp `getSignInfo`：官方 OPENAPI 没有，取自控制台前端。
- OpenFrp 验证码 appId `app_a287…`：从 `console.openfrp.net` 的网页里取的，是控制台自己的 appId。
- 樱花 `api.natfrp.com/v4` 的 `/user/info`、`/nodes`、`/tunnels`：官方公开 OpenAPI，访问密钥鉴权。
- 樱花 `www.natfrp.com/cgi/user/login` 和 OpenID 的 `client_id`：笔记自述是静态探测和混淆脚本还原得来，不在任何公开文档里。

条款：OpenFrp 官方 OPENAPI 对第三方客户端的要求有五条（以下都在官方 README 原文里逐字核对过）：请求 OPENAPI 或相关资源站点必须带应用程序 UA，否则可能被防火墙拦截，也可以把 UA 提交给第三方开发者交流群；必须在项目的明显可见位置注明使用 OpenFrp OPENAPI；要在项目有关位置加上"此项目由社区开发，OpenFrp 官方不负责除节点问题以外的技术支持"，并尽可能附上技术支持方式；不应设计自动签到，自动签到属于滥用、违反服务条款；用 OPENAPI 做商业活动必须有 OpenFrp Project 项目组的书面授权。PR 做到了 UA（`MineDeck/<版本>`）、界面上的社区声明和不自动签到；README 没有注明，声明里没有附技术支持方式，UA 没有提交。另外官方文档写着 Authorization "请求任意接口时，有概率返回新值"、最长有效期 30 天，但没说新值放在哪个响应头，PR 按 `Authorization` 响应头处理是猜的。复用控制台的验证码 appId 是否被允许，文档没说，需要问 OpenFrp。樱花这边，公开游戏服务器只能用特定节点，PR 在后端用"节点 flag 第 11 位或节点名含「多线」"来判断（`accounts.go:677,819`），这和樱花官方 API 定义写明的判定条件一致（违反会封号且不退款），但界面根本没有把"公开服"选项接上（见 S5）。以上请法务一并看：内嵌签到、复用 appId、笔记里的逆向探测记录、OpenFrp 的商业使用条款（MineDeck 是否有任何收费或捐赠形态）。

频率和错误处理：HTTP 客户端 20 秒超时、不跟随跳转（`accounts.go:74-79`），响应最多读 2 MiB（`:1091`），没有任何循环重试，也没有定时任务。授权轮询前端 5 秒一次，服务端另有 5 秒节流和 5 分钟过期（`:285-295`），符合官方"5 秒一次、最长 5 分钟"的要求。签到只在用户点按钮后调用。不足：一次概览要连发四个请求且不缓存（`:584-618`），签到后前端还会重复拉概览（`app.js:3600-3615`）；429 没有专门的提示（`responseError`，`:1098-1108`）。

#### 5. 代码质量

没有新起 goroutine，请求都带调用方的 context，HTTP 客户端有超时，`pending` 表的读写都在锁里，过期项在下次发起登录时清掉，没看到泄漏。错误提示是中文、说得清楚，失败时多数会告诉用户下一步（比如"OpenFrp 已创建隧道，但无法唯一识别新隧道；请刷新平台隧道列表后手动导入"）。

没有误删或回退 main 上的改动：PR 只有两处删除行，是 `main.go` 和 `routes_test.go` 里构造注册表的那一行被替换成带 `Accounts` 的版本。和现有隧道逻辑一致：导入和创建最终都调 `Manager.Add`，凭据加密、frpc 下载（包括 main 上 567 的修复）、绑定实例、跟随启动全部复用；账户接口全部经操作层登记，和项目其他接口一个写法。

测试：Go 测试用 httptest 假服务覆盖了远程授权的加解密、概览、签到、创建、导入、樱花连接，操作层测试覆盖了"仅人工、仅本机、AI 拿不到"。缺的是：Authorization 轮换、登录过期和授权地址不在 `console.openfrp.net` 时的拒绝、断开与在途请求的竞争、导入重复、中文隧道名、樱花创建请求的格式（mock 不看 Content-Type）、真实的 `captcha.html`（界面测试把它整个换成了假页面）。

**M5. 凭据写入的两个漏洞。**
文件：`internal/tunnel/accounts.go:959-963`，`:339-347`，`:406-418`。
原因：其一，OpenFrp 轮换的 Authorization 在判断状态码之前就写盘，也不做登录时那样的长度和换行校验（对比 `:336`），401 或 5xx 响应里带的头也会覆盖已保存的凭据。其二，断开和在途请求有竞争：授权轮询或某个 `openFrpPost` 正在进行时用户点"断开"，请求回来后仍会把授权写回去，用户看到的是"断开了又自己连上了"。

#### 建议改

**S1. 账户读接口对局域网会话开放，界面在局域网下也显示全部按钮。**
文件：`internal/ops/catalog/accounts.go:97`（overview）及 `:22,67,111,143`；`internal/web/ui/app.js:3345` 起的 `paintAccCards`。
原因：见第 3 节第 2 点。知道局域网访问密码的设备能看到平台用户名、流量、隧道列表和公网地址，每看一次概览都用本机凭据向平台发四个请求，还可能由这次"读"改写 `secrets.json`；局域网打开时界面照样显示签到、创建、导入按钮，点了才报 403。

**S2. （只在日后经 OpenFrp 同意、保留 OpenFrp 签到状态时适用）"连续 N 天"其实是累计签到次数；"今日已签"按本机时区算。**

原因：PR 自己的笔记写 `totalsign` 是累计签到次数，界面却显示成"连续 N 天"；OpenFrp 的日期按北京时间，不在东八区的用户在日界附近会看到错误的"今日未签"。按 M1 拿掉 `getSignInfo` 后这一条自然消失。
改法：字段改名为累计次数，界面写"累计签到 N 次"；日期按 `time.FixedZone("CST", 8*3600)` 计算。樱花的 `sign.days` 才是连续天数，两边分开。

**S3. 导入时隧道编号没有规范化。**
文件：`internal/tunnel/accounts.go:848-867,888-891,920`。
原因：用 `Atoi` 匹配平台隧道，存的却是用户传来的原字符串，"007"能匹配 7 号隧道并绕过重复检查，原样进入 frpc 的命令行参数。

**S4. 导入总是按"游戏"用途。**
文件：`internal/web/ui/app.js:3694`。
原因：UDP 语音隧道导入后被当成游戏隧道，公网地址不会写进实例的 `voice_host`。
改法：按平台隧道的类型推断（UDP 默认语音），或在导入对话框里让用户选；后端在 `purpose` 为空时已经会推断，前端不传即可。

**S5. "公开服"规则只做了一半。**
文件：`internal/tunnel/accounts.go:624`（OpenFrp 所有节点写死 `PublicGameAllowed: true`）、`:677,819`（樱花的判定），界面从不发送 `publicServer`。
原因：樱花官方 API 定义在「创建隧道」的说明里写明，公开游戏服务器只能用 `flag & 2048 != 0` 或名称含「多线」的节点（「三线」不算），违反会封号且不退款。后端的判定和官方一致（复审时我误以为按名称判断不可靠，已更正），但界面从来没让用户说明是不是公开服务器，这条检查等于没生效。
改法：在樱花的创建对话框里加"这是公开服务器"选项，解释官方的节点要求，勾选后只列符合条件的节点、请求带 `publicServer`；OpenFrp 没有对应的公开规则，不显示这个选项。

**S6. 概览不缓存，429 没有专门提示。**
文件：`internal/tunnel/accounts.go:584-618,1098-1108`，`internal/web/ui/app.js:3600-3615`。
原因：每开一次概览向 OpenFrp 连发四个请求，签到、创建、导入之后前端还会再拉，签到后甚至拉两次；官方文档写明超出请求阈值会全部返回 429，而现在 429 只显示成笼统的"穿透平台返回 HTTP 429"。
改法：概览在后端按账户缓存 30 到 60 秒；429 映射成"请求太频繁，稍等再试"；签到后的刷新只拉一次。

**S7. 樱花流量没有单位；错误信息按字节截断。**
文件：`internal/tunnel/accounts.go:1195`，`:1110-1116`。
原因：`今日已用 %d · 剩余 %d` 直接打印接口返回的整数，用户看不出是字节还是 MiB；`safeMessage` 用 `s[:240]` 按字节截，平台返回的中文报错可能被切成半个字，界面上出现乱码。
改法：按官方文档的单位格式化（MiB/GiB）；`safeMessage` 按字符截断，免得把中文切成半个字。

**S8. 断开账户的说明不准确，换电脑后没有原因提示。**
文件：`internal/web/ui/app.js` 的 `disconnectAccount` 确认框，`internal/tunnel/accounts.go:214-218`。
原因：樱花导入隧道里的凭据就是账户访问密钥本身，断开账户并不会清掉它；断开也不会在平台侧作废授权。换电脑后密钥解不开，界面只显示"未连接"。
改法：确认框写明"已导入的隧道仍保存着密钥，要彻底清除请删除这些隧道，并到平台作废访问密钥或授权"；`Status` 把"读不出来"也带回前端，显示"需要重新连接"。

**S9. 文档和署名。**
文件：`README.md`、`README_EN.md`、`docs/功能清单.md`、`docs/API.md`。
原因：OpenFrp 官方要求在项目明显可见位置注明使用了 OpenFrp OPENAPI，社区开发声明要尽可能附技术支持方式；项目惯例是新功能写进功能清单；`docs/API.md` 里"iframe 无法读取父页面 localStorage"等说法要和最终实现对上。
改法：README 加一段 OpenFrp OPENAPI 说明和社区开发声明（附上 MineDeck 的 issue 地址作为技术支持方式）；功能清单"内网穿透"一节补平台账户；API.md 随 M1 到 M3 同步。要不要把 `MineDeck/<版本>` 这个 UA 提交给 OpenFrp 的开发者交流群，由维护者决定、由维护者去做，不放进这个 PR。

### 第一轮

结论：**不建议直接合并。** 未发现账户锁死锁或正常成功响应直接返回凭据，但发现“仅本机”权限可经隧道转发绕过、日志脱敏遗漏、授权撤销竞态，以及两处明确的前端功能问题。

本次仅做静态只读审查：未修改文件、未运行测试、未联网、未调用其他 Agent。以下行号均对应当前工作目录源码。

**1. 并发和凭据写入：部分正确，仍有中等严重程度问题**

- **锁顺序未见死锁。** 账户写入采用 `a.mu → secret.fileMu`；`Store.Get/State` 在返回前释放 `fileMu`，secret 包也没有反向获取 `a.mu` 的回调。证据：`internal/tunnel/accounts.go:372、436、451、938`；`internal/secret/secret.go:116–126、130–155`。
- **未发现持有 `a.mu` 发网络请求。** Poll 在第 329 行解锁后请求；樱花连接在请求完成后才加锁；Authorization 换发也在请求完成后加锁。证据：`internal/tunnel/accounts.go:329–332、428–436、924–938`。锁内存在 DPAPI 和文件写入，但不是网络请求。
- **Poll 的 defer 顺序正确。** 第 373 行登记的 `Unlock` 先于第 330 行的 `clear(privateKey[:])` 执行。后者清理的是第 328 行复制出来的局部数组；共享私钥仍在锁内清理，没有重复加锁或清零竞态。
- **连接代数没有覆盖完整生命周期。** `ConnectSakura` 的“取代数—请求—持锁检查并写入”正确；Disconnect 的删除、清 pending、增加代数也处于同一临界区。但 OpenFrp 读取凭据和读取代数不是原子操作，可能在断开后重新写回旧账户授权；Begin/Poll 也没有完整绑定登录代数。详见 M3、M4。
- **缓存对连接变化的写入检查正确，但失效语义不完整。** 第 496 行能阻止断开前的结果进入新代数缓存；不过仍会返回该旧结果。创建/导入只删除缓存、不增加缓存版本，在途旧概览可以随后重新填入缓存。证据：`internal/tunnel/accounts.go:245–249、478–500、705–706、885–887`，严重程度低，见 S2。

**2. 凭据保密：正常路径通过，但存在确定的日志明文路径〔中〕**

账户凭据先经 DPAPI 加密再写文件；导入隧道的客户端凭据也先加密。成功响应使用不含凭据的账户结构，隧道返回值会清空 `Credential`。证据：`internal/secret/secret.go:145–178`；`internal/tunnel/tunnel.go:203–211、266–284`；`internal/tunnel/accounts.go:107–156、1178–1188`。

但不能认定“凭据不会明文落盘”：

- **确定遗漏：** `redact` 遇到同时含 `key`、`value` 的对象，会停止遮盖同级 `token` 字段；账户接口允许额外字段保留到日志。详见 M2。
- **条件性泄露：** `safeMessage` 只截断、不脱敏。平台若在错误 `msg` 中回显凭据，该内容会进入错误 JSON；连接、创建、导入等操作还会把错误原文写入操作日志。证据：`internal/tunnel/accounts.go:955–956、1021–1022、1084–1096`；`internal/ops/ops.go:451–455`；`internal/web/server.go:224–234`。未验证真实平台是否会回显，见 S1。
- OpenFrp、樱花的 frpc 密钥仍出现在进程参数中，这是已有实现明确记载的限制；启动代码没有直接打印这些参数。证据：`internal/tunnel/providers.go:198–226`；`internal/tunnel/tunnel.go:502、518`。

**3. “仅本机”：直接请求限制有效，但组合边界可绕过〔高〕**

`login、poll、natfrp.connect、disconnect、overview、create、import` 共七项是 `HumanOnly + LocalOnly`，因为它们修改凭据或使用本机凭据访问平台。证据：`internal/ops/catalog/accounts.go:32、40、54、71、87、129、156`。

`status、sign、purchase` 允许已认证局域网会话调用是合理的：status 只返回连接/可读性布尔值；另外两项只返回固定官网链接，不执行签到、购买或平台请求。证据：同文件第 `24、101、115` 行；`internal/tunnel/accounts.go:209–212、505–540`。

访问边界具体表现为：

- **直接局域网请求、单纯伪造 Host：不能获得 LocalOnly 权限。** `Local` 根据 `RemoteAddr` 判断，不采用 Host 或转发头。证据：`internal/web/hostonly.go:9–17`；`internal/web/server.go:246–258`；`internal/ops/ops.go:276–281`。
- **LAN 关闭时，DNS rebinding 的非本地主机名会被拒绝。** LAN 开启时不再校验 Host，但 API 仍要求有效 Token 或会话。纯 rebinding 不等于绕过认证；若已有有效 LAN 会话的请求经本机浏览器重绑定或本机代理转入，则会被判为本机。
- **普通跨站写请求受到 Token、浏览器同源限制和 `SameSite=Lax` 约束，但服务端没有独立 Origin 校验。** 有登录 Cookie 时，跨站顶层 GET 可以触发概览，外站通常不能读取响应。证据：`internal/web/server.go:145–168`；`internal/web/auth.go:141–143`。
- **已确认的组合绕过：** 普通隧道添加/启动允许 LAN 用户操作，可以建立指向管理端口的本机转发；携带原 LAN 会话沿隧道进入后，账户操作被认作本机。创建账户隧道时的端口检查没有覆盖这条路径，也没有覆盖账户隧道导入。见 M1。

**4. 输入校验：主要校验正确，管理端口保护不完整〔高〕**

OpenFrp 名称正则、正整数隧道编号规范化、创建端口范围、TCP/UDP 类型及 provider 白名单均有后端检查。未知 provider 不会被用于拼接平台主机地址。证据：`internal/tunnel/accounts.go:48、657–703、811–817、825–869`。

凭据禁止 CR/LF，平台地址固定，HTTP 客户端拒绝重定向；frpc 使用参数数组启动，没有经过 shell。未发现本次账户路径可通过名称、编号或 provider 注入命令行参数或 HTTP 头。证据：`internal/tunnel/accounts.go:89–93、215–217、1051–1063`；`internal/tunnel/providers.go:201、226`；`internal/tunnel/tunnel.go:502`。

**缺口是导入和其他隧道入口没有统一禁止管理端口映射。** OpenFrp 导入甚至没有保留查到的 `LocalIP/LocalPort` 供检查；樱花虽保留，也没有检查。证据：`internal/tunnel/accounts.go:833、856、871–885`，见 M1。

**5. 前端账户区：未发现可达 XSS，正常 LAN 页面只读；另有中等功能问题**

签到、购买、获取密钥链接来自后端常量；登录 URL 经后端检查 HTTPS、准确主机名及无 userinfo。**官网限制主要由后端保证，前端并没有完整域名白名单。** 当前未发现用户可以直接指定任意外链的路径。证据：`internal/tunnel/accounts.go:34–41、304–306、505–535`。

后续（11-14 上午）：加固由作者开的另一个会话做完，是 PR #20（https://github.com/Trasperioooooon/MineDeck/pull/20 ，分支 `claude/local-needs-token-redact-fix`，代码提交 `8de04b2`，文档提交 `c89a291`），没有合并。"仅本机"现在要连接来自回环并且带本次启动的网页令牌；自定义 frps 隧道不许指向网页端口；脱敏不再漏掉键值对旁边的字段，名单加了 authorization。复审由本会话跑 Codex（请求 gpt-6-astra、max，客户端日志同此，实际型号未确认）：第一轮结论"可以合并、没有必须改"，并确认和 PR #13 没有语义冲突；补充的第二轮查"只有局域网 Cookie 的人能不能拿到网页令牌"，跑到一半被 OpenAI 的内容过滤打断（"flagged for possible cybersecurity risk"），没有绕过、也没去申请权限，剩下的由主控自己核对。原始输出放在桌面应用的会话笔记目录 〔`.claude/archive/2026-11-14-review-materials/pr13/side-session-notes/`，原文写的是桌面应用在作者电脑上的会话笔记目录，收尾时挪到了这里〕。PR #13 `febf290` 加 `8de04b2` 的试合并没有文本冲突，Windows 构建、vet、34 个 Go 测试包和前端 148/148 全过。

核对时确认了一件要作者知道的事：有局域网访问密码的人可以上传任意 jar 当模组（`modcart.local.add` 文档写明不限本机）、改 JVM 参数（`instance.settings.set` 局域网可用），再启动服务器，等于在主机上以当前用户身份运行代码，自然也能读到网页令牌。所以面对恶意的局域网密码持有人，"仅本机"不是一道硬边界，局域网密码实际上等于对这台电脑的信任；PR #20 堵住的是不需要运行代码的那条捷径。这是产品原有的信任模型，要收紧就得改局域网用户能做的事，由作者决定；至少文档应当写明"局域网密码只给你信得过、愿意让他动这台电脑的人"。
