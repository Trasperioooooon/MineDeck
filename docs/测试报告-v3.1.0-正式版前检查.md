## 发版前要先办的两件事

### 正式版会用停止维护的 Go 编

两个工作流 `.github/workflows/release.yml` 和 `test.yml` 写的都是 `go-version: "1.25"`。2026-11-12 查 go.dev，还在维护的只剩 go1.27.4 和 go1.26.11，1.25 已经不出补丁了。

Codex 用本机的 Go 1.27.1 跑 govulncheck，标准库有 12 条代码实际会走到的已知漏洞。其中两条直接对着程序的 HTTP 服务：
- 大量小区间的 Range 请求会耗 CPU；
- multipart 头解析的内存上限能被绕过。

govulncheck 列出的修复版本最高是 1.27.4，用 1.27.4 编就都修了；停留在 1.25 的话，以后也等不到补丁。

改法很小：两个工作流的 `go-version` 都改成 `"1.27"`。本机的全部测试本来就是在 Go 1.27 上跑的，都通过；改了以后，推到 main 那次 CI 会在 Windows 上再跑一遍。

**已修（`53a7407`、`f5cc069`）。** 两个工作流都改成了 `"1.27"`，又加了 `check-latest: true`。只写版本号的话，setup-go 会先看运行机的缓存，里面有 1.27.x 就直接用，可能比最新的早几个补丁；加上这一项，每次都去取最新的 1.27.x。这一条要推上去、看 CI 真跑过才算验证完。

### ServerPackCreator 打的 Server Pack 报内部错误

作者放进来的三份真包都是 ServerPackCreator 打的：BMC4（Forge 1.20.1）、BMC5 Neo（NeoForge 1.21.1）、Prominence II（Fabric 1.20.1，外面又套了一层 zip，解开里层再试的）。它们的最外层都有一份 ServerPackCreator 自己的 `manifest.json`。

程序只看文件名，就把它当成 CurseForge 整合包的清单去解析，回的是这样一句，没有人话提示：

```
解析 manifest.json 失败: json: cannot unmarshal string into ...
```

这三份包都只带启动脚本，没有装好的加载器，被拒绝本身是对的。问题在说法：beta.4 的发布说明刚写了「这种包会被拒绝，提示『看着像现成服务端，但没认出核心和版本』」，对最常见的这种包并不成立。

出问题的地方是 `internal/modpack/format.go` 的 `indexKind`：只要文件名是 `manifest.json` 就算 CurseForge。然后 `internal/modpack/modpack.go` 的 `Parse` 直接交给 `parseCurseForge`，不再往下按服务端去认。

建议发版前改识别。CurseForge 整合包的清单里有 `"manifestType": "minecraftModpack"`；ServerPackCreator 的没有这一项，有 `serverPackCreatorVersion`，`files` 是一串字符串。认出不是整合包清单，就接着按服务端去认，这样会落到已经写好的那句提示上，详情里也有 Codex 这次改好的下一步说明。

**已修（`86f0649`、`40f14b7`、`1d891b6`）。** 名字叫 `manifest.json` 的文件，现在先看内容再定：写了 `manifestType` 的，必须是 `minecraftModpack`；没写这一项的，必须有 `minecraft` 那一段，老一些或别的工具导出的 CurseForge 清单就是这样。两样都不符合的不算整合包清单，接着按服务端去认。开头带 BOM 的先去掉再看。看内容要解压，所以这一步也设了上限：一次最多解开 64 MB，每份至少按 64 KB 算，超了的只按文件名算，和以前一样。这个上限是复审时补严的，原先申报大小写成 0 的不扣额度。

用最终的代码把真包重新认了一遍：BMC4、BMC5 Neo 和 Prominence II 的里层，现在报的都是「看着像现成服务端，但没认出核心和版本」，详情里是 Codex 改好的下一步说明；Prominence II 外面那层 zip 套 zip，报的是「没认出这个压缩包，既没有整合包清单，也看不出是服务端」。要说清楚的是，修的是说法，不是能直接导入了：这三份只带启动脚本，没有装好的加载器，仍然要先运行包里的启动脚本或安装器把加载器装好，再用「接管已有服务器」。

## 建议发版前顺手修的

这四处改动都不大，各自的前提写在里面。

### 局域网登录不限请求大小（B-1）

没登录的人发一个几 MB 的 JSON，程序会整份读进来才回 401。Codex 用 8 MiB 的请求实测过。失败后的等待，只是每个请求各睡 0.7 秒，同时发很多个请求不受限制。

前提：作者打开了局域网访问，发请求的人在同一个网络里。

改法：`internal/web/auth.go` 的 `handleLogin` 先用 `http.MaxBytesReader` 把请求限到几 KB，密码长度设个上限，失败次数按来源限速。

**已修（`9fa9faf`、`c12222a`）。** 登录的请求体限 4 KB，超了回 413「请求太大」。读完请求体以后才去占校验名额，慢慢发请求体的连接占不住它。同一个来源同时只校验一个，全部来源加起来最多 8 个，占不到的回 429「请求太频繁，稍等几秒再试」。猜错仍然要等 0.7 秒才回，这段时间名额一直占着，所以同一个来源一秒钟只能猜一次多一点。密码长度没有另设上限：4 KB 的请求体已经把它卡住了，bcrypt 校验一次的开销也不随密码变长。

复审指出，有人同时从 8 个以上的地址不停地猜，别人新登录就会一直收到 429。这是有意的取舍：不设总数，bcrypt 就能被并发请求打满 CPU。本机用令牌不经过登录，已经登录的会话也不受影响。

### 服务器名字里的换行、JVM 参数里的双引号能改写 run.bat（B-7）

- `internal/inst/inst.go` 的 `validateName` 不拦控制字符；`title` 那一行的转义（`batEscapeTitle`）管不住换行。
- `internal/inst/install.go` 的 `batQuoteArg` 给每个参数加了引号，但参数里自带的引号会把它提前关掉。

Codex 用无害的 `echo` 实测过，两种都能让 cmd 多执行一行。只影响手动双击 `run.bat` 的时候：MineDeck 自己开服是直接起 java，不经过它。

改法：名字里拒绝控制字符；JVM 参数里有 `"` 就拒绝，或者换成 cmd 认的转义。

**已修（`027909a`、`afede3b`、`a5c265b`）。** 新建、导入、接管时，名字里有换行、制表符这类控制字符的一律拒绝；保存设置时，新加或改过的 JVM 参数里有控制字符或双引号的也拒绝。原来就有的参数不查：界面每次保存都把整张参数表发过来，只改内存也一样，连老参数一起查的话，老参数里带双引号的就什么都存不了了。生成 `run.bat` 时再兜一层，管住以前存下的和接管来的值：控制字符换成空格；参数里自带的双引号写成两个，cmd 看到的是「关上、马上又打开」，`&` 这类符号始终在引号里。

复审又找出一处以前就有的毛病，正好在同一个函数里：java.exe 拆参数时，反斜杠挨着双引号才算转义，所以结尾是反斜杠的参数（比如 `-Ddir=C:\My Server\`）会把收尾的引号转义掉，后面的参数全都串位。拿真的 java 试过，下一个参数整个被吞了进去。现在双引号前面的反斜杠、参数结尾的反斜杠都写成两个。点「启动」本来就不受影响，MineDeck 自己起进程时会转义，只有手动双击 `run.bat` 才会碰到。

新加的测试会让 cmd 真跑生成的 `run.bat`：一条看注入的 `echo` 有没有执行；另一条起本机或 CI 上的 java，核对 JVM 收到的参数一字不差，反斜杠结尾、双引号、`%`、`&`、空格都在里面，找不到 java 就跳过。

### 整合包的 overrides 解压没有总量上限（B-4）

现成服务端压缩包有「解开后 8 GB、20 万个文件」的上限；Modrinth 和 CurseForge 整合包的 overrides 文件夹没有。Codex 造了一个 8 MB 的整合包，overrides 里解出来是 8 GB。实测时输出直接丢掉了，没有真的写盘。用户导入一个恶意整合包，就能把磁盘写满。

改法：`internal/modpack/modpack.go` 的 `ExtractOverrides` 照服务端压缩包那样，先按申报的大小和个数卡一遍，解压时再按实际写出的字节累计。这一条的改动比另外三条大一点。

**已修（`e3a1199`、`1d891b6`）。** 和现成服务端压缩包用同一个上限：解压之前，先按 zip 里写的大小把要解的文件数一遍，超过 20 万个文件或 8 GB 就一个都不写，直接报错。实际大小由 Go 的 zip 库核对：每读一次都查有没有超过写的大小，读到结尾再查够不够、校验和对不对，对不上就报错；写的时候再套一层上限兜底。复审一度认为这层兜底会让 zip 库的检查失效，核实以后不成立，补了测试为证：写的大小比实际大、比实际小都会报错，把兜底那层拿掉也一样。

顺手修了一处以前就有的毛病：Windows 上的一些工具打包时，目录会写成反斜杠结尾，以前被当成文件，整包导入失败；符号链接以前会写成一个普通文件。现在这两种都跳过，和解现成服务端时一样。

### 自定义 frps 的地址会被当成模板解释（B-5）

隧道地址原样进了 frpc 配置的模板。地址里填模板写法，就能把这条隧道的 frps 令牌拼进主机名，frpc 一解析这个域名，令牌就带出去了。Codex 只在内存里渲染过配置，没有真起 frpc、没有真发 DNS 查询。

前提：要有人能改隧道设置。新增、修改隧道是「要人点」的操作，但没有限定只许本机（`internal/ops/catalog/tunnels.go`），所以登录了局域网访问的人也能改。这些人本来读不到令牌，借这一条就能拿到。

改法：`internal/tunnel/providers.go` 的 customProvider 里，地址只认字面的主机名或 IP。

**已修（`624db85`、`9deb761`）。** 地址只认域名或 IP，存的时候去掉前后空格和 IPv6 的方括号；启动 frpc 之前再查一遍，以前存下的不合规地址，启动时报错，不生成配置。域名的规则放得比较宽，每段可以是字母（中文也行）、数字、连字符、下划线：目的只是挡住模板的花括号、引号、空白这类字符，域名写得对不对交给 frpc 去解析，这样中文域名和带下划线的旧配置升级以后照常能用。地址不合规时的报错缩到了 60 个字以内，界面能把原因接在「保存失败」后面，不会只剩一句「保存失败」。

同一类的还有一个口子，也一起堵了：修改隧道时凭据留空表示不改，局域网登录的人只要把地址改成自己的服务器，旧令牌就会被送过去。现在换了服务商，或者自定义 frps 换了地址、端口，凭据留空就会被拒，要重新填一次。

复审另外提了两点，都没改。一是自定义 frps 存过凭据以后清不掉，只能删掉隧道重建，这是以前就有的，记在「可以放到以后的」里。二是地址只是大小写不同、或者 IPv6 换了一种写法，也算换了地址、要重填凭据，偏严，但不会漏。

## 修好以后，升级的人会碰到的变化

这几条要写进正式版的发布说明：
- **新加的 JVM 参数里不能再有双引号。** 在「内存 / 启动」里新加或改过的参数带双引号，保存时会被拒绝，去掉引号就行。界面是按空格和换行把参数分开的，加了引号也不能让带空格的值算成一个参数。已经存下的参数不受影响，照常启动，只改内存时也照常保存。
- **自定义 frps 的地址只能填域名或 IP。** 不能带 `http://`，也不能带端口，端口填在旁边那一栏。以前存下的地址里带了这些的，启动时会报错，要去隧道设置里改一下；这样的地址 frpc 本来也连不上。
- **改自定义 frps 的地址或端口要重填凭据。** 把服务商的隧道改成自定义 frps 时也一样。只改远程端口、本地端口、名字这些，凭据照旧留着。
- **局域网登录。** 同一台电脑同时发好几个登录请求，后到的会收到「请求太频繁，稍等几秒再试」；正常在网页上登录碰不到。
- **导入整合包。** 覆盖文件超过 20 万个或 8 GB 的会被拒绝，和现成服务端压缩包的上限一样，正常的整合包到不了。
- **ServerPackCreator 打的服务端包。** 只带启动脚本、没装好加载器的，现在报一句看得懂的话，告诉用户先装好加载器再接管；仍然不能直接导入。

## 可以放到以后的

- **自定义 frps 的凭据清不掉。** 存过凭据以后，修改时凭据留空表示「不改」，没有办法把它改成「不用凭据」，只能删掉隧道重建。以前就这样，复审时提到的。
- **cmd 全局打开了延迟展开时，名字和参数里的 `!xx!` 会被换掉。** 只有用户在注册表里给 cmd 全局打开了 DelayedExpansion 才会发生，`run.bat` 的标题和参数里成对的感叹号之间的字会被当成变量换掉。这一步发生在 cmd 拆完命令以后，不能多执行命令，只是显示和参数会走样。
- **配置写入会顺着目录联接写出去（B-9）。** 服务器文件夹里已经有一个目录联接的话，写配置能顺着它写到服务器文件夹外面。代码在 `internal/ops/catalog/files.go`：检查真实落点的那一步出错时，没有拦，照常写了。前提是联接已经在那儿，导入的包造不出联接。
- **写盘失败时 Key 和地址会对不上（B-10）。** 切换 AI 服务商时，如果写盘失败，后面的请求会把旧 Key 发到新地址（`internal/ai/service.go`）。前提是写盘失败。
- **局域网能读到完整的 Webhook 地址（B-2）。** 登录了局域网访问的人能读到完整的 Webhook 地址，地址里带着令牌的话会露出来（`internal/ops/catalog/appops.go`）。
- **几种 Windows 文件名照收（C-2e）。** 现成服务端压缩包里的这几种名字被收下了：`CON.txt`、`COM1.txt`，结尾带点或空格的，只差大小写的两个同名文件。它们都落在服务器文件夹里，没有越界，Windows 11 上落成普通文件；大小写重名时，后一个盖掉前一个。别的 12 种恶意写法都按预期拒绝或跳过了。
- **端口被占着时提示来得晚（D-5）。** 「启动」接口照样回成功，要等服务器自己报 BindException 才提示。最后的诊断和横幅是对的。代码在 `internal/inst/proc.go`。
- **OpenFrp 的 frpc（D-6）。** 下载不校验哈希、不限定 https、缓存文件名是固定的，这三点交接说明里早就记过。这次真机下载、解压都成功，几分钟后 Windows 安全中心把它当作木马隔离了；作者给的保护历史截图证实了这一点。隧道卡片上那段中文说明，这次没有在界面上看到。
- **字体生成物和仓库里的对不上（A-6）。** 重新生成的中文字体比仓库里的多一个减号（U+2212），西文字体本来就有它，界面不缺字。下次换字体时一起重新生成。
- **宿主函数没有来源检查（B-13）。** WebView2 宿主开给页面的函数不查来源。Claude 补看了代码：开出去的只有拖动、最小化、最大化、关闭、藏到托盘这类窗口函数（`main.go` 里 `w.Bind` 那一段），没有读写文件或执行命令的；界面里的外部链接也都带 `target="_blank"`。影响很小。
- **外部链接没有用默认浏览器打开（B-13 的后续，作者测原生窗口时发现）。** 当初以为带 `target="_blank"` 的链接会交给系统默认浏览器，作者实测不是：点「更新与关于」里的 openfrp.net，弹出来的是 WebView2 自己的简易窗口，顶上只有一条很简单的栏，用不了自己浏览器里的密码管理器、扩展和登录状态。原因是宿主没有接管 WebView2 的「开新窗口」请求（NewWindowRequested），它就用自带的弹窗打开。这和电脑上有没有 Edge 无关，装着 Edge 也是这个弹窗。安全上没有新问题：弹窗里是外部网站，拿不到宿主函数，也读不到 MineDeck 的本地存储。作者定了 3.1.0 不改，下个版本修。改法有两种：一种是前端拦下外部链接的点击，交给一个新的宿主函数，只认 http 和 https，用系统默认浏览器打开（`main.go` 里 WebView2 不可用时已经在用 `rundll32 url.dll,FileProtocolHandler`）；另一种是宿主直接接管新窗口请求，但 go-webview2 只在接口表里留了这个事件的位置，没有封装，要自己写 COM 回调。前一种简单。顺带可以让主窗口只停在 MineDeck 自己的页面上，把 B-13 一起收掉。
- **安全扫描插件没出报告。** Codex 起过一次，但它的正式报告受客户端的显示限制没生成完。不要当成「插件扫描通过」。

## 要作者定的

- **局域网能改哪些设置。** 现在除了主机路径、AI 和 MCP，普通设置局域网都能改，`docs/API.md` 里写明了，其中也包括更新源。所以登录了局域网的人，能把更新源指到自己的仓库再触发更新，等于能在这台电脑上跑程序。不过他们本来就能给服务器装模组和插件，效果一样。要收紧，就得定哪些设置只许本机改。

  修复时的复审又指出一条同类的：JVM 参数里能写 `-XX:OnOutOfMemoryError=…`、`-agentlib:jdwp=…`、`-javaagent:…` 这类，服务器一启动或者一出错，就能在这台电脑上执行命令；点「启动」和双击 `run.bat` 都一样。这和装模组、改更新源是同一件事，都是「局域网登录的人能在本机跑代码」，所以这次没有单独改。真要收紧，要连这几样一起定：改 JVM 参数、装模组插件、改更新源，哪些只许本机做。
- **交接说明里挂着的那几件。** 交接包 8 GiB 的上限、导入客户端整合包时要不要提醒、文案收尾时替作者拿的主意、导入现成服务端时沿用包里的正版验证。每件的建议写在 `docs/v3.1.0-发版清单.md` 的「要作者拿主意的事项」里。
