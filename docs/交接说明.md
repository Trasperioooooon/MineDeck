#### 第一阶段和设计文档的出入

都以代码为准，原因如下：

1. **包结构**：设计文档只列了 `ops/`。框架放在 `internal/ops`，具体操作放在子包 `internal/ops/catalog`：框架不碰 Windows API、能在 Linux 上测；`inst` 要把定时任务报给操作层，具体操作又要引用 `inst`，分开才不循环引用（`inst` 只暴露一个回调 `SetAutoHook`）。
2. **操作名**：按 §3.2 用带领域前缀的点号写法（`instance.props.set`，给 AI 的工具名是 `instance_props_set`），没用 §5.2 表里的短名（`props_set`、`player_op`）。玩家操作按风险拆成 7 个（加减白名单是写，op / deop / 踢人 / 封禁 / 解封是危险）。
3. **权限细节**：`Caller` 多了 `Local`（发起的人是否在这台电脑上，局域网打开的助手会话要用它判断「仅本机」）；`Op` 多了 `LocalMsg`（保留原来 403 的提示原文）、`InGame`（游戏内 AI 和 AI 伙伴只能调明确开放的读操作，目前一个都没开放，比设计稿的「只开放少数几个」保守）、`NoLog`（选择文件夹、打开目录不记）。`Do` 先判权限再校验参数（设计稿的顺序是先校验），这样仅本机的接口仍是先报 403。确认提案时：只认人；仅本机的操作要本机的人确认；危险操作要带 `ack`；过期报 410，前置条件变了报 409。
4. **自定义 frps 的 token**：frp 0.61.1 用 `html/template` 渲染配置文件（`pkg/config/load.go`），原样代入环境变量会把 `+ & " ' < >` 转成 HTML 实体，token 就对不上。所以环境变量 `MINEDECK_FRP_TOKEN` 里放的是逐字写成 TOML `\uXXXX` 转义的 token，配置第一行写 `auth.token = "{{ .Envs.MINEDECK_FRP_TOKEN }}"`（放在第一行，免得前面用户填的内容改变转义上下文）。用官方 0.61.1 的 frps / frpc（含 Windows 版 frpc.exe，在 wine 下）实测：token 含这些符号、中文和 emoji 都能登录。
5. **进服、退服识别**：除了设计稿的「joined the game」「left the game」，还认 PlayerList 的「X[/地址] logged in with entity id …」和「X lost connection: …」：它们写的是账号名，不受队伍前缀影响，插件关掉进服提示时也照样有；两种都出现时事件只推一次。进服退服的名字放宽到 1–16 个不含空白和 `< > [ ]` 的字符（设计稿是 `[A-Za-z0-9_]{1,16}`），因为离线模式允许 `Mr-X` 这类名字、Floodgate 的基岩版玩家带 `.` 前缀，按设计稿的写法这些人会从在线人数里消失；放宽不影响防伪造（聊天、/me、/say 的正文都带空格或以 `<` 开头）。聊天的发送者仍只认 `[A-Za-z0-9_]{1,16}`。Forge 格式下进服退服认任何 `minecraft/…` 记录器，聊天只认 MinecraftServer / DedicatedServer。聊天发送者必须在线、名字规则放宽这两条留给第四阶段；在线名单里可能出现 `@a` 这类名字，到时按 §6.1 先丢掉以 `@` 开头和含 `" \ §` 的名字。
6. **日志样本**：`internal/mclog/testdata/logs` 的五份样本是按各端 log4j2 配置的格式手写的，不是真服实录（这次在云端起不了服务端）。原版的格式和几句英文已对照 1.21.1 官方服务端 jar 里的 log4j2.xml、语言文件和日志格式串核对过。
7. **接口细节**：`/api/app` 除了 `cfKeySet` 还给 `cfKeyBroken`（设计稿只写了界面提示）；隧道列表多了 `credBroken`。壁纸的列表和图片都不走操作层（设计稿只点了「壁纸图片」）。操作记录多了 `session`、`err` 两个字段，查询多了 `op` 过滤；Webhook 地址和 server.properties 里像密码的项（`rcon.password` 等）也写成 `***`。来源 `ui` 和 `api` 靠请求头 `Sec-Fetch-Site: same-origin` 区分（浏览器和 WebView2 里的界面会带）；局域网的 `actor` 是设备地址，因为所有局域网登录共用一个会话值，没有会话编号。
8. **CurseForge Key 输入框**：设计稿 §3.5 / §14 第 14 项原定跟界面重做一起改，界面 v5 已合入，所以这次一起改了。只填空白不会被当成清除。
9. `web.go` 拆分前是 1218 行（设计稿写的是 1172 行）。「47 个接口」= 46 个 `/api/` 路由加 `GET /bg/{name}`。

#### 第二阶段和设计文档的出入

都以代码为准，原因如下：

1. **注册表没挪**：操作层的注册表仍在 `web.New` 里建。这一阶段只有设置接口要用 AI，不需要挪；`ai.Service` 在 `main` 里建好后传进 `web.New`。
2. **AI 设置全部「仅人工」，局域网能看**：7 个 `ai.*` 操作都是「仅人工」，连 `ai.settings.get` 也是，以后的 AI 功能看不到也改不了自己的设置。修改类的「仅本机」，局域网登录的设备只能看设置页，而且看不到 Key。设计稿 §10.3 只说设置「仅本机」，没说能不能看。
3. **接口不全是「未启用」**：§4.5 写的是没配置时 `/api/ai/*` 返回「未启用」。实际上设置页本身要用这些接口：
   - `GET /api/ai/settings` 照常返回，带 `enabled: false` 和 `missing`（还差什么）。
   - 测试连接和刷新价格返回 400「AI 未启用……」。
   - 取模型列表在没配置时也能用。Kimi、智谱、OpenAI 没有建议模型，要先取列表才能配完，所以只要人在设置页里点「获取模型列表」，就用表单里还没保存的地址发出请求。这是没配置时唯一可能的对外连接，而且只在人点了之后发；没有任何自动的或后台的请求。
   - Key 不会发到别的地址：不传 Key 时，只有服务商、协议和地址都和已保存的一样，才用已存的 Key。
4. **AI 是设置页的一个分区**，不是 §4.5 说的「默认折叠的区块」：v5 的设置页按分区切换，不点进去就看不到，效果相同。
5. **额度按全部 token 算**：输入、输出、缓存命中和缓存写入都算（思考已算在输出里）。设计稿没说怎么算，这样最好理解。缺点是缓存命中便宜却按全额计入，以后有需要可以改成只算输入和输出。额度在请求前检查，一次回复不会中途截断，所以当天的用量可能略微超过额度。
6. **测试连接不计入额度**，也不记账。界面上写明了「花一点点 token，不计入额度」。
7. **Claude 服务端回退的用量**：按 `usage.iterations` 逐次累加，每次尝试按各自模型的价格算，和 §4.4 一致。
8. **自定义预设可以不填 Key**：有的中转和本机服务不需要认证。其余预设除 Ollama 外都必须填 Key。
9. **逐家兼容的两处默认做法**（都是「摘要」，要实测）：
   - Kimi 的工具结果消息带 `name`。
   - DeepSeek 的回复把 `reasoning_content` 原样带回。§4.2 说思考模式下工具循环可能需要这样做。
10. **空回复不能追加进历史**：Claude 返回空的 `end_turn`，或者 OpenAI 兼容的服务只返回思考内容时，`AddResult` 会报错。Claude 不接受内容为空的 assistant 消息，所以不能硬塞。第三阶段要处理这种情况，比如提示「模型没有给出回复」，再 `UndoUser` 让用户重问。
11. **代理只认环境变量**：OpenAI 的预设要代理才连得上时，读的是 `HTTPS_PROXY` 等环境变量（`http.ProxyFromEnvironment`）。设置页里没有单独的代理设置。
12. **价格文件的地址已核实**：§4.4 标的是推断。2026-10-28 从云端打开过 `https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json`，共 2,967,643 字节；ghfast.top 和 gh-proxy.com 也都能转发它。但从国内访问这两个镜像还没测过。
13. **测试用的价格样本**：`internal/ai/testdata/litellm/` 里是从 LiteLLM 1.106.5 自带的价格文件中原样摘出的 27 条（32 KB），旁边附上它的 MIT 许可证。其中 3 条是解析时要跳过的：`sample_spec`、一个嵌入模型、一个画图模型。写坏的数据在测试里现场构造。

#### 第三、四阶段开始前要知道的事

- **怎么用 AI 接入层**：

#### 第三阶段和设计文档的出入

都以代码为准，原因如下：

1. **操作名**：沿用第一阶段的点号写法。`console_tail` → `instance.console.tail`，`logfile_read` → `instance.logs.read`，`crash_reports` → `instance.crashes`，`mods_list` → `instance.mods.list`，`config_read` / `config_write` → `instance.config.read` / `.write`，`port_check` → `port.check`，`java_set` → `instance.java.set`，`mod_toggle` → `instance.mods.toggle`，`instance_restart` → `instance.restart`。另加了 `instance.diag`，让 AI 也拿得到本地规则的结论。
2. **风险等级**：重启是危险操作（在线的人会掉线），换 Java、改配置、禁用模组是写操作。换 Java 时本机没有这个版本，就在后台下载便携版，返回任务编号。
3. **面板不是「临时面板」**：做成了标题栏入口的侧边浮层，手机宽度占满。§9 的各项都有，「发送内容预览」分两处：「让 AI 分析」发送前的预览，以及每条消息上「查看实际发送的内容」。
4. **横幅**：在实例的控制台标签里显示。打开控制台时跑一次本地规则；之后出现报错行、启动或退出时，防抖后再跑，不是后端推送。实例卡片上没有横幅。关掉横幅只对这一次的问题有效（换了问题或者重新启动后会再出现）。
5. **规则**：13 类之外，`jvm-option` 从 §5.3 第 7 条里单列出来，`crash` 是兜底（异常退出但没认出原因）。「好友进不来」（`client-mismatch`）是提醒级别，不算崩溃。「配置文件被改坏」§5.3 写的是原文待收集，现在按 Forge / NeoForge 的「Failed loading config file … for modid …」、Night Config 的 `ParsingException` 和「Invalid TOML」这几种写法来认，真服上的原文还要再收集。样本是按各端的日志格式手写的，不是真服实录。
6. **脱敏比 §5.3 多做了几样**：
   - 计算机名、程序目录和用户目录也换成占位符；
   - 本机各网卡的地址都换掉，哪怕是公网地址；IPv6 的 ULA、链路本地地址和 CGNAT 地址也算局域网 IP；
   - 配置里像密码的值，以及 JSON 里键名像密钥的值，写成 `***`。
   AI 照着占位符写回配置文件会被拒绝。
7. **看、删会话不要求 AI 配好**：停用 AI 之后，历史照样能看、能清空。
8. **一轮最多 8 次工具调用**：到上限后的调用不执行，交回「到上限了」的说明，再请求一次让 AI 收尾（一轮最多请求 11 次）。超过 16 KB 的工具结果，带 `lines` 的从最旧的行删起，其余的截掉后面。
9. **AI 设置改了**：换了服务商、协议或地址，或者 Claude 换了模型，旧会话不能接着用，要开新会话。OpenAI 兼容的服务换模型可以接着用。
10. **局域网开关关掉后**，局域网的设备看不到入口、会话，也处理不了提案；本机不受影响。开关打开时，局域网开的会话里的提案由那台设备上的人自己确认，主机本机也能处理。

#### 第三阶段要用真实 Key 验证的

云端只用 httptest 起的假服务测过，下面这些要在用户的电脑上用真实的 Key 走一遍：

  - 停止或作废之后接着说话时，会出现两条连续的 user 消息，确认服务商接受（应该会合并）；

#### 第四阶段和设计文档的出入

都以代码为准，原因如下：

1. **回复里的中文写成 `\uXXXX`**：§6.3 和 §2.3 原来说回复里不用 `\u` 这类转义。用户定了改成：JSON 文本里所有非 ASCII 的字都写成 `\uXXXX`，超出 BMP 的写成代理对，整条命令只有 ASCII。原因如下：
   - 核实过 MineDeck 写标准输入时不转码，Go 的字符串原样写出，就是 UTF-8。实例的「控制台编码」只管怎么读输出。
   - 服务器按什么编码读标准输入，取决于核心和 Java 的设置；整条命令只有 ASCII 时，在任何编码下读出来都一样。
   - 1.21.4 及以前，文本组件用 Gson 解析，认 `\uXXXX`。1.21.5 起改用 SNBT，SNBT 带引号的字符串也认 `\uXXXX`（推断，要实测）。
   - 换行、控制字符和 `§` 仍然去掉，不用 `\n`。
2. **放宽名字规则后也只认 ASCII**：§6.1 第 4 步放宽成 `[^\s<>]{1,16}`，再丢掉以 `@` 开头、含 `"`、`\`、`§` 的名字。实际放宽成 1–16 个可打印的 ASCII 字符（不含空格和 `< >`），再丢掉以 `@` 开头、含 `"`、`\` 的。中文名不认，因为名字要写进 tellraw 的目标和命令模板里的「自己」，而命令要保证整条只有 ASCII。
3. **AI 要执行的命令也只能是 ASCII**：§6.6 校验的第 1 步之外，命令里有中文或全角字符也拒绝。模板里的参数（ID、数字、坐标、名字）本来都是 ASCII。
4. **隐私提示的时机**：§10.1 说「游戏内第一次有人触发时」告诉大家一次。实际是每次开服后、受理第一个提问之前，全服发一次（灰色）。`/帮助`、`/额度` 这类不调用 AI 的不算，因为它们不会把任何东西发给服务商。重新开服后再发一次，因为在线的可能换了一批人。
5. **次数怎么算**：§6.7 没说没答上的算不算。实际上受理一个提问就算一次、开始冷却；AI 出错、超时、空回复也算，花掉的 token 照实记，免得服务商出问题时玩家一直重问。
   - 全服每天的 token 上限按实例算，键名叫 `budget`：操作记录会把键名里带 token 的值当成密钥写成 `***`。
   - 「设置 → AI」里游戏内 AI 的每日额度另外管所有实例的合计，两个都满足才问 AI。
6. **禁止清单多了几类**：设计稿的清单都在，另外加了三类：
   - 同样危险的：`place`、`fillbiome`、`loot`、`damage`、`setworldspawn`、`defaultgamemode`、`return`；
   - 会冒充别人说话的：`tellraw`、`title`、`say`、`me`、`msg`、`tell`、`w`、`teammsg`、`tm`、`bossbar`、`trigger`；
   - 各家加载器和插件端的命令：`forge`、`neoforge`、`fabric`、`bukkit`、`paper`、`plugins`、`version` 等。
   不在模板里的命令本来就不执行，这张表让拒绝的原因说清楚，也防止以后加模板时误放。模板也多认两种写法：`teleport`（同 `tp`）和旧版的 `locatebiome`。
7. **每个问题的上限**：设计稿没写。一个问题最多请求 4 次 AI、调用 6 次工具、执行 3 条命令，2 分钟没答完按超时处理。执行命令后收集控制台输出交给 AI（2026-11 起收到就返回：普通命令最多等 2 秒，locate 一类最多等 5 秒、只认它自己的反馈，见设计文档 §6.6 第 6 步），但去掉聊天行（不把别人的聊天交给 AI，§6.4）和 MineDeck 自己的行，最多 2000 字节，先脱敏。
8. **一键开启白名单**：服务器运行中时，除了照 §6.5 发 `whitelist add` 和 `whitelist on`，还先把 server.properties 的 `white-list` 改成 true，不依赖 `whitelist on` 会不会写回这个文件（§6.5 标了要实测）。先改文件再发命令，免得两边同时写。名字只收 1–16 位字母、数字、下划线（复用 `PlayerAction`），带 `-` 这类字符的名字，界面上单独列出来说明加不进去。
9. **整个设置都仅本机**：§10.3 说授权名单和命令模板仅本机。实际上开关、前缀、限流、高级识别和一键开启白名单也都仅本机；局域网能看设置和最近的问答，能做识别测试。
10. **样本的位置**：§11 写的是 `testdata/logs/{forge-1.20.1,neoforge-1.21.1,vanilla,paper,fabric}/` 这几个目录。实际在 `internal/chatai/testdata/logs/` 下，每类一个文件：`forge-1.20.1.log`、`neoforge-1.21.1.log`、`vanilla-1.21.1.log`、`paper-1.21.4.log`、`fabric-1.20.1.log`。样本是按各端的日志格式手写的，不是真服实录。
11. **工具名**：`game_info` 在操作层里叫 `game.info`（沿用点号写法），给 AI 的工具名仍是 `game_info`。`run_command` 不是操作层的操作：游戏内调用者的写操作在操作层一律 403，命令按 §6.6 走 chatai 自己的白名单，每条记成一条 `gameai.command`。
12. **「最近来过的名字」**：从进服的日志和提问里记下，最多 50 个，用来列可以授权的人。打开了游戏内 AI 才写盘；没打开时只记在内存里，重启 MineDeck 就没了。

**两个隐患的核实结论**

两个都属实。改之前的模组在新加的 devtest 小节里共有 5 项失败，改完全部通过。详情见 `bridge/voicechat/README.md` 的「验证情况」。

1. **音频线程上的阻塞式 socket 写入**：每 2 秒的定时检查原来跑在音频线程上，给广播连接发 STATUS 要拿这个连接的写锁。发送端只发不收时，连接线程回 PONG 卡在 socket 写入上，写锁一直不放，音频线程也跟着卡住：所有人的音乐、自测音和配置重读全停，这个连接也永远不会被断开。
   - 改法：定时检查挪到单独的线程；每个连接有自己的发送线程和队列；一次写入卡住 5 秒就断开。
2. **配置热重读的竞态**：有两处。
   - 原来按修改时间和大小判断文件变没变，同一毫秒里写两次会漏掉改动。改法：逐字节比较内容，发现变化后隔 0.15 秒再读一遍，两次一样才应用。
   - 定时检查读完配置、还没应用时，语音服务器停了。停服之后才应用的配置会重新打开端口，留下一个没人管的监听端口，SVC 重启语音服务器后，新连接会连到这个死掉的旧对象上，听众收不到声音。改法：停服时先停定时检查线程；已经关掉的 ControlServer 不再打开端口。
   - Go 这一侧也有对应的问题：原型 testsend 只在启动时读一次配置，模组改了端口或令牌后，永远重连不上。新的客户端每次连接前都重读配置。

**和设计文档的出入**

都以代码为准，原因如下：

1. **包结构**：§1 只列了 `bridge/` 和 `music/`。实际的分法：
   - 协议客户端和内置的 jar 在 `internal/bridge`。
   - 采集仍在 `internal/music`，原型的代码原样保留。
   - 把这些串起来的逻辑（广播、检查清单、voice_host）放在新包 `internal/musicshare`，免得 music 包去依赖 inst 和 tunnel。
2. **连接方向**：§8.3 写的是模组读环境变量 `MINEDECK_BRIDGE`，再主动连 MineDeck。原型已经改成模组在 127.0.0.1 上监听、MineDeck 去连，端口和令牌写在实例的 `config/minedeck/voicebridge.properties`。原因：
   - 服务器不一定是 MineDeck 启动的（双击 run.bat 也能开），环境变量带不过去。
   - 改成监听以后，谁先启动都行，MineDeck 重启后也能接上。
3. **协议**：第 1 版只传 PCM，没有 §8.4 表里的 START、STOP、OPUS 帧。
   - 连上就是开始，发 END 就是停。
   - 广播者的游戏名改成配置里的 `exclude`：可以填几个名字，2 秒内生效，不用重连。
   - 音量在 MineDeck 这边调（PCM 乘系数），不发给模组。
   - Opus 由 SVC 编码。OPUS 帧留给阶段 6 的浏览器方案。
4. **jar 的位置和名字**：§8.9 写的是 `internal/music/bridgejar/` 和 `mods/minedeck-svc-bridge-<版本>.jar`。实际在 `internal/bridge/jar/`；装进 mods 时叫 `minedeck-voicebridge-<版本>.jar`，备用加载方式叫 `minedeck-voicebridge-javafml-<版本>.jar`。两种都打进 exe：默认的在真服上没被 SVC 加载时，界面上可以一键换成备用的。
5. **构建和 CI**：不用 Gradle（§8.9），用 `build.sh`（`javac --release 8` 加 jar）。可复现靠固定时间戳、固定文件顺序，以及自己写清单里的 `Created-By`。没加 CI 任务，改在本地用 `update-embedded.sh --check` 检查。要加的话，就在 release.yml 里加一个装 JDK 21 的 ubuntu 任务，跑这个脚本。
6. **支持的核心**：§8.7 写的是 NeoForge / Forge / Fabric。
   - 桥接模组只有 Forge 系的元数据，Fabric 版没做。
   - NeoForge 要 1.20.5 以上（更早的读旧的 mods.toml），Forge 要 1.20.1 以上。
   - Mohist 按 Forge 处理，界面上标着「还没测过」。
7. **SVC 没装时只给指引**：写明去哪下、客户端也要装同一个版本，并链到「资源」页让用户自己搜，不自动从 Modrinth 安装（§8.7 第 2 条）。这是按本阶段的任务说明做的。
8. **权限**：§8.6 没细分。
   - 开始广播、列音源、确认整机录音都仅本机，因为录的是主机的声音。
   - 局域网登录的设备能看状态、停止广播、改名字和音量。
   - 广播控制类的操作都是仅人工，AI 只能看状态、提议装桥接模组和改 voice_host。
9. **接口路径**：§3.5 说新功能用 `/api/music/*`。和实例有关的接口放在 `/api/instances/{name}/music…` 下，和备份、玩家这些接口一致；只有不属于某个实例的（音源列表、确认整机录音）放在 `/api/music/` 下。
10. **听众状态**：§9 第 5 条说要显示谁没装 SVC、谁版本不兼容。做法是读控制台里 SVC 自己打的英文日志，不用改 SVC，模组也不用多报：
    - 连上语音的；
    - 版本不兼容的，带两边的兼容号；
    - 在线却没连上语音的。
    MineDeck 开服以后中途才开始看控制台时，界面会标明可能漏人。日志的原文是读 SVC 源码确认的，要在真服上核对。
11. **「我在游戏里的名字」**：放在页面的设置里，存进模组的配置，不用每次开始广播时填。
12. **voice_host**：改前备份成 `.bak`。MineDeck 会记下自己写过的值，用户改成别的值后就不再自动覆盖，界面上可以点「改用隧道地址」。也支持手动填写。
13. **模组端口**：从 24470 起找一个空着的，避开别的实例已经用了的和现在被占用的。不用系统随机给的端口，因为动态端口随时可能被别的出站连接占走。

**以后的阶段要知道的事**

- **阶段 6（远程朋友广播）**：协议第 1 版只有 PCM。要转发浏览器编好的 Opus，得加帧类型并升协议版本，模组那边在 `ControlServer` 收帧的地方。现在的广播者只有「本机」，邀请和远程广播者要扩展 `musicshare.StartReq`。
- **阶段 7（AI 伙伴）**：设计稿说复用 `bridge`。现在的 `bridge.Client` 只单向推音频，伙伴要双向收发消息，到时另加帧类型，或者另开一条连接。

**和设计文档、协议的出入**

都以代码为准，原因如下：

1. **指挥伙伴要经游戏内 AI**：名字触发、伙伴工具都在游戏内 AI 里，所以实例的游戏内 AI 也要打开；没开时「伙伴」标签顶部提醒。「伙伴」标签的开关就是配置文件里的 `enabled`（模组开不开控制端口），没有另存一份。
2. **额度怎么算**：叫着伙伴的名字问的记在 AI 伙伴名下（只查 AI 伙伴的每日额度），用 `@AI` 问、顺带让伙伴干活的照旧记在游戏内 AI 名下。两种都受实例的冷却、每人每天、全服每天的次数和 token 限制。任务做完或失败不再调用 AI（用户定的），所以 §7.2「任务完成 / 失败时才调用 LLM」不成立了。
3. **伙伴的名字收紧到 1–16 个字**，不能有空白、`@`、选项标记、冒号、逗号和 `< > " \ §`（协议允许 1–32 个字）：玩家要在聊天里用「@名字」叫它；也不能和游戏内 AI 以 `@` 开头的前缀撞。testctl 这类别的程序刷出的名字管不到，带空格的就叫不到。
4. **伙伴的动作不是操作层的操作**（同 `run_command`）：游戏内调用者的写操作在操作层一律 403，所以动作经游戏内 AI 的工具直接交给伙伴模组，每个记一条 `companion.action`（来源 companion）。`companion.status` 也不对游戏内开放，游戏内 AI 用自己的 `companion_status` 工具。工具的 `companion` 参数写伙伴的名字（也认编号）。
5. **上限**：一个问题最多让伙伴做 4 件事（查状态不算），工具调用的总数仍是 6 次。
6. **不支持 Mohist**：清单里只有 NeoForge 1.21.1、Forge 1.20.1，Mohist 没测过；「伙伴」标签只给 NeoForge、Forge 实例，别的版本说明原因。
7. **回退的条件**：只有实测过的版本回 404 / 410 才去 Modrinth 上找别的版本；网络出错、大小或 sha512 对不上直接报错，不回退（对不上说明内容被改过，换个版本也不该装）。
8. **不走镜像**：只连 `cdn.modrinth.com`（下载）和 `api.modrinth.com`（回退时查版本），只在人点了「安装」（或确认了 AI 的提案）时连。国内访问 Modrinth 可能慢或连不上，要实测；要加 MCIM 这类镜像，先和用户确认（会多一种对外请求）。
9. **最近的事件只在内存里**，重启 MineDeck 就没了；伙伴本身存在世界存档里。
10. **禁挖区域的两个角**按配置文件里写的顺序存；模组报来的是整理过的 min / max，比较「改了还没生效」时两边都先整理。

**修了什么**（都配了测试，wine 下全部包通过）

1. **NeoForge 1.21.1 上控制台的中文全是「?」，游戏内 AI 认不出「@小木」**（`inst.launchArgs`）。Java 18 起 `System.out` 不跟 `file.encoding`，跟 `stdout.encoding`，没设时用系统编码；MineDeck 只传了 `-Dfile.encoding=UTF-8`，对 Java 17 的 Forge 有用，对 Java 21 的 NeoForge 1.21.1 没用。实测（系统编码不是 UTF-8 时）：`latest.log` 里是 `<Steve> @小木 跟着我`，MineDeck 读到的是 `<Steve> @?? ???`，伙伴不响应。中文 Windows 上系统编码是 GBK，大多能按 GBK 解出来，但短句的 GBK 恰好是合法的 UTF-8 时会被当成 UTF-8 解错（测试里核实：`[Not Secure] <Steve> @小木 停` 解成 `@Сľ ͣ`）。改成再加 `-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8`（旧版 Java 忽略这两个），托管启动和 run.bat 一起改；联调程序用同样的参数，中文聊天、模组日志都正常。测试 `TestLaunchArgsConsoleUTF8`。合并时补了一条：实例的控制台编码手动选了 GBK 时不加这两个参数，保持 v2.6.1 的行为（用户认定输出是 GBK，强制成 UTF-8 反而按 GBK 解成乱码）。
2. **关服时界面报「和伙伴模组的连接断开了……会自动重连」，关服期间还一直重连**（`companion`）。关服时是模组先发 END「服务器正在关闭」、再关端口（协议如此），MineDeck 原来当成意外断线。改成：实例正在停或者已经停了时，记一条 info「服务器正在关闭，和伙伴模组的连接断开了（伙伴留在存档里，下次开服自动接管）」，不再重连，连接状态是 `waiting`，等下次开服再连；服务器开着时断开照旧报出来、自动重连。所以原来写的「关服时模组日志里有 MineDeck 发来的 END」做不到、也不需要：模组那边先断；退出 MineDeck、关掉伙伴时 MineDeck 照常先发 END（实测）。「伙伴」标签的连接框这时写「服务器正在关闭，伙伴留在存档里，下次开服后自动连上」（原来写的是「服务器还在启动」）。测试 `TestServiceServerClosing`，前端交互测试在原有的一条里加了关服的情形（共 61 条，全部通过；用到的字都在字体子集里）。
3. **任务结束的通知可能漏掉**（`companion`，模组那边的竞态，MineDeck 兜底）。见下面模组的第 1 条：握手落在任务结束的那个 tick 里时，`task_finished` 被丢掉、WELCOME 里也还没有这次的 `lastResult`，MineDeck 原来只在 WELCOME 里找，就再也不通知了。改成每个 STATUS 里伙伴的 `lastResult` 也对一遍：是有人发起、还没通知过的任务就照样通知（只通知一次）。测试 `TestServiceStatusCatchesLostFinish`（假模组加了 `FinishLost`）。
4. **`@小木 给我 1 个原木` 什么都没给，却通知「做完了：交出了 0 个」**（`companion`，绕开 PlayerEngine 的问题）。游戏内 AI 的提示让模型写完整的 ID（`minecraft:oak_log`），模组 0.2.0 原样拼进 PlayerEngine 的 `give Steve minecraft:oak_log 1`，PlayerEngine 1.4.0 的 `GiveCommand` 只认 `oak_log` 这种写法（`ItemHelper.stripItemName`：原版物品不带命名空间，模组物品带），找不到就结束，模组报 `done`、`given: 0`（实测 21 毫秒就结束了）。`collect`（PlayerEngine 的 `get`）两种写法都认。`Service.Act` 发 `give` 时把原版物品的 `minecraft:` 去掉，模组物品照写；改完两个加载器实测都是「交出了 1 个，背包里还有 2 个」，Steve 背包里多了一个原木。测试 `TestActGiveItemName`。

**模组那边的问题**（没改模组，建议下一版改）

1. **WELCOME 和事件之间有缝**。`ControlServer` 在连接线程上用 `companionsJson`（每 tick 末尾才刷新的快照）生成 WELCOME，连接就绪（`ready`）之前 `control.event()` 发的事件直接丢掉。握手落在一个 tick 中间时，这个 tick 里的变化（接管、刷出、`task_finished`……）既不在 WELCOME 里、也收不到事件，要等下一个 STATUS。实测：两个加载器每次重启都是「控制连接已建立」和「接管存档里的伙伴」同一毫秒，WELCOME 里 0 个伙伴，`adopted` 也没收到，2 秒后的 STATUS 才有。MineDeck 已兜底（STATUS 2 秒内补上伙伴列表，`lastResult` 补发通知）。建议：握手校验完以后，在主线程上（`server.execute`）刷新快照、生成 WELCOME、放进发送队列、置 `ready`，连接线程等它做完；这样 WELCOME 之后的事件一个不漏。
2. **`give` 的物品名**：拼 PlayerEngine 指令前把 `minecraft:` 去掉（或者像 `collect` 一样先用 PlayerEngine 的解析检查，不认识回 `rejected`）；MineDeck 现在已经替它去掉了，别的发送端（testctl）写全名时还是会白跑一趟。
3. **`give` 什么都没给也报 `done`**：PlayerEngine 找不到物品、或者 `fetch` 时弄不到，都只是结束任务；模组按「PlayerEngine 结束了」报 `done`。建议 `given` 少于 `count` 时报 `incomplete`（或 `failed`，`detail` 写原因），协议里 `incomplete` 的说明补上 `give`。MineDeck 按协议照 `result` 写通知，这时会说「做完了：交出了 0 个」。
4. **伙伴空闲时站在水里会淹死**（README「已知问题」里写了「会淹水」，这次碰到的是空闲的时候）：一次联调里伙伴采集时去了场地外的一棵树，砍完停在河边的水里，紧接着的 `follow` 0.4 秒后被 `stop` 停下，之后空闲约 30 秒淹死（`died` → `removed`，MineDeck 的事件和清理都正常）。PlayerEngine 的 `WorldSurvivalChain.handleDrowning` 会在水里按跳上浮，推断 `stop`（连闲置动作一起停）以后这条链不再跑，要读源码核实；建议空闲时伙伴在水里也能上浮（或者模组自己在伙伴头在水下时按跳）。联调程序后来把场地挪到了 y=100 的悬空平台上，避开了这个问题。

### 第七阶段：伙伴模组 0.2.1（2026-10-31，分支 mod021）

两半联调时发现的模组问题（上一节「模组那边的问题」第 1–4 条：WELCOME 和事件之间的缝、`give` 的两条、空闲时淹水），改在伙伴模组 0.2.1，两个加载器一起改。协议仍是 v1：只多了一个可选字段（`give` 的 `task_finished` 带 `want`），`result` 用的是已有的值，MineDeck 的协议客户端不用改。内置的 jar 和清单用 `companion/update-embedded.sh` 重新可复现构建（`--check` 通过，sha256 `6ea730ab…`、`06449d88…`）；发布页的伙伴模组文件名由清单决定，跟着变成 `…-0.2.1.jar`。PlayerEngine 没改，也没重新打包。

**改了什么**

1. **WELCOME 和事件之间的缝**（`ControlServer`、`CompanionManager`）：握手时把「生成 WELCOME（先刷新快照）、放进发送队列、置成就绪」交给服务器主线程（`Handler.onMainThread`），事件本来就在主线程上发，所以握手时发生的每件事要么在 WELCOME 里，要么作为事件跟在它后面。主线程 4 秒都没空（卡住了或者正在关闭）时回 ERROR 5，MineDeck 照常重试。
2. **`give`**（`CompanionManager`、`Args`、两个 `ServerCompanion`）：交给 PlayerEngine 时原版物品去掉 `minecraft:`（PlayerEngine 1.4.0 的 `GiveCommand` 只认 `oak_log`）；交出的个数改成伙伴扔东西时数（`spawnAtLocation`），不再看背包少了几个（`fetch` 时背包是先多后少）；PlayerEngine 结束了、交出的却少于 `count` 时报 `incomplete`，一个都没交出去报 `failed`，`detail` 写原因：不在线、不在伙伴所在的维度；`fetch` 时「原来只有 2 个，也没弄到更多」「原来一个都没有，也没弄到」「……只弄到了 1 个」；看不出来时是 PlayerEngine 的说明，或者「PlayerEngine 没把东西交出去」（交了一部分时「……没把剩下的交出去」）。`task_finished` 多了 `want`。
3. **空闲时淹水**（新的 `IdleFloat`，两个 `ServerCompanion` 每 tick 调）：读 PlayerEngine 1.4.0 源码确认——防淹水的 `WorldSurvivalChain.handleDrowning` 在 `getPriority()` 里，`TaskRunner.tick()` 只在启用时才问各条链；`PlayerEngineController.stop()` 调了 `TaskRunner.disable()`，刚建好的控制器第一次接任务前也没启用，这时站在水底的伙伴没人按跳。现在 `TaskRunner` 没在跑、也没在寻路时，伙伴照原版 `FloatGoal`：水深过了 `getFluidJumpThreshold`（或者在岩浆里）就按住跳，浮上来以后松开；PlayerEngine 只在它的按键变了时才写 `jumping`，所以我们按下的跳自己松开（它正按着跳时不松）。只动跳，不走、不转身，不改 PlayerEngine 的状态，`stop` 的意思不变。这一步出错时和 PlayerEngine 的 tick 一样只记日志（5 秒一次），不会让服务器崩。
- MineDeck 侧（`internal/companion/texts.go`）：`give` 的通知写「交出了 N 个（要 M 个）」（0.2.0 不带 `want` 时照旧）；不到半秒就结束的（多半是一下子就失败了）不再写「用时 0 秒」。新测试 `TestResultText`（做完、没做够、失败、0.2.0 的写法）。`Service.Act` 去掉 `minecraft:` 的那一步留着：和模组的做法一样，不冲突。
- 版本号：两个工程的 `gradle.properties`、清单、`companion/README.md`（构建产物、WELCOME 示例、真客户端自测）、《好友测试指南》里的文件名例子改成 0.2.1；历史记录里的 0.2.0 不动。`tools/ui-dev` 的仿真数据（0.2.0）只在仿真后端里自圆其说，测试不依赖真实清单，没改。

### MCP 接口（2026-10-31，分支 mcp）

用户定了现在就做，随 v2.9.0-beta.2 发测试版。让同一台电脑上的其他 AI 工具（Claude Desktop、Cherry Studio、Cursor、VS Code 等）经 MCP 用 MineDeck 的操作层，默认关闭。设计和决定写在设计文档 §15，接口在 `docs/API.md` 的「MCP 接口（外部 AI 工具）」，测试项是 `docs/测试计划.md` 的 J 组。

**做了什么**

- 协议：查了规范仓库，当前版本是 2026-07-28（无状态：每个请求的 `_meta` 带版本和客户端能力，有 `server/discover`，HTTP 上核对镜像头，去掉了会话和 ping）。做成两代都认：带 2026-07-28 的 `_meta` 就无状态处理；`initialize` 按旧版握手，认 2025-11-25、2025-06-18、2025-03-26、2024-11-05，旧版的批量请求也收。只提供工具，`listChanged` 为 false。没用任何 SDK，JSON-RPC 自己写。
- 新包 `internal/mcp`（不碰 Windows API，只有桥检查进程的那个函数分平台；Linux 上能直接测，`-race` 通过）：
  - `rpc.go`：JSON-RPC、两代的分流、版本协商、镜像头核对。校验顺序照官方 Go SDK：先看版本头在不在、`_meta` 里有没有版本（没有是 -32602）、两边一不一致（-32020），最后看支不支持（-32022）。
  - `http.go`：`/mcp`。只收本机的 POST；Host、Origin 必须是本机（防 DNS 重绑定）；MCP 接口打开着；`Authorization: Bearer <MCP 令牌>`。
  - `mcp.go`：开关（`data/mcp/settings.json`）；令牌（DPAPI 加密存进 `secrets.json` 的 `mcp.token`，内存里只留 SHA-256）；运行时文件 `data/mcp/runtime.json`（端口、进程号，打开时写，关掉和退出时删）；本次启动以来连过的客户端；旧版的会话。
  - `tools.go`：工具清单和调用、提案的记录、`proposal_status`、给界面的等确认列表和订阅。
  - `bridge.go`：`MineDeck.exe -mcp` 的 stdio 桥。
  - `config.go`：各家客户端的配置片段。
- 操作层：新来源 `ops.SrcMCP`（`mcp`），权限同应用内助手（读直接执行，写和危险只生成提案，仅人工的拒绝），调用者算本机。
- assistant：工具映射和结果整理抽成 `ToolOps`、`ToolDesc`、`FormatResult`，助手和 MCP 共用，助手的行为逐字节不变。`Redactor` 处理一整个 JSON 时只取一次已知的密钥：以前每个字符串都读一次 `secrets.json` 解一次 DPAPI。
- catalog：`NewMCP(reg, token)` 建服务，同时登记 4 个仅人工的操作 `mcp.get`、`mcp.set`、`mcp.token.reset`、`mcp.config`（修改类仅本机）。`NewRedactor` 多认 MCP 令牌。
- web：`web.New` 多了可选参数 `WithMCP`，原来的调用不用改；路由在新文件 `web/mcp.go`，有 `/mcp`、`/api/mcp*`，还有界面用的 `/api/mcp/events`（SSE，只给本机）。确认、拒绝提案的接口多一条规矩：外部 AI 的提案只有本机能处理（`mcp.CanDecide`）。
- main：`-mcp` 参数进桥的模式（在 `setDPIAware` 之前，不建窗口、不初始化数据目录），见 `mcpbridge.go`。`mcpbridge_windows.go` 调一次 `GetMessage`，关掉 Windows 给刚启动的 GUI 程序显示的「后台运行」光标。启动后 `mcpSvc.Start(端口, 想用的端口)`，退出时 `Stop()`。
- 界面：
  - 新文件 `mcp.js`、`mcp.css`；`app.js` 只加了 3 处钩子，另外 `toast()` 改成返回它建的元素；`assistant.js` 在面板顶上加了「外部 AI 的请求」，标题栏入口的小方块也算上它。
  - 「设置 → AI（可选）」的「MCP 接口」分组：开关、地址、令牌、复制配置、连过的 AI 工具，局域网只能看。
  - 外部 AI 提了写操作：弹提示（点一下打开面板），标题栏「AI 助手」亮小方块，面板顶上用助手同一种确认卡片。没配 AI 时也能处理。
  - 界面新用到的字都在字体子集里，`build_fonts.py --check` 通过。

**顺手修的一个老问题**：操作层 `Do` 在 AI 发起的写操作预览失败时（比如重启一台没在运行的服务器），返回的是装着 nil `*Proposal` 的 `any`。调用方的类型断言会把它当成提案：MCP 因此出错（真客户端联调时发现）；应用内助手会把这次调用显示成「等你确认」，交回空的错误。改成返回 nil 和错误，ops、assistant、mcp 各加了回归测试。

**和设计、任务说明的出入**（都以代码为准）

1. **令牌不进运行时文件**：任务说明是「运行时文件里写端口和认证的办法」。实际文件里只有端口和进程号；桥自己从 `secrets.json` 用 DPAPI 解令牌（同一个 Windows 用户才解得开），所以不会在磁盘上多一份明文。桥会先核对文件里的进程还在、是同一目录下的程序，再发令牌。
2. **认不出的旧版会话照常处理，不回 404**：规范说服务端结束了的会话要回 404、客户端重新握手；但 TypeScript SDK 1.x 收到 404 直接报错、不会自动重新握手（读 1.32.2 的源码核实），MineDeck 一重启，Cherry Studio 这类客户端就得手动重连。所以照常处理，只是不知道客户端的名字，记成「MCP 客户端」。stdio 桥另外带着名字（`X-MineDeck-Client`），重启后照样记得对。
3. **外部 AI 的提案只能在本机确认**：局域网的设备看不到，也处理不了（应用内助手的提案，局域网能处理自己会话里的）。外部 AI 工具就在主机上，确认的人也应该在主机上。
4. **「连过的 AI 工具」只在内存里**：只列本次启动以来的，最多 8 个，重启就清空，不另存文件。
5. **多了几样任务没写的**：同时等确认的 MCP 提案最多 10 个，免得外部 AI 一直提，挤掉助手的提案（操作层一共留 100 个）；关掉 MCP 时没处理的提案作废；`proposal_status` 不填 id 列出最近的提案，可以等最多 30 秒；工具带 `annotations`（读操作 readOnlyHint，危险操作 destructiveHint）。
6. **不做的**：2024-11-05 的 HTTP+SSE 传输（只认这个版本号）、GET 的事件流、resources、prompts、`subscriptions/listen`、CORS（浏览器里的网页本来就拿不到令牌）。
7. **2026-07-28 去掉了的方法**（initialize、ping）带着它的 `_meta` 来时回 404，和官方 Go SDK 一致。不带 `_meta` 的 `server/discover` 回「没有这个方法」，双代的客户端据此退回 initialize。
8. **客户端配置的写法**：Claude Desktop、VS Code（`servers`、`type: "http"`）是照官方文档写的，Cherry Studio（`type: "streamableHttp"`）是照它的源码写的。Cursor（`mcpServers`、`url`、`headers`）没能核实：这次云端打不开 cursor.com。几家的菜单名称也都要实测。

### v2.9.0-beta.2 的实测和第一批修复（2026-11-02）

2026-11-01 到 11-02，用户本机的 AI 测试员照《测试计划》在 Windows 上实测了 beta.2，报告是 `docs/测试报告-v2.9.0-beta.2.md`，已经入库；报告里提到的几个 `.bak` 是测试员插段落前留的备份，已经删了。根目录那个没有扩展名的 `minedeck` 文件是 Codex 后台脚本的一段运行日志，也不是项目内容。85 项里有结论的 72 项，其中 50 项通过、18 项部分通过、4 项不通过；手机端界面基本用不了，手机那一批测试停在那里，等界面修好再测。报告末尾「收工与发布前的建议」按影响排了一张清单，下面说的都出自那里，我逐条对过代码。

这一轮先修了后端的七件事，界面只改了配套的提示。验证情况：`go test ./...` 全部通过，`tools/ui-dev` 的交互测试 66 条全过（新加一条，按新规则改了一条），新加的界面文字都在字体子集的 GB2312 范围里。

第一件是 Key 被静默清空。原来改了服务商、协议或接口地址，保存时 Key 一律清掉，测试员只是把地址改到同一个网站的另一个路径，Key 就没了。这么设计的初衷是防止有人把地址改成自己的服务器、把 Key 骗走，所以没有整个推翻，而是把「换地址」收窄成「换了网站」：http/https、域名、端口有一样不同才清，只改路径或接口协议就保留。判断写在 `internal/ai/client.go` 的 `SameSite`，取模型列表用不用已存的 Key 也按同一条。界面上只有真要清 Key 时才提示，保存前弹确认框；确认后请求里明着带上空 Key，操作记录里看得出这次清过。

第二件是在控制台敲 `stop` 会被当成崩溃，开着崩溃自动重启时服务器 10 秒后又被拉起来。根因是进程退出时只看 `userStop` 这个标记，而它只有界面的停止和强杀会设。现在控制台发 stop（Velocity 是 shutdown、end、stop，Waterfall 是 end）时就把这次运行记成主动停服、状态改成 stopping；游戏里的管理员或 RCON 发 stop 时，服务器会打一行 `Stopping the server`，看到这一行也一样处理。伙伴模组关服时发来的「服务器正在关闭」现在不管实例状态跟没跟上，都当正常关服，不再报警告、不再重连。

第三件是停服不停隧道。原来跟随启动只挂在界面的「启动」「重启」两个操作上，所以停服、强杀、崩溃自动重启都不管隧道。现在挪到 `tunnel.FollowInstances`，在 `main.go` 里订阅实例事件：实例启动时拉起跟随的隧道，包括崩溃自动重启那次；实例停了之后等 5 秒，还是停着就把跟随的隧道停掉，这样重启时不会来回开关。没勾跟随启动的隧道不动。

第四件是语音隧道停了 `voice_host` 不清。隧道的公网地址存在 `tunnels.json` 里，停了也留着，所以下次开服前照样会写回 `voice_host`，页面也一直说「远程好友连服后就能听到」。现在开服前只认正在运行的、或者勾了跟随启动的语音隧道；一条都没有时，如果 `voice_host` 还是 MineDeck 上次写的那个值，就清回空，用户自己填的不动。音乐共享页多了一种状态「语音隧道没开」：隧道勾了跟随启动的，说开服时会跟着启动、`voice_host` 照旧；没勾的，说下次开服前会清回去。清的时候和写的时候一样，先把当时的文件备份成 `voicechat-server.properties.bak`，所以清过一次以后，`.bak` 里是带隧道地址的那一版，不再是最早的原文件。

第五件是 `instance.json` 开头带 UTF-8 BOM 时，那台服务器会从列表里消失。现在读之前先去掉 BOM，读不出来时在日志里写一行；保存时先写临时文件再改名，免得断电留下半截文件。列表页提示「有几个目录读不出来」这一步没做，因为现在的接口直接返回一个数组，要加得改接口形状。

第六件是检查端口占用时，端口明明被占却报空闲。原来是「试着绑一下，成功就算空闲」，而 Windows 上别的程序只占了 0.0.0.0 时，再绑一次 IPv6 双栈照样成功。现在先查监听表（原来就有的 `portOwners`），查到有人监听就算被占，查不到才退回去试绑。

第七件是报错横幅。一是没认出「少装前置模组」：S2 那次的日志里，Forge 给的版本范围是空的（`Expected range: ''`），两条规则都要求范围里至少有一个字，所以都没匹配上；现在空范围也认，并且写明「装了但加载器认为版本不对」。样本取自 S2 的真实日志，在 `internal/diag/testdata/positive/missing-deps@forge-1.20.1-connector.log`。二是横幅标题说「异常退出」，证据却是「服务器已正常关闭」：模组加载失败时 Java 的退出码也是 0。现在只有用户自己停服时才写「已正常关闭」，没人让它停的退出码 0 写成「服务器进程已退出（退出码 0，但没人让它停）」，诊断模块按前缀匹配，不用跟着改。

还没做、留给下一批的，主要是这几样。手机端界面要改 `100vh` 和安全区，改完得拿真机看。F-04 的长回复拆分永远触发不了，因为系统提示限 150 字、拆分线是 180 字，这要用户定是放宽提示还是删掉这条测试项。开服前的端口预检 `inst.CheckPort` 同样是试绑，端口被占时仍会先起 Java 再报错，好在横幅能认出「端口被占」。控制台认停服命令时，Velocity 的 `stop` 是按「shutdown 的别名」算的，这一点凭记忆、没核实；要是它其实不是别名，在 Velocity 上敲 stop 会让界面停在「正在停止」，直到点「停止」按钮。此外还有一串体验问题，报告里都写了：跟随启动不写操作记录，隧道卡片状态更新慢、启动失败时卡片上看不出来，公网地址优先取了 IP 而不是域名，双击标题栏不能最大化，开机自启时白窗口一闪，「好友进不来」横幅里打出整串 GameProfile，游戏内 AI 防刷屏的默认值偏紧，命令输出只等 1 秒导致 `locate` 拿不到结果。

请用户在 Windows 上复测这几项：同一网站只改接口路径，Key 还在，换到别的网站时先弹确认（D-01）；控制台敲 stop 后服务器不再被拉起来，伙伴页记的是普通提示（H-02）；停服 5 秒后隧道跟着停（C-03）；停掉语音隧道后音乐共享页显示「语音隧道没开」，下次开服前 `voice_host` 清回空（G-07）；给某台服务器的 `instance.json` 加上 BOM 后重启程序，那台服务器还在（发现 10）；占住 0.0.0.0 的端口后问助手，能查到是谁占的（E-09）；把 continuity 放回 S2 的 mods，横幅认成「缺少前置模组」（E-06）。

## 接手的第一步

接着做设计文档里的功能时，从最新的 main 开分支。云端会话按会话指定的分支名来，只做快进推送。

如果你手上的分支是改名之前开的，代码已经过时了：那些 claude/ 分支在远端都已删掉，代码里也还没有改名。请先 `git fetch origin`，再切到 main 并更新到最新（`git switch main && git pull`）。之后的工作从 main 新开分支，不要再往旧分支上推。改名之后 module 名是 minedeck，写 import 和跑命令时都要注意这一点。

## 改名带来的三件事（已定）

**老用户的自动更新：不做过渡。** 用户说目前还没有外部用户，v2.6.1 的几次下载基本是自己下的。新版 Release 里只有 MineDeck.exe，v2.6.1 及更早的版本在 SHA256SUMS 里找不到 AutoMCHUB.exe 那一行，点更新会报「无法获取该版本的官方校验和……已取消更新」，只能手动下载一次新 exe。`release.yml` 不改。老配置里存的更新仓库还是 Trasperioooooon/AutoMCHUB，靠 GitHub 的改名重定向照样能用，也可以在「设置 → 更新」里改成新名。不要再新建叫 AutoMCHUB 的仓库，否则这个重定向会失效。

**开机自启：删除旧值。** 新版每次启动都会删掉注册表 Run 键下旧的 AutoMCHUB 值（`autostart.RemoveLegacy`）。所以升级后开机自启是关闭的，需要的话到设置里重新打开。

**界面偏好：数据目录固定。** 创建窗口时显式指定 WebView2 数据目录 `%LocalAppData%\MineDeck\WebView2`（见 `webviewdata_windows.go`），以后 exe 改名也不会丢主题、配色和控制台历史。这个目录还不存在时，先把旧的默认目录整体移过来：优先用 `%AppData%\<当前 exe 文件名>`，没有就用 `%AppData%\AutoMCHUB.exe`。移动失败（比如旧进程的 WebView2 还没退干净）就本次沿用旧目录，下次启动再试。多份安装共用这一套偏好。

第一阶段（架构调整）新增的几项：

- **CurseForge Key 迁移**：用旧版填过 Key 的程序目录启动一次新版，`config.json` 里的 `cfApiKey` 消失、出现 `secrets.json`（值以 `dpapi:` 开头）；设置页显示「已设置」；导入一个 CurseForge 整合包，模组照常自动下载。整个文件夹拷到另一台电脑或另一个 Windows 用户下，设置页应提示「密钥无法解开」。

第二阶段（AI 接入层）新增的几项，要用真实的 Key：

- **设计稿的验收标准**：至少用两家服务商的真实 Key 走一遍：选预设、填 Key、获取模型列表、保存、测试连接。测试连接要显示「连接正常」和「能调用工具」，费用估算的单价和来源也要对。
- **各家的实际格式**：测试样本是按各家官方文档的格式手写的，不是录下来的。下面这些地方只读到了摘要，要用真实请求确认：
  - DeepSeek 带回 `reasoning_content`；

  - 通义千问的 Key 分地域；
  - OpenAI 经 `HTTPS_PROXY` 代理。
  测试连接失败时，报错里有 HTTP 状态码和服务商的原话（Key 会写成 `***`），把它记下来。
- **Claude 官方地址**（能连上的话）：确认这几项不报错：`anthropic-version: 2026-10-21`、服务端回退的 beta 请求头、`eager_input_streaming`、思考深度的各档。确认获取模型列表能分页取全。

v5 新增的几项：

- **字体渲染**：在 100%、125%、150% 缩放下看中文、西文和控制台的等宽字是否清晰，400 / 500 / 600 三档字重是否分得开。GB2312 以外的生僻字（比如「堃」「喆」）应该由微软雅黑补上，不显示成方框。云端截图用的是 Linux 的字体渲染，和 Windows 的 DirectWrite 有差别。
- **连续曲率圆角**：卡片、按钮、键帽的圆角应该是平滑过渡的「方圆」形，不是普通圆角那种圆弧接直线。这要求 WebView2 运行时支持 `corner-shape`；运行时太旧会自动回退成普通圆角，这也算正常，但要记下用户的 WebView2 版本（在「设置 → 应用 → 已安装的应用」里看 Microsoft Edge WebView2 Runtime 的版本号）。
- **白闪**：系统分别设成浅色和深色，各冷启动一次，窗口出现到界面画出之间不应闪白。换一套配色或切换浅深色后关掉程序再开，窗口底色应该和新的标题栏颜色一致。自动更新重启后也看一次。原生窗口刚出现的一瞬间（约 0.1–0.3 秒，WebView2 还没创建好）可能仍看得到系统标题栏或空白客户区，这一段要靠下文待办里的「CBT 钩子 + DWM 隐身」解决。
- **启动画面**：冷启动时播一次（方块拼出图标，约 1 秒）；点击或按任意键立即跳过，按 1–4 跳过时不应该顺带切页。按 F5 刷新、从托盘恢复窗口都不再播；Windows「设置 → 辅助功能 → 视觉效果 → 动画效果」关掉时不播；开机自启静默进托盘后，第一次从托盘打开也不应补播。
- **任务栏和托盘图标**：新图标在任务栏（大、小图标）、托盘、Alt+Tab、资源管理器里 exe 文件上的样子，100% / 125% / 150% / 200% 缩放下都看一下是否清晰。ICO 里画了 16、24、32、48、64、128、256 七档，没画 20、30、36、40 这几档，125% 缩放下的托盘图标（20 像素）等由系统从相邻档缩放，可能略糊。
- **局域网手机访问**：手机浏览器（尤其 iPhone 的 Safari）打开时圆角回退成普通圆角、侧栏变成底部标签栏，不播启动画面；再次打开时字体走缓存（服务端返回 304）。

CI 有两个工作流，都在 GitHub 的 Windows 机器上跑：

- `test.yml`：任何分支推送、PR 时跑 `go test ./...`。这是 Go 测试在真正的 Windows 上跑的地方，云端会话只能借 wine 跑。2026-10-31 第一次运行就抓到两个 wine 下测不出的问题，都是测试的假设不对，已修好：
  - Windows 上 Go 的时钟一跳 0.5～15.6 毫秒，本机连接的心跳往返常量成 0。测试的假模组改成晚 20 毫秒回 PONG。
  - DPAPI 密文的前 20 字节（版本号、提供者 GUID）不在签名范围内，改了照样解得开。测试改成篡改最后一个字节（签名）。

  之后又抓到一次，同样是时钟精度：MCP 的「连过的客户端」按最近来访的时间排，前后脚来的两个时间一样，排不出先后（列表满了时刚来的还可能被挤掉）。改成按递增的序号排，提案列表也一样。**写代码时别只靠时间戳排先后、判断谁新谁旧**：Windows 上前后几毫秒的两个时间常常相等。
- `release.yml`：推 `v` 开头的 tag 时触发，依次跑 Go 测试、构建 MineDeck.exe、复制出好友客户端要装的伙伴模组（文件名带版本，同 `manifest.json` 的 `installName`）、生成包含全部附件的 SHA256SUMS，然后创建 Release。tag 里带「-」的（如 `v2.9.0-beta.1`）发成预发布：不算 Latest，老版本的检查更新看不到它。如果有 `docs/releases/<tag>.md`，就用它作发布说明，后面再接上自动生成的变更列表。

发版流程如下：

1. 改 `internal/app/app.go` 里的 Version 并提交。测试版写成 `2.9.0-beta.1` 这样；同号的正式版比测试版新（`update.newer`），装了测试版的人能收到正式版的更新。
2. 需要的话写 `docs/releases/<tag>.md`。
3. 正式版：合入 main，打 tag，推送 main 和 tag。预发布：可以直接在工作分支上打 tag 推送，main 等测试通过后再合。
4. 推 tag 触发 CI，等它跑完后，到 Release 页面核对附件和说明。

发版时 `site/` 里的版本号要跟着改：`site/index.html`、`site/en/index.html` 的眉标和结构化数据里的 `softwareVersion`，`site/llms.txt` 的「Current version」和发布说明的链接。

云端会话推不了 tag：代理只放行会话指定的工作分支，推 tag 会被拒（HTTP 403），不要重试或绕开。打 tag 要请用户来，二选一：在自己电脑上 `git tag` 后推送；或者在 Release 页面新建 Release，「Choose a tag」里填新 tag、Target 选工作分支、勾上 pre-release 后发布。2026-10-31 的 v2.9.0-beta.1 用的是后一种：发布后 release.yml 照样被触发，工作流把附件补进这个 Release，`docs/releases/<tag>.md` 的说明放在最前，后面接着 GitHub 自动生成的变更列表。

发出去以后的核对：下载全部附件，逐个对照 SHA256SUMS；伙伴模组的 jar 要和 `internal/companion/jar/manifest.json` 的 sha256、大小一致；exe 是 GUI 子系统、里面有新版本号；在 wine 里用 `-nogui` 启动一次，首页能打开；`releases/latest` 仍是上一个正式版（预发布不推给老版本）。

### 起因

v3.0.0 发布以后有了真实用户，呼声最高的一件事是：能不能把以前自己开的服务器收进 MineDeck 统一管理。有一位用户这样问作者：导入服务端以后少了很多配置文件，能不能把文件全部覆盖过去再启动；整合包要 Java 25，这台服务器显示的却是 17，能不能改，改了会不会出问题。

查下来，3.0.0 里这两件事都没有正路。「导入」只认整合包（.mrpack 和 CurseForge 的 zip），做法是照清单重新下载、新建一台服务器，本来就不会带上用户老服务器里的配置。换 Java 的后端操作 `instance.java.set`（接口 `PUT /api/instances/{name}/java`）第三阶段就有了，可是界面上没有入口，只有 AI 助手会调。另外，Java 并不是「默认 17」：新建和导入时按 Minecraft 版本从官方元数据里取，1.18 到 1.20.4 是 17，1.20.5 到 1.21.x 是 21，26.1 起是 25。

给那位用户的答复（针对已经发布的 3.0.0）已经交给作者去回了，要点是三条。老服务器的文件可以拷进导入出来的那台服务器的文件夹里，但只拷存档、mods、config、server.properties 和几个名单文件，不要覆盖 `instance.json` 和 `run.bat`，也不要拷 `libraries` 和服务端的 jar。卡片上显示 Java 17 说明这台服务器是 1.18 到 1.20.4 之间的版本，先问清楚整合包到底是哪个 Minecraft 版本。3.0.0 里想换 Java，只能把 MineDeck 完全退出以后手动改 `instance.json` 里的 `javaMajor` 和 `javaPath`（程序开着的时候改不算数，设置是启动时读进内存的；测试报告里那条「改了没生效」就是这个原因），或者让 AI 助手去换。

### 做了什么

第一件，接管已有服务器。「新建服务器」页多了第三张卡片。用户选一个文件夹（可以点「浏览」，也可以直接填路径），点「识别」，后端只读地看一遍，认出核心、Minecraft 版本、启动文件和原来分的内存，填进表单；用户确认或修改以后点「接管这台服务器」，后台任务把这个文件夹就地登记成实例。文件不搬，存档、模组、插件和配置都不动。往文件夹里写的只有这些：MineDeck 自己的 `instance.json`；按这里的设置生成的 `run.bat`，原来有 `run.bat` 的先另存为 `run.before-minedeck.bat`；Forge 和 NeoForge 的 `user_jvm_args.txt`，原来的另存为 `user_jvm_args.before-minedeck.txt`，里面除内存以外的 JVM 参数带到「自定义 JVM 参数」里；`eula.txt`，只在原来没同意过、这次用户勾了同意时写；1.12 到 1.16.5 的 log4shell 缓解配置，和新建时一样。备份已经存在就不再覆盖，所以留着的总是用户最早的那份原件。接管失败不删任何东西，因为这个文件夹是用户的，不是半成品；这次动过的那几个文件还会恢复原样，失败之后文件夹和接管之前一模一样。

代码在 `internal/inst/adopt_scan.go`（识别）、`internal/inst/adopt.go`（校验、接管）和 `internal/inst/realpath_windows.go`（取文件夹的真实路径）。操作层登记了两个操作 `instance.adopt.scan` 和 `instance.adopt`，在 `internal/ops/catalog/instances.go` 的 `adoptOps` 里；网页接口是 `POST /api/adopt/scan` 和 `POST /api/adopt`。这两个操作要读主机上任意一个文件夹，所以和选文件夹、添加 Java 一样，只许人在本机操作，AI 和局域网里的设备都调不了。界面在 `app.js` 的 `drawAdopt`。请求和返回的字段写在 `docs/API.md` 的「接管已有服务器」一段。

这些文件夹不让接管：整个磁盘；MineDeck 自己的程序目录和它的上层；缓存、运行时目录里面的；和备份目录叠在一起的（在它里面，或者把它包在里面，后一种是怕连文件夹一起删服务器时把备份也删了）；存放服务器的总目录（内置的 servers 和设置里配的那个）；已经在列表里的服务器的目录，以及它的里面和外面；正在新建或正在接管的目录，以及它的里面和外面。比较路径时用的是真实路径：经目录联接（junction）、符号链接、subst 出来的盘符绕一圈进来的同一个文件夹，认得出是同一个。登记成实例的目录仍然是用户选的那个路径。文件夹里找不到能启动的东西会报错；如果它下一层有像服务器的文件夹，报错里会点出名字，因为最常见的错是选到了上一层。

接管时后端会重新识别一遍，不信请求里带来的东西：启动文件必须是这次识别出来的候选之一；指定的 java.exe 必须在已知的 Java 列表里，这一条在操作层查，免得有人借接管让程序去执行任意一个 exe。

第二件，「移出列表」。以前删除服务器时不勾「同时删除服务器文件夹」，只是把它从内存里的列表拿掉，`instance.json` 还在，下次启动又被扫出来，界面上也是这么如实写的。现在不勾选时，后端把 `instance.json` 改名成 `instance.json.bak`，重启后不会再出现；以后想加回来，用「接管已有服务器」选这个文件夹，原来的名称、内存、JVM 参数、定时任务、控制台编码都从 `.bak` 里带回来。这个改动对所有服务器都生效，不只是接管进来的。接管进来的服务器在 `instance.json` 里多一个 `adopted: true`，删除确认框对它默认不勾「同时删除文件夹」，并且写出是哪个文件夹；不勾选时按钮上的字是「移出列表」，不是「删除服务器」。

第三件，换 Java 的入口。每台服务器的「内存 / 启动」页多了一个 Java 选择框，列出 MineDeck 下载的、本机装的，再加上本机还没有但可以现下一份的版本（8、11、16、17、21、25），标出现在用的是哪个。选一个本机已有的，点「更换 Java」立刻生效（下次启动用它）；选本机没有的，后台下载便携版，转到任务页看进度。接管的表单里也能选 Java，默认是「自动」。原来那句写死的「MineDeck 下载的」去掉了，它在用本机 Java 的服务器上是错的。启动时找不到 Java 的报错也改了，以前让人「删掉这个实例再新建」，现在让人到「内存 / 启动」里重新选。

任务页原来的说法全是「部署」「创建」，接管和换 Java 也走这一页，所以任务多了一个 `kind`（没有是部署，`adopt` 是接管，`java` 是换 Java），界面按它换标题、完成提示和完成后去哪里。

### 识别靠什么

Forge 和 NeoForge（1.17 起）看 `libraries` 下面的 `win_args.txt`，里面有 `--fml.mcVersion` 和加载器版本；装过好几个版本的都列出来，原来的启动脚本点名用的那个优先，否则加载器版本新的优先。新版 Forge 放在根目录的 `forge-…-shim.jar` 和参数文件是同一个服务端的两种启动写法，有参数文件时只列参数文件。根目录里的 jar 逐个打开看：清单里的 Main-Class，原版 jar 根上的 `version.json`（里面有版本号和它要的 Java），Paper 系的 `META-INF/versions.list`，Fabric 启动器的 `install.properties`，老 Forge 看文件名。旁边同时有加载器和原版 jar 的，选加载器；认不出的 jar 和原版 jar 放在一起时选认不出的那个（Arclight 这类混合服就是这样摆的）；同一种服务端新旧两个 jar 都留着时选版本新的。jar 自己没写版本时，依次看 `logs/latest.log` 里的「Starting minecraft server version」、旁边的原版 jar、目录结构（Fabric 的 `.fabric/server`，原版和 Paper 的 `versions`）。

原来的启动脚本（根目录的 bat、cmd、ps1、sh）一行一行看：注释掉的行不算；`-jar` 后面的文件名可以带引号、带 `%~dp0`；内存取点名那个启动文件的那一行里的 `-Xmx`。有 Windows 的脚本时不看 `.sh`，因为 Forge 安装器会同时留下 `run.bat` 和 `run.sh`，用户后来往往只改了前一个。`user_jvm_args.txt` 按 Java 参数文件的写法读：行尾的 `#` 注释不算参数，带空格的参数带不过来（界面上的 JVM 参数是按空白分开的），会数出来提醒用户。认不出核心时表单里留空让用户选，Spigot 和 Paper 的分支按 Paper 管，BungeeCord 按 Waterfall 管，表单上会说明。

这些规则里，Forge、NeoForge、原版和日志那一条，拿作者机器上真实的服务器核对过（`D:\MineDeck\servers` 里的 S1、S2 和缓存里的原版 1.21.1，只读地跑了一遍识别，结果都对）。Paper 系和 Fabric 是照它们启动器的源码写的（PaperMC/Paperclip 读 `META-INF/versions.list` 和 `main-class`，FabricMC/fabric-installer 的 ServerLauncher 读 `install.properties` 里的 `game-version` 和 `fabric-loader-version`），这台机器上没有真实的 jar 可以对。老 Forge、Mohist、Banner、Velocity、Waterfall、Leaves 的 Main-Class 是凭印象写的，没有核对。认错了也不要紧到哪里去：表单上都能改，接管以后 Java 也能换；但发版前最好各拿一个真实的服务端试一次。

### 验证过的

Go 的测试全过，新加的在 `internal/inst/adopt_test.go`、`internal/inst/adopt_review_test.go`（复审指出的问题，一条一个用例）和 `internal/ops/catalog/adopt_test.go`：三十来种目录内容的识别、哪些文件夹不许接管（包括经目录联接进来的）、接管 NeoForge 后每个原有文件逐字节没变而两份备份和原件一致、中途失败后文件夹恢复原样、没同意 EULA 时拒绝且什么都不写、离线时怎么定 Java、请求里的启动文件和 Java 不可信、同一个文件夹及其上下层不能同时接管、移出列表后重新扫描不再出现、再接管时设置带回来。这些测试用一个已经取消的 context 跑，不联网。失败恢复那一条做过反向检查：把恢复那一行去掉，测试会挂。`go vet`（要测的几个包）和 gofmt 干净。

界面测试 `tools/ui-dev` 当时一共 95 条全过，其中 4 条是新加的（接管的流程两条、换 Java、删除确认框）；把 main 并进来以后加上 PR #3 带来的用例是 108 条，也全过。仿真后端加了对应的接口，`/__mock/state` 多了 `inst`、`instReset`、`adoptScan` 三个开关，说明写在 `server.js` 里那段注释中。新加的界面文字只多了两个字，都在 GB2312 里，内嵌字体不用重新生成（`build_fonts.py --check` 在这台机器上缺 brotli 跑不起来，是另写了几行脚本比的）。

真后端也跑了一遍。把 exe 编到一个临时文件夹里启动，另造一个「老服务器」文件夹：一个自己编译的小 jar，启动后打印一行 `Done`、读到 stop 就退出，加上用户自己的 `run.bat`、插件和存档文件，路径里带中文。然后用脚本在真实界面上操作：选到上一层时报错里点出了文件夹名；识别出启动文件和原来的 1536 MB 内存，提醒没认出类型；选类型、填版本、选 Java 17，接管；任务页显示接管完成；启动后控制台里是 Java 17、1536M、中文没乱码，状态变成运行中；发命令、停止都正常；列表里这台是接管进来的、用的是本机的 JDK；删除确认框默认只移出列表；移出后重启程序，列表是空的；再接管时名称、类型、版本、内存都带回来了。磁盘上核对过：原来的 `run.bat` 和备份逐字节一样，插件和存档文件没动。这个假 jar 是按代理端接管的，所以没有碰 Minecraft 的 EULA。

### 没验证的、要知道的

没有用真实的 Minecraft 服务端走过完整的接管再启动。原因是那要在测试里替人同意 Mojang 的 EULA，我没有这么做。请作者拿自己的服务器试：把 `D:\MineDeck\servers\S1` 复制一份到别处（比如 `D:\adopt-test\S1`，复制品里的 `instance.json` 可以留着也可以删掉，两种都值得试），在新版里接管它，启动，进服看一眼。原生窗口里点「浏览」弹出的系统文件夹选择框也只有真机能试。选一个本机没有的 Java 版本、看它下载完再换上，这条路在仿真后端上测过界面，真的下载没有跑。

几件要知道的事。接管一个文件夹以后，它的上一层会被记成扫描根，所以下次启动时，上一层里别的带 `instance.json` 的文件夹也会出现在列表里（比如老版本 MineDeck 的 servers 目录，接管其中一台，重启后另外几台也回来了）；这多半是用户想要的，但会有点意外。服务器直接放在盘根下面（比如 `D:\server`）时，扫描根就是 `D:\`，启动时会把盘根下每个文件夹看一眼有没有 `instance.json`，很快，但值得知道。原来的启动脚本里除内存以外的 JVM 参数不会自动带过来（只有 `user_jvm_args.txt` 里的会），表单上有提醒；脚本里传给服务端的程序参数也不带，MineDeck 一律加 `nogui`。原来的服务器还开着就去接管不会出错，但启动时端口会冲突，表单上写了要先关掉。

README 的功能表加了一行「接管已有服务器」，「Java 不用自己装」那行加了一句可以换。介绍页 `site/` 和发布说明还没写，发版时再补。

### 复审

按作者的规矩，Claude 写的代码要交别家模型做只读复审。这次的经过：MiMo Pro 额度用完了（接口返回 429）；Grok 没登录，而且带自动批准工具的调法会被 Claude Code 的安全分类器拦下；最后用的是 Gemini 4 Argon（medium），不给它任何工具权限，把代码分两份贴进提示词让它挑错（命令行有长度上限，所以分两份：一份是校验、接管、删除，一份是识别）。它一共提了十九条，逐条核对后成立并改掉的有这些：

- 接管中途失败时，前面已经改过的文件没有恢复。现在先记下要动的几个文件的原样，失败就全部恢复。
- 移出列表后再接管、这回改用 Forge 的参数文件启动时，用户写在 `user_jvm_args.txt` 里的参数会丢。现在只要用参数文件启动，就把这个文件里的参数并进来再改写它。
- 目录的比较只按字面，目录联接能绕过去，同一个文件夹可能被接管两次。现在按真实路径比（Go 1.23 起 `filepath.EvalSymlinks` 在 Windows 上不解目录联接，所以用的是 `GetFinalPathNameByHandle`）。
- 识别文件夹要花时间，这期间另一个请求可能接管了它的上层或下层。现在拿着锁再查一遍，正在接管和正在新建的目录也算在内；新建流水线为此在 `validateCreate` 里多占了一个目录的位，`CreateAsync` 和 `ImportModpackAsync` 结束时放掉。
- 把备份目录包在里面的文件夹没有拒绝。
- 移出列表时，`instance.json` 被人改过名字或改坏了就不改名，下次启动又冒出来。现在只要这个文件在就改名。
- 启动脚本里注释掉的旧命令被当真；Forge 留下的 `run.sh` 压过了用户改过的 `run.bat`；`"%~dp0xxx.jar"` 认不出；内存只认脚本里的第一个 `-Xmx`。
- `user_jvm_args.txt` 行尾的注释被当成参数带进来，会让服务器起不来。
- Forge 跨 Minecraft 版本升级过的目录里，版本新旧比反了（目录名是「Minecraft 版本-Forge 版本」，不能整个拿来比）；带 `-beta` 的排到了正式版前面。
- 新版 Forge 的 `shim.jar` 被当成另一个启动文件列出来；没有连字符的文件名（`purpur.jar`）认错；改了名的 Mohist、Banner、BungeeCord 认不出版本；安装器装的 Fabric（原版 jar 在 `.fabric/server` 下面）认不出版本。
- 认不出的 jar 排在原版 jar 后面，混合服会选错；新旧两个 jar 并存时按文件名选到了旧的。
- 几个小的：`level-name` 带子目录时存档判断错；信了原来的设置之后候选的说明没跟着改；`-Xmx` 后面的数字特别大时溢出；选错成有几十万个文件的文件夹时一次读完整个目录（现在每个文件夹最多看 5000 项）。

没有照改的几条和原因：它说 `writeRunBat` 吞掉了写 `user_jvm_args.txt` 的错误、内存设置会不生效，这是它没看到 `launchArgs` 造成的误会，MineDeck 启动时内存是直接写在命令行上的，不靠那个文件。删除和启动之间的竞态是原来就有的，不是这次引入的，没有动。jar 里声明的条目特别多会占内存，这要有人故意造一个坏 jar 放进自己的服务器文件夹，没有处理。它还提到程序目录里别的子文件夹（不是 servers、cache、runtimes、backups）可以被接管，这是有意留的口子，方便把老服务器直接拷进 MineDeck 文件夹里的人。

改完以后 Go 测试、界面测试和真后端的那一遍都重跑过。复审之后改的这些没有再交给别家看第二轮。

## 2026-11-09 导入魔改模组：逐文件处置、本地继承、Java 事前提示（Mistral Vibe 写）

分支 `fix-custom-mod-choice`，从 main（3ec1dcc）开。用户反馈原文：「导入本地已有的之前已经运行的服务器仓库，一些魔改的模组不受信，无法下载，希望能加上选择功能」。用户是 1.20.1 服（官方元数据给 Java 17），魔改模组要 Java 25，切换 Java 之后魔改的 MOD 仍显示「不受信」无法自动下载。

### 触点判定（没有复现原始触点，按候选路径做的普适机制）

Go 代码里没有「不受信」字样，全仓核了一遍用户可见文案后，最像用户看到的两句话是：

- mrpack（Modrinth 格式）路线：`internal/modpack/modpack.go` 的 validateDownloads 原文案「整合包里有不允许的下载地址（只允许 https 的 Modrinth、GitHub、GitLab）：…」——魔改模组常由作者挂在自建站点（https 但不在白名单内），此前在解析阶段就拒绝**整个**整合包，用户没有任何逐文件发言权。这句最像「不受信、无法下载」。缺 SHA-1 的文件也是同样整包拒绝。
- CurseForge zip 路线：`internal/inst/import.go` 的 cf-unresolved 告警「N 个模组需手动补装…无法自动下载」——单文件降级、导入能完成，但用户只有一张清单没有处置权。

字面上像「导入本地已有仓库」的「接管已有服务器」（adopt.go）被排除：它就地登记文件夹，全程不下载、不校验 mods，不可能产生这些文案；切换 Java 的接口本来就有，与「无法下载」零因果。**未复现原始触点**：PR 正文已如实写明，实现的是覆盖两条候选路径及其同类的普适机制，需按用户原始反馈回归验证。

### 做了什么（三件套，四个模块提交）

第一件，导入期逐文件处置。解析不再整包拒绝：白名单外直链（host）、缺校验值（nohash）、非 https（badurl）的文件进「待决清单」；下载后 SHA-1 对不上（dl 新增 ErrVerify 哨兵，inst 据此降级）、CurseForge 未解析（cf）也进清单，网络失败仍算整次失败（保持原行为，重试很快）。任务快照新增 `pending[]`（逐项带原因、说明、候选地址、SHA-1、可用处置），已结束的任务也保留，处置接口是 `POST /api/import/pending/{taskId}`（操作 `instance.import.pending`，仅人工 + 仅本机）：每项可选 skip（记入任务日志）/ local（给本地文件或目录，目录按相对路径、mods、plugins 下的同名文件匹配，复制进实例、内容不校验）/ trust（确认自定义站点后下载）。「导入待决清单.txt」进了实例目录留底，任务摘要带 pendingCount。

第二件，本地继承。导入表单新增「本地来源目录（可选）」（CreateReq.LocalSource，和 root 一样仅本机生效）：待决文件凡整合包覆盖目录（用户把魔改 jar 随包带的情形，覆盖目录本来就不校验）或这个目录里已有的，按原样复制进实例、列进「按原样保留」（import-kept）告警，不再要求线上匹配——这是用户诉求的主场景；目录里没有的才留在待决面板。

第三件，Java 事前提示。`modinfo` 新增 `JavaMajorOf`：解析 fabric.mod.json 的 `depends.java`（如 `">=25"`）和 mods.toml 的 java 区间（如 `[25,)`，多种写法都认，8–40 以外不当 Java）。导入收尾扫 mods/plugins 两个目录，要求高于实例 javaMajor 时给 java-req 告警（点出是哪个模组要什么版本）；`instance.mods.list` 的响应多 `needJava`，实例详情页头据此显示提示行，两处都给「内存 / 启动」的换 Java 入口。只提示不阻断：1.20.1 配声明 Java 25 的模组是允许的组合。

信任站点的安全边界：任何选择都不放宽到非 https 或私网地址——trust 只对 host 类待决开放，地址必须在候选之列，主机解析到内网 / 本机 / 回环 / 链路本地 / CGNAT 的一律拒绝（IP 字面量和 DNS 解析出来的每条记录都查，授予信任和每次下载各查一遍，防 DNS 变动），首次每个站点必须用户在面板里读过风险说明后确认（ack），下载必须过整合包声明的 SHA-1。确认记进全局配置 `trustedHosts`（带作用域字段 `scope=modpack`，确认按域名记忆——不同端口也一并信任，同站点第二次导入不再列为待决——Reclassify 在导入启动时带记忆重过一遍）；`PUT /api/config` 不收这个键，不存在「默认信任一切」的口子。SSRF 防线（白名单 + https）原样保留在自动下载链路上，并新增执行层：整合包文件下载（自动的和 trust 的）都走 `dl.GuardedClient`——拨号级（每个解析出的 IP 连接前过公网检查，信任站点日后被解析到内网也连不出去）与重定向级（302 跳到 http 或允许列表之外的站点即中断），地址段判定收敛为 `dl.AddrIsPublic`（modpack 的 HostIsPublic 复用它）。评审指出的两个必修（host 待决项丢 SHA-1、信任记账后缺连接级检查）照此修掉。

### 验证过的

- `go test ./...` 全绿（本机 Windows，各包逐个跑过）。新增测试：modpack 逐文件分类与 HostIsPublic（不依赖外网 DNS 的 IP 字面量用例）、dl ErrVerify、tasks 待决清单的快照/摘要/处置、inst 收尾记账、本地匹配规则、逐项处置成败混批、**信任下载**（注入假 HTTP 客户端不联网：站点是公网 IP 字面量，ack 门、同站点二次免确认、SHA-1 校验）与安全门全关（候选外地址 / 非 https / 内网 IP / 没 ack 一律拒绝且不记信任）、catalog 权限门与 needJava、web 路由表四行。
- `tools/ui-dev` 111 条全过（新增 3 条：待决面板全流程含未确认信任被留清单、本地代替没给路径拦下、实例详情 Java 提示与表单字段；仿真后端加 `/api/import/pending/{taskId}` 和 `/api/instances/{n}/mods`）。字体子集按老办法只比了字符集：新文案没有出现 GB2312 之外的字（em dash、⚠、✔ 都是现有代码已在用的）。

### 没验证的、要知道的

- **信任下载的真实网络路径**只跑过注入假客户端的测试（Unresolved-file 到公网站点的真实下载、重定向、大小写主机名等真实 Internet 行为没跑）。Go 侧也没有完整走一遍「真整合包解析→导入→处置」的端到端（runCreate 要联网下载核心），分层的单测覆盖了各段；发布前最好拿一个带自定义直链的真整合包试一次。
- 信任站点记的是主机名（端口跟着文件的地址走）：`a.com:8443` 和 `a.com:443` 视为同主机，信任是「这个域名可以下载」，不是「这条 URL」。主机名下列出 K 条不同端口的候选都会被放行。
- 导入中拒掉的 `hash` 待决项不再给 trust（重下也多半对不上），只给跳过 / 本地代替；badurl（非 https）任何处置都不下载。
- `GET /api/instances/{name}/mods` 现在 400 的场景（vanilla / 代理端没有模组目录）不变，前端封了静默。
- 已知偶发失败 `internal/companion` 的 TestServiceAutoConnect 与本轮无关（main 的交接说明里记过），遇到重跑即可。
