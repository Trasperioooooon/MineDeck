# 工具箱：首版调研与方案备忘

BRANCH `wt/b3-toolbox`。本文记录工具箱模块首版两个工具（「离线皮肤包生成」与「导出 Modrinth 整合包」）的协议与源码依据、参考开源项目许可证边界，以及围绕朋友联机服务器调研的十余项辅助工具思路与后续优先级判断。

## 一、底层规则与一手核对

### 1.1 Java 版离线皮肤分配机制与资源包格式

正版玩家进服时客户端向 Mojang 会话服务器拉取带签名的材质地址；离线服（`online-mode=false`）缺少这层签名验证，客户端对未知皮肤的玩家会按 UUID 映射到内置默认皮肤贴图。要让朋友们在原版离线客户端里互相看见各自皮肤（而不安装自定义皮肤站 Mod / SkinRestorer 等插件），标准解法是发给每位玩家一份资源包，直接覆盖对应的默认皮肤纹理路径。

核对 Mojang 客户端反混淆逻辑及社区公开规范：

1. **离线 UUID（Version 3）**：无论是原版服务端 `UUIDUtil.createOfflinePlayerUUID` 还是 MineDeck 现有的 `internal/inst/players.go`，生成规则都相同——对 `"OfflinePlayer:" + <玩家名>`（区分大小写）做 MD5 摘要后按 RFC 4122 置入 Version 3 与 Variant 2 位。
2. **默认皮肤槽位挑选**：客户端通过 `Math.floorMod(profileId.hashCode(), DEFAULT_SKINS.length)` 从内置数组取值。其中 Java `UUID.hashCode()` 等于将 128 位 UUID 拆成高 64 位与低 64 位做异或 `long hilo = mostSigBits ^ leastSigBits`，再对高低 32 位异或 `(int)(hilo >> 32) ^ (int)hilo`；四个 32 位大端有符号整数依次异或的结果完全等价。需要注意的是 `Math.floorMod` 针对负数余数向负无穷取整，这和 Go/C 的截断取余 `%` 不同——负数哈希直接用 `%` 再偏移错位是常见坑点。
3. **1.19.2 与 1.19.3 的分水岭**：
   - `<= 1.19.2`：客户端仅内置 2 套默认皮肤，对应资源包路径 `assets/minecraft/textures/entity/steve.png`（经典 4px 手臂）与 `assets/minecraft/textures/entity/alex.png`（纤细 3px 手臂）。如果朋友超过 2 人，在未引入任何皮肤 Mod 的纯原版环境下必然会撞进同一槽位；此时界面应明确告警并让用户抉择，或在允许覆盖公共模板时使用顺位替换。
   - `>= 1.19.3`：Mojang 在 `DefaultPlayerSkin.DEFAULT_SKINS` 扩展到 9 名角色（`alex`、`ari`、`efe`、`kai`、`makena`、`noor`、`steve`、`sunny`、`zuri`）各带 `slim` 与 `wide` 两套模型，总共 18 个固定槽位，前 9 项为 `assets/minecraft/textures/entity/player/slim/<角色>.png`，后 9 项为 `assets/minecraft/textures/entity/player/wide/<角色>.png`。离线玩家的粗细手模型同样完全由 `hashCode` 决定，资源包只能替换贴图内容，无法把命中的 `slim` 槽位强行渲染为 `wide`。
4. **旧版 64×32 皮肤升级**：玩家常从老皮肤站下载到 1.8 之前的 `64×32` 单层 PNG。如果原封不动放进现代默认皮肤路径，渲染时左腿、左臂和外层衣物像素位置会错乱甚至整片透明或拉伸。工程处理应在打包期统一扩充为 `64×64` 画布：先保留上半部分 `0..31` 行像素，将右腿区域（宽 16×高 16，源 `(0,16)`）复制到左腿位 `(16,48)` 并分别水平翻转正面/背面/顶面/底面及左右侧面对应块；右臂区域（宽 16×高 16，源 `(40,16)`）按同样 UV 布局扩充复制到左臂位 `(32,48)`。
5. **跨版本 `pack.mcmeta` 规范（1.8 ~ 26.1）**：
   - 早期版本使用整型 `pack.pack_format`（如 `1.8=1`、`1.12=3`、`1.16.5=6`、`1.20.1=15`、`1.21.4=46`、`1.21.5=55`、`1.21.6=63`、`1.21.7–1.21.8=64`）。
   - 自 `1.21.9`（资源包格式版本号 `69`）及之后（含 `1.21.11=75`、年份版本 `26.1=84`、`26.2=88`、`26.3=97.1`），Minecraft 改用 `min_format` / `max_format`，可以写整数或 `[major, minor]`；`max_format` 写整数表示这个大版本下的任何小版本，写成 `[97, 0]` 反而会把 26.3 的 97.1 排除在外，所以工具箱一律写整数（主会话 2026-11-16 复审时对照 Minecraft Wiki 改正，原稿写的是数组、表里只到 26.1）。格式版本号达到 `65` 以上时不再携带旧版 `supported_formats`。比表里更新的版本按最新一档算，客户端会提示「为旧版本制作」，确认后照样能用。

### 1.2 服务端下发资源包与外部托管边界

`server.properties` 原生支持三个参数控制全服统一下发资源包：
- `resource-pack=<HTTPS 或 HTTP 直链>`
- `resource-pack-sha1=<40 位十六进制小写 SHA-1>`
- `require-resource-pack=true|false`

工具箱首版**有意不直接修改或覆写已有服务器的 `server.properties`**，原因有三点：
1. MineDeck 是桌面管理端而非公网 CDN；如果把本机内网地址或仅在运行期开启的临时 HTTP 下载端口填进 `resource-pack`，通过穿透、跨网段甚至服务端重启后地址一换，朋友的客户端进服便会拉取失败（勾选 `require-resource-pack=true` 时甚至直接踢出玩家）。
2. 工具箱定位是「无副作用的工具集」——生成好的 `.zip` 与 `说明.txt`、以及一点击复制的 40 位 `resource-pack-sha1` 交给服主：本地少人游玩时发文件进 `.minecraft/resourcepacks/` 最稳妥；若确需全服自动推包，服主上传到对象存储/网盘直链后，在服务器的「设置 → 全部配置」里填 `resource-pack` 和这个 `resource-pack-sha1` 即可，权责清晰、不埋隐患。

### 1.3 Modrinth 整合包（`.mrpack`）格式规范

依据 Modrinth 官方 Format Definition（`formatVersion: 1`）：
- 包体本质为 ZIP 压缩包，后缀 `.mrpack`。根目录必须存在 `modrinth.index.json`，核心字段包含：
  - `formatVersion`: `1`
  - `game`: `"minecraft"`
  - `versionId`、`name`、`summary?`
  - `dependencies`: 键名必须使用规范标识——`"minecraft"`，以及 `"fabric-loader"`、`"forge"` 或 `"neoforge"`（注意 Fabric 键名不是 `"fabric"`）。
  - `files[]`: 每条含 `path`（以 `/` 分隔，如 `"mods/create-mc1.20.1.jar"`，禁止 `..` 与绝对路径）、`hashes.sha1` 与 `hashes.sha512`（两者在规范中均为必填）、`downloads[]`、`fileSize`，以及可选 `env.client` / `env.server`（`"required"` | `"optional"` | `"unsupported"`）。
- `overrides/` 目录内的文件在客户端启动器解包时原样覆盖到 `.minecraft/` 根目录（例如 `overrides/mods/xxx.jar` 对应无官方直链的自制或闭源模组，`overrides/config/...` 对应服主调好的模组配置）。
- **安全与隐私过滤（实例导出模式）**：服务器 `config/` 下常混杂第三方插件密钥、RCON/数据库口令、甚至 MineDeck 自己的内部桥接令牌（`config/minedeck/`）或 `.db`/`.sqlite` 本地数据。导出端除了复用 `modpack.AllowedURL`（仅保留 Modrinth CDN、GitHub Releases 等白名单 HTTPS 下载地址到 `files[]`，其余改走 `overrides/mods/`），对 `config/` 也按文件名、扩展名和内容过滤：名字里带 password、token、secret、discord、mysql、luckperms 之类的，`.db`、`.pem`、`.key`、`.env`、`.log` 这类文件，以及文本配置里写着 `xxxToken = "一串值"`、`"apiKey": "…"` 的，都不打进包，跳过的文件列在预览的提醒里。（原稿写了这句但代码里没有做，主会话复审时补上。）

## 二、参考开源项目与许可证核查

在设计数据结构与校验规则前调研了以下公开项目，明确只借鉴格式理解与行业惯例，不复制任何代码片段：

| 项目 | 仓库 / 许可证 | 借鉴与边界说明 |
|---|---|---|
| **packwiz** | `packwiz/packwiz`（**MIT**） | 参考其对 `.mrpack` `dependencies` 键名（`fabric-loader` / `neoforge`）及 `env.server` / `env.client` 默认值的处理方式，以及 `hashes` 双校验字段与 `overrides` 分流原则。MIT 许可宽松，本次仅作格式行为对照，具体打包实现全部按 Go 标准库和 MineDeck 既有模块重写。 |
| **HMCL** | `HMCL-dev/HMCL`（**GPLv3**，附带附加条款） | 对照其 Modrinth `.mrpack` 导出与导入解析逻辑、`files[]` 下载域名白名单安全校验以及旧版 `64×32` 皮肤在启动器预览面板里的扩充贴图坐标系。由于 GPLv3 的强传染性（MineDeck 当前尚未以 GPLv3 开源发布），严格做到只查资料与对照思路，不引入、不移植其任何源码。 |

## 三、联机朋友服高频需求头脑风暴与首版聚焦

围绕「朋友一起开私服/模组服」常见折腾点，结合 MineDeck 现有的架构能力，梳理了 12 个候选工具构想：

1. **离线皮肤包生成**（已入选首版）：解决 `online-mode=false` 好友联机时所有人顶着同款默认 Steve 的痛点，零服务端侵入。
2. **导出 Modrinth 整合包（`.mrpack`）**（已入选首版）：解决「建完模组服后怎么把模组打包发给朋友」的最后一公里问题，打通创服选模组与客户端分发。
3. **跨世界维度裁剪与区块清理器**（待排期）：随着游玩时间增加，跑图导致世界体积膨胀到十余 GB；按中心坐标+半径或玩家活跃热区裁剪未建造区块（如只删 `r.*.mca` 中 inhabited time 极低的区块）。风险：写坏 `.mca` 会毁坏存档，需与备份/恢复点强绑定，不适合轻量化工具箱首版匆忙上线。
4. **局域网直连一键配置包 / 服务器入口卡片生成器**（待排期）：生成一张可分享的连接信息卡（含穿透域名/端口、所需核心与客户端版本、配套整合包/皮肤包 SHA-1 与文字教程），方便群里新人照着连。
5. **`server.properties` + 游戏规则中文对比/模板转换器**（待排期）：针对「生电空岛」「RPG 副本」「养老原版」切换整套 `gamerule` 与 `server.properties` 预设，并高亮差异项。
6. **白名单批量管理与玩家 UUID 互查器**（待排期）：输入一批玩家 ID 一次性算出离线模式 UUID、正版 API UUID（可选联网）及 `whitelist.json` JSON 片段，解决玩家先离线玩后来转正版时 `playerdata/<uuid>.dat` 迁移改名的问题！
7. **整合包模组端侧分类审查与精简器**（待排期）：批量扫描本地一群现成 `.jar`，识别仅客户端模组（小地图、动态光源、光影补丁、JEI/REI UI 插件）并一键隔离出服务端 `mods/`，降低「直接把客户端 mods 拖进开服文件夹导致服务端崩溃」的概率。
8. **崩溃日志与卡死线程快照离线体检**（待排期）：解析单个 `.log` 或 `crash-reports/`，按本地已知特征规则标出常见缺前置、Java 版本不对、Mixin 冲突模组，方便没有配 AI Key 时自助排障（目前部分已整合进助手排错资料打包流程）。
9. **自定义 MOTD 色码与渐变预览器**（待排期）：支持 `§` 十六色、Minecraft 1.16+ RGB Hex 渐变效果、服务端图标（`64×64 server-icon.png`）裁剪转码并实时还原多人游戏列表效果。
10. **Datapack 数据包合集与合成表冲突检查**（待排期）：扫描一个世界里所有启用的数据包 ZIP/文件夹，检查命名空间函数与战利品表覆盖关系。
11. **红石高频 / 实体拥堵诊断摘要助手**（待排期）：读取 Spark 报告或原版 `/debug` 输出，把高频卡顿坐标和实体数量排名前十转成人话提示。
12. **跨版本 Java 端口与系统防火墙连通性自检器**（待排期）：一键测试主机本地环回、局域网网卡监听与 Windows 防火墙放行规则，输出图文排查结论。

### 下一步最值得做的 Top 3 候选工具评估

除了首版已经落地的皮肤包与 `.mrpack` 导出，后续若继续扩充 `toolbox.js` 工具矩阵，优先推荐这三项：

| 排序 | 工具 | 为什么值得做 | 估算复杂度 | 主要参考与前置依赖 | 风险与规避 |
|---|---|---|---|---|---|
| **1** | **正版 / 离线玩家 UUID 迁移器（含 `whitelist.json` / `playerdata` 重命名）** | 朋友服极常遇到「一开始没开正版验证先玩了几天，后来凑齐正版想打开 `online-mode=true`」，切开关后所有人的背包、末影箱、成就瞬间清零。用现有 `OfflineUUID` 算法配合物理停服检测即可解决大痛点。 | **中低** | Mojang `OfflinePlayer:` 算法 + `Mojang API` 批量查正版 UUID（`/profiles/minecraft`）+ 已有服务器停服锁 | 必须强校验目标服务器处于停止状态，迁移前生成一份 `playerdata/` 快照备份，且目标文件已存在时禁止直接覆盖。 |
| **2** | **服务端仅客户端模组隔离审查器** | 从各种整合包网盘拖来的 `mods/` 往开服包里一放经常因为 `Sodium`、`Iris`、`Sound Physics`、`Mouse Tweaks` 等仅客户端模组报 `invalid dist DEDICATED_SERVER` 崩溃。利用既有 `modinfo` 与 `modcart` 批量识别 `server_side=unsupported` 并列出清单，比发去问 AI 快得多。 | **低** | 复用 `internal/modinfo` 与 `internal/modcart` `LookupSHA1` 批查 | 仅依赖 jar 元数据有漏判风险（部分老模组不写端侧声明），因此首版宜做到「标注高概率仅客户端 + 让服主勾选停用为 `.jar.disabled`」，不做静默删除。 |
| **3** | **连接名片与客户端图标（`server-icon.png` / MOTD 色码）工坊** | 复用已有的 `renderMotd` 预览和像素头像组件，把任何图片自动缩裁为合法的 `64×64 PNG server-icon`，顺带导出含穿透地址、版本要求和开服说明文本的群公告卡片，投入小但体感提升明显。 | **低** | 标准库 `image` + 现有 `renderMotd` 渲染函数 | 本工具箱仅输出下载或写入显式选中的服务器图片，不隐式修改远程开服配置。 |
