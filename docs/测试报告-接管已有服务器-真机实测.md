# 「接管已有服务器」真机实测报告

日期：2026-11-09 晚。被测的是从 main（3ec1dcc）编出来的程序，在作者的 Windows 11 电脑上跑，用的是真实的 Minecraft 服务端。

## 结论

要测的步骤一共 31 步，全部做完，功能上都和预期一致：识别、接管、启动真实的服务器、换 Java、移出列表再接管、带原设置的文件夹、连文件夹一起删。作者 `D:\MineDeck` 里的原件前后哈希完全一样，没有被动过。

有一件事值得作者拿主意，它不是出错，是实测把一个已知的行为摆到了眼前：接管了某个文件夹以后，程序下次启动时，同一个上层文件夹里别的带 `instance.json` 的文件夹会自己出现在列表里。细节见「发现」一节。

## 谁做的

这次实测本来全部交给 vibe 里的 GLM 5.3（思考档位 max，会话记录里的模型是 `zai-glm-5-3`）来做。它做完了前半段，后半段被 vibe 自己的安全层拦住了，是 Claude 照同一份说明补跑的。

GLM 做的：启动和基线，识别（只读），接管 NeoForge 的那台并让程序下载 Java 21，启动、发命令、停止，接管并启动 Forge 的那台。这些 Claude 没有照单全收，另外拿事先记的哈希、服务器自己的日志和程序的操作记录核对过，都对得上。

Claude 补的：识别里剩下的两个该被拒绝的情况，换 Java，移出列表再接管，带原设置的文件夹，连文件夹一起删，收尾。

GLM 没做完的原因：启动 vibe 时不能用「自动批准所有命令」（会被 Claude Code 自动模式的安全分类器拦下），用的是 vibe 自带的 `--smart-approve`。这一层把换 Java、改定时任务、删除这类 PUT 和 DELETE 的接口调用自动拒了。GLM 没有硬闯，停下来请求授权；回了它授权以后安全层照旧拦，接着 vibe 连 Mistral 的连接出了 SSL 错误，那一轮就结束了。两轮一共用了约 37 分钟。

## 测试用的东西

都在 `D:\md-adopt-test`，不在仓库里。`old` 里是从作者的 `D:\MineDeck\servers` 复制来的服务器副本：S1-plain 是 NeoForge 1.21.1，S2b-plain 是 Forge 1.20.1 的整合包，这两份去掉了 MineDeck 的痕迹，装成没用过 MineDeck 的老服务器；S1-managed 带着原来的 `instance.json`。端口改成了 25601 到 25603。`实测说明.md` 是完整的步骤和预期，`evidence` 里是每一步存下的原始输出，文件名以 `claude-` 开头的是 Claude 补跑时存的。

## 逐项结果

识别。两台老服务器的核心、版本、加载器版本、启动文件、原来分的内存、端口、是否同意过 EULA、有没有存档，全部认对；NeoForge 那台 `user_jvm_args.txt` 里的 `-XX:+UseG1GC` 被认出来并提示会带过来。五种不该接管的情况都被拒绝，提示也对：选到上一层时点出了下面三个文件夹的名字，选整个磁盘、选程序目录、不存在的文件夹、相对路径各有各的说法。识别前后文件夹的哈希完全一样，确实是只读的。

接管 NeoForge 1.21.1（S1-plain）。Java 选的是自动，程序按官方元数据定下 Java 21，本机没有，就从清华镜像下载了一份（21.0.13，压缩包 49 MB），从发请求到接管完成不到半分钟。接管之后文件夹里恰好五处不同：多了 `instance.json`、`run.before-minedeck.bat`、`user_jvm_args.before-minedeck.txt`，改了 `run.bat` 和 `user_jvm_args.txt`。两份备份和原件的哈希一样。存档、模组、配置一个字节都没变。

启动真实的服务器。服务器自己的日志里写着用的是刚下载的 Java 21.0.13，监听 25601，`Done (1.219s)`；从点启动到启动完成大约 15 秒。启动命令里内存是 5120M，带着 `-XX:+UseG1GC`。发 `list` 得到「There are 0 of a max of 15 players online」。停止后控制台写的是「服务器已正常关闭」。

接管 Forge 1.20.1（S2b-plain）。程序定下 Java 17，本机正好有，直接用了，没有下载。同样只有那五处不同。启动大约 26 秒，`Done (2.681s)`，日志里是 Java 17.0.20.1、端口 25603，正常关闭。

换 Java。换成本机的 Java 17 是立刻换好的，`run.bat` 跟着改了。换成 Java 25 时本机没有，程序起了一个下载任务，从清华镜像下了 25.0.5（压缩包 59 MB），连下载带换上一共 33 秒，任务的种类是 `java`。换回 Java 21 以后再开一次服，24 秒起来，正常关闭。

移出列表再接管。先给这台设了崩溃重启和一条 04:00 的定时重启，然后不删文件地移出列表：`instance.json` 变成了 `instance.json.bak`，存档、模组、配置都在。重启程序，它没有再出现。再识别这个文件夹，程序认出它以前被管过，名称、内存、JVM 参数都填好了。接管回来以后，崩溃重启和那条定时任务都还在，`.bak` 没有了，`run.before-minedeck.bat` 仍然是用户最早那份 `run.bat`，没有被 MineDeck 自己生成的盖掉。

带着原来 `instance.json` 的文件夹（S1-managed）。这份里记的 Java 路径指向作者另一处 MineDeck 的运行时。接管以后 Java 改成了这次测试目录里下载的那一份，原来的崩溃重启和 21:42 的定时命令都带了过来；文件夹里只改了 `instance.json`、`run.bat`、`user_jvm_args.txt` 三个本来就是 MineDeck 生成的文件，没有多出备份。启动 17 秒起来，正常关闭。

连文件夹一起删。对接管进来的这台带着 `files=1` 删除，整个文件夹没了，旁边两台不受影响。

收尾。被测程序和所有服务器都已关掉，没有留下进程，测试用的端口都空着。

## 发现

第一，同一层里别的 MineDeck 服务器会在下次启动时自己出现。接管 `old\S1-plain` 的时候，程序把它的上一层 `old` 记成了扫描根。之后重启程序，`old\S1-managed`（里面有 `instance.json`）没经过接管就出现在了列表里，名字是 `S1`，不带「接管进来的」标记，Java 路径还是它原来记的、指向作者另一处 MineDeck 的那一个。这件事在交接说明里记过，当时的判断是「多半是用户想要的，但会有点意外」。实测里它还带出一个连带的结果：原计划里「接管 S1-managed」那一步因此被拒绝了，提示是这个文件夹已经在列表里。后来把副本放到另一个上层文件夹里，才按原意测了这条路。

对真实用户来说，最常见的情形是老版本 MineDeck 的 `servers` 目录：接管其中一台，重启以后其余几台都回来了，而且它们的 Java 路径可能指向已经不存在的地方（启动时会提示去「内存 / 启动」里重新选）。建议改成只登记被接管的那一个文件夹，不把它的上一层当成扫描根，这样不会有没点过接管却自己出现的服务器。

作者当晚定了要改，第二天改完并验证过了：现在接管只登记被接管的那一个文件夹。用一个全新的程序目录重新试了一遍：接管 `old\S1-plain`，旁边的 `old\S2b-plain` 带着 `instance.json`；重启以后列表里只有 S1-plain。把它移出列表再重启，列表是空的；再接管回来，重启后还在。做法和别的验证记在交接说明里。

第二，vibe 的 `--smart-approve` 不适合跑这种测试。它放行了启动程序、识别、接管、启动服务器，拦下了换 Java、改定时任务、删除，以及「识别整个磁盘」「识别不存在的文件夹」这两个本意就是让程序拒绝的调用。下次想让别的模型把整套跑完，要么由作者自己在终端里用自动批准的方式启动，要么在 Claude Code 的设置里给这条命令加允许规则。

第三，vibe 每次启动都会在日志里写一句 `glm-5-3` 不可用、改用 Mistral Medium 3.5，这句话不能当真，原因和核对办法写在交接说明里。

## 没有覆盖的

这次是通过接口测的，没有在真实窗口里点界面：系统的选文件夹窗口（「浏览」按钮）、接管页和「内存 / 启动」页在 WebView2 里的样子，还要作者自己看一眼。界面的逻辑有 108 条仿真后端上的测试盖着。

真实的服务端只测了 NeoForge 1.21.1 和 Forge 1.20.1 两种。Paper、Fabric、老 Forge、Velocity 这些的识别规则只有单元测试，没有拿真实的服务端试过。

局域网设备和 AI 调不了接管接口这一条，只有 Go 测试盖着，这次没有在真机上试。
