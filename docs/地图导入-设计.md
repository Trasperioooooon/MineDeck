# 地图导入：首版设计

分支 `feat-world-import`。这份文件说清首版做什么、不做什么，导入引擎怎么保证出错时能回到原来的地图，以及验证分到哪几层。实现细节以代码为准，这里只记决定和理由。开工时间是 2026-11-13，写这份文件的是 Claude（主会话），需求来自作者交来的任务说明。

## 首版做什么

玩家手里有一份完整的 Java 版世界：下载来的冒险、空岛、跑酷地图，自己玩了很久的单人存档，朋友发来的旧服世界。首版让它能安全地用在两个地方：新建服务器时直接用这张地图开服，或者替换一台已有服务器正在用的默认世界，替换前留下恢复点，随时能换回去。对应任务说明里的场景 A 到 E。

两个入口共用一套引擎。新建服务器时，先选地图、读出摘要，再选核心和版本，地图在服务器登记进列表之前就放好，失败就整台不建，不会留下一台启动后随机生成新世界的实例。服务器详情里的入口叫「导入并替换当前地图」，默认保留这台服务器的核心、版本、Java、内存、端口、正版验证、模组插件、白名单、OP、穿透和各项管理设置，只换世界。

这些不在首版里，但会认出来并指到正确的地方：同一台服务器同时加载多个世界（多世界插件的事）；城堡这类建筑蓝图（.schem、.schematic、.litematic，要用 WorldEdit、Litematica 粘贴）；基岩版的 .mcworld（格式不同，改扩展名转不过来）；只有种子（新建世界时填种子，种子里没有建筑和玩家进度）；资源包、数据包、整合包和完整服务端、.mdpack 交接包（各有自己的功能）。RAR、7z、加密或分卷的压缩包，提示先解压，再选解出来的文件夹。

同一台服务器停服换图、再换回来，靠的是导入前的恢复点，不是多世界。

## 怎么认出一张地图

来源有三种：本机的世界文件夹、本机的 ZIP、局域网网页上传的 ZIP。本机文件夹只有坐在这台电脑前的人能选；局域网上的人只能上传自己的 ZIP，不能拿一个字符串让程序去读主机上的路径。

认地图看的是能解析的 level.dat 和真实的目录结构，不看扩展名，也不看文件夹是不是叫 world。根目录有没有 region 不作为条件：没生成过区块的空白世界、26.1 起的新布局都可能没有。只有 level.dat_old、level.dat 读不出来、只有零散的 .mca，都说清楚是哪一种，指出怎么补救，不替用户造一份 level.dat。

ZIP 里的世界可以在根目录，也可以套几层文件夹，旁边可以有说明书、截图、资源包。扫描有深度、条目数和体积上限。一个包里找到几张地图，就列出来让用户选，不默默挑第一个。旧 Paper 的 `X`、`X_nether`（里面是 `DIM-1`）、`X_the_end`（里面是 `DIM1`）认成同一张地图的三个维度，不显示成三张。数据包、资源包本身也是 ZIP，包里的 ZIP 一律不再往下解。

读到的元数据：最后保存的版本名和数据版本号（`Data.Version.Name`、`Data.DataVersion`）、是不是快照、地图名、`ServerBrands` 和 `WasModded`（用过什么核心和加载器的线索）、单人主人数据（旧版的 `Data.Player`，26.1 起的 `singleplayer_uuid`）、26.3 起的 `version_history`、数据包启用清单、游戏规则、难度和游戏模式、自定义维度。缺的字段就是缺，不补值。这些都只读，首版从不改写 level.dat。

## 版本和布局

开工前核对过的一手资料（2026-11-13）：

- Mojang 26.1 的世界存储改动（快照 6 起）：主世界从世界根目录搬到 `dimensions/minecraft/overworld`，下界、末地在 `dimensions/minecraft/the_nether`、`the_end`；根目录的 `data` 只放各维度共用的数据，文件按命名空间放进 `data/minecraft/`；`playerdata`、`advancements`、`stats` 搬进 `players/data`、`players/advancements`、`players/stats`；level.dat 里原来的 `Player` 标签换成指向玩家文件的 `singleplayer_uuid`。
- Paper 26.1：维度也搬进 `world/dimensions/`，每个维度自带 `paper-world.yml`，Paper 自己的数据在 `data/paper/`。Paper 的迁移文档写明，26.1 起从 Paper 换回原版，要把 `game_rules.dat`、`scheduled_events.dat`、`wandering_trader.dat`、`weather.dat`、`world_gen_settings.dat` 五个文件从 `world/dimensions/minecraft/overworld/data/minecraft/` 挪到 `world/data/minecraft/`；从原版换到 Paper（任何版本）直接换核心启动即可；26.1 前从 Paper 换回原版，要把 `world_nether/DIM-1`、`world_the_end/DIM1` 拷进 `world`，再去掉 `world_nether`、`world_the_end`，否则下界和末地看起来像被重置。升级到 26.1 是单向的。

按这些事实，首版的做法是：

- 先比版本。用 Mojang 版本清单的发布顺序比地图最后保存的版本和目标服务器的版本，不拿字符串比「1.x」和「26.x」。目标核心的 jar 里读得到 `version.json` 时，再拿数据版本号对一遍。同版本直接放行。地图比服务器新，拦下，建议新建一台同版本的服务器，不改数据版本号去装作兼容。地图比服务器旧，要用户明确确认：第一次启动时由游戏或核心自己升级这份副本，原来的地图留在恢复点里，升级后的副本不能再给旧版本用。版本认不出来、是快照、和目录布局对不上，都单独列出来，不标成「没问题」。
- 布局由引擎在暂存副本里按目标核心摆好，只做资料里写明的那几种挪动：旧 Paper 三目录放进原版或 Fabric、Forge 一类目标时，把 `DIM-1`、`DIM1` 并进主目录（Paper 文档的步骤）；26.1 起的 Paper 世界放进原版类目标时，挪那五个共用数据文件；原版布局放进 Paper 一类目标时原样放下，由 Paper 第一次启动时自己迁移（Paper 文档写的就是直接换核心）。资料没写、样本也没验证过的组合，拦下并说明，不猜。
- 模组世界（`ServerBrands`、`WasModded`、存档里出现非 minecraft 命名空间的维度或数据）放进不对应的核心，列成「需要确认」，说清缺什么，不悄悄换个核心试启动。没有可靠证据就写「无法确认」，不写「纯原版、没有依赖」。
- 目标服务器的世界根：MineDeck 自己启动时只传 `-jar server.jar nogui`，不带 `--universe`、`--world-container` 这类参数；Bukkit 一类核心的 `bukkit.yml` 里如果设了 `settings.world-container`，世界根就不在服务器文件夹，首版拦下。代理端（Velocity、Waterfall）没有世界，后端直接拒绝，不只是隐藏按钮。

真实服务端上验证过的组合会记在本文件末尾，没记的就是没验证。

## 保留什么、换掉什么

导入的是一张完整的逻辑世界：地形和建筑、实体、箱子和方块实体、主世界下界末地、认得出的自定义维度、level.dat 和各版本的世界元数据、计分板和命令存储、世界里的数据包、资源包和模组数据、来源里的玩家数据，以及没见过但看着合理的世界文件。

不带进来的：`session.lock`（由游戏重新建）；导入包里的服务端核心、mods、plugins、启动脚本、instance.json、server.properties、账号和管理配置。`uid.dat` 首版原样保留、不删不改，它和插件对世界 UUID 的引用还要按版本查清楚，在那之前不为了消除报错去动它。

目标服务器原来的世界整体换下：主目录和旧式的 `_nether`、`_the_end` 一起移进恢复点，新地图没带的维度也不会从旧图接过来。目标服务器第一次用到这个维度时会自己新建，界面上分开说「地图没有提供」和「丢失」。level-name 之外的其他世界（多世界插件建的）不动。

## 玩家数据

默认保留来源里的玩家数据，不和目标旧世界的玩家文件混在一起。箱子里的东西属于世界，跟着地图走；玩家身上的背包、末影箱、经验、位置、统计、进度是按玩家 UUID 存的文件。

单人存档的主人进度是首版要说清的重点。旧版本单人存档里，主人的数据同时在 level.dat 的 `Data.Player` 和 `playerdata/<UUID>.dat` 里，单人游戏读前者；专用服务器不读 level.dat 里的这份，只按进服玩家的 UUID 找 `playerdata`。26.1 起 level.dat 只留 `singleplayer_uuid`，数据在 `players/data/<UUID>.dat`。所以主人用同一个正版账号进开着正版验证的服务器，一般会接上自己的背包；离线模式的 UUID 是按名字算的，和正版的不同，接不上。这些规则会用真实服务端核实；在核实之前，首版只做检测和提示，不自动改写玩家文件，界面在导入前就说清「世界和建筑会保留；单人角色的背包、经验等能不能接上，要看你用哪个账号、服务器开没开正版验证」，并给出那个版本能照着做的办法。不按昵称推正版 UUID，不建议为此改 online-mode。

## 冒险地图的玩法要求

能从地图里读到的（数据包、资源包、游戏规则、难度、模式、命令方块相关的设置）列出来；说明书按不可信的纯文本显示，不当作指令执行，里面的链接不自动打开。现有服务器默认保留原设置，地图需要不同设置时列出差异，用户勾选了才改，改动记进恢复点，换回旧图时一并改回。不一律打开命令方块、关出生点保护、改和平或冒险模式。地图自带的 `resources.zip` 只保留并提示：远端玩家要拿到材质，得配一个能访问的资源包地址或者自己装，首版不替用户上传到任何地方。

## 数据怎么走

推荐流程是：选来源 → 认地图 → 核对版本和依赖 → 看清会发生什么 → 停服并建立恢复点 → 导入 → 启动检查或换回旧图。

**扫描和预览**不需要停服。扫描结果、候选和导入计划都由后端保管，绑定发起请求的人（本机界面、局域网设备的地址），过期或取消时清掉自己的临时文件。预览里绑定了来源的指纹（文件清单的大小和修改时间）、选中的候选、目标服务器的核心、版本、level-name 和世界目录现状。提交前再核一遍，任何一项变了就要求重新检测，不会出现「确认的是 A、导入的是 B」。

**暂存**放在目标服务器文件夹里的 `.minedeck/world-import/<编号>/`，和目标世界在同一个盘上，后面的切换都是改名，不再复制。`.minedeck/` 本来就是 MineDeck 的控制目录：交接包和整合包带了这个目录一律不收，交接包导出也不带它，所以别人给的包没法伪造一份导入记录。来源复制到暂存区是流式的，边复制边按阶段报进度；文件夹来源复制完再对一遍指纹，期间被改过就作废重来；ZIP 来源解压时校验 CRC，实际解压量超过声明就停。来源始终只读，复制完不删。估算空间按暂存加余量算，写的时候盘满了照样能干净地停下。

**维护占位**：真正替换之前，给这台服务器占上「正在换地图」的位，占位和服务器状态在同一把锁里检查，`Start` 也在同一把锁里看这个位，所以界面、接口、定时重启、崩溃自动重启、AI 和 MCP 都启动不了它。同一时间不能删除、还原备份、打包交接包、定时备份、改 level-name、再导入一次。扫描和暂存不占这个位，传大文件的时候服务器照常能玩。

服务器还开着时，界面上提供一个明确的「停服并导入」，用的是不强杀的停服：发 `stop`，等 Java 进程自己退出；等不到就放弃导入，一个文件都不换，服务器继续关它自己的，不替用户强杀。普通的停止按钮行为不变（照旧超时强杀）。MineDeck 之外启动的服务器（手动双击 run.bat 之类）管理器看不到，所以提交前还要看世界目录有没有被占用：试着锁一下 `session.lock`，并且所有切换都是整目录改名，Windows 上有文件被打开时改名会失败，失败就原样退回。不靠「session.lock 文件存在」判断世界在不在用。

**提交**按一份持久的记录分步走：记录写盘用临时文件、刷盘、再改名，每一步前后各写一次。顺序是：把旧世界的各个目录整体移进恢复点 → 把暂存好的新世界目录移到位 → 写用户选了要改的设置 → 标记完成。没有「先删旧图再往原处解压」的时候。旧 Paper 的三个目录不可能一次改名同时换掉，所以每个目录是一步，每一步都能单独往回撤。

**中断和恢复**：任务页的进度只在内存里，靠不住；靠的是这份记录。MineDeck 启动时，在调度器和崩溃重启开始工作之前，先把每台服务器没完成的导入处理掉：没标记完成的一律退回旧图。每一步怎么退，看的是磁盘上的实际情况（源和目标哪个在），不是记录里最后写的状态，所以退到一半再断电，下次照样能接着退，不会把唯一完整的那份删掉。退不回去的（两边都在、两边都不在），不删任何东西，把这台服务器标成「恢复未完成，已暂停启动」，界面上给出具体路径。

**恢复点**就是被移下来的旧世界目录本身，原样、完整，不是重新压缩的一份，也不在普通备份的轮换里，不会被定时备份挤掉。它一直留着，直到用户在界面上确认不要了才删；界面上显示它占了多大地方。导入完成后服务器默认保持停止，状态写「地图文件已导入，尚未启动检查」。用户启动以后，游戏可能升级、改写新地图，这和「提交时退回」是两回事：之后点「恢复导入前的地图」，同样按记录分步走，把当前世界（导入的那份，可能已经被改过）移到旁边留着，把旧世界搬回原位，设置改回去，旧世界导入时有 level.dat 的再核对它和移下来时一致。

同一个世界导入过几次，就有几个恢复点，换回只能从最近的一次往前一次次来：先换回最近那次，前一次的恢复点里存的才是这时候该搬回来的世界。原来哪个恢复点都能点，乱序换回会把中间那张图移进某个恢复点的旁边，再没有入口搬出来（Gemini 4 Argon 复审查出来的）。新建服务器时放进去的地图没有「导入前的世界」，它的记录不能换回，只能删。

记录本身坏了（读不出来、内容通不过核对），说明不知道换到了哪一步：服务器保持暂停启动，「地图 / 世界」页把它标成读不出来并给出文件夹，由人去看。启动时的恢复处理完记录以后，按盘上的记录再判断一遍要不要封锁，用的和加载实例时设封锁是同一个判断；「重试恢复」也一样，并且不碰同一台服务器上正在复制的另一次导入。

## 不可信文件和接口边界

ZIP 解压沿用交接包那套防线并补齐：路径穿越、绝对路径、盘符和 UNC、符号链接条目、NTFS 备用数据流、Windows 设备名、只差大小写的重名、结尾的点和空格、文件和目录同名、目录深度、条目数、实际解压体积、整数溢出、压缩炸弹、CRC 错误。文件夹来源同样检查：遇到符号链接、目录联接这类重解析点不跟进去，来源和目标不能互相包含。NBT 和 gzip 的解析有展开大小、嵌套深度和列表长度的上限。世界图标、说明书都按不可信输入处理。包里的 instance.json、启动脚本、相对路径一概进不了 MineDeck 的管理层。

上传走流式写盘，不经过系统临时目录再拷一遍，多 GB 的地图不会在别的盘上多占一份。

操作层：读本机文件夹的扫描只认本机的人；替换和恢复是「仅人工」，AI 和 MCP 调不了，界面之外直接调接口也要带上计划编号和明确的替换确认，后端自己核对，不靠前端弹窗。给 AI 的只有只读的状态摘要，里面不放本机路径。基础导入功能不依赖 AI。

## 验证分几层

报告里分开写四层，哪一层没做到就照实写：

1. 已实现、已自动测试：Go 单元测试（识别、版本比较、布局映射、解压防线、NBT 上限、记录的每一步故障注入和重复恢复、并发的启动删除还原打包），前端交互测试和界面原型场景。
2. 已在真实服务端启动：用 MineDeck 下载的官方服务端，在 `D:\` 下的测试副本、独立端口、独立的应用数据目录里跑。样本地图由真实服务端生成，用控制台命令在主世界、下界、末地各放一块标记方块，存盘停服后当作来源；导入到另一台服务器启动后，用 `execute if block` 在三个维度分别检查标记，再恢复一次旧图，检查旧标记回来了。这一层能证明「服务器加载的是导入的那张图、三个维度都对」。
3. 已进服验证：要用客户端进服看建筑、出生点、维度，以及（如果声称）背包、经验、末影箱。这台电脑上的会话没有可自动驾驶的客户端，这一层留给作者，会准备好样本和步骤。
4. 声称支持而没验证过的组合，不写进「支持」。

## 真实服务端上验证过的组合
