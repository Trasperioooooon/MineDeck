# MineDeck v3.1.0-beta.1 补测：给 AI 测试员的任务说明

这份说明是自包含的。你不需要了解这个项目，也不需要读它的源代码，照着做就能测完。你的工作目录是这份说明所在的文件夹，下面叫「测试目录」（默认是 `D:\MineDeck-handover-test`）。所有命令都在测试目录里运行。

## 1. 你要做的事

MineDeck 是 Windows 上的 Minecraft 开服工具，一个单文件程序 `MineDeck.exe`。v3.1.0-beta.1 新加了「交接包」：把一台服务器打成一个 `.mdpack` 文件，拿到另一台电脑的 MineDeck 里导入，就能照原样开起来。交接包有两种大小：瘦身包不带服务端核心，导入时重新下载；完整包把核心也带上。

这一版发布前有三块没有实测过，请你补上：

- F 组：Forge 和 NeoForge 服务器的交接。
- G 组：几个 GB 的大交接包。
- C 组：CurseForge 格式整合包的导入。这一组要用户先做两件事，见 C 组开头。

你是测试员，不是开发者。你的任务是如实记录做了什么、预期什么、实际看到什么，并留下证据。发现问题就记下来，继续下一项。不要去修，也不要想办法绕过去让它通过。一个如实写着「不通过」的报告，比一个全是「通过」但没有证据的报告有用得多。

## 2. 环境

用户已经双击脚本把环境准备好了，你不用安装任何东西。

- 测试目录里有两份互不相干的 MineDeck，都在后台运行、没有窗口。副本 A 在 `A\`，当作原来的电脑；副本 B 在 `B\`，当作接手的电脑。
- `copies.json` 是两份副本的地址和令牌。
- `handover.py` 跑一条完整的交接流程，`cfpack.py` 导入一个整合包，`run.py` 把它们放到后台跑，`mdtest.py` 是它们共用的模块。
- `packs\` 是用户放 CurseForge 整合包的地方。`work\` 是临时文件。`results\` 放结果和证据。
- 电脑上有 Python 3.12，命令是 `python`。

开始之前先确认两份副本都在：

```
python mdtest.py A GET /api/app
python mdtest.py B GET /api/app
```

两条都应该打印 `HTTP 200`，里面的 `version` 是 `3.1.0-beta.1`。如果连不上，停下来请用户双击「启动测试副本.bat」。不要自己去启动 `MineDeck.exe`。

这份说明里的命令在 PowerShell 和 Git Bash 里都能原样运行，不用改写。

## 3. 规矩

下面每一条都要守。拿不准某件事算不算违反，就当它算，先问用户。

1. 只在测试目录里读写文件。
2. 不要读、写、删 `E:\Archive_files\MineDeck` 和它下面的任何东西。那是用户正在用的 MineDeck 和项目源码，里面有他真实的服务器和存档。
3. 只访问 `copies.json` 里的两个地址。不要访问本机别的端口。用户平时用的那份 MineDeck 在别的端口上，它不是测试对象。调接口只通过这里给的脚本。
4. 不要按名字结束进程。不要用 `taskkill /IM`、`Stop-Process -Name`、`pkill`、`killall`。尤其不要动 `java.exe` 和 `MineDeck.exe`：用户自己的服务器也是 java 进程。脚本会通过接口把它开的服务器停掉。
5. 不要用 git。不要改 MineDeck 的文件或这里的脚本来让测试通过。脚本本身出错了就照第 10 条记下来。
6. 不要读 `secrets.json`，不要设法读出 CurseForge API Key。Key 由用户自己在界面里填。
7. 报告和证据里不出现令牌和 API Key。脚本存证据时会自动抹掉令牌。路径里的 Windows 用户名写成 `<用户名>`。
8. 不要改系统设置、防火墙、注册表、计划任务，不要安装软件。不要开启 MineDeck 的开机自启、内网穿透和局域网访问。
9. 不要删服务器，不要删备份，不要删 `A\`、`B\` 里的东西。脚本会自己删掉它造的填充文件和导出的交接包，你不用手动清理。
10. 遇到意料之外的错误：把脚本的输出原样留在证据里，这一项记「不通过」或「没法测」，然后继续下一项。不要换一种办法反复试到成功，不要自己猜别的接口去调。
11. 要人来做的事停下来请用户做：填 Key、下载整合包、决定要不要信任某个下载站点。不要替他做。
12. 一次只跑一条测试。`run.py` 会拦住同时启动的第二条。

## 4. 怎么跑一条测试

每条测试要几分钟到几十分钟，所以都放到后台跑：

```
python run.py handover.py --id F-1a （后面是这一条的参数）
```

这条命令马上返回。之后每隔一两分钟看一次进度：

```
python run.py --status
```

它会说测试还在运行还是已结束，并打印最近的输出。脚本每做完一步打印一行，开头是 `[通过]`、`[不通过]` 或 `[信息]`。最后一行是 `总结果：……`，看到它才算跑完。全部输出在 `results\<编号>\输出.txt`，同一个文件夹里还有每一步的原始证据（任务记录、日志末尾、文件比对）。

等的时候不要做别的测试。下载慢的时候一步可能十几分钟没有新输出，这是正常的：Forge 的安装器要下载几百个文件。超过 40 分钟没有任何新输出，再记为卡住。

`[不通过]` 的每一行，你都要打开对应的证据文件看一眼，在报告里写清楚实际发生了什么。`[信息]` 的行不算通过也不算不通过，是给你判断用的。

如果 `python run.py --status` 说进程已经不在了，输出里却没有 `总结果` 那一行，说明这条测试被中途打断了。重跑一次：编号后面加 `-r2`，`--dst` 的名字后面加 `-r2`，`--dst-port` 加 20，其余不变。重跑还是被打断，多半是你的平台会把后台进程一起结束。这时改成在前台直接运行，也就是把命令里的 `run.py ` 去掉（例如 `python handover.py --id F-1a-r3 ……`），并把平台对单条命令的时间限制调到最长。在报告里写明哪几条是这样跑的。

## 5. 测试项

按下面的顺序做。每条命令里的名字和端口都已经排好，不要改。

### F 组：Forge 和 NeoForge 的交接

每一条做的事相同：在副本 A 上建一台服务器并开一次（源服务器已经在就直接用），放进标记文件，导出交接包，传给副本 B，导入，比对每个文件，再把导入出来的服务器开一次。第一次建 Forge 或 NeoForge 服务器要下载并运行官方安装器，五到十五分钟都正常。

F-1a：Forge 1.20.1，瘦身包，服主交接，带一个模组。

```
python run.py handover.py --id F-1a --core forge --mc 1.20.1 --src fg-src --src-port 25741 --dst fg-slim --dst-port 25751 --mod jei
```

F-1b：同一台源服务器，完整包，发给朋友。

```
python run.py handover.py --id F-1b --core forge --mc 1.20.1 --src fg-src --src-port 25741 --dst fg-full --dst-port 25752 --full --mode distributable
```

F-2a：NeoForge 1.21.1，瘦身包，带一个模组。

```
python run.py handover.py --id F-2a --core neoforge --mc 1.21.1 --src nf-src --src-port 25742 --dst nf-slim --dst-port 25753 --mod jei
```

F-2b：NeoForge 1.21.1，完整包，发给朋友。

```
python run.py handover.py --id F-2b --core neoforge --mc 1.21.1 --src nf-src --src-port 25742 --dst nf-full --dst-port 25754 --full --mode distributable
```

F-3a：旧版 Forge 1.16.5，瘦身包。旧版的启动方式和新版不同，用的是 Java 8。

```
python run.py handover.py --id F-3a --core forge --mc 1.16.5 --src fo-src --src-port 25743 --dst fo-slim --dst-port 25755
```

F-3b：旧版 Forge 1.16.5，完整包。

```
python run.py handover.py --id F-3b --core forge --mc 1.16.5 --src fo-src --src-port 25743 --dst fo-full --dst-port 25756 --full
```

F-4：导入时起一个带中文和空格的名字。

```
python run.py handover.py --id F-4 --core forge --mc 1.20.1 --src fg-src --src-port 25741 --dst fg-cn --dst-port 25760 --chinese-name
```

每一条怎样算通过：

- 导出、上传、导入三个任务都完成，没有报错。
- `mods`、`config` 和世界文件夹里的文件，导入后一个不缺、内容一个不变。多出来的文件不算问题，但要在报告里写出是哪些。
- 导入后的核心、MC 版本、构建号和源服务器相同。
- 导入后的 `server.properties` 里端口是这次填的新端口，`enable-rcon` 是关着的。
- 导入出来的服务器能开到日志里出现 `Done`，日志里有同一个加载器版本。带了模组的，日志里提到这个模组。

除了脚本的检查，你还要自己看两样东西并写进报告：

- `results\<编号>\导出任务.json` 里的日志：导出时有没有提醒哪些东西没有进包，提醒得对不对。
- `results\<编号>\导入任务.json` 里的日志：有没有看不懂的话、报错、或者和实际情况对不上的话。

脚本输出里如果出现 `开服接口的响应没收到`，不算不通过，但要在报告里写明一共出现了几次、在哪几条里。

### G 组：几个 GB 的大交接包

这一组用 Paper 服务器，往世界文件夹里放随机内容的填充文件来把包撑大。随机内容压不小，所以放了几个 GB，包就是几个 GB。脚本开始前会检查磁盘空间，不够会直接停下并说明，这时把这一项记「没法测」。

G-1：五个文件，每个 1 GiB，合计 5 GiB。

```
python run.py handover.py --id G-1 --core paper --mc 1.20.1 --src big-src --src-port 25744 --dst big-many --dst-port 25757 --filler 5x1024
```

G-2：单独一个 4.5 GiB 的文件。单个文件超过 4 GiB 是 zip 格式的一道坎。

```
python run.py handover.py --id G-2 --core paper --mc 1.20.1 --src big-src --src-port 25744 --dst big-one --dst-port 25758 --filler 1x4608
```

G-3：9 GiB 的包。MineDeck 导入交接包的上限是 8 GiB，这个包预期在上传时被拒绝。

```
python run.py handover.py --id G-3 --core paper --mc 1.20.1 --src big-src --src-port 25744 --dst big-over --dst-port 25759 --filler 9x1024 --expect-upload-reject
```

每一条怎样算通过：

- G-1 和 G-2：和 F 组一样的全部检查都通过。填充文件导入后和原来逐字节相同（脚本比的是 SHA-256）。
- 导出、上传、导入期间，MineDeck 的内存不跟着包的大小涨。脚本以 1 GB 为线。把实际的最高值写进报告，哪怕没过线。
- 上传结束以后，系统临时目录里没有留下几个 GB 的临时文件。导入完成以后，副本 B 的上传目录是空的。
- G-3：上传被拒绝。被拒绝以后临时目录和上传目录里都没有留下半截文件。
- G-3 还有一项要你自己判断：脚本会打印一行 `被拒绝时拿到的回应`。看那句话，一个不懂技术的用户能不能看出是包超过了 8 GiB 的上限。能看出来算通过。只说连接断了、解析失败，或者是一句英文报错，算不通过，把原话贴进报告。

把每一步用了多少秒、包有多大也写进报告：导出、上传、导入各花了多久，用户关心这个。

### C 组：CurseForge 整合包

这一组需要用户先做两件事。开始之前检查一下：

- `packs\` 里有没有 `.zip` 文件。这是用户从 CurseForge 网站下载的整合包本体。
- 运行 `python mdtest.py A GET /api/app`，看 `cfKeySet` 是不是 `true`。这表示用户已经在副本 A 的界面里填了 CurseForge API Key。

`packs\` 里没有 zip，整个 C 组记「没法测」，写明缺整合包。有 zip 但 `cfKeySet` 是 `false`，只做 C-1，其余记「没法测」，写明缺 Key。不要自己去下载整合包，也不要自己去申请或填写 Key。

下面命令里的 `packs/整合包.zip` 换成实际的文件名，路径用正斜杠，两头的引号留着。`packs\` 里有几个 zip，就对每一个都做一遍 C-1 和 C-2，编号写成 C-1-1、C-1-2 这样，服务器名字和端口也跟着换（名字后面加 `-2`，端口加 10）。

C-1：没有 Key 时导入。副本 B 没填 Key，所以在 B 上做。

```
python run.py cfpack.py --id C-1 --copy B --zip "packs/整合包.zip" --name cf-nokey --port 25761
```

预期：导入不会整个失败。清单里的模组进了待处理清单，任务日志里写明了和 API Key 有关。

C-2：有 Key 时导入，导入完开一次。在副本 A 上做。

```
python run.py cfpack.py --id C-2 --copy A --zip "packs/整合包.zip" --name cf-key --port 25762 --boot
```

预期：清单里的模组大部分下载到了 `mods`。少数作者禁止第三方下载的模组会留在待处理清单里，这是 CurseForge 的规定，不是问题。脚本会打印清单里有多少项、下载到多少、待处理多少，把这三个数写进报告。

开服这一步脚本只记录、不判定。整合包里常有只能装在客户端的模组，服务器因此开不起来不一定是 MineDeck 的问题。没开起来时，打开 `results\C-2\latest.log末尾.txt` 和崩溃报告，找出是哪个模组报的错，写进报告，并写明你判断这是整合包的问题还是 MineDeck 的问题、依据是什么。

C-3：处理待处理的文件。C-2 的输出里有一行 `导入任务编号 t几`，把它填到下面。C-2 没有留下待处理文件，这一项记「没法测」，写明原因。

先把待处理清单里每一项的原因、说明和可选的处理方式写进报告（在 `results\C-2\待处理文件.json`）。然后全部按「跳过」处理：

```
python run.py cfpack.py --id C-3 --copy A --resolve-task t几 --skip-pending
```

预期：接口返回成功，处理完以后任务里不再有待处理文件。

待处理文件还有两种处理方式，「用本地文件代替」和「信任站点后下载」。这两种都要用户参与，你不要做，在报告里列为「需要人来测」。

## 6. 已经知道的情况

下面这些已经记录在案，遇到了在报告里提一句即可，不用当成新问题：

- 副本重启以后，整合包导入留下的待处理清单就没有了。
- 超过 8 GiB 的交接包不能导入，这是设定的上限。G-3 测的是被拒绝时说得清不清楚、有没有留下垃圾。
- 瘦身导出 Forge 服务器时，会提醒 `defaultconfigs/` 没有进包。那个文件夹其实是空的。
- 两份副本在同一台电脑、同一个 Windows 用户下。换一台电脑、换一个用户的情况这里测不到。

## 7. 报告

全部做完以后，写一份 `results\报告.md`。先是一张汇总表，每条测试一行：

| 编号 | 结果 | 一句话 |
|---|---|---|
| F-1a | 通过 | |
| G-2 | 不通过 | 见问题 1 |
| C-3 | 没法测 | 缺 CurseForge Key |

结果只有三种：通过、不通过、没法测。脚本的总结果是「全部通过」，而且你自己看日志也没发现问题，才写通过。

然后是 G 组的用时和大小：每条的包大小，导出、上传、导入各多少秒，内存最高多少 MB。

然后每个问题写一条，用这个格式：

```
【编号】G-2
【结果】不通过
【版本】v3.1.0-beta.1
【服务器】Paper 1.20.1，填充文件 1 个 4.5 GiB
【步骤】运行的命令原样贴上
【预期】……
【实际】……（贴脚本输出里相关的几行，和证据文件里相关的几行）
【证据】results\G-2\ 里的哪几个文件
【你的判断】这是 MineDeck 的问题、测试脚本的问题、网络的问题，还是说不准。依据是什么。
```

最后列一段「需要人来测」：你做不了、要用户自己做的事。比如用游戏客户端进导入出来的服务器看世界在不在，待处理文件的另外两种处理方式。

写报告时守三条：

- 只写你实际看到的。没跑的项不要写通过，没看的日志不要说没问题。
- 数字从脚本输出和证据文件里抄，不要估。
- 不贴令牌和 API Key，路径里的 Windows 用户名写成 `<用户名>`。

## 8. 收尾

- 分别运行 `python mdtest.py A GET /api/instances` 和 `python mdtest.py B GET /api/instances`，确认每台服务器的 `status` 都是 `stopped`。有还在运行的，在报告末尾写出它的名字，请用户处理。不要自己去结束进程。
- 不要删任何东西，不要停两份副本。告诉用户报告在 `results\报告.md`，测试目录现在占了多少空间。用户看完以后自己双击「停止测试副本.bat」。
